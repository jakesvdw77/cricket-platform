# Design System

> **Page layout decisions live in `docs/standards/page-anatomy.md`** (top row, Season pill, figure cards, flat filter bar, buttons, review log). Check it before designing or changing any page.

Screens are composed from a library, not invented per page — the mechanical fix for "screens aren't mobile-friendly and UX isn't consistent." Built on **Material UI (MUI) v5** — the same library the original Cricket Legend app used (`ui/src/theme.ts`, `createTheme`) — not a hand-rolled utility-CSS system. See `docs/standards/frontend.md` for component anatomy and `docs/specs/001-tenancy-identity-model.md`'s White-Labelling section for how per-club branding layers on top of this.

## Workflow

1. **Tokens** — colour, type scale, spacing unit, and breakpoints, defined once in `ui/src/theme.ts` via MUI's `createTheme()`. This is the single source both Claude Design and the app read from.
2. **Component library** — Button, Input, Card, Nav, EmptyState first; Table, Modal, and loading states next — thin wrappers around `@mui/material` primitives with our variants locked in, built once against the theme, before any real screen.
3. **Storybook** — every component gets a story with the viewport addon at 375/768/1280. Mobile-friendliness is visible per-component, not discovered on a phone after ship.
4. **Screens** — composed only from the library. A screen needing a new visual pattern spins that off as a library addition first, spec'd on its own.
5. **Record** — tokens + component specs checked into this file; the `design-token-sync` skill keeps it and the code in lockstep.

*(Tokens and the first five components are done — see below and `ui/src/components/`. Table, Modal, and loading states are next.)*

## Record list / create-edit pattern

**Every screen that lists records and/or creates/edits one uses this pattern — not a per-screen layout.** Established via `docs/specs/008-product-catalog.md`'s Products screens (the reference implementation) after manual review found ad-hoc list screens inconsistent (no search/sort, inline "add" tiles cluttering record grids, no Back action, forms stuck at mobile width on desktop). Three components, `ui/src/components/`:

| Component | Use |
|---|---|
| `ListToolbar` | Header above any record list/grid: search (debounced into a backend query, never client-filtered), a sort control (backend-driven — selecting an option re-fetches with a new `sort` param, never client-side re-order), and the primary "Add `<Record>`" action. The create action lives here, never as a tile inside the record grid. |
| `RecordCard` | Grid unit for a record list. Fixed slot order: an optional leading avatar (photo/logo, falling back to initials or a fixed icon — `circular` for a person-shaped record, `rounded` for an organisation/named-thing a logo belongs to) + title + status badge, a required description (2-line clamp), a row of key fields, an optional row of attribute chips, then a footer edit action. The card itself carries a light ~5% `primary`-tinted background (`alpha(theme.palette.primary.main, 0.05)`) rather than plain white, and its footer Edit/secondary actions render a leading icon (e.g. `EditOutlined`, `ToggleOff`/`ToggleOn` for deactivate/reactivate, `LinkOff` for unlink) — real user feedback that an all-white card grid with text-only footer actions read as bland and easy to miss. `NavTile` (dashboard nav cards) uses the same tint plus an icon tile for the same reason. Every avatar/logo/initials-fallback across the app — this card's own avatar, `RecordDetailScreen`'s header, `TeamCard`, the new `PlayerCard`, `RecordIconButton`, `ShellHeader`'s club logo, and `AvatarMenu` — renders as a **gold disc** (a radial from `#f4d676` to `#E8B83D`) with dark green (`#0B3D26`) initials in the display face (Barlow Condensed 700, `docs/specs/120` Decisions 9 and 19), whatever the club's colour, via the shared `avatarSx(size, fontSize?)` helper exported from `RecordCard.tsx` (alongside `badgeSx`), not a per-site hand-rolled tint. Logo and photo images have no tile once loaded (shared `LogoAvatar`, `components/LogoAvatar`: transparent, `object-fit: contain`; the tile shows while the image loads or if it fails). The fallback tile is by kind: a **record** (league, team, field, sponsor; the `LogoAvatar` default) is the soft green tint (`alpha(primary.main, 0.14)`, `primary.dark` initials, no gold); a **person** (players, contacts, the account avatar; `kind="person"`) keeps the gold disc. Gold is for people only. A caller that wants a muted look (an opponent team) overrides `bgcolor` and sets `backgroundImage: 'none'`. A record's own primary avatar (a list-card avatar or a detail-page header avatar alike) is always 56px — one size for both contexts, not two; smaller "icon button" contexts (`RecordIconButton`'s quick-view grid, `TeamCard`'s sponsor-logo row, `ShellHeader`'s club logo, `AvatarMenu`, `TeamDetailPage`'s dense `SquadPlayerTile` grid) keep their own smaller sizes, restyled only. A card name (`RecordCard`, `PlayerCard`, `FieldCard`) uses `cardTitleSx` from `theme.ts` (Barlow Condensed 600, about 21 px, uppercase, 0.03em) and the card body gap is 14 px (`docs/specs/120` Decision 16). `badgesBelow` (`docs/specs/087-matches-polls-alignment.md`) puts the badges in a left-aligned row under the header while `headerActions` stay top-right (the poll-card layout); `badgesAbove` wins if both are set. |
| `RecordFormScreen` | Wrapper for any create/edit screen: a visible Back action above the title (plain header on the page wash, title in the Overview greeting's `h5`/700 style — 081), a responsive field grid (single column at `xs`, two columns from `md`, long-form fields spanning both), and an actions bar below a divider. Desktop uses the available width instead of staying a centered mobile-width column. |
| `ManageScreenHeader` | Header for any `/manage` screen that is a bare list or other non-form layout — i.e. NOT already wrapped in `RecordFormScreen` (which bundles its own back-action-plus-title). Renders the page-title `<h1>` `RecordFormScreen` uses (plain header on the page wash — no band, accent line or shadow; 081), plus a Back action only when `backTo` is passed (079), so every `/manage` screen carries a title whether or not it happens to be a form. |

Sorting/search are backend-driven, consistent with pagination's existing rule below — a list screen never filters or sorts a fetched page client-side. New list/CRUD screens (Subscriptions, Discounts & Promotions, Invoicing, System Settings, and manager-side screens) compose from these three directly; a genuinely new visual need gets a library addition first, per the Workflow step above — not a fork of this pattern.

**Every `/manage` screen must render a page title — no exceptions by omission.** `ManageScreenHeader` exists specifically because `ClubContactList.tsx` and `SponsorList.tsx` each independently hand-rolled just the Back button and silently dropped the title, while `ManageClubProfilePage.tsx` (built on `RecordFormScreen`) had one for free — the inconsistency was only caught by a user screenshot, not review. A screen wrapped in `RecordFormScreen` already satisfies this via that component; every other bare `/manage` screen (list, tree/org-chart editor, dashboard-adjacent view) renders `ManageScreenHeader` instead of a local back button. Do not hand-roll a Back button/title pair — extend `ManageScreenHeader` if it doesn't fit rather than duplicating it a fourth time.

### Record detail page (the Player page, `docs/specs/088-players-polls-alignment.md` section G; the match page, `docs/specs/089-match-page-form-and-list-view.md`)

A detail page for a person opens with a large header (80 px avatar with a soft ring, 72 px on a phone; name at 1.75 rem, 1.4 rem on a phone; status badge first, then the section chips; actions on the right, two full-width halves under the header on a phone), then a strip of key figures (a tinted icon tile, a large figure, a caption; four across, two across on a phone), then equal-height cards. Each card has a solid-green 32 px icon tile and an uppercase heading, label-over-bold-value fields in two columns ("–" muted when empty), and chips for short attribute sets (a dashed muted chip for "not on file"). Only real data is shown; a figure with no source yet is "–" with a "More coming soon" note, never invented. Pieces: the shared `KeyFigureTile` (a tinted icon tile, a value, a caption; amber tone for a time within 24 hours), `pages/manage/playerDetail/PlayerKeyFigures` and `PlayerInfoCard`, and for a match `pages/manage/matchDetail/MatchKeyFigures` (Starts with the live countdown, Venue, League, Poll) and `MatchTeamCard` (icon-tile heading, selection progress, compact zebra Playing XI rows). The same rules apply to any further detail page (the league page, `docs/specs/091` and `126`, is another: Back, the filled `ManageMenu` button "Manage League" (Edit League Details, Duplicate League, Import History, Share League) on the top row, the Season pill beside the title, the name in the display face at 32 px (26 px on a phone) keeping its capitals, 16 px (12 px on a phone) between bands, text-only toolbar buttons, and the figures as four static compact `PageCounters` cards (an optional `info` icon on a counter carries the age sentence; no icons, no FILTER tag), the same on every tab, the format and Active badges, a contacts and links line, a key-figure strip, then tabs each with its own toolbar line carrying that tab's actions with at most one filled button; section cards are the shared `InfoCard` - the Player page's cards, now also the league Conditions tab). A page's header follows the poll page: Back on the left of the top row with the page-level actions (Edit, external links) on the right, the title below with the workflow buttons right-aligned beside it, no status badges that a card below already shows, and a logo only where a team has one. A selection or progress figure is drawn as the shared `SelectionGauge` (a 10 px bar with a colour-keyed count legend), like the poll response gauge.

**Teams (`docs/specs/092-teams-gold-standard.md`).** The Teams page follows the Leagues list: Season pill, counters, `FilterBar` (Section, search), content line, Cards | List. The team card is board 2b of the approved mockup (logo, name, Section and Active chips, Players and Matches figures, Captain / Manager / Coach rows, sponsors, footer links); `TeamTable` is the list view. The team page header follows the poll page (Back, Season pill, filled Edit team), then a key-figure strip (`KeyFigureTile`), then Contacts and Sponsors as equal-height `InfoCard`s and the Squad card. The Edit / Add team Details tab is one sectioned card (Basic info, Branding and social, with `FormSectionHeading`) with a Cancel button.

**Compact forms and switches (`docs/specs/089`).** A create/edit form is one card with icon-tile section headings, a three-column field grid on a desktop (one column on a phone), 40 px inputs, "(optional)" in the label and example URLs as placeholders instead of helper text (validation errors still show under the field), and a footer with Cancel and the primary button; the section headings are the shared `FormSectionHeading` (Match and League forms). A choice between two to four short options is the shared `CompactToggleGroup` (the small tinted segmented switch the Cards | List switch uses; `fullWidth` for the phone Filters sheet, `fullWidthOnPhone` inside a form), never a full-width MUI `ToggleButtonGroup`.

## Manager shell and header (`docs/specs/079-manager-shell-and-overview.md`)

- **`ShellHeader`** is the platform chrome for every shell and every club (`docs/specs/120`): solid `chrome.header` (`#0B3D26`), cream (`chrome.text`, `#F7F3E8`) text, the brand name in the display face (19 px, uppercase, 0.05em), the club logo (or its initials) on a white 6 px tile, and `AvatarMenu` with a gold disc and the dark dropdown (`darkMenuProps` from `brandTokens.ts`). There is no `tone` prop and no club-colour header: a club's identity on the chrome is its name and logo only, and `withClubBranding` tints the body (buttons, links, counters, chips) only. `notificationsTo` (the manager shell passes `/manage/notifications`) adds a 28 px `NotificationsOutlined` bell link beside the account button, no badge; the admin and player shells pass nothing and have no bell. Every chrome control shows a 2px cream outline (2px offset) on keyboard focus.
- **`ManagerShell`** (`components/ManagerShell`) lays out the header, `SideMenu` (232 px from `lg`; a 64 px icons-only rail from `md` with tooltips and `aria-label`; absent below `md`; the Schedule group is Seasons, Leagues, Matches, Availability, Team selection, Results (Seasons first, `docs/specs/094-club-structure-and-seasons.md`, highlighted on every `/manage/fixtures/seasons` route); Availability and Team selection follow Matches in the Schedule group (schedule, ask availability, pick the team, record the result), the People group is Teams, Players, Communication, and Notifications is the header bell, not a menu item), the `<main>` with `pageBackgroundGradient` (the fixed cream ground, the same for every club), and the `Footer` (`chrome.header`, cream 12 px text). Below `md` it renders `BottomTabBar` (Home, Matches, Availability, Players, Menu) and `MenuSheet` (a bottom `SwipeableDrawer`, grouped tiles with 40 px `BrandIcon`s, closes on choosing a destination) instead, both dark (`BottomSheet tone="dark"`; every other sheet stays light).
- **One nav config**: `components/ManagerShell/managerNav.ts` feeds the side menu, bottom bar, Menu sheet and the Overview tile grid. The active item is resolved by route prefix (first match in menu order), so a nested route such as a match edit page keeps Matches highlighted. Menu icons sit on a cream rounded tile on the dark chrome (`onDark`, `docs/specs/120` Decision 13): 32 px artwork on a 36 px tile in the side menu, 40 px in the Menu sheet and 32 px in the bottom bar (078 + 080 rules). The side menu (`chrome.menu`, `#0a2e1d`, right border `chrome.menuLine`) has 17 px display-face uppercase labels and 11 px group headings; the current row is gold (`chrome.selected`) bold text on `chrome.selectedBg` with `aria-current="page"`; the bottom bar and Menu sheet use the same gold current state, the sheet's tiles being dark raised panels with a gold outline when current. Count badges keep `error.main` with a cream 1.5px ring. `AppShell` (platform admin) and `BottomTabShell` use the same chrome (header, drawers, footer; `Nav` is the same dark bar with a gold selected tab). Overview uses a MUI home glyph on a primary disc until `nav/overview.svg` exists.
- **Back links**: `ManageScreenHeader` has no default `backTo`; no `backTo` means no back link (the persistent menu replaces "Back to Dashboard"). Pass `backTo`/`backLabel` only for a meaningful parent (a parent record or the Club Profile).

**Page header (`PageHeaderBand`, `docs/specs/081-plain-page-header-and-counters.md`, amends 046).** `PageHeaderBand` is a plain container used by `RecordDetailScreen`, `RecordFormScreen`, `ManageScreenHeader` and the detail pages: title left, page actions right, directly on the page wash, with only a small bottom gap (`mb` 2/3). No band background, top accent line, shadow, rounded corners, negative bleed margins or border. Titles (and the Overview greeting) use `pageTitleSx` from `theme.ts` (`docs/specs/120`): Barlow Condensed 700, uppercase, 0.05em tracking, 32 px on a phone and 40 px from `md`. `headerBandShadow` was removed from `theme.ts`.

**Page counters (`PageCounters`, `ui/src/components/PageCounters`, `docs/specs/081-plain-page-header-and-counters.md`).** A row of key-figure cards directly under a page header, for the few numbers a manager needs before reading the list (first use: the Availability Polls view; there all four counters are drill-downs, 085 G). Use it for at most four counters; a counter that needs attention takes `tone: 'warning'` (the theme warning colour on the value, always paired with its label), the one the list below is filtered to takes `active` (a subtle `primary` outline), and a counter that also filters passes `onSelect` (and a `hint` such as "Tap to filter"), which renders it as a real button with a visible focus ring (a toggle with `aria-pressed` for `kind` `'filter'`, see below). ## Two token layers

Per-club white-labelling means the token system has two layers, not one:

| Layer | Set at | Varies per club? | Examples |
|---|---|---|---|
| Structural tokens | Build time, `ui/src/theme.ts` | Never | Type scale, spacing unit, breakpoints, semantic colours, shape |
| Brand tokens | Runtime, per request | Always | Logo, favicon, display name, primary colour — the closed `ClubBranding` field set |

**Platform brand tokens (`docs/specs/120`).** The greens, gold, sand, cream, the cream page ground, the card hairline and the font stacks live once in `ui/src/brandTokens.ts` (`BRAND`, `CHROME`, `FONT_DISPLAY`, `FONT_BODY`, `GROUND_GRADIENT`, `darkMenuProps`); `theme.ts`, `PageBackdrop`'s `BACKDROP_COLOURS` and the console's `HUB` read from it, so no hex for these colours is declared a second time in `ui/src`. The chrome palette (`theme.palette.chrome`: `header`, `menu`, `menuLine`, `text`, `selected`, `selectedBg`, `hover`) never varies per club.

**Brand tokens stay a closed set.** The alternative — a club admin pasting in custom CSS — trades away everything this system is for: consistent components, accessible contrast, one shape per concern. A brand colour that fails contrast against the base neutrals is rejected at save time, not shipped. Where the club colour is used as text or a thin control edge on white or the cream ground (links, text and outlined buttons, the selected tab), `readablePrimary(theme, 'text' | 'edge')` in `theme.ts` returns `primary.main` when it passes 4.5:1 (3:1 for edges) and otherwise `primary.dark`, darkened until it does (`docs/specs/120` Decision 22); fills keep the club colour.

**Runtime override mechanism:** `ui/src/theme.ts` exports `withClubBranding(primaryColor)`, which calls `createTheme(baseTheme, { palette: { primary: { main: primaryColor } } })` — MUI deep-merges this over the base theme, so every component styled through `theme.palette.primary` (which is all of them, via MUI's own theming) picks up the club's colour automatically. No CSS variable injection needed; this is MUI's own supported composition pattern.

### Spacing & breakpoints

MUI's default spacing function (`theme.spacing(n)` = `n × 8px`) and default breakpoints (`xs` 0 / `sm` 600 / `md` 900 / `lg` 1200 / `xl` 1536) are used unmodified — matching the original Cricket Legend app's theme and avoiding a fight with the library's own scale. 375px remains the mobile-first *design baseline* — author unprefixed / `xs` styles at this width first per `docs/standards/frontend.md` — even though it isn't one of MUI's named breakpoints itself.

### Shape

`theme.shape.borderRadius: 6` (`docs/specs/120`) — a single radius value applied across components by default (MUI multiplies it per-component as needed, e.g. `Chip` renders fully rounded). No separate custom radius tokens.

### Elevation

MUI's built-in `theme.shadows` (25-step array, used via the `elevation` prop) rather than custom shadow tokens. Our `Card` wrapper defaults to `variant="outlined"` (bordered, flat) rather than elevated — a deliberate flat, data-dense aesthetic; reach for `elevation` explicitly only where something genuinely floats above the page (menus, dialogs).

## Layout density: no component alone in its own row (owner rule, 2026-10-30)
- **Do not give a single control, button or short label a full row of its own** unless there is genuinely no other place for it. A lone button under a heading, a lone switch under a table, or a "Show help" row that is mostly empty wastes vertical space and looks unfinished.
- **Prefer, in this order:** (1) the section's header or toolbar line (right-aligned beside the title, as "Import history" and "Convert with AI" sit together); (2) the same row as its neighbouring controls (fields and their Save and helper buttons on one line, wrapping on narrow widths); (3) inside the card, alert or panel it belongs to (a warning's action goes in the warning, not below it); (4) a menu or dialog opened from a toolbar button for occasional actions.
- **On a phone** stacking is fine: below `md` controls may stack, because there the row is narrow, not empty.
- **League page (`docs/specs/126`, one Manage League button):** the title row carries ONE filled **Manage League** button (`ManageMenu`) that holds every league action, grouped with a description each (the League group is always first and Edit League Details its first item, then the active tab's group); a small icon-only edit pencil (32 px white secondary look, green edge, 6 px radius, 44 px on a phone, tooltip "Edit league details") sits directly after the title and badges as the visible shortcut to the same edit page; the tab rows carry no buttons by default and at most one white secondary text-only button where the action would not be obvious (Schedule **Import Schedule**, Teams **Add Team**, Conditions **Edit Conditions**), right-aligned beside the tab names (full width under the tabs on a phone, 44 px). Empty tabs carry their own action inside the `EmptyState` (Teams a filled **Add Team**; Schedule **Import Schedule** and **Add Match**), the one place a lone button in the content is right. **Add Team** (panel, tab row or empty state) opens `components/AddTeamChooserDialog` ("Add a team", three large tiles, each with a title and a one-to-two-sentence explanation: **Our team** links a club team, **Opponent team** adds a league team, **Copy teams** opens the copy-league-teams dialog and is disabled with the reason when there is no season); the panel reaches it with `?add=team` on the Teams tab. ## Buttons: sizes and when to use each (`docs/specs/118-result-review-fixes.md`)

A standing rule for the whole app.
- **Normal size** (`Button`, default `size="md"`): primary page-level actions and the footer buttons of a form or wizard (Save, Cancel, Back, Next, Publish).
- **Compact** (`Button size="compact"`, or `sx={compactButtonSx}` on a `MuiButton` that needs `component={RouterLink}`): every button inside a card, a form section or a toolbar (Fix, Add player, Edit, Show more, Clear filters, Try again, Hide / Show, View as table, View statistics). About 32 px high, 6px/12px padding, 13px sentence-case text, a 16 px icon.
- **Phone hit area:** below `md` a transparent `::after` extends the touch target to 44 px without enlarging the look (the technique is built into the compact size, as in `TeamFormStrip`). Never give a compact button `minHeight: 44`.
- **Secondary = outlined = white-filled** (owner rule 2026-10-30): `Button variant="secondary"` and MUI `variant="outlined"` get `background.paper` from the theme (`MuiButton.outlined`) with the readable green edge and text, so they read the same on the cream wash and on white cards; hover adds a faint primary tint layered as `backgroundImage`. Disabled outlined buttons keep the white fill with the muted MUI border and text. Text and ghost buttons stay transparent: only OUTLINED is filled.
- **Button and menu labels use Title Case** (owner rule 2026-10-30): Import Schedule, Add Match, Edit League, Share League..., Import History (2). Applied first on the league page and its menus; older screens move over as they are swept.
- **Dark-surface exceptions** (outlined stays transparent with a light edge, set with `bgcolor: 'transparent'` plus `backgroundImage: 'none'` on hover): the Player Hub and account console (`hubOutlineButton` and the `.MuiButton-outlined` rule in `darkFieldSx`, both in `pages/view/myPlayers/hubStyle.ts`), the account shell header buttons (`AccountShell`), the `StatusScreen` secondary action, and the landing page hero/footer cream outline buttons (`creamOutlineSx`). The manager side menu has no outlined buttons. The share dialogs' zoom toolbar sits on a light panel, so it keeps the white fill.
- `size="sm"` is the older small size and is being replaced by `compact` as screens are swept.

- **`components/StatusScreen`** is the one full-page look for "you cannot be here" and "something is wrong": the dark cricket-scene `PageBackdrop`, the Cricket Legend mark, a small inline illustration, a cricket-flavoured heading, one plain sentence and at most two compact buttons (gold filled primary, cream outline secondary). No header or footer, so it works signed in or out and fits a 375 px phone without scrolling. Kinds and their headings: `not-authorised` (Not out, but not in either; stumps with a bail off), `signed-out` (Stumps for today), `suspended` (Play is suspended), `session-expired` (Your innings has ended), `not-found` (Not on the scorecard; empty pavilion), `unreachable` (Rain stopped play; rain cloud over the pitch), `error` (Dropped catch; ball). Copy is friendly and never blames the person. Use it for a whole-screen guard (AdminHome, ManagerHome, suspended account, the catch-all 404); a small "not authorised" inside a working page stays an `EmptyState`.
- **Unreachable server.** `api/axiosConfig.ts` reports every response to `api/connectionStatus.ts`: no response at all (network error, timeout) or a 502/503/504 marks the backend unreachable; any other answer, 4xx included, marks it reachable. `ConnectionGuard` (in `App.tsx`) shows `StatusScreen kind="unreachable"` as an overlay while it is, pings `GET /api/v1/public/ping` every 10 seconds (any non-gateway answer counts as up), and refetches failed queries when it recovers. Public pages that make no API call never trigger it. `AppErrorBoundary` shows `kind="error"` for a render crash.
- **`components/BrandMark`** is the one drawing of the Cricket Legend mark (the green favicon tile: cream bat, red ball with a straight seam). **The mark never sits on a white tile** (the cream bat vanishes); on the dark chrome use `edge` for a thin light ring. A real club logo may keep its white tile (`ShellHeader`). Used by the landing page header, `StatusScreen`, `FullPageLoader` and `AccountShell`.
- **`components/CricketBallLoader`** (a bouncing cricket ball, inline SVG and CSS, `size` sm/md/lg, `tone` light/dark, `label` as the accessible name, reduced motion becomes an opacity pulse) and its `FullPageLoader` wrapper (`variant` backdrop for sign-in and sign-out screens, plain for a whole-page wait inside a shell) replace plain "Loading..." text and spinners for full-page waits. Inline button spinners, skeletons and small section loaders are unchanged.

## Share League dialog and ShareCore (`docs/specs/122-league-sharing.md`)

- **`ShareLeagueDialog`** (`components/ShareLeagueDialog`): one dialog for every league share entry point (card, list row, Playing Conditions tab, league view header, league edit page): what to share, then the format, then the format's own screen (PDF, Poster, Calendar, WhatsApp, Facebook). It fills about 96% of the screen from `sm` (the whole screen on a phone), has no outer scrollbar, and pins its footer (Close at the right). A format is offered when at least one ticked content supports it; contents it cannot carry are left out with a note.
- **`ShareCore`** (`components/ShareCore`) holds the content-neutral share pieces (initials, logo and sponsor controls, editable text, PDF and image actions); `ShareResultDialog` and `ShareLeagueDialog` both use it. `ShareFillContext` lets `SharePreviewStage` and `ShareFormatScreen` fill the height (opt-in; Results does not use it).
- **Club format switches** (`components/ShareFormatsSettings`, club administrators only, on the club overview page) hide a format per content type; the Player Hub honours them too.
- **Player Hub sharing is one tap**: `HubLeagueShare` produces the standard league poster (Share through the native sheet, plus Download); the manager dialog is never shown to players or parents.
