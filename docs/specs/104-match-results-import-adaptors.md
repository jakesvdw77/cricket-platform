# 104 — Match Results: Import Adaptors and the Result Processor

**Depends on:** `100-match-results-core.md` (`match_result` with `source` / `external_id` / `source_payload`, the draft and publish gate, `ResultDraft`, `ResultValidator`; this spec is its slice 104), `101-match-results-our-side-scorecard.md` (the merged full-scorecard flow: `ScorecardDto`, `result_player`, batting / bowling entries with dismissal bowler and fielder, `DismissalCredits`, `StandoutRules`, the Teams-first wizard, the side toggle, `scorecard/prefill`; built on `feature/101-our-side-scorecard` and awaiting merge, 104 is built after it merges), `097-import-framework.md` (the principles that bind every import: always an explicit confirm, validation first, never blindly import, AI only proposes; its tables and token are **not** reused, see Decision 1), `001-tenancy-identity-model.md` (club, person, player profile), `035-section-scoped-access.md` and `029` (`canAccessClub`, section narrowing on matches), `099-fields-directory.md` (the venue text in a file is **not** linked to a field here), `docs/standards/*.md`.
**Status:** draft (written 2026-10-15 from the user's brief and confirmed decisions; not planned or built; open questions at the end need the human). The `docs/roadmap.md` update is the caller's.

## Problem & Goals

A club's results already exist somewhere else: a scoring app's match report (STUMPS PDF), a CricClubs export, a spreadsheet, or a JSON file someone prepared. Today the only way into the platform is to retype the scorecard in the capture wizard (`100`, `101`), which is exactly the slow, error-prone work the wizard was designed to shorten. Importing is risky in a specific way: external files spell player names differently ("Nazar A", "vdW", "Cd Mescht"), many players are children, a wrong automatic link would put runs on the wrong child's statistics (`103`), and a file can be wrong or half-read. `100` reserved `source`, `external_id`, `source_payload` and the `ResultDraft` shape for this slice; `097` set the principles (always an explicit confirm, validation first, AI only proposes) but its batch machinery was designed for tabular master data, not for one match at a time that ends in a wizard the manager already knows.

This spec builds an **adaptor framework** and **one shared Result Processor**. Each external format is an *Adaptor*: a small, stateless class that turns its input into ONE **common import format**. The processor accepts only that format, knows nothing about adaptors, resolves team and player names against our data, and produces a **draft** result with its scorecard, which opens in the existing result wizard for the manager to check, correct and publish by hand. The first adaptor is our own JSON adaptor. The STUMPS PDF adaptor follows as its own spec slice; CricClubs CSV after it.

Goals:
- **A. Backend-driven adaptor discovery:** the UI has no hard-coded knowledge of adaptors. A GET endpoint lists each adaptor with its type, display name, description and supported input formats (each flagged text based or binary). A new adaptor is one class plus a registered subtype; no endpoint or UI change.
- **B. An abstract Adaptor** with default behaviour wherever sensible, a dedicated invalid-input exception hierarchy whose validation failures carry a list of human-readable errors the UI can show, and one template method (read if file, validate, transform, then validate the output against the common format).
- **C. One common import format** (names, not ids; a reference to the match; everything needed for the scorecard, result, standouts inputs and player of the match), with an **exactness** property on every section filled in by the processor.
- **D. One Result Processor** that resolves team and player names deterministically in three tiers (exact, normalised, initials and prefixes) and only then, for the leftovers and only if allowed, asks an AI that is told explicitly to answer "no match" unless confident. It derives the draft and resolution notes, never publishes, is idempotent per provider match id, and remembers confirmed name mappings as per-club aliases so the same name is never asked twice.
- **E. An import wizard** (Source, Match, Teams) that ends in the **existing** result wizard, pre-populated, with every player who was not matched exactly visibly flagged as a **guess** until the manager confirms or changes it. Saving and publishing are the normal existing flow.
- **F. The first adaptor, our own JSON adaptor**, proving the whole path end to end with no new third-party library for it.

## Non-goals

- **The STUMPS PDF adaptor, the CricClubs CSV adaptor and any Excel adaptor.** Context only; the abstract class, the common format and the format enum are shaped so they drop in. Each gets its own spec slice (first version scope, decision 2026-10-15: JSON adaptor, then STUMPS). The libraries they need (Apache PDFBox, Commons CSV, Apache POI) are **not** added here (see Rollout Notes).
- **Bulk import** (many matches from one file or a season export). One match per import; bulk later.
- **Publishing.** An import produces a draft only. Publishing is the existing manual Publish in the result wizard (`100`), with its warnings and acknowledgements. Nothing an adaptor or the processor does can publish, and no endpoint here can.
- **Keeping the uploaded file or its content.** The raw payload is not stored (decision 2026-10-15): the file and pasted content live in memory for the request and are discarded; `match_result.source_payload` stays null for imports. Reason: children's names. (A retention option is a later, separate decision.)
- **Reusing `097`'s batch tables and confirmation token.** The wizard draft is the staging area (Decision 1, unconfirmed by the human, see Open Questions). `097`'s *principles* are followed in full; its machinery is not.
- **Fall of wickets, partnerships, over-by-over, wagon wheels.** Accepted by the common format as optional properties and **explicitly ignored** (the platform is not a scoring app, `100`; `101` Non-goals). Dot balls per bowler are imported (`bowling_entry.dots`).
- **Fielding credits and standouts as imported data.** They are derived: fielding credits and bowler wickets follow the dismissals (`DismissalCredits`), standouts are computed on read (`StandoutRules`). The common format carries no fielding and no standout section.
- **Super-over scorecards.** Entries on a super-over innings are rejected by `101` (`SCORECARD_SUPER_OVER_NOT_SUPPORTED`, super overs are `105`). An import may carry super-over innings totals (they are `100` data); their batting and bowling rows are dropped with a visible note.
- **Creating players, persons or profiles.** The processor never creates a `Person` or `PlayerProfile`. A name that cannot be resolved becomes a guest (ours) or a typed name (opposition), exactly as in `101`.
- **Resolving opposition names to people, opposition player directory, cross-fixture identity.** Opposition players stay names (`101`). The processor only unifies spellings of the same opposition player *within one file*.
- **Aliases for opposition players, a "Remembered names" management screen, a club-level alias import.** Aliases cover our players and our teams only; the management screen is deferred (roadmap).
- **Linking the file's venue to a field (`099`), changing the match's field, or creating league teams or matches.** The import fills an existing match; it never creates a match. If no match fits, the manager creates it first (the normal flow).
- **A per-club time zone.** Dates and times in a file are read in the server zone like everywhere else (`docs/roadmap.md`, "Club time zones gap"); the common format carries no zone in version 1.
- **Per-club AI settings, a platform-admin AI settings screen, commercial AI tiers.** The AI configuration is system-wide for now (decision 2026-10-15); per-club or commercial control is later.
- **Persisted low-confidence highlights on non-player sections** (a score or toss read by a vision model). Section exactness is reported at import time; only player guesses are persisted for the wizard. Persisting the others belongs to the first adaptor that can produce them (the STUMPS vision fallback).
- **Section-narrowed rights beyond what result capture has.** Same rights as capture, no new role.

## User Stories

- As a club manager, I can choose a source from a list the system provides (for example "Our JSON format"), see which file types it accepts, and upload a file or, for text formats, paste the content, so that I never retype a scorecard that exists elsewhere.
- As a club manager, I see clear, human-readable errors (what is wrong and where) when my file or pasted content is not valid for that source, without losing what I pasted, so that I can fix it and try again.
- As a club manager, I see the match information read from the file and the matches in our fixtures it could belong to, with the reasons, and I choose the right one myself, so that a result never lands on the wrong match.
- As a club manager, I confirm or correct which of my teams is which team in the file, so that home and away are never swapped by accident.
- As a club manager, I am told when the match already has a result or draft, and I must explicitly agree to replace a draft; a published result is never touched, so that no work is lost silently.
- As a club manager, I land in the normal result wizard with the draft already filled in, the team lists showing, and every player who was not matched exactly marked as a **guess** with what the file said, so that I check the risky ones first.
- As a club manager, I can confirm a guess with one tap or change it to the right player with the normal picker, and every part of the scorecard that player appears in follows, so that a correction is made once.
- As a club manager, I am not asked about the same file spelling twice: a name I confirmed or corrected is remembered for my club.
- As a club manager, I cannot publish a result that still contains an unconfirmed guessed player link, so that a wrong guess never reaches a child's statistics.
- As a club manager, I can import the same match again (a corrected file, the same provider match id) and it updates the same draft instead of creating a second result.
- As a club manager, I can opt in, per import, to an AI suggestion for names the rules could not match, knowing which names are sent, and the AI only suggests: it answers "no match" rather than guess, and I confirm every suggestion.
- As a platform operator, I can see every AI call the product made (feature, model, token usage) and switch the feature off or cap it, so that cost and privacy stay controlled.
- As a developer, I can add a new source by writing one adaptor class and registering its subtype, with no change to the discovery endpoint, the processor or the UI.
- As a developer, I can test every adaptor and the processor without a network call, because the AI sits behind an interface.

### The common import format (version 1)

One JSON document, built from the existing `ResultDraft` / `ScorecardDto` shapes (`100`, `101`) but with **names instead of ids** and teams referenced by a short key. It is the only thing the processor accepts and the only thing an adaptor produces. The Java form is a nested-record DTO, `ImportedResultDto`, in `com.cricketlegend.dto`. All section and property names below are the JSON names. "Required" means required for the document to be valid (shape and references only; cricket arithmetic stays in `ResultValidator`, see below).

| Section | Properties | Rules |
|---|---|---|
| `schemaVersion` | integer, required | `1`. An unknown version is a validation error naming the supported versions |
| `source` | `adaptor` (the `AdaptorType`), `provider` (string, 1-40, for example `STUMPS`), `externalMatchId` (string, 1-255), `fileName` (string, optional) | `adaptor` and `fileName` are **set by the adaptor base class**, not trusted from input. `externalMatchId` requires `provider`. Together `(provider, externalMatchId)` is the idempotency key |
| `match` | `matchId` (uuid, optional, our match if the document already knows it), `date` (`yyyy-MM-dd`), `startTime` (`HH:mm`, optional), `venue` (text, optional), `competition` (text, optional) | At least one locator must exist: `matchId`, or `date`, or `source.externalMatchId`. A `matchId` is only a proposal, the manager still confirms the match |
| `teams` | array of exactly two: `key` (1-8 chars `[A-Za-z0-9_-]`, unique), `name` (1-100), `shortName` (optional) | Keys are how every other section refers to a team. Order carries no meaning (no home/away claim) |
| `toss` | `wonBy` (team key), `decision` (`BAT` / `BOWL`) | Optional; both or neither |
| `result` | `outcome` (`WON`, `TIE`, `DRAW`, `NO_RESULT`, `ABANDONED`, `FORFEIT`), `winner` (team key), `decidedBy` (`REGULAR`, `DLS`, `SUPER_OVER`; default `REGULAR`), `margin` (`type` `RUNS`/`WICKETS`, `value` >= 0), `dls` (`target`, `revisedOvers`), `scheduledOvers` (int), `ballsPerOver` (int, default 6), `note` (text) | Optional as a whole (a team-list-only import is valid). Outcome-shape rules (a winner for `WON`, none for `TIE`) are `ResultValidator`'s, not repeated here |
| `innings[]` | `battingTeam` (key), `kind` (`REGULAR` default / `SUPER_OVER`), `runs`, `wickets`, `overs` (string as scorecards print it, `"36.4"`, validated against `ballsPerOver`), `extras` {`wides`, `noBalls`, `byes`, `legByes`, `penalty`}, `batting[]`, `didNotBat[]` (names), `bowling[]`, `fallOfWickets`, `overByOver` | Order is the order of play. `fallOfWickets` and `overByOver` are accepted and **ignored** (an INFO note says so). At most 2 regular innings plus super overs |
| `innings[].batting[]` | `player` (name, 1-100), `position` (int, optional, else list order), `howOut` (a `DismissalType`), `bowler` (name, optional), `fielder` (name, optional), `runs`, `balls`, `fours`, `sixes` (ints >= 0, `balls` / `fours` / `sixes` optional) | `bowler` / `fielder` only where `DismissalType` allows them (the same table as `101`), and each is a player of the **fielding** team, so the processor resolves them against the other side. A dismissal given only as text ("c Smith b Jones") is **not** accepted: the adaptor parses it into `howOut`, `bowler`, `fielder` |
| `innings[].bowling[]` | `player`, `overs` (string), `maidens`, `runs`, `wickets`, `wides`, `noBalls`, `dots` (ints >= 0, last three optional) | Bowlers belong to the team that did **not** bat in that innings. `wickets` is imported as the scorecard says (a `MANUAL` value in `101` terms); a difference from the dismissals surfaces as the existing `BOWLER_WICKETS_DIFFER_FROM_DISMISSALS` warning |
| `players[]` | `team` (key), `name`, `substitute` (boolean) | Optional team-sheet additions for people who neither batted nor bowled (the 12th man, a substitute fielder). Everyone named in batting, `didNotBat` and bowling is on the team sheet automatically |
| `awards` | `playerOfMatch` {`name`, `team` (key, optional)} | The official award only. Team awards are not imported |
| `exactness` | enum on **each section** (`match`, `teams`, `toss`, `result`, each innings, `awards`, and each resolved name) | **Output-only.** Filled by the processor. An adaptor that used AI to read a section may set `AI_SUGGESTED` on it; the processor keeps the lower of what it received and what it computes and never raises it |

**Exactness levels.** `EXACT`: taken as written or matched exactly (including a remembered alias and an opposition name taken as typed). `NORMALISED`: matched by a deterministic rule that is not identity (case, accents, spacing, word order, initials, prefixes). `AI_SUGGESTED`: chosen by the AI step from the candidate list. `UNRESOLVED`: no match (a guest or a typed name; for a team or match, the manager must choose). A section's exactness is the **worst** of its parts.

**Strictness.** Unknown properties are an error (a misspelt `bowlr` must not be silently dropped), except the two explicitly ignored ones above and anything under an `x-` prefixed property, which is ignored for the adaptor authors' own annotations.

Example (shape only; names invented):

```json
{
  "schemaVersion": 1,
  "source": { "provider": "STUMPS", "externalMatchId": "abc12345" },
  "match": { "date": "2026-10-10", "startTime": "09:00", "venue": "Main Oval" },
  "teams": [ { "key": "A", "name": "Irene Villagers 1" }, { "key": "B", "name": "CBC 1" } ],
  "toss": { "wonBy": "B", "decision": "BAT" },
  "result": { "outcome": "WON", "winner": "A", "margin": { "type": "RUNS", "value": 24 }, "scheduledOvers": 40 },
  "innings": [
    { "battingTeam": "B", "runs": 180, "wickets": 9, "overs": "40.0",
      "extras": { "wides": 6, "noBalls": 1, "byes": 2, "legByes": 1, "penalty": 0 },
      "batting": [ { "player": "J Smith", "howOut": "CAUGHT", "fielder": "Nazar A", "bowler": "Cd Mescht", "runs": 42, "balls": 51, "fours": 4, "sixes": 1 } ],
      "didNotBat": [ "P Jones" ],
      "bowling": [ { "player": "Cd Mescht", "overs": "8.0", "maidens": 1, "runs": 31, "wickets": 3, "dots": 22 } ] }
```

**Where each concern lives (one place each).** *Shape and reference validation of the document* is one pure class, `ImportedResultValidator` (structure, references between sections, `DismissalType` allowances, overs notation, size caps). *Cricket plausibility* (runs plus extras equal the total, wickets, balls, outcome versus scores) is **only** the existing `ResultValidator`, run on the produced draft; it is **not** duplicated in the adaptor or the common-format validator, and it is the safety net that checks an extraction (a PDF read wrongly shows up as a failed reconciliation).

### The Adaptor contract (backend, package `com.cricketlegend.service.adaptor`)

Adaptors are **stateless Spring beans**, auto-registered by an `AdaptorRegistry` that receives every `Adaptor` bean (constructor injection of `List<Adaptor>`), so adding one needs no registry, endpoint or UI edit.

- **`AdaptorType`** (enum): `JSON` now; `STUMPS_PDF`, `CRICCLUBS_CSV` named in their own specs. **`ImportInputFormat`** (enum): `JSON(text)`, `CSV(text)`, `EXCEL(binary)`, `PDF(binary)`, each with `isTextBased()`; extensible. Text-based formats allow file upload **or** paste; binary formats allow file upload only.
- **`Adaptor`** (interface) and **`AbstractAdaptor`** (abstract base), following the user's pattern: `@JsonTypeInfo(use = NAME, include = EXISTING_PROPERTY, property = "type")` and `@JsonSubTypes({@Type(value = JsonAdaptor.class, name = "JSON"), ...})` on `AbstractAdaptor`, which `implements Serializable, Adaptor` and holds `@NotNull private AdaptorType type`, set by each subclass's constructor and exposed through an explicitly annotated `getType()`. Only descriptive getters are `@JsonProperty`; behaviour methods are not serialised.

  **Where the Jackson annotations are actually needed.** Strictly, *serialising* an adaptor needs only the `type` property; `@JsonSubTypes` matters the moment an adaptor-shaped payload is **read back**. In this spec that is (a) the contract test that deserialises the discovery payload, and (b) the future **per-club adaptor settings** (enabled adaptors, provider options, stored as JSON), which must deserialise to the right subclass by `type`. The discovery endpoint itself returns a mapped `AdaptorDescriptorDto` (below), not the bean (`docs/standards/backend.md`: DTOs only cross the controller). A unit test enforces that every `AdaptorType` constant has exactly one registered bean and exactly one `@Type` line, and that serialisation round-trips `type` (Open Question 6).
- **Responsibilities and defaults** of `AbstractAdaptor`:

| Member | Default | Notes |
|---|---|---|
| `getType()`, `getDisplayName()`, `getDescription()` | `type` from the constructor; display name and description supplied by the subclass | Display name and description are short, plain-English, never translated into ids the UI would need to know |
| `getSupportedFormats()` | abstract | A non-empty set of `ImportInputFormat` |
| `isSupported(format)` | `getSupportedFormats().contains(format)` | |
| `isAiAllowed()` | `false` | Whether AI **may** be used inside this adaptor's `transform`. A second gate (the per-import opt-in plus the platform switch) must also pass; see "AI" |
| `read(ImportInput)` | text formats: strict UTF-8 decode (BOM tolerated) to a `TextContent`; binary formats: throws `UnsupportedImportFormatException` unless the subclass overrides | Returns the adaptor's **working form** (`AdaptorContent`, a small marker interface; `TextContent` is the default). A binary adaptor overrides with its own form (a PDF adaptor: positioned words). Malformed bytes or a corrupt file: `UnreadableImportInputException` |
| `validate(AdaptorContent)` | abstract | Confirms the content is correct **for this adaptor**; throws `ImportInputValidationException` carrying the list of errors |
| `transform(AdaptorContent, AdaptorContext)` | abstract | Returns an `ImportedResultDto`. `AdaptorContext` carries the AI facade, usable only when `isAiAllowed()` **and** the import opted in; otherwise any use throws |
| `importFrom(ImportInput)` | **final template method** | (1) `isSupported(format)` else `UnsupportedImportFormatException` naming the supported formats; (2) if the input is a **file**, `read`; if it is **pasted** text, wrap it as `TextContent` (same size cap); (3) `validate`; (4) `transform`; (5) stamp `source.adaptor` and `source.fileName`; (6) `ImportedResultValidator.validate(output)`, throwing `ImportInputValidationException` if the adaptor produced an invalid document (a bug in the adaptor is reported as such, not passed on). Returns the document. It never touches a repository or a result service |

- **`ImportInput`**: `format`, `fileName` (optional), `bytes` (file) or `text` (paste), `byteSize`. Size caps: see "File and size limits".
- **Exception hierarchy** (`com.cricketlegend.exception`, all under the existing `ValidationException` base, HTTP 400, no new base type or status category; `backend.md`'s allowance for a named subclass to carry structured detail applies, as for `InvalidResultException`):
  - `InvalidImportInputException` (abstract-ish parent, extends `ValidationException`)
    - `UnsupportedImportFormatException` (carries `requested` and `supported`)
    - `UnreadableImportInputException` (not decodable or not parseable at all: not UTF-8, malformed JSON with line and column, corrupt file; one message)
    - `ImportInputValidationException` (readable but wrong for this adaptor or for the common format; carries `errors`: a list of `ImportErrorDto {path, code, message}` in plain English, for example `path "innings[0].batting[3].howOut"`, message "Dismissal 'caught' needs a fielder or a bowler to be named, or use CAUGHT_AND_BOWLED."). Capped at 50 errors with a total count)
  - `GlobalExceptionHandler` maps the parent to a `ProblemDetail` with `errors` / `supported` properties.
  Further named conflicts introduced by the processor (all `ConflictException`, 409): `ImportMatchAlreadyHasResultException`, `ImportExternalIdAlreadyUsedException` (carries the other match id), `ImportWouldOverwriteDraftException` (the overwrite acknowledgement is missing).
- **Structural rule (ArchUnit):** classes in `service.adaptor` may depend only on `dto`, `exception`, the JDK, Jackson and (for the AI facade) the `AdaptorContext` interface. They may **not** depend on any repository, on `ResultService`, `ScorecardService`, `ResultServiceImpl`, any `domain` entity, or on the processor. This is how "no adaptor may bypass the processor or write results directly" is enforced rather than hoped for. (Standards extension: `docs/standards/backend.md` says the package layout is flat; `service.adaptor` is a new sibling of `service.impl` and `service.support`, Open Question 6.)

### The Result Processor

`ResultImportProcessor` accepts **only** an `ImportedResultDto` plus the club, the caller's authentication, the chosen match, the confirmed team mapping and the options. It knows nothing about adaptors, files or formats. It lives in `service.support` (pure and collaborating helpers) behind `ResultImportService` (interface plus `Impl`, the only caller; `@Transactional` on the write).

**Stages.**

1. **Match location** (`preview`, read only). Candidates are matches of the club the caller can access (the same narrowing as the Matches list, `035`), active, with a date within one day of `match.date` when given. A candidate is scored deterministically by evidence and each piece of evidence is shown as a reason: provider id already imported to that match (`EXTERNAL_ID`, the strongest), the document's `match.matchId` (`GIVEN`), date and start time (`DATE`), both file team names resolving to the two sides (`TEAMS`), venue text similarity (`VENUE`), league name (`COMPETITION`). Nothing is auto-selected for writing: even a single strong candidate is only pre-selected in the wizard, and the manager confirms. A match that already has a result is flagged (`existingResult`: status, source, whether it has a scorecard, last updated).
2. **Team mapping** (`preview` proposes, the manager confirms). For the chosen match, each file team is mapped to `HOME` or `AWAY` by name against the side's name (our team name, the league team name or the free-text opponent) using the same three tiers below plus a remembered `TEAM` alias; a team that cannot be placed is `UNRESOLVED` and the manager picks. A swap control exists. The confirmed mapping is sent to `resolve`; the server re-validates that it is a bijection onto `HOME` / `AWAY`.
3. **Player resolution** (`resolve`). Per side, names are resolved against that side's **candidate set**:
   - *Our side:* the registered players of that match's selection for that team (`MatchSide` / `MatchSidePlayer`, exactly what `scorecard/prefill` returns, including the 12th man) plus the team's squad for the match's season (`TeamSquadMember`). **Not** the whole club: a name outside both becomes a guest the manager can link with the normal picker. (Narrow on purpose: fewer false matches, and less personal data ever leaves for the AI.)
   - *The opposition:* no registered candidates. Names are **unified within the file** (the same person spelt differently in batting and bowling becomes one `result_player`) and against the names already on an existing draft of this result for a re-import. Otherwise taken as written.
   - **Tier 1, exact:** equal after trimming (full name; word order as typed). A remembered alias hit is also `EXACT`, reason `ALIAS`.
   - **Tier 2, normalised:** equal after the shared normalisation (case, accents, whitespace, hyphens, apostrophes and dots, one leading surname particle such as van, von, du, de stripped), in either word order ("Smith J" and "J Smith"). **Reuses `PlayerNameMatcher.canonical` / `canonicalSurname`** (`077`) rather than a second normaliser. No typo tolerance in the deterministic tiers.
   - **Tier 3, initials and prefixes:** (a) *surname plus initials*: "Nazar A", "A Nazar", "A. Nazar", "AB Nazar": the surname equals the candidate's (particles stripped) and the initials are a prefix of the candidate's given-name initials; (b) *abbreviated particle surname*: "vdW" or "Sam vdW" matches "van der Walt" (particle initials followed by the first letter of the main surname, the same rule as the Full name / First name toggle in `101`); (c) *surname prefix*: a surname token of at least three characters that is a prefix of the candidate's surname ("Mescht", "Cd Mescht" with initials agreeing) provided the initials, if any, agree. A rule only counts when it identifies **exactly one** candidate; two candidates satisfying a rule are *ambiguous* and the name moves on (and a note says "could be A or B").
   - **One person per row:** two *different* batting rows of one innings resolving to the same candidate is a collision: the first keeps the link, the second becomes `UNRESOLVED` (a guest) with a note, never a duplicate row (`101`'s one row per player per innings). The same file spelling or two spellings of one person across batting, bowling, dismissals and the award are deliberately the same `result_player`.
   - **Tier 4, AI (optional, leftovers only):** see "AI". Sets `AI_SUGGESTED`.
   - Whatever is left is `UNRESOLVED`: ours becomes a guest (`display_name` only, the existing Guest chip), the opposition a typed name.
4. **Draft derivation** (`resolve`). Maps the document and the resolutions to a `ResultDraft` plus `ScorecardDto` with the existing builders: sides from the mapping; `outcomeType` / `winningSide` / margin / DLS / toss / `scheduledBalls` (league default via `withDefaults`) / `note`; innings with `balls` from the `overs` text through `OversFormat` and the file's `ballsPerOver`, the extras breakdown, wickets and runs; `result_player` rows (new rows carry a `clientKey`; ours linked rows carry `playerProfileId`, the file spelling in `displayName`, `plannedBattingOrder` from the selection where the player is selected, `substitute` from `players[]` / the 12th man; opposition rows `opposition = true`); batting entries in file order with `position`, `howOut` and dismissal `bowlerPlayerId` / `fielderPlayerId` referring to the **fielding side's** rows (a name not yet on that side's list is added, as typing a name does in `101`); bowling entries with `balls` and `wicketsSource = MANUAL`; the official player of the match; `didNotBat` as `DID_NOT_BAT` rows. **No fielding rows and no standouts are produced**; the server's save recomputes `DERIVED` fielding credits and `non_bowler_wickets` from the dismissals exactly as for a typed scorecard, and standouts are computed on read. `status` is always `DRAFT`; `detail_level` is set by the server (`FULL` when opposition players exist).
5. **Persist as a draft** through a new method on `ResultService` (`saveImportedDraft`), which is `upsertDraft` plus the origin: it sets `source = IMPORT:<provider>` and `external_id` (a client can never send these on the normal `PUT`; they are not on `ResultDraft`), keeps the existing structural validation, and refuses a published result (`ResultPublishedException`). Idempotency: an existing result for `(club, source, external_id)` is the same result; a re-import onto that match **replaces the draft's imported content in place** (innings reconciled in place as `101` already does), after the overwrite acknowledgement. The unique index turns a race or a wrong-match retry into `ImportExternalIdAlreadyUsedException`.
6. **Report.** The response carries per-section exactness, a count of names by level, the resolution notes (each name: what the file said, what it became, level, reason, the candidate), and the **`ResultValidator` output for the produced draft** (errors, warnings, info) so the wizard can say "Imported. Checks: 0 errors, 2 warnings" before the hand-off.

**Aliases.** Written by the server inside the normal scorecard save (not by a separate client call, so the client cannot write an alias for something it did not actually save): when a save clears a row's `import_match`, or changes the linked player of a row that was created by an import (`result.source` starts with `IMPORT:` and the row has a `display_name`), the pair (normalised `display_name`, profile) is upserted for the club. Confirming a team mapping in the wizard writes the `TEAM` alias in `resolve`.

**Unconfirmed guesses block publishing.** `ResultValidator` gains the error `IMPORTED_NAME_UNCONFIRMED` (`step TEAMS`, `side` set): one per our row whose `import_match` is not null, message "File said 'Nazar A', matched to Ahmed Nazar by initials. Confirm or change this player." It blocks publish (Open Question 4 asks whether this should instead be an acknowledgeable warning). This is the server-enforced explicit confirm for the part of an import that can do real harm: a wrong link would put figures on the wrong child's statistics. Guests, exact matches and aliased matches need nothing.

### AI (name matching, behind an interface)

- **Interface:** `NameMatchingAssistant`: input a request of *unresolved names* (each with an opaque request key and its side) and the *candidate list* for that side (each with an opaque candidate key `c1..cN` and the display name); output, per request key, either a candidate key with a stated confidence (`HIGH`, `MEDIUM`, `LOW`) and a short reason, or `no_match`. Implementations: the real one calling the provider; `NoOpNameMatchingAssistant` when the feature is switched off; tests use a fake. The processor depends only on the interface.
- **The AI must never guess.** The prompt (a classpath resource `results/import/prompts/name-matching/v1.md`, versioned like `097`'s prompts) must say, in these words or their equivalent: *return no_match unless you are confident; a wrong match is worse than no match; choose only from the candidate keys supplied; never invent a candidate; never use any knowledge of real people outside the supplied lists.* A unit test asserts the packaged prompt contains these statements, so the rule cannot be edited out silently.
- **Server-side checks on the answer:** the chosen key must be in the list sent; only `HIGH` is accepted (becomes `AI_SUGGESTED`, flagged as a guess); `MEDIUM`, `LOW`, a key not sent, an unparseable answer, or two different names given the same candidate where tier 3 already placed that candidate, are treated as `no_match`. An accepted suggestion is still only a suggestion: it is flagged and blocks publish until the manager confirms it.
- **What is sent:** only the unresolved names and that side's candidate display names (opaque keys, no ids, no dates of birth, no figures, no team names, no scorecard). One call per side at most, and only when at least one name is unresolved. Our-side candidates are the selection and squad (small); the opposition is never sent (nothing to match against).
- **When it runs:** only at `resolve` (after the manager confirmed match and teams, so no cost is incurred by someone who abandons the import), only if the **platform switch is on**, the **per-import opt-in** (`useAi`) is true, and the club's daily cap is not reached.
- **Cost controls:** one batched call per side; at most 40 names and 60 candidates per call (more: the rest stay unresolved with a note); a small `max_tokens` and a fixed low temperature; per-club daily call cap (`app.ai.name-matching.daily-call-cap-per-club`); a platform kill switch (`app.ai.name-matching.enabled`, **default false**); model from configuration (`app.ai.name-matching.model`, a small fast tier, chosen by running a fixture set of real name pairs against candidates and recording accuracy and cost). Every call is logged to `ai_usage_log`.
- **Errors and retry:** a 15-second timeout; up to two retries with exponential backoff, only for rate limiting (429), server errors (5xx) and network failures; one retry for an answer that fails our parsing; never a retry for a refusal or a 4xx. **An AI failure never fails the import**: the names stay `UNRESOLVED` (guests), the response carries the note `AI_UNAVAILABLE` or `AI_CAP_REACHED`, and the manager continues. A re-run is simply another import of the same match (aliases keep it cheap).
- **The adaptor-level flag is separate.** `Adaptor.isAiAllowed()` governs AI *inside an adaptor's transform* (for example a vision read of a PDF in the STUMPS slice); the name-matching AI above is the processor's and is not gated by it. Both obey the same switch, opt-in and logging.
- **Provider and library (recommendation, flagged):** the **Anthropic Java SDK** behind our own interface, rather than Spring AI. One dependency, a typed usage object for logging, structured output, and no Spring AI BOM or auto-configuration to track against Spring Boot 3.4 for what is a single-purpose call. Spring AI is the alternative (the legacy app uses it, so its `AiSettings` / usage-log patterns are reusable). Because everything sits behind `NameMatchingAssistant`, the choice is replaceable in one class. **Neither is on the approved list** (`CLAUDE.md`): flagged for approval (Open Question 3). The API key comes from the environment or a secret manager (`ANTHROPIC_API_KEY`), is never stored in a database column, never logged, never returned by any endpoint.
- **Privacy of junior names:** the candidate list contains children's names and leaves the platform to the model provider. Mitigations: AI is off by default; opt-in per import with the exact consequence shown in plain words; only unresolved names and the single team's candidates are sent; nothing stored; no names in the usage log or application logs. Before it is switched on for real clubs the operator must confirm the provider's retention terms (POPIA applies to South African clubs); that is an operator step, not code (Open Question 2).

### File and size limits

Constants in one `ResultImportLimits` class, returned by the discovery endpoint so the UI never hard-codes them: pasted text at most 1,000,000 characters; an uploaded file at most the adaptor's declared limit but never above the existing global multipart limit (`spring.servlet.multipart.max-file-size=5MB`, unchanged); JSON and CSV 2 MB, PDF and Excel 5 MB; at most 30 players per side, 2 regular innings (plus super-over innings), 100 characters per name, 50 validation errors reported. Uploaded bytes are read into memory and discarded at the end of the request; nothing is written to disk by us (the servlet container's own temporary file is removed by the container).

## API Contract

All routes under `/api/v1/manage/clubs/{clubId}`, access `@PreAuthorize("@access.canAccessClub(authentication, #clubId)")` (any club manager, as result capture), consistent with `MatchResultController`. Section narrowing is exactly as for capture: the match candidates the preview shows are only matches the caller can administer, and `resolve` calls `matchService.requireAdministrableMatch` (a manager outside the match's section gets the same refusal as capture; another club's match is `404`). A `clubId` that is not the caller's is `404`. New `ResultImportController` / `ResultImportService` + `ResultImportServiceImpl` / `AdaptorRegistry` / `AdaptorMapper` (MapStruct) / `NameAliasRepository` / flat DTOs; every read `@Transactional(readOnly = true)`, the write `@Transactional` (`backend.md`).

| Endpoint | Access | Purpose |
|---|---|---|
| `GET /results/import/adaptors` | club manager | The registered adaptors as `AdaptorDescriptorDto[]`: `type`, `displayName`, `description`, `inputs[]` (`format`, `textBased`, `extensions`, `maxBytes`, `acceptsPaste` = textBased), `aiAllowed`, optional `example` (a short sample input for a text format, so the UI can offer "Insert example"). Plus `limits`. Backed by `AdaptorRegistry`; adding an adaptor changes nothing here. Sorted by display name. **Reads no data of the club** |
| `POST /results/import/preview` | club manager | Multipart: part `request` (JSON `ImportPreviewRequest`: `adaptor`, `format`, optional `content` text for a paste, optional `matchId` when launched from a match) and optional part `file`. Exactly one of `file` / `content` (paste only for a text format). Runs the adaptor (`importFrom`), then the processor's match location and team-mapping proposals. **Writes nothing.** Returns `ImportPreviewDto`: `document` (the common-format document with exactness filled for match / teams / toss / result), `matchCandidates[]`, `teamMapping[]`, `existingForExternalId` (the match already imported from this provider id, if any), `notes[]`. Errors: `400 UnsupportedImportFormatException`, `400 UnreadableImportInputException`, `400 ImportInputValidationException` (`errors[]`), `413`/`400` for oversize, `404` for a `matchId` of another club |
| `POST /results/import/resolve` | club manager | JSON `ImportResolveRequest`: `document` (as returned by preview; the server re-validates it fully, it trusts nothing about it, including exactness, which it recomputes), `matchId`, `teamMapping[]` (file team key to `HOME`/`AWAY`), `useAi` (default false), `replaceExistingDraft` (must be true when the match has any result in `DRAFT`). Resolves players (and, if allowed, asks the AI), builds the draft and **saves it as a draft** (this call is the explicit confirm; nothing is published). Returns `ImportResolveDto`: `matchId`, `resultStatus` (`DRAFT`), per-section `exactness`, `counts` by level, `notes[]` (per name: file text, outcome, level, reason, candidate), `validation` (the existing `ResultValidationDto` of the produced draft). Errors: `409 ImportMatchAlreadyHasResultException` (published result: unpublish first), `409 ImportWouldOverwriteDraftException` (no acknowledgement), `409 ImportExternalIdAlreadyUsedException` (the provider id is already on another match), `400` invalid document or mapping, `404` match not in this club, `403` outside the caller's section |

Nothing else is added: reading, editing, validating, publishing and unpublishing the imported draft use the **existing** `100` / `101` endpoints unchanged. The existing `PUT .../result` gains no source fields. `ResultPlayerDto` gains `importMatch` (read, clear-only write) and `MatchResultDto` already exposes `source` and `externalId`. `ResultValidator` gains `IMPORTED_NAME_UNCONFIRMED`. **OpenAPI:** `backend/openapi/openapi.yaml` updated by hand per the repo's practice, additions only.

**DTO shapes (summary).** `AdaptorDescriptorDto {type, displayName, description, inputs: InputFormatDto[{format, textBased, extensions[], maxBytes}], aiAllowed, example?}`. `ImportErrorDto {path, code, message}`. `MatchCandidateDto {matchId, label, matchDate, homeName, awayName, leagueName, venue, reasons[] (EXTERNAL_ID, GIVEN, DATE, TEAMS, VENUE, COMPETITION), existingResult? {status, source, hasScorecard, updatedAt}}`. `TeamMappingDto {fileKey, fileName, side? (HOME|AWAY), exactness, reason}`. `ImportNoteDto {code, severity (INFO|WARNING), section, message, fileText?, candidateName?, level?}`. `ImportedResultDto` as the schema above.

## Test Plan

Per `docs/standards/testing.md`. Per the user's working rule ("build first, tests after approval"), tests and the standards review run after the user has checked the function in the browser; the plan still lists them. AI parts are never called for real in any automated test.

**Backend unit (JUnit 5):**
- `AbstractAdaptor` defaults, through a minimal test adaptor: `isSupported`; `isAiAllowed` false; `read` of a text format decodes UTF-8 with and without BOM and rejects invalid bytes (`UnreadableImportInputException`); a binary format with no override throws `UnsupportedImportFormatException`; `importFrom` order (read only for a file, never for a paste), rejects an unsupported format listing the supported ones, stamps `source.adaptor` and `fileName`, and **validates the transform output against the common format** (an adaptor returning an invalid document fails with `ImportInputValidationException`, not a pass-through); AI use in `transform` throws when the adaptor does not allow it or the import did not opt in.
- Exception hierarchy and `GlobalExceptionHandler` mapping (400, with `errors` / `supported` properties).
- Registry: every `Adaptor` bean is discovered; duplicate `AdaptorType` fails at start-up; every `AdaptorType` has one bean and one `@Type`; `type` round-trips through Jackson; deserialising a descriptor payload yields the right subtype.
- `JsonAdaptor`: valid documents (minimal match-only, team-list-only, full innings with dismissals, DLS, super-over innings), and invalid ones, each asserting the **path, code and message** of the errors: malformed JSON (unreadable, with line and column), wrong `schemaVersion`, unknown property (and the two ignored ones accepted), missing locator, one team or two identical teams, a team key that does not exist, bad overs digit for `ballsPerOver`, `bowler` on a run-out, `howOut` given as free text, a negative figure, an over-long name, a document over the size cap, more than 50 errors truncated with the total; `transform` returns the input unchanged (field-for-field equality); AI permission false.
- `ImportedResultValidator` (pure): every rule once, plus reference checks across sections.
- Discovery: `AdaptorMapper` and the descriptor shape (formats flagged text based or binary; paste only on text formats); a second, test-only adaptor registered in a test context appears with no change to the endpoint.
- **Processor, deterministic matching (the heart of this spec), parameterised from a fixtures table of file spelling, candidate list, expected tier and result:** tier 1 exact; alias hit is `EXACT/ALIAS`; tier 2 case, accents, spacing, hyphen and apostrophe, word order ("Smith J"), particle stripped; tier 3 "Nazar A", "A Nazar", "A. Nazar", "AB Nazar", "vdW", "Sam vdW", "Cd Mescht", surname prefix with and without initials; **ambiguity** (two candidates fit: stays unresolved, note names both); two different rows resolving to one candidate (second becomes a guest); the same person across batting, bowling, dismissal and award is one `result_player`; initials that disagree do not match; a name outside the candidate set is unresolved (never matched against the whole club); an alias whose target is outside the candidate set is ignored with a note; opposition names unified within the file only when unambiguous; exactness is the worst of parts; an adaptor-supplied `AI_SUGGESTED` is never raised.
- **Processor, AI step with a fake `NameMatchingAssistant`:** called only for unresolved names, only when the platform switch **and** `useAi` are on, once per side at most, never for the opposition; the request contains only the unresolved names and the candidate display names with opaque keys (assert no id, no date of birth, no figures, no team name); `HIGH` answer accepted as `AI_SUGGESTED` and flagged; `MEDIUM`, `LOW`, `no_match`, a key that was not sent, malformed output, and the duplicate-candidate case are all `UNRESOLVED`; assistant throwing or timing out leaves the import complete with the `AI_UNAVAILABLE` note; the daily cap yields `CAP_REACHED` and the note; the packaged prompt contains the "return no_match unless confident / never guess / only these keys" statements; retry policy (429 and 5xx retried with backoff up to the limit, 4xx and refusals not).
- Draft derivation: outcome, winner and toss through the team mapping (including swapped sides); overs to balls with `ballsPerOver` other than 6; extras breakdown; position order; `DID_NOT_BAT` rows; dismissal bowler and fielder refer to the fielding side's rows; no fielding rows and no standout fields produced; bowling `wicketsSource` is `MANUAL`; `status` always `DRAFT`; super-over innings totals kept and their rows dropped with a note; derby (both sides ours, each against its own selection).
- `IMPORTED_NAME_UNCONFIRMED`: raised per unconfirmed ours row, blocks publish, cleared by confirm, by swap and by link; a client cannot set or raise `import_match` (ignored on save); never raised for guests, exact, alias or opposition rows.

## Acceptance Criteria

- `GET /results/import/adaptors` returns every registered adaptor with type, display name, description and each supported input format flagged text based or binary, with limits; the UI contains no adaptor names, formats or limits as constants; registering a new adaptor bean (a class, an `AdaptorType` constant and a `@Type` line) makes it appear in the Source step with no change to the endpoint, the processor or any UI file (shown by the test-only second adaptor).
- Text-based formats offer file upload **and** paste; binary formats (Excel, PDF) offer file upload only and a paste is refused by the server for them.
- A club manager can import a valid JSON document by upload or by paste and end in the existing result wizard with the draft filled in; a document that is not valid JSON, not valid for the common format, or in a format the adaptor does not support is refused with a specific, plain-English message and, for validation failures, the list of errors with their locations; the pasted text is not lost.
- The abstract adaptor validates the **transform output** against the common format before returning it; an adaptor that emits an invalid document fails the import with a validation error rather than reaching the processor.
- No adaptor can write a result: the ArchUnit rule fails the build if a class in `service.adaptor` depends on a repository, a result service, an entity or the processor; the only way a result is produced from an import is `ResultImportService` calling the processor.
- `preview` writes nothing (no match, result, player, alias or log row). `resolve` is the only write, it creates or updates **one DRAFT** result for **one match the manager chose and the caller may administer**, never publishes, never creates a `Person`, `PlayerProfile`, match or league team, and is refused (`409`) for a match whose result is published.
- Re-importing the same provider and external match id updates the same draft (one result per match, `source = IMPORT:<provider>`, `external_id` set, `source_payload` null); replacing an existing draft requires an explicit acknowledgement that the server enforces; the same provider id onto a different match is refused with the other match named.
- The raw uploaded or pasted content is not stored anywhere (database, disk, logs); no player or team name appears in the application logs or in `ai_usage_log`.
- Names resolve in the stated order: exact, remembered alias, normalised, initials and prefixes, then (only if switched on and opted in) AI, then unresolved. "Nazar A", "A Nazar", "vdW", "Sam vdW" and "Cd Mescht" resolve to the single matching candidate in the parameterised test; a name that fits two candidates is not resolved by a rule.
- Our players are matched only against the match's selection and the team's squad, never the whole club; the opposition gets no registered matching; an import creates no `result_player` for a registered player who is not in the file.
- Every player of ours who was linked by a rule other than an exact match or a remembered alias carries `import_match` and is shown with a **Guess** chip, the file's spelling and the reason, in the Teams step and on every row that player appears in; correcting the player once updates every row.
- A client cannot set or raise `import_match`; confirming, swapping, linking or removing the row clears it.
- A result with an unconfirmed guess **cannot be published**: Review lists it as an error with a Fix link, and the server refuses publish with `IMPORTED_NAME_UNCONFIRMED`.
- A name confirmed or corrected in an imported draft is remembered for the club; importing the same spelling again resolves it without a flag and without asking; an alias never applies to another club or to a player outside the match's candidates.
- The AI is called only for unresolved names, only when the platform switch **and** the per-import opt-in are on, at most once per side, with only the unresolved names and that side's candidate display names (opaque keys); its prompt states it must answer "no match" unless confident and use only the supplied keys; an answer that is not `HIGH` confidence or names an unsupplied key is treated as no match; every accepted suggestion is flagged as a guess; every call is recorded in `ai_usage_log` with feature, model and token usage; a failure, timeout or cap leaves the import complete with a visible note.
- The AI switch defaults to off; the API key is read from the environment or secret manager only, never stored in a table, logged or returned.
- Fall of wickets and over-by-over in a document are accepted and ignored with an info note; no fielding rows and no standout values are taken from a document; fielding credits and `non_bowler_wickets` in the saved draft are the server's derivation from the dismissals; standouts are computed on read as for a typed scorecard.
- The produced draft runs through the unchanged `ResultValidator`; its errors, warnings and info are returned by `resolve` and shown in Review, so a mis-read total or a mismatched bowling figure is visible before publish.
- A section manager sees and can import only matches of their sections; another club's manager gets `404`.
- Files over the limits are refused with a specific message; the global 5 MB multipart limit is unchanged.
- The import wizard and the Guess chip work at 375 px with no horizontal scroll; the Source step shows the pasted text and file after an error.
- OpenAPI changes are additive; new services have unit tests and new queries integration tests in the same PR; no new third-party library is added by slices 1 to 5 other than the AI client in slice 4b, which needs approval first.

### Decisions

Confirmed by the user, 2026-10-15:
1. The AI key and model are **system-wide** for now (platform-level configuration), per-club or commercial later; **every AI call is logged** (feature name, model, usage); **only unresolved names plus the candidate list are sent**, never the whole scorecard.
2. The raw uploaded payload is **not kept** (`source_payload` stays null for imports): children's names.
3. The import **may create a DRAFT result** before the final confirm; a draft is invisible to players; nothing is published by an import.
4. A **third deterministic matching tier** (initials and prefixes) runs before AI.
5. **Re-import of the same external match id updates the same draft.**
6. **First version scope:** the JSON adaptor, then the STUMPS PDF adaptor as the next spec slice; **one match at a time**, bulk later.
7. **Build order: 104 before 103.**

Taken by this spec (recommendations; the human may veto any):
- **D1. `097`'s batch tables and confirmation token are not reused** (the user's Q1 is unconfirmed). Reasons: an import here is one match that ends in a wizard that is itself the review; the draft is the staging area; `097`'s `PREVIEW`/`COMMITTED`/`DELETED` batch, payload retention and delete-undo would store the very content we decided not to keep. `097`'s principles are honoured: validation first (adaptor, common-format validation, then `ResultValidator`); an explicit, server-enforced confirm (the manager's match choice, team mapping and overwrite acknowledgement before any write, and `IMPORTED_NAME_UNCONFIRMED` before publish); AI only proposes.
- **D2. Stateless preview:** the document goes to the browser and comes back with `resolve`; the server recomputes everything (including exactness) and trusts none of it. No server-side staging store.
- **D3. Match, team mapping and overwrite are always confirmed by the manager;** the processor never auto-selects a match for writing.
- **D4. Our players resolve only against the match's selection and squad;** the whole club is not searched.
- **D5. Alias hits are `EXACT/ALIAS` and unflagged** ("never asked twice"); the note says so; a wrong alias is corrected by correcting the row, which replaces it.
- **D6. Unconfirmed guesses block publish** (error).
- **D7. A re-import replaces the draft's imported content wholesale** after an acknowledgement (aliases make the second pass cheap) rather than merging with the manager's edits.
- **D8. The AI is opt-in per import and platform-off by default,** and its answer is accepted only at `HIGH` confidence.
- **D9. Anthropic Java SDK recommended over Spring AI,** behind our own interface; both need approval.
- **D10. Imported dismissals must be structured** (`howOut`, `bowler`, `fielder`); parsing "c X b Y" belongs to each adaptor.
