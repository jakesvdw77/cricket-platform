## Problem & Goals

A match's venue is a free-text string today (`Match.venue`). Every club types "Irene Main Oval", "Irene oval", "irene main oval (home)" differently, so nothing can be filtered, linked to a map, checked for clashes, or reused by the next club that plays there. Roadmap already lists "a venue entity" as a deferred item (`docs/roadmap.md`, from `098`). Clubs also play away on other clubs', schools' and provinces' fields, and those fields are shared knowledge: the first club to capture one should save every other club the work.

This spec adds a **Fields directory**: a platform-wide list of cricket fields, captured by club managers, **verified by a platform admin**, reusable by every club, and selectable (or creatable on the spot) when a match is set up. It also fixes the data shape now so that **facility management** (grounds that contain fields and nets, with a booking and availability system) can be added in step 2 without reshaping any field row.

**Goals**
- A club manager can capture a field once (name, owner, type, address, map link) and every club can then find and reuse it.
- Every field has an explicit verification state. A field captured by a manager is **Unverified** until a platform admin verifies it; an unverified field is usable but visibly flagged wherever it is chosen or shown on a match.
- A club links fields to itself as **home** (it manages or plays at it, whether or not it owns it), so the manager sees "Our fields" first. More than one club may share a home field.
- Creating or editing a match picks a field from the directory, or creates one inline in one small dialog.
- **Setting up a match never makes the user think about grounds, area types or facilities.** A manager sees one box called Field.
- Fields can be filtered by type (School, Club, Academy, Provincial).
- The data model leaves clear room for grounds (facilities), nets and bookings (step 2) without a migration that rewrites field rows.

## Terminology

Decided with the user (2026-10-13), using their club as the example. **Irene Country Club** is a facility that contains **Irene Main Oval** (a cricket field) and nets that are booked out. **Irene Estate Oval** is a field the club manages and plays home games on but does not own. Away games are played on cricket fields all over.

- **Field** is what a match is played on, and what a manager sees and picks: "Irene Main Oval", "Irene Estate Oval", an away field. This is the only word on match screens and in this directory's UI.
- **Playing area** is the internal name of the generic record behind it (`PlayingArea`, table `playing_area`). It carries an `area_type` enum: `CRICKET_FIELD` today; later `CRICKET_NETS`, `PADEL_COURT` and so on. Nothing in this spec shows `area_type` to a user. Every area created here is `CRICKET_FIELD`.
- **Ground** is the facility above fields and nets (Irene Country Club). **Not built here.** Step 2 adds it and links fields and nets to it.
- A field **never needs a ground**. An away field is a standalone field. A field only joins a ground later, if a club that manages a facility chooses to group it.

## Non-goals

- **No grounds, nets or bookings.** Step 2, a separate spec. This spec only fixes the shape they hang on (see Data Model Changes, "Designed for step 2"). No `ground` table, no booking table, no nets screens.
- **No creating any area type except `CRICKET_FIELD`.** The enum and column exist; the UI and API accept only that value now. A match accepts only a `CRICKET_FIELD`.
- **No geocoding, address autocomplete or map embed.** The map is a link the manager pastes. Latitude and longitude are not stored. Same posture as `012`'s Non-goals on address validation.
- **No photos, facilities lists, capacity, opening hours or contact people.**
- **No "suggest a correction" flow for a verified field.** Once verified, only a platform admin edits identifying details.
- **No automatic conversion of existing `Match.venue` text into fields.** Existing matches keep their text and show no flag. A manager can attach a field when they next edit the match.
- **No change to the import (`097`/`098`).** Imported venues stay text. Resolving an imported venue to a field is a roadmap item.
- **No owner linked to a platform club.** Owner is free text only (the Irene Estate Oval's owner is an estate, not a club on the platform). Linking an owner to a club is a roadmap item.
- **No public (unauthenticated) page for fields.** Public schedule pages (`051`) keep showing the match's venue text, which now carries the field name.
- **No per-club time zones** (`project_club_time_zones` in memory): unchanged assumption.

## User Stories

- As a club manager, I can add a field (name, owner, type, address, map link) so my club's field is in the system.
- As a club manager, I can add an away field while setting up a match, in one dialog, without being asked about grounds or area types.
- As a club manager, I am shown "Did you mean ...?" matches before saving a new field, so I link an existing field instead of creating a duplicate.
- As a club manager, I can search the directory of all clubs' fields, filtered by type and by city, province or country, so I find an away field someone already captured.
- As a club manager, I can mark a field as a home field for my club, whether we own it (Irene Main Oval) or only manage it (Irene Estate Oval), so it appears under "Our fields". More than one club may share a home field.
- As a club manager creating or editing a match, I can pick a field from a searchable list (my club's home fields first) or add a new one right there, without losing what I typed on the match.
- As a club manager, when the field on a match is not verified, I see a clear flag on the match form, match page and match card, so I know the address may be wrong and can check it before telling players.
- As a club manager, I can edit a field my club captured while it is still unverified.
- As a platform admin, I see a queue of unverified fields with a counter, and can open each, correct it, and **Verify** it.
- As a platform admin, I can **Reject** a field with a reason (spam, test data), so it stops appearing in search.
- As a platform admin, I can **merge** a duplicate field into another, so every match and club link moves to the surviving field.
- As a platform admin, I can edit any field, verified or not.
- As a club manager of club X, I cannot edit another club's unverified field or any verified field, even by guessing ids.
- As a player or public viewer, I see the field's name on the match as before; the directory itself is manager-only.

### New entity `PlayingArea` (platform-wide, not club-scoped)

A field is **not** owned by a club row: it is shared. It deliberately has no `club_id`. Who captured it is recorded separately; who uses it is the `club_playing_area` link.

Indexes and constraints:
- `ux_playing_area_identity` on `(area_type, lower(name), lower(address_city), address_country)` **where `merged_into_id is null`**: a hard stop on the exact duplicate, a functional unique index as `ux_league_team_name` is. A violation maps to `DuplicateFieldException extends ConflictException` (409) whose response carries the existing record's id (see API). This is the safety net; the softer "Did you mean" check is the first line of defence. A `DataIntegrityViolationException` from a race falls to the existing generic 409 handler.
- `ix_playing_area_search` on `(address_country, lower(address_city))`; `ix_playing_area_status` on `(verification_status)`.

### Change to `Match`

- Add `playing_area_id uuid null` FK `playing_area`. Index `ix_match_playing_area`. `Match` uses flat UUID columns (no `@ManyToOne`), so the entity gets `@Column(name = "playing_area_id") UUID playingAreaId`.
- **`venue` stays**, kept in step by the service: when `playingAreaId` is set, `venue` is written to the field's `name` (the same copy-the-display-text pattern `070` uses for league team names). This keeps every existing consumer working unchanged. The backend readers of `venue` (`MatchServiceImpl` create/update/`enrichList`, `ManagerOverviewServiceImpl`, `TeamSelectionServiceImpl`, `PlayerAvailabilityServiceImpl`, `PublicAvailabilityPollServiceImpl`, `MatchAvailabilityPollServiceImpl`, `SectionAvailabilityRoundServiceImpl`, and the DTOs that carry `venue`) and the frontend ones (schedule PDF, poster, calendar export, fixtures table, poll cards) read the same string as today. A match with no `playingAreaId` keeps whatever text it had. The two are never edited independently in the UI: choosing a field fills `venue`; clearing the field clears `playing_area_id` and sets `venue` null.
- `MatchDto` gains `playingAreaId`, `playingAreaName` (same as `venue` when linked), `playingAreaVerificationStatus` (null when none). `CreateMatchRequest`/`UpdateMatchRequest` gain optional `playingAreaId`; if both `playingAreaId` and a differing `venue` are sent, `playingAreaId` wins. `MatchServiceImpl.enrichList` rebuilds `MatchDto` positionally, so it is updated with the new components.
- A `playingAreaId` whose `area_type` is not `CRICKET_FIELD` is refused with `PlayingAreaNotMatchableException extends ValidationException`; a `REJECTED` one with `FieldRejectedException extends ValidationException`; a merged-away id is transparently resolved to its target.
- `Match.venue` as a client-writable field remains accepted for backward compatibility with `097`/`098` imports and existing clients, until a later spec retires it.

### Designed for step 2 (facility management and booking) — not built here

Decisions made now so step 2 needs no rework:
- **Two concerns, one record.** Field picking for matches and facility management both reference `playing_area.id`. A standalone field (every away field, Irene Estate Oval) never needs a ground. Irene Main Oval gains a ground later by setting `ground_id`.
- **Grounds.** Step 2 adds `ground(id, name, owner, address, map_url, verification, ...)` and the FK on `playing_area.ground_id`. A ground's address becomes the source for fields inside it; the field's own address columns stay as the fallback, which is why they are required now. The home link for a ground (who manages the facility) is a `club_ground` link analogous to `club_playing_area`.
- **Nets and other areas** are further `playing_area` rows with another `area_type` (`CRICKET_NETS`, `PADEL_COURT`), created only inside a ground. They never appear in the match picker, which filters `area_type = CRICKET_FIELD`.
- **Bookings** reference `playing_area.id`: `booking(id, playing_area_id, club_id, starts_at, ends_at, purpose, match_id?, status, ...)`. The clubs that may grant a booking are the home clubs of the ground (or of the standalone field).
- **Matches reference bookings optionally**, not the reverse: `booking.match_id`. Nothing on `Match` changes again.
- **Clash checks** run on `(playing_area_id, time range)`, which is why the id is on `Match` now rather than inferred from text.
- **Time zones:** a ground will eventually carry its own zone; omitted today.

## API Contract

Two surfaces. Club-scoped under `/api/v1/manage/clubs/{clubId}/playing-areas` (guarded by `@PreAuthorize("@access.canAccessClub(authentication, #clubId)")`, so a section manager who creates matches can capture and link fields). The directory data is global; `clubId` scopes the caller and the `linkedHome` flag. Platform-admin under **`/api/v1/platform/playing-areas`**: every existing platform controller sits under `/api/v1/platform/**`, which `SecurityConfig` gates to `platform_admin` by URL, so no per-method annotation is needed (`/api/v1/admin/**` would be open to any logged-in user). DTOs only; MapStruct mappers; controller → service interface + impl → repository. List endpoints return `Page<T>` with real `LIMIT/OFFSET`; counters use the same `Specification` as the list (`MatchSpecifications` precedent) so counters equal lists. Every service `list`/`get` is `@Transactional(readOnly = true)`, every write `@Transactional` (open-in-view is off).

| Endpoint | Access | Purpose |
|---|---|---|
| `GET /api/v1/manage/clubs/{clubId}/playing-areas` | club manager | Search the whole directory. Params: `q` (name/city, case-insensitive substring), `category` (repeatable), `country`, `province`, `city`, `verification` (`UNVERIFIED`/`VERIFIED`), `mine` (only this club's home fields), `areaType` (defaults to `CRICKET_FIELD`, the only value accepted now). Excludes `REJECTED` and merged-away rows. Paged. Each item carries `linkedHome` and `verificationStatus`. Default sort: home fields first, then name |
| `GET /api/v1/manage/clubs/{clubId}/playing-areas/summary` | club manager | Counters for the same filters: Our fields, In the directory, Unverified |
| `GET /api/v1/manage/clubs/{clubId}/playing-areas/filter-options` | club manager | Distinct countries, provinces and cities reachable under the current selection, as `GET /matches/filter-options` does, to fill the Country, Province and City selects |
| `GET /api/v1/manage/clubs/{clubId}/playing-areas/similar` | club manager | "Did you mean": params `name`, `city`, `country`; up to 5 existing fields by normalised-name match within the same country (see Open question 4). Read-only |
| `GET /api/v1/manage/clubs/{clubId}/playing-areas/{id}` | club manager | One field with `linkedHome`, creator club name, verification details, this club's match count |
| `POST /api/v1/manage/clubs/{clubId}/playing-areas` | club manager | Capture a field. `area_type` is set to `CRICKET_FIELD` by the service (not accepted from the client in this spec). Creates it `UNVERIFIED` with `created_by_club_id = clubId` and auto-links it home. 409 `DuplicateFieldException` on the identity index, as a `ProblemDetail` with a property `existingPlayingAreaId` (a dedicated handler in `GlobalExceptionHandler`, following `SelectionRejectedException`) |
| `PUT /api/v1/manage/clubs/{clubId}/playing-areas/{id}` | club manager | Edit. Allowed only when the record is `UNVERIFIED` **and** `created_by_club_id = clubId`; otherwise 409 `FieldNotEditableException` whose message says who can edit (see Open question 5) |
| `PUT /api/v1/manage/clubs/{clubId}/playing-areas/{id}/home` | club manager | Link home for this club (idempotent). `DELETE` unlinks. Body-less |
| `GET /api/v1/platform/playing-areas` | platform admin | Moderation list. Params: `verification` (default `UNVERIFIED`), `q`, `category`, `country`. Paged, oldest unverified first |
| `GET /api/v1/platform/playing-areas/summary` | platform admin | Counters: Unverified, Verified, Rejected |
| `GET /api/v1/platform/playing-areas/{id}` | platform admin | Full detail with every linked club, match count, creator club, possible duplicates |
| `PUT /api/v1/platform/playing-areas/{id}` | platform admin | Edit any field, any state; editing a verified field keeps it verified |
| `POST /api/v1/platform/playing-areas/{id}/verify` | platform admin | `UNVERIFIED` → `VERIFIED`; stamps `verified_at` and `verified_by_subject` (from `Authentication`). Idempotent on an already verified field. 409 `InvalidStatusTransitionException` from `REJECTED` (reopen first; this differs from player verification, which allows Rejected → Verified) |
| `POST /api/v1/platform/playing-areas/{id}/reject` | platform admin | Body `{reason}` (required). → `REJECTED`. Existing matches keep their link and show a "Field rejected" flag |
| `POST /api/v1/platform/playing-areas/{id}/reopen` | platform admin | `REJECTED` → `UNVERIFIED` |
| `POST /api/v1/platform/playing-areas/{id}/merge` | platform admin | Body `{targetPlayingAreaId}`. One transaction: set `merged_into_id`; repoint `match.playing_area_id` with a bulk `@Modifying` update (the `propagateLeagueTeamToHomeSide` style) and copy the target's name to those matches' `venue`; move `club_playing_area` links to the target (de-duplicated on `(club_id, playing_area_id)`, a home link stays home if either was home). Refused (409) if the target is merged away, rejected, or the same row |
| Existing match create/update/get/list | as today | `MatchDto` and request DTOs gain the playing-area fields. `GET /matches` gains an optional `playingAreaId` filter (backend param, added as a `MatchSpecifications.playingAreaIdEquals` spec) |

New exceptions in `com.cricketlegend.exception`: `DuplicateFieldException`, `FieldNotEditableException` (both extend `ConflictException`), `PlayingAreaNotMatchableException`, `FieldRejectedException` (both extend `ValidationException`). No new base type, so the status matrix in `docs/standards/backend.md` is unchanged. `InvalidStatusTransitionException` is reused. `DuplicateFieldException` also needs its own handler for the extra property.

The OpenAPI schema `backend/openapi/openapi.yaml` is regenerated by hand and checked in (per `feedback_dont_build_under_live_backend`: do not run `mvn` under the live backend; verify in a scratch copy). There is no automated contract diff step in CI today (`docs/standards/backend.md` describes one); flagged for the plan.

## Acceptance Criteria

- A club manager can add a field with name, type, owner (type and name), city, country, and optionally street and province/county, optional map link and location notes, and it appears in their directory marked **Unverified** and under **Our fields**.
- A club can mark a field it only manages (not owns) as a home field, with the real owner recorded as free text, and several clubs can have the same field as home.
- **A manager can create a match with an away field in one dialog, with no ground, playing-area or area-type step, and no screen a manager uses to set up a match shows those words.**
- The Country field defaults from the browser's time zone (falling back to the locale region, then the club's own country) and the manager can change it.
- Saving a field whose name and city match an existing field offers to use that field; an exact duplicate (same name, city, country, ignoring case) is refused with 409 and the existing field offered.
- The directory lists fields from every club, can be filtered by type (School, Club, Academy, Provincial), country, province and city, searched by name, and is paged by the backend.
- A manager can edit a field only while it is unverified and their club captured it; they cannot edit anyone else's field or any verified field, and the API enforces it, not just the UI.
- Creating or editing a match offers one searchable Field box (own home fields first) listing cricket fields only, and an **Add a new field...** option that creates the field without leaving or resetting the match form.
- Selecting an unverified field on a match shows a visible warning on the form, and an **Unverified field** flag on the match card, list and page; a verified field shows none.
- Choosing a field sets the match's `venue` text to the field name, so existing cards, schedule PDFs, calendar exports, public schedule pages and imports show the same text as before; matches without a field are unchanged. No migration changes existing `venue` text, and no existing match is given a field automatically.
- A platform admin has a queue of unverified fields with a count, and can verify, edit, reject (with a reason), reopen and merge them. Verifying clears the flag on every match using that field without editing any match. The admin dashboard shows a "Fields to verify" tile with the count.
- Rejecting a field removes it from search and picker results; matches already using it show a **Field rejected** flag and cannot be saved until a manager chooses another field or clears it.
- Merging field A into B moves all matches and club links to B in one transaction, B's name appears as the venue on those matches, and A no longer appears anywhere; nothing merges without an explicit confirmation showing the counts.
- The model supports step 2 without changing existing field rows: `playing_area.area_type` and a nullable `ground_id` exist; nets and other areas can be added as further rows; a booking can reference `playing_area.id`; the match-to-field link is a column, not text; a standalone field (every away field) needs no ground.
- The Fields list, card, list view, detail page and form match the Players/Matches/Leagues gold standard: the same shared components, every card the same parts and height whatever its status, and no bespoke layout. Approved mockups exist before the UI slice is built.
- All list endpoints are paged server-side; no screen fetches the whole directory to filter in the browser.
- All new UI is mobile-first at 375 px and uses MUI v5 with `theme.ts` tokens only.

### Open questions (recommended defaults, accepted unless the reviewer says otherwise)

1. **Naming:** decided. UI says Field; the record is `PlayingArea` with an `area_type`; Ground is the step 2 facility above it.
2. **Visibility of other clubs' unverified fields.** Recommended: visible and selectable by every manager, flagged. Alternative: visible only to the capturing club until verified (safer against spam, defeats the reuse goal).
3. **Type vs owner type overlap.** `category` (what it is, for filtering) and `owner_type` (who owns it) often agree. Recommended: keep both, because a club can manage a field on school or estate land (Irene Estate Oval). Alternative: drop `owner_type` and keep only free-text owner.
4. **Similarity matching** for "Did you mean": recommended Postgres `pg_trgm` over a normalised name within the same country (no migration uses extensions today; `CREATE EXTENSION IF NOT EXISTS pg_trgm` must be allowed for the production database role, to be confirmed). Alternative with no extension: normalised prefix/contains match only.
5. **HTTP status for "not editable".** Recommended 409 via `FieldNotEditableException extends ConflictException` (no new base type). Alternative: add a 403 base type, which means a standards-table change first.
6. **Country from browser zone.** Recommended: time zone first (as requested), locale second.
7. **Who may verify.** Recommended: platform admins only. Alternative at scale: also club admins of the owning club. Not before real volume.
8. **Merge in this spec or later?** Recommended in: verification without merge leaves duplicates unfixable once matches reference them.
9. **Who may capture and link a field.** Recommended: anyone `canAccessClub` (including a section manager, who creates matches). Alternative: `canAdministerClub` (club-wide admins only), stricter but a section manager could not add an away field while setting up a match.
