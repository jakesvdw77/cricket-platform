# 046 — Header/Body Elevation Standard

**Depends on:** `044-detail-screen-gradient-header.md` and `045-form-and-manage-header-gradient-rollout.md` (both **superseded by this spec** — their saturated brand-gradient banner direction was reviewed live against the running app and rolled back in full, nothing shipped; their blast-radius research — the exact `RecordDetailScreen`/`RecordFormScreen`/`ManageScreenHeader` call-site tables, the `/admin` scope question and its resolution — is reused verbatim below, re-verified by grep rather than re-derived, since that research stays accurate independent of which visual direction was chosen), `036-view-first-record-detail-screens.md` (built `RecordDetailScreen`, its eight `*DetailPage.tsx` call sites, `DetailFieldGrid`/`DetailFieldRow`), `008-product-catalog.md` (built `RecordFormScreen`, the reference create/edit shape), `041-list-screen-header-actions.md` (built `ManageScreenHeader`'s `action` slot), `043-list-toolbar-gold-standard.md` (the precedent this spec's body-card treatment for `ListToolbar`/`RecordCard` is confirmed to already satisfy, unchanged), `docs/standards/design-system.md` (Two Token Layers, Token table, Record list / create-edit pattern table — the literal palette/shape/elevation values this spec derives from), `docs/standards/frontend.md`'s >70%-shared-markup extraction rule.
**Status:** proposed

## Problem & Goals

`RecordDetailScreen`, `RecordFormScreen`, and `ManageScreenHeader` — the three shared header-bearing components every `/manage` and `/admin` detail/form/list screen composes from (`docs/standards/design-system.md`'s Record list / create-edit pattern table) — render their back-link/title zone as plain text sitting directly on the page's existing subtle wash (`pageBackgroundGradient()`), with no visual separation from the content below. `044` tried a full-bleed, saturated brand-gradient banner as the fix; reviewed live, that read as a consumer/marketing convention out of step with this product's dense B2B admin surface (Stripe Dashboard, Linear, GitHub, Notion, not a travel-booking hero), and was rolled back before `045` extended it further. A second visual direction — a flat white header with a restrained top accent line and a shadow, plus whitened/shadowed body content where it was still bare — was mocked up against the real Matches screens (list, view, edit) and approved as-is, with the explicit instruction to build it "as close as possible to the design."

This spec is that approved direction, covering the full header surface `044`/`045` together identified (`RecordDetailScreen`, `RecordFormScreen`, `ManageScreenHeader`) plus the body-content whitening `044`/`045` never touched — the real fix for "components fading into the background" that a header treatment alone can't solve.

**Goals**
- `RecordDetailScreen`, `RecordFormScreen`, and `ManageScreenHeader` render an identical header treatment: solid white background, a bottom divider border, a soft downward separation shadow, and a 3px `primary.main` accent bar along the header's own top edge — full-bleed to the top of whichever shell's `<main>` renders it, reusing `044`'s already-worked-out negative-margin bleed technique.
- Every header's title renders at `fontWeight: 700` (heavier than MUI's default `h6` 600), the one deliberate, flagged deviation from `docs/standards/design-system.md`'s "MUI's default type scale is used unmodified" rule.
- Everything else already in each header — back-link colour, the tinted-primary avatar/icon chip, badge tones, `secondaryActions`/Edit/`action` button treatments — is unchanged from what ships today. This is a narrower diff than `044`'s: no dark-banner badge/button variants needed, because nothing renders on top of a colour fill anymore.
- `RecordDetailScreen`'s per-section content and `RecordFormScreen`'s entire body render as solid white, shadowed cards — reusing `RecordCard.tsx`'s own existing `bgcolor: 'background.paper'` / `boxShadow: 2` card convention directly, not a new shadow recipe — so populated content reads as a surface floating above the page wash, matching what `ListToolbar`/`RecordCard` already do on list screens.
- The header treatment (`PageHeaderBand`) and the body-card treatment (`ContentCard`) are each defined exactly once and reused everywhere they apply, per `docs/standards/frontend.md`'s extraction rule — not copy-pasted `sx` across three (header) or two (body) components.
- Ships as one PR (or a small, tightly-sequenced set) covering the whole surface at once — not staged per-entity or per-component, per the user's explicit instruction that this is the one thing `044`'s original component-by-component rollout got wrong operationally, not just visually.

## Non-goals

- **No backend change.** Purely frontend/presentational — same boundary `044`/`045` already established. No entity, migration, or endpoint is added or touched.
- **No change to `pageBackgroundGradient()` or the page wash itself.** Confirmed correct as-is by the user directly — it had nothing to contrast against before; the new white headers/cards give it that contrast, without changing the wash itself.
- **No change to `ListToolbar`/`RecordCard`'s existing surface treatment.** Both already render a white, bordered/shadowed surface (`043`); list screens using `ManageScreenHeader` get the header change only, zero body change.
- **No change to badge/avatar/button colours anywhere.** Re-stated explicitly: this reverses `044`'s core premise (colour band, everything on it re-tinted) rather than extending it, so there is no dark-banner badge variant to build. Confirmed by reading `RecordCard.tsx` directly: its exported `badgeSx(tone)` takes a single `tone` parameter only — no `onDarkBanner` second parameter/overload exists in the current codebase, i.e. the `044` rollback already removed that variant in full; there is no dead code left to clean up here.
- **No new `theme.ts` contrast-clamp logic.** `044`'s `detailHeaderGradient`/`detailHeaderShadow` contrast-clamped gradient helpers do not exist in the current `theme.ts` either — confirmed by reading the file directly, the rollback was complete. This spec's accent bar is a flat `primary.main` line with no text rendered on top of it, so the accessibility risk that drove `044`'s whole clamp mechanism (light-club-colour text-on-gradient contrast failure) does not apply here — see Test Plan.
- **`/admin`'s scope is already a settled decision, not reopened here.** `045` put the question to the user explicitly (apply `RecordFormScreen`'s restyle everywhere it's used, `/admin`'s 4 call sites included, since the component has no notion of which route rendered it) and got it confirmed. That decision carries forward unchanged: all 13 `RecordFormScreen` call sites (9 `/manage`, 4 `/admin`) get this spec's header/body treatment identically. Not re-litigated.
- **No resolution of `SponsorContactList.tsx`'s own hand-rolled back button.** Confirmed by grep (below) it still uses neither `RecordFormScreen` nor `ManageScreenHeader` — a pre-existing, separately-flagged gap, out of scope here exactly as `045` scoped it out.
- **No change to `RecordDetailScreen`'s, `RecordFormScreen`'s, or `ManageScreenHeader`'s public props.** `avatar`/`badge`/`secondaryActions`/`editTo`/`editLabel`/`sections` (`RecordDetailScreen`), `title`/`backTo`/`backLabel`/`actions`/`children` (`RecordFormScreen`), and `title`/`backTo`/`backLabel`/`action` (`ManageScreenHeader`) all keep their exact current shape and call-site values — styling-only, not a data or behaviour change.
- **No staged/per-entity rollout.** Explicitly rejected as a Rollout Notes requirement (see below) — this is the one thing called out as a deliberate correction versus how `036`'s original detail-screen rollout happened to proceed.

## User Stories

- As a club admin moving between any detail, form, or bare list/tree `/manage` screen, every header renders the identical white-with-top-accent treatment — no visible "some screens got restyled, some didn't" seam anywhere in the app.
- As a club admin viewing a Match (or any entity) detail screen, each section's content (Details, Home/Away XI, Availability) reads as a distinct white card floating above the page wash, instead of bare text sitting directly on it.
- As a club admin creating or editing a record, the whole form body — tabs where present, fields, and the Save/Cancel actions bar — reads as one coherent white card, matching the mockup's Match Edit screen.
- As a club admin viewing a match with no playing XI selected yet, the "No XI selected yet" empty-state box keeps its own distinct grey-tinted treatment, visually different from populated content, exactly as it renders today.
- As a platform operator using `/admin` screens (Club, Product, Subscription, Email Settings forms), the same header/body treatment applies there too, consistent with `045`'s already-confirmed decision that `RecordFormScreen`'s restyle isn't `/manage`-only.
- As a developer maintaining any of the three header-bearing components, the header band's markup/colour derivation lives in one shared component, not three independently maintained copies; the body-card treatment lives in one shared component (or one consistent, directly-reused `sx` shape), not copy-pasted per caller.
- As a reviewer, every colour/spacing/shadow value this spec introduces is a literal, theme-token-derived requirement I can check against the code, not a description I have to interpret — and the finished build is compared against the approved mockup before being called done, not just unit-tested for behaviour.

## Data Model Changes

None. Purely a frontend, presentational-layer change to existing shared components. No entity, field, migration, or endpoint is added or touched.

## API Contract

None. No endpoint is added, removed, or changed.

### 1. Shared header component — `ui/src/components/PageHeaderBand/PageHeaderBand.tsx` (new, full four-file anatomy: `.tsx`/`.test.tsx`/`.stories.tsx`/`index.ts`)

A small wrapper taking only `children: ReactNode` (no other configurable props — the band's bleed/colour/border/shadow/accent values are fixed by definition, not per-caller variance, same reasoning `045` used for its own now-superseded `HeaderGradientBand`). `RecordDetailScreen`, `RecordFormScreen`, and `ManageScreenHeader` each render their existing header content (back-link, avatar/title/badge/secondaryActions/Edit for `RecordDetailScreen`; back-link/title for `RecordFormScreen`; back-link/title/action for `ManageScreenHeader`) as `PageHeaderBand`'s `children`, in place of each one's own literal header `Box`. This is the extraction requirement per `docs/standards/frontend.md`'s >70%-shared-markup rule — three components about to render byte-identical band chrome is exactly the "extract immediately" trigger, not a "leave it duplicated for now."

**`PageHeaderBand`'s own `sx`, every value theme-token-derived, none hardcoded:**
- Background: `theme.palette.background.paper` (flat white — the core reversal from `044`: no gradient, no fill colour anywhere in the band except the accent bar below).
- Bottom border: `` `1px solid ${theme.palette.divider}` ``.
- Box shadow: a new `ui/src/theme.ts` helper, alongside `pageBackgroundGradient()` (same "derive from `theme.palette`, never hardcode" precedent) — e.g. `headerBandShadow(theme: Theme): string` returning `` `0 2px 6px ${alpha(theme.palette.text.primary, 0.06)}` ``. This is the theme-token-derived equivalent of the mockup's literal `0 2px 6px rgba(20, 35, 28, 0.06)` — `theme.palette.text.primary` is `#14231C` (`docs/standards/design-system.md`'s Token table), and `alpha(..., 0.06)` reproduces the mockup's measured opacity exactly; the raw rgba in the mockup is illustrative of the *value* to hit, not license to hardcode it in the component. **Binding requirement, stated explicitly per the note below:** no literal `rgba(20, 35, 28, 0.06)` (or any other raw hex/rgba) may appear in `PageHeaderBand.tsx` or `theme.ts`'s new helper's call sites — only the `alpha(theme.palette.text.primary, 0.06)` derivation.
- Top accent: a 3px solid bar of `theme.palette.primary.main` along the band's very top edge — its only saturated-colour element. Implemented as `borderTop: `3px solid ${theme.palette.primary.main}`` (simplest, no extra element) or an absolutely-positioned 3px-tall inner `Box`, either is acceptable at build time as long as it renders flush with the band's own top edge and doesn't shift the band's other content by more than that 3px.
- Full-bleed bounds: identical technique `044` already worked out — negative margins (`mx`/`mt` of `{ xs: -2, md: -3 }`) cancelling `AppShell`'s/`GridNavShell`'s shared `<main>` padding, plus matching internal padding (`px`/`pt` of `{ xs: 2, md: 3 }`) on the band itself, bottom margin `0` so page content immediately below stays exactly where it is. Square top corners (flush with `<main>`'s edge); bottom corners rounded via `theme.shape.borderRadius × 2`, same as `044`'s own precedent.
- No gradient recipe, no contrast clamp, no `withClubBranding()`-dependent lightening logic — none of `044`'s gradient-stop machinery is reused; this header's only colour-on-colour element is a flat `primary.main` line with zero text rendered on top of it.

**Title weight — the one explicit deviation from `docs/standards/design-system.md`'s type-scale rule.** Each header's title renders `variant="h6"` (unchanged size) with `fontWeight: 700` (heavier than MUI's default `h6` weight of 600) — the mockup's ~21px/700 treatment, expressed as a weight override at the existing size rather than a new scale entry. `docs/standards/design-system.md` states "MUI's default type scale is used unmodified"; this spec asks for a narrow, named exception (weight only, never size) and flags it here explicitly for review sign-off rather than treating it as already-settled — **a reviewer should confirm this is an acceptable, minimal exception before merge, not a precedent for further type-scale overrides elsewhere.**

**Everything else in each header keeps its exact current colour/treatment — restated explicitly so it isn't lost among the above:**
- `RecordDetailScreen`: back-link `text.secondary`; avatar `alpha(primary.main, 0.14)` bg / `primary.dark` icon (unchanged); badge tones unchanged (`badgeSx`, no `onDarkBanner` variant); `secondaryActions` outlined-`color="inherit"` unchanged; Edit button's tinted-primary treatment (`alpha(primary.main, 0.12)` bg, `primary.dark` text, transparent border) unchanged.
- `RecordFormScreen`: back-link `text.secondary` unchanged. No avatar/badge/secondaryActions slots to restyle.
- `ManageScreenHeader`: back-link `text.secondary` unchanged; `action` (typically a plain MUI `contained` primary `Button`, e.g. "Add Match") unchanged — it already renders as its own solid, self-contained surface, not part of the band's own white/text treatment, so nothing about it needs to change now that the band itself is white instead of coloured.

### 2. Shared body-card component — `ui/src/components/ContentCard/ContentCard.tsx` (new, full four-file anatomy)

A thin wrapper reusing `RecordCard.tsx`'s own existing card convention directly — `sx={{ bgcolor: 'background.paper', boxShadow: 2 }}` (MUI's `elevation` step 2, the exact value `RecordCard`'s `MuiCard` already uses) — rather than inventing a new shadow value. Takes `children: ReactNode` and an optional `sx` passthrough for per-caller padding/spacing needs (unlike `PageHeaderBand`, which has none, `ContentCard` is a generic content wrapper reused in two structurally different places below, so a minimal passthrough is warranted rather than two near-duplicate wrappers).

**Applied to `RecordDetailScreen.tsx`:** today, `sections` renders as a flat vertical stack — each section's heading + `note` + `content`, separated from the next by a top border (`index > 0 ? { pt: 3, borderTop: 1, borderColor: 'divider' } : undefined`), all sitting directly on the page wash. This spec replaces that with: **every entry in `sections` is individually wrapped in its own `ContentCard`** (heading, `note`, and `content` all render inside the card, exactly as they do today, just inside a white/shadowed surface instead of a bare `Box`), with normal vertical spacing (the stack's existing `gap: 3`) between cards in place of the border-top divider. This is a generalisation of the mockup's own two example sections (Match's "Details" grid and "Availability" text block) up to the component level — `RecordDetailScreen` is shared by all eight entities' varying section shapes (`DetailFieldGrid`-based, `PlayingXiSummary`-based, plain `Stack`-based), and the card wrapping applies uniformly to every section regardless of what its `content` renders, not opted into per entity.
   - **Explicit decision, not an oversight:** the existing "No XI selected yet" `EmptyState` box (rendered by `PlayingXiSummary` when a side has no XI selected — `bgcolor: 'action.hover'`, its own distinct grey-tinted, bordered treatment) is left exactly as it renders today, nested inside whatever `ContentCard` its containing section now gets. It is **not** converted to match the white-card treatment — an empty state is deliberately visually distinct from populated content, and that distinction should read clearly even nested inside a now-white section card.
- **Applied to `RecordFormScreen.tsx`:** today, the field grid (`children`) and the actions bar (below a `borderTop: 1, borderColor: 'divider'`) render as two separate `Box`es on the page wash. This spec wraps **both together, as one `ContentCard`** — the grid and the actions bar (divider between them preserved, now an internal border inside the card rather than a border on bare page background) become a single white, shadowed surface, matching the mockup's Match Edit screen (tabs + fields + Save/Deactivate actions all inside one card). Confirmed by reading `RecordFormScreen.tsx` directly: it has no tab-row rendering of its own — a consuming page (e.g. `MatchFormPage.tsx`, which renders MUI `Tabs` directly) passes its tabs as part of `children`, inside the same grid `Box` this spec now wraps in `ContentCard` — so wrapping `RecordFormScreen`'s own body automatically wraps whatever tabs a consuming page renders too, with no per-page change needed anywhere in the 13-call-site table above.
- **Not applied to `ManageScreenHeader`'s own consuming screens.** List/tree/dashboard-adjacent `/manage` screens compose `ManageScreenHeader` + whatever body the page renders below it (`ListToolbar` + record grid, `ClubStructure`'s tree, `AvailabilityPollsDashboard`'s poll list, `ManageFixturesHome`'s cards). `ListToolbar` (per `043`) already renders its own white, bordered, shadowed `background.paper` surface; `RecordCard` (the record-grid unit) already renders `bgcolor: 'background.paper'` / `boxShadow: 2`. **Stated explicitly: the "body needs whitening" problem this spec fixes was specific to `RecordDetailScreen`'s bare section content and `RecordFormScreen`'s bare field grid/actions bar — list screens composing `ManageScreenHeader` were already correct and need zero body change here.** `ManageScreenHeader`'s own body call sites get the header change only.

**Mobile-first:** verified at 375/768/1280, same Storybook viewport convention every touched component already uses — no new breakpoint logic invented; `PageHeaderBand`'s bleed values reuse the exact `{ xs, md }` shape `044` already proved.

### Design fidelity — its own explicit requirement, not folded into the bullets above

Past builds from this codebase's specs have drifted visually from the approved design during implementation — real, recurring feedback. Every colour/spacing/shadow/weight value in this section is written as a literal, checkable requirement (a theme-token derivation, an exact pixel value, an exact `fontWeight` number) specifically so a reviewer can check the built component against this text line by line, not interpret a description. Nothing above should be read as illustrative language to be "approximated" — where a mockup's own raw value is quoted (the shadow's rgba, the accent bar's 3px), it is quoted to name the target value the theme-derived expression must reproduce, never as permission to hardcode it.

**Simplification versus `044`, stated explicitly so a reviewer doesn't expect old machinery to reappear:** no `getContrastRatio`/contrast-clamp test is needed anywhere in this spec. `044`'s entire contrast-clamp mechanism existed because white text rendered on top of a variable-lightness brand-coloured gradient, and a light club colour could make that combination fail WCAG. Here, no text renders on top of any colour fill — the header background is always flat white, and the only saturated-colour element (the 3px top accent bar) carries no text or icon content over it. That accessibility risk categorically does not exist in this design, so no equivalent test machinery is built or expected.

**Design-fidelity check, required before this spec is called done:** in addition to the component/unit tests above, the built `PageHeaderBand` and `ContentCard` treatments (rendered live on at least the Match list/view/edit screens the mockup was approved against) must be visually compared side-by-side against the approved mockup before merge — not just asserted to pass the component tests above. This is a manual, named step in the PR's own checklist, not assumed to be covered by the automated tests.
