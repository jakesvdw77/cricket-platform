# 045 — Form and Manage Header Gradient Rollout

**Depends on:** `044-detail-screen-gradient-header.md` (built the pattern this spec extends verbatim — `ui/src/theme.ts`'s `detailHeaderGradient(theme)`/`detailHeaderShadow(theme)` contrast-clamped gradient helpers, and `RecordCard.tsx`'s `badgeSx(tone, { onDarkBanner: true })` dark-banner badge variant — both reused here, not reimplemented; `044`'s own Non-goals explicitly scoped `RecordFormScreen`/`ManageScreenHeader` out, naming them as sharing "visual DNA" with `RecordDetailScreen` but leaving them for a later pass — this is that pass), `008-product-catalog.md` (built `RecordFormScreen`, the reference create/edit shape), `036-view-first-record-detail-screens.md` (the read-only counterpart `RecordFormScreen` already existed alongside), `041-list-screen-header-actions.md` (built `ManageScreenHeader`'s `action` slot, and the precedent this spec's Open Question below is measured against), `docs/standards/design-system.md`'s Record list / create-edit pattern table (names `RecordFormScreen`/`ManageScreenHeader` as the third and fourth header-bearing shared components, alongside `RecordCard`/`RecordDetailScreen`), `docs/standards/frontend.md`'s reuse/extraction rule (">70% shared markup or logic is the signal to extract a shared component immediately").
**Status:** superseded by `046`, before any implementation started — `044`'s gradient-band direction this spec extended was rolled back in full (see `044`'s own updated Status line). `046` replaces both specs with a single tonal/elevation-based header + body treatment covering `RecordDetailScreen`, `RecordFormScreen`, and `ManageScreenHeader` together. The blast-radius research here (every `RecordFormScreen`/`ManageScreenHeader` call site, the `/admin` scope question and its resolution) remains accurate and is carried forward into `046` rather than re-derived.

## Problem & Goals

`044` gave `RecordDetailScreen` — the shared read-only header on all eight `*DetailPage.tsx` screens — a full-bleed brand-gradient banner header. `RecordFormScreen` (every create/edit screen) and `ManageScreenHeader` (every bare list/tree/dashboard-adjacent `/manage` screen) were deliberately left untouched by that spec, even though `docs/standards/design-system.md`'s own Record list / create-edit pattern table lists all three components side by side as the header-bearing pieces of the same pattern. The result, confirmed live by screenshot on `ManageClubProfilePage.tsx` (a `RecordFormScreen` screen): its back-link/title sit on the old plain wash — `text.secondary` back-link, plain black title, no band — directly beside screens that now render the new gradient band, reading as two different design systems inside the same app.

Asked to scope the fix, the answer chosen was the widest of the options offered: extend the `044` gradient-band treatment to both `RecordFormScreen` and `ManageScreenHeader`, not `RecordFormScreen` alone.

**Goals**
- `RecordFormScreen`'s header zone (back-link + title) renders the identical full-bleed gradient band `RecordDetailScreen` established in `044` — same theme.ts helpers, same white-on-gradient treatment, same negative-margin bleed technique.
- `ManageScreenHeader`'s header zone (back-link + title + optional `action` slot) gets the same band, with its `action` button (a page-level "Add X") restyled to a dark-banner-appropriate treatment, decided explicitly rather than left ambiguous between `044`'s two existing button treatments.
- Every screen composing either component inherits the new header automatically — no page-level edits to any `*FormPage.tsx`/`*List.tsx`/`ClubStructure.tsx`/`AvailabilityPollsDashboard.tsx`/`ManageFixturesHome.tsx` call site.
- No new colour decision: every value this spec needs already exists from `044` (`detailHeaderGradient`, `detailHeaderShadow`, `badgeSx`'s dark-banner tones aren't needed here since neither component renders a badge, but the same "derive from `theme.palette`, never hardcode" discipline applies to anything new).
- The real, three-call-site duplication this creates (`RecordDetailScreen`, `RecordFormScreen`, `ManageScreenHeader` all now rendering near-identical band markup) is resolved per `docs/standards/frontend.md`'s extraction rule, not left as copy-pasted `sx`.

## Resolved Scope Question — does this also mean every `/admin` screen?

**Confirmed by the human: yes, apply the gradient band everywhere `RecordFormScreen` is used, `/admin` included** — the recommendation below was put to the user explicitly (not silently decided) and accepted as-is, no override. `RecordFormScreen` is used by two distinct groups of screens, confirmed by grep (`grep -rl "RecordFormScreen" ui/src/pages`):

- **`/manage`** (club-admin-facing, club-branded via `withClubBranding()` when that eventually ships): `PlayerFormPage`, `TeamFormPage`, `MatchFormPage`, `LeagueFormPage`, `SeasonFormPage`, `ClubContactFormPage`, `SponsorFormPage`, `SponsorContactFormPage`, `ManageClubProfilePage` — the group the user's screenshot and scope request were actually about.
- **`/admin`** (platform-operator-facing, never club-branded — `theme.palette.primary` there is always the base platform default, `withClubBranding()` is never called on this route): `ClubFormPage.tsx`, `ProductFormPage.tsx`, `SubscriptionFormPage.tsx`, `EmailSettings.tsx`.

`RecordFormScreen` is one shared component with no notion of which route rendered it — it has no prop today expressing "is this a club-branded screen." Restyling the component necessarily restyles both groups identically; there is no way to apply this only to `/manage` short of adding a new prop that every one of `RecordFormScreen`'s 13 call sites would need to pass (or default), threading a which-persona/whether-branded distinction into a component that has never needed one.

Note this is a **different** situation from `041-list-screen-header-actions.md`'s own precedent of leaving `/admin` out of a `ManageScreenHeader` rollout: `041` scoped out `/admin` because its list screens (`ProductList`, `ClubList`, `SubscriptionList`) don't use `ManageScreenHeader` at all — a different, untouched header story, confirmed still true by this spec's own grep (`ManageScreenHeader`'s only call sites are `/manage`). That's "not yet brought onto the shared component." Here, `/admin`'s `RecordFormScreen` call sites are already on the shared component this spec is restyling — the question isn't whether to bring `/admin` onto something new, it's whether changing something `/admin` already uses should visually affect `/admin` too.

**Decision: apply the gradient band everywhere `RecordFormScreen` is used, `/admin` included.** Reasoning:
- The whole motivation for this spec is "one shared component, no inconsistency between screens that compose it" — the same reasoning that justified `044` shipping to all eight `*DetailPage.tsx` screens uniformly regardless of per-entity slot contents. Carving `/admin` out reintroduces exactly the kind of two-systems-in-one-app inconsistency this spec exists to remove, just at a different boundary (`/manage` vs `/admin` instead of `RecordDetailScreen` vs `RecordFormScreen`).
- The alternative (a new conditional prop, e.g. `branded?: boolean`, threaded through all 13 call sites) is real added complexity for a component that has zero knowledge of its route today, to preserve a visual distinction nobody has asked for — the platform default gradient (`theme.palette.primary.main`/`.dark`, the same green already used everywhere in `/admin` today) is what `/admin` would render, not a club's colour, since `withClubBranding()` is never called there. `/admin` doesn't lose "platform-operator" visual identity — it gains the same banded-header treatment its own default palette already produces on `/manage`.
- No functional/permission implication either way — this is presentational only, identical to `044`'s own boundary.

Confirmed by the user directly (not a foregone conclusion baked in silently) — matching `043-list-toolbar-gold-standard.md`'s own precedent of flagging a recommendation before treating it as decided rather than deciding it unilaterally.

## Non-goals

- **No change to `RecordFormScreen`'s or `ManageScreenHeader`'s props**, beyond whatever minimal internal change the shared-band extraction below needs. `title`/`backTo`/`backLabel`/`actions`/`children` (`RecordFormScreen`) and `title`/`backTo`/`backLabel`/`action` (`ManageScreenHeader`) keep their exact current shape and call-site values — this is styling-only, not a data or behavior change.
- **No change to content below either header.** `RecordFormScreen`'s field grid and actions bar, and whatever the consuming page renders below `ManageScreenHeader` (a tab row, `ListToolbar` + record grid, `ClubStructure`'s tree, `AvailabilityPollsDashboard`'s poll list) are unchanged — only the back-link+title (+ `action`, for `ManageScreenHeader`) zone gets the band. Explicitly re-stating `044`'s own boundary: the Club Profile screenshot's tab row (Contact/Address/Branding/Social Media) is rendered by `ManageClubProfilePage.tsx` itself, inside `RecordFormScreen`'s `children`, not by `RecordFormScreen` — it stays on the plain wash, unchanged, exactly as it renders today.
- **No change to `RecordCard`'s own header, `RecordDetailScreen`'s external props/call sites, or `RecordDetailScreen`'s own rendered output.** `044`'s already-shipped gradient band is reused, not touched — this spec's only permitted change to `RecordDetailScreen.tsx` is the internal refactor described in UI Requirements (extracting its band markup into a shared piece both this spec's components also use), which must not alter anything `044`'s own Test Plan/Acceptance Criteria already assert.
- **No change to `AppShell`'s or `GridNavShell`'s persistent nav/sidebar chrome.** Same boundary `044` drew — only each page's own back-link+title zone changes, never the shell wrapping it.
- **No backend change.** No entity, migration, or endpoint is added or touched — purely a frontend, presentational-layer change to two existing shared components (plus the shared-band extraction).
- **No new theme.ts contrast logic.** `detailHeaderGradient`/`detailHeaderShadow` are reused exactly as `044` built them — this spec introduces no new gradient recipe, no new clamp, no new hardcoded colour.
- **No resolution of `SponsorContactList.tsx`'s own hand-rolled back button** (confirmed by grep to use neither `RecordFormScreen` nor `ManageScreenHeader` — it rolls its own, a pre-existing `design-system.md` rule violation noted in its own code comment). Out of scope here; not this spec's gap to fix.
- **`/admin`'s scope was a named, flagged decision, not something this spec decided silently** — see the Resolved Scope Question above (confirmed: applies everywhere). It applies to all four `/admin` `RecordFormScreen` call sites uniformly, not a per-screen carve-out.

## User Stories

- As a club admin moving between a Club Profile edit screen (`RecordFormScreen`) and a Player detail screen (`RecordDetailScreen`), both render the same brand-gradient header band — no visible "two design systems" seam between view and edit/create screens.
- As a club admin on any bare `/manage` list or tree screen (Contacts, Sponsors, Structure, Players, Teams, Leagues, Seasons, Matches, Availability Polls, Fixtures Home), the header renders the same gradient band as every detail and form screen, including its "Add X" action rendered legibly against the gradient.
- As a club admin at a club with its own brand colour, both headers re-tint automatically via `withClubBranding()`, the same way `RecordDetailScreen`'s already does — no separate colour logic to keep in sync.
- As a developer maintaining any of the three header-bearing components, the full-bleed band's markup and colour derivation live in one shared place, not copy-pasted three times with the risk of silently drifting apart.
- As a platform operator using `/admin` screens (Club, Product, Subscription, Email Settings forms), the same consistent header treatment applies there too, rendered in the platform's own default palette since `/admin` never calls `withClubBranding()`.

## Data Model Changes

None. Purely a frontend, presentational-layer change to existing shared components. No entity, field, migration, or endpoint is added or touched.

## API Contract

None. No endpoint is added, removed, or changed.

## UI Requirements

**Blast radius, stated explicitly:** this spec changes `ui/src/components/RecordFormScreen/RecordFormScreen.tsx` and `ui/src/components/ManageScreenHeader/ManageScreenHeader.tsx`, plus the shared-band extraction (new component, and a matching internal refactor of `ui/src/components/RecordDetailScreen/RecordDetailScreen.tsx` to consume it — see item 3). No `theme.ts` change — `detailHeaderGradient`/`detailHeaderShadow` are reused exactly as `044` shipped them. Every screen composing `RecordFormScreen` (13 call sites: 9 `/manage`, 4 `/admin` — see Open Question) or `ManageScreenHeader` (11 call sites, `/manage`-only) inherits the new header automatically; none of those page files is edited by this spec.

**1. `RecordFormScreen.tsx`'s header zone becomes the same full-bleed band `RecordDetailScreen` uses.** Today the back-link `MuiButton` + title `Typography` sit in a plain `Box` directly on the page body's wash. This becomes the identical band: same negative-margin bleed (`mx`/`mt` of `{ xs: -2, md: -3 }` cancelling the shared `p: { xs: 2, md: 3 }` `<main>` padding both `AppShell` and `GridNavShell` apply — `044`'s own confirmed, flagged coupling, unchanged here), same `detailHeaderGradient(theme)` background and `detailHeaderShadow(theme)` shadow, same square-top/rounded-bottom corners (`theme.shape.borderRadius × 2`). Colour treatment inside the band:
   - Back-link text/icon: `alpha(theme.palette.common.white, 0.85)` (replacing `text.secondary`).
   - Title: `theme.palette.common.white` (replacing the default `text.primary`).
   - No avatar, badge, or secondaryActions/Edit row to restyle — `RecordFormScreen` has none of those slots (per its own props above), so this is a strict subset of `044`'s own header restyle, introducing zero new colour decisions.
   - The field grid and actions bar below the band are unchanged, still on the page's existing `pageBackgroundGradient()` wash — restated explicitly per `044`'s own precedent of calling this out rather than assuming it's obvious.

**2. `ManageScreenHeader.tsx`'s header zone gets the same band treatment, plus its `action` slot restyled.** Same negative-margin bleed/background/shadow/corner treatment as item 1. Colour treatment:
   - Back-link text/icon: `alpha(theme.palette.common.white, 0.85)`.
   - Title: `theme.palette.common.white`, `fontWeight={600}` unchanged.
   - **`action` (the page-level "Add X" button): filled-white, not outlined-white.** Decision, stated explicitly with reasoning: `044` established two dark-banner button treatments — outlined-white for `secondaryActions` (multiple, co-equal actions sitting beside a primary Edit) and filled-white for the single Edit button itself ("the one visually loudest element in the band, consistent with it being the screen's one mutating affordance"). `ManageScreenHeader.action` is structurally the second case, not the first: it is always a single, primary "create" action (`ListToolbar`'s own deprecated `createLabel`/`onCreate` moved here specifically to be *the* primary action, per `041`), with no co-equal sibling action rendered alongside it in the header. It gets the same `bgcolor: common.white` / `color: primary.dark` treatment `RecordDetailScreen`'s Edit button uses, not the outlined treatment. Passed through unchanged when `action` is omitted (every title-only call site, e.g. `AvailabilityPollsDashboard`) — this only affects the visual container the caller's own `Button` renders inside; per the component's existing contract, `action` accepts any `ReactNode`, so the caller's `Button` (typically MUI's default filled `variant="contained"`, per every current `WithAction`-shaped call site) already renders filled — this item's decision is about *if* `ManageScreenHeader` needs to override or constrain that (it doesn't: a filled `Button` already sitting on the gradient reads correctly with no additional styling, since MUI's own `contained` primary button already renders `primary.main`-on-white-text by default, which itself needs no on-dark-banner variant since it isn't part of the band's white/text-on-gradient treatment — it's its own solid, self-contained surface). Restated for clarity: no `ManageScreenHeader`-level `sx` override is applied to `action`'s contents; the "filled, not outlined" decision above documents why nothing further needs to change here, not a new internal style rule to build.
   - Content below `ManageScreenHeader` (the `ListToolbar` + record grid/`EmptyState`, `ClubStructure`'s tree, `AvailabilityPollsDashboard`'s poll list, `ManageFixturesHome`'s cards) is unchanged, still on the page's `pageBackgroundGradient()` wash.

**3. Shared-band extraction, required per `docs/standards/frontend.md`'s >70%-duplication rule.** After items 1–2, three components (`RecordDetailScreen`, `RecordFormScreen`, `ManageScreenHeader`) each render a `Box` with the identical full-bleed band `sx` shape (negative-margin bleed values, `detailHeaderGradient`/`detailHeaderShadow` background/shadow, corner radii) — well past the 70% threshold the standard names as "extract immediately," not "in a follow-up." Extract a small, additive shared component — `ui/src/components/HeaderGradientBand/HeaderGradientBand.tsx` (new component folder, full four-file anatomy: `.tsx`/`.test.tsx`/`.stories.tsx`/`index.ts`, per `docs/standards/frontend.md`'s component anatomy rule) — wrapping `children` in the band `Box` and exposing nothing else configurable (no props beyond `children`; the band's bleed/colour/shape values are fixed by definition, not per-caller variance). All three components render their existing header content (avatar/title/badge/actions for `RecordDetailScreen`; back-link/title for `RecordFormScreen`; back-link/title/action for `ManageScreenHeader`) as `HeaderGradientBand`'s `children`, in place of each one's own literal band `Box`.
   - This requires a small, behavior-preserving internal refactor of `RecordDetailScreen.tsx` (swapping its existing literal band `Box` for `<HeaderGradientBand>`) — permitted explicitly by this spec (see Non-goals) precisely because it changes no prop, no rendered markup shape, and no colour, only where the `sx` values are defined; `044`'s own component test/Acceptance Criteria assertions (back-link href, title, sections order, Edit href, secondaryActions ordering, the contrast assertions) must all still pass unmodified against the refactored component — this is the acceptance bar for "behavior-preserving," not a new assertion this spec has to write.
   - Considered and rejected: leaving three separate literal `sx` blocks. Three real call sites sharing this exact shape is the concrete trigger the standard names, and a fourth full-page header (a plausible next screen family) would make a fourth copy-paste an even harder case to justify not having extracted already.

**Mobile-first:** verified at 375/768/1280, same viewport convention `044` and both components' existing Storybook stories already use — no new breakpoint logic invented; the extracted `HeaderGradientBand`'s bleed values are the exact `{ xs, md }` shape already proven at `044`.

## Acceptance Criteria

- Every `RecordFormScreen` call site (9 `/manage`, plus `/admin`'s 4, per the confirmed Resolved Scope Question above) and every `ManageScreenHeader` call site (11, all `/manage`) renders the new gradient-band header automatically, with zero edits to any page-level `*FormPage.tsx`/`*List.tsx`/`ClubStructure.tsx`/`AvailabilityPollsDashboard.tsx`/`ManageFixturesHome.tsx` file.
- No literal brand hex string appears anywhere in `RecordFormScreen.tsx`, `ManageScreenHeader.tsx`, or the new `HeaderGradientBand.tsx` — every band colour traces to `theme.palette.primary.*`/`common.white`, computed at render time via the reused `044` helpers.
- `ManageScreenHeader`'s `action` button, when present, renders filled-white/`primary.dark` text against the gradient, legible under both the default theme and a synthetic light `withClubBranding()` colour.
- Content below each header (field grid + actions bar for `RecordFormScreen`; whatever the consuming page renders for `ManageScreenHeader`) is visually unchanged — still on the existing `pageBackgroundGradient()` wash.
- `RecordDetailScreen`'s own rendered output and every one of `044`'s existing component-test/Acceptance-Criteria assertions still pass unmodified after the `HeaderGradientBand` extraction.
- `RecordDetailScreen`, `RecordFormScreen`, and `ManageScreenHeader` share one definition of the full-bleed band's `sx` (via `HeaderGradientBand`), not three independently-maintained copies.
- The `/admin` scope question was explicitly confirmed (apply everywhere) rather than silently resolved by whichever way the build happened to go — see the Resolved Scope Question above.
- No backend file, endpoint, entity, or migration is touched.
