# 019 — Resend Subscription Welcome Email

**Depends on:** `017-subscription-welcome-email.md` (`SubscriptionWelcomeEmailService.sendWelcomeEmail(Person, Subscription, Club, Product)`, `EmailService`/`EmailDeliveryException`, currently implemented, tested, and CI-green on `feature/017-subscription-welcome-email`, not yet merged to `master` — treated as a firm dependency; its own Non-goals explicitly named "an admin-facing 'resend welcome email' action" as unbuilt and deferred — this spec is that follow-up), `009-subscriptions.md` (`Subscription`/`SubscriptionStatus` shape, `SubscriptionServiceImpl`'s existing `findClubOrThrow`/`findProductOrThrow`/`findPersonOrThrow`/`findOrThrow` private helpers this spec reuses rather than re-deriving), `014-subscription-responsible-contact.md` (the responsible `Person` this email is always addressed to), `018-email-configuration-and-test-send.md` (sibling in-flight work establishing the precedent this spec follows for an explicit, admin-triggered email action: a failed send is real, visible response data, not caught-logged-swallowed — see Real Architectural Judgment Calls #1), `docs/standards/backend.md` (the fixed three-exception status table, and `InvalidStatusTransitionException`'s existing, reused-not-reinvented shape), `docs/standards/frontend.md`/`docs/standards/design-system.md` (the Record list pattern `RecordCard` this spec extends, per this repo's mandatory list/CRUD convention).
**Status:** draft.

## Problem & Goals

`017` sends a Subscription's responsible `Person` a one-time welcome email at creation, and its own Non-goals named the exact gap left behind: no way for a platform admin to trigger that email again if it never arrived, landed in spam, or the admin simply wants to hand it to the responsible person a second time in a support conversation. Today the only way to get that content re-sent is a direct database/SMTP-log investigation, or recreating the Subscription itself — neither is a reasonable admin action. This spec adds a single "Resend welcome email" action to the existing Subscription card, calling `017`'s already-built `SubscriptionWelcomeEmailService` directly.

**Goals**
- A platform admin can trigger a resend of a Subscription's welcome email directly from `SubscriptionList.tsx`'s existing per-row card, with no navigation away from the list.
- The resend uses the Subscription's *current* state (its current Product, current dates, current responsible Person) — not a replay of whatever the content happened to be at original creation time.
- Unlike `017`'s own automatic send, a failed resend is real, visible data returned to the admin who triggered it — never caught, logged, and silently swallowed.
- Resend is only offered, and only permitted server-side, for a Subscription that is currently `ACTIVE` — see Real Architectural Judgment Calls #2.

## Non-goals

- **Resending for a `CANCELLED` Subscription.** Rejected outright, both in the UI (the action isn't rendered) and server-side (`InvalidStatusTransitionException`, 409). See Real Architectural Judgment Calls #2 for the reasoning.
- **Persisting a resend history, "last resent at" timestamp, or delivery-status tracking of any kind.** `017`'s own Non-goals already named this as a distinct, unresolved gap ("send history, or delivery-status tracking. No screen, no table, no endpoint"); this spec resolves the *action* half of that Non-goal, not the *history* half — that stays unbuilt, flagged again in Rollout Notes.
- **A free-text "send to" override.** The email always goes to the Subscription's own `responsiblePerson.email`, exactly as `017`'s original send does — never an admin-supplied address. Mirrors `018`'s own judgment call #2 (its test-send is always the caller's own JWT email, never a request-body destination) for the identical reason: broadening this into "send an email to anyone" would be a real misuse surface with no corresponding benefit.
- **Rate limiting or a cooldown between resends.** Considered and rejected for this pass — see Real Architectural Judgment Calls #4.
- **Any change to `017`'s own automatic, best-effort welcome-email send on Subscription creation.** That posture (caught, logged, swallowed, never fails the request) is untouched — this spec adds a second, differently-postured caller of the same `SubscriptionWelcomeEmailService.sendWelcomeEmail(...)` method, it does not change the method or its existing caller.
- **A distinct "this is a resend, not your original welcome email" banner or copy variant in the email itself.** `email/subscription-welcome.html` (`017`) is reused completely unmodified — its content already just describes the Subscription's current club/product/dates, which is exactly as accurate on a fifth send as a first. No new template, no new Thymeleaf variable.
- **Editing the Subscription, its Product, or its dates from this action.** Resend is read-only against the Subscription's existing state — it triggers a send, nothing else. `SubscriptionFormPage.tsx`'s existing edit flow is untouched.
- **Bulk resend across multiple Subscriptions at once.** One action, one card, one Subscription at a time — no multi-select, no "resend to all" toolbar action on `ListToolbar`.
- **Any change to `SubscriptionOwnerType`/`SECTION`-owned Subscriptions.** `009`'s existing `CLUB`-only constraint is untouched; this action is reachable for exactly the same set of Subscriptions the list already shows.
- **`018`'s own email-settings/test-send screen.** No shared code, no shared endpoint — `018`'s `EmailTestSendService` sends a generic diagnostic email to the caller's own address; this spec's action sends `017`'s real welcome-email content to the Subscription's responsible person. Related in posture (see Real Architectural Judgment Calls #1), not in implementation.

## User Stories

- As a platform admin, I can click "Resend welcome email" on an `ACTIVE` Subscription's card in `SubscriptionList.tsx` and know immediately, without leaving the page, whether it actually sent.
- As a platform admin, if a resend fails (e.g. the SMTP server is down), I see a specific, readable reason on the card itself, so I know to try again later or investigate rather than assuming it silently worked.
- As a platform admin, I cannot resend a welcome email for a `CANCELLED` Subscription — the action isn't offered on that card at all, since there's no active entitlement left to welcome anyone to.
- As a developer reading `SubscriptionServiceImpl`, I can see clearly that this action's failure posture is the deliberate opposite of `sendWelcomeEmailBestEffort`'s (`017`) catch-log-swallow behaviour, because this one is an explicit, admin-triggered diagnostic-adjacent action rather than a side effect of an unrelated business action.
- As anyone without the `platform_admin` role, I cannot trigger a resend — the new endpoint sits under the existing `/api/v1/platform/**` gate, unchanged.

## Real Architectural Judgment Calls

Resolved explicitly here, not silently assumed — a reviewer should be able to challenge each one on its own terms.

**1. A failed resend is returned as `{success: false, message, sentTo}` inside a normal `200 OK`, not thrown to `GlobalExceptionHandler` — the same shape `018` already established for its own admin-triggered test-send, not `017`'s catch-log-swallow posture.**
Three options existed. First: let `EmailDeliveryException` (`017`) propagate uncaught — rejected for the same reason `018`'s own judgment call #3 already rejected it: `GlobalExceptionHandler` has no handler for it by design (its Javadoc states it is "always caught at the call site... never reaches `GlobalExceptionHandler`"), so an uncaught propagation would fall through to an undocumented generic 500 carrying none of the real failure reason. Second: extend `docs/standards/backend.md`'s fixed three-exception status table with a new base type mapping to a `5xx`. Rejected for the identical reason `018` rejected it — that table is a cross-cutting contract shared by every controller, and a single action's send outcome is legitimately just response data, not a transport-level error. Third, the one adopted: catch `EmailDeliveryException` at the point this spec's own new service method calls `sendWelcomeEmail(...)`, and always return a result DTO — mirroring `018`'s `EmailTestSendResultDto` shape exactly (`success`, `message`, and here `sentTo` is always the responsible person's own email, useful confirmation on a card with no other visible "who does this go to" field). This is the deliberate contrast named in the Problem & Goals section: `017`'s own automatic send on creation stays best-effort because it's a side effect of an unrelated action (creating the Subscription) that shouldn't inherit its success from SMTP's uptime; this action's *entire purpose* is sending an email on request, so its outcome belongs in the response, exactly as `018` already decided for its own comparable action.

**2. Resend is permitted only for a Subscription whose `status` is `ACTIVE` — a `CANCELLED` Subscription cannot be resent, in the UI or the API.**
A welcome email's content (`017`) describes an active entitlement: which club, which product, which dates, and a working login link. Resending it for a `CANCELLED` Subscription would hand the responsible person a message that reads as current when the entitlement it describes no longer exists — actively misleading, not merely unnecessary. `SubscriptionStatus` (`009`) has exactly two values, `ACTIVE`/`CANCELLED`, no `EXPIRED`/`PAST_DUE` to reason about here — the check is a single equality test. Server-side, this reuses `docs/standards/backend.md`'s existing, already-in-use `InvalidStatusTransitionException extends ConflictException` (409) rather than introducing a new exception type: `SubscriptionServiceImpl.update()` already throws this exact exception for "Cannot update a cancelled subscription," a materially identical shape ("this action isn't valid against a Subscription in its current status") even though resend isn't itself a state transition — the existing exception's name and its 409 semantics fit this case as well as they fit `update()`'s, and `docs/standards/backend.md`'s own guidance is to prefer a specific, already-named exception over inventing a new one. Client-side, `SubscriptionList.tsx` simply doesn't render the resend action on a `CANCELLED` card at all (mirroring how `SubscriptionFormPage.tsx` already hides its own "Cancel Subscription" action once a Subscription is already `CANCELLED`) — the 409 path exists as defence-in-depth against a stale card or a direct API call, not as the primary UX guard.

**3. Lives on the existing `SubscriptionService`/`SubscriptionServiceImpl`, not a new dedicated service.**
`018` introduced new, dedicated `EmailSettingsService`/`EmailTestSendService` classes because no existing service had any reason to know about email configuration. This case is different: resolving a Subscription's current `Club`/`Product`/responsible `Person` from its id is exactly what `SubscriptionServiceImpl` already does in `get()`, `update()`, and `cancel()`, via its own private `findClubOrThrow`/`findProductOrThrow`/`findPersonOrThrow`/`findOrThrow` helpers. A new, second service would either duplicate those four lookups or take `SubscriptionServiceImpl` as a collaborator just to reach them — both worse than adding one method to the service that already owns this entity and already depends on `SubscriptionWelcomeEmailService` (`017`) for its own, differently-postured automatic send. Per `CLAUDE.md`'s "reuse before you write," the new method lives in `SubscriptionService`/`SubscriptionServiceImpl` alongside `create`/`get`/`list`/`update`/`cancel`.

**4. No rate limiting or cooldown between resends.**
Considered and rejected for this pass. `POST /api/v1/platform/subscriptions/{id}/resend-welcome-email` sits behind the same `platform_admin`-only gate every other `/api/v1/platform/**` endpoint already does — an internal, trusted, low-volume actor, not a public or self-serve surface a hostile party could reach. The realistic failure mode of no guard is an admin double-clicking the button or retrying after a genuine failure, both of which are exactly the intended use of the feature, not abuse of it. A cooldown would only get in the way of the legitimate "it didn't arrive, try again" case this spec exists to serve, for a threat model (a rogue platform admin spamming a responsible person's inbox) that isn't this pass's concern and isn't guarded against anywhere else in this codebase's existing `platform_admin` surface either. Flagged in Rollout Notes as a real, deliberate call to revisit only if actual abuse is ever observed — not a forgotten gap.

## Data Model Changes

**None.** No new entity, no new column, no migration. This spec reads `Subscription`/`Club`/`Product`/`Person` exactly as `SubscriptionServiceImpl` already resolves them for `get()`, and calls `SubscriptionWelcomeEmailService.sendWelcomeEmail(...)` (`017`) exactly as `create()`'s own `sendWelcomeEmailBestEffort` already does — nothing about this spec requires a schema change.

## API Contract

| Endpoint | Access | Purpose |
|---|---|---|
| `POST /api/v1/platform/subscriptions/{id}/resend-welcome-email` | `platform_admin` | Resends `017`'s welcome email to the Subscription's current `responsiblePerson`, using the Subscription's current `Club`/`Product`/dates. Only valid for a Subscription whose `status` is `ACTIVE` — a `CANCELLED` Subscription throws `InvalidStatusTransitionException` (409). Always returns `200` with a `ResendWelcomeEmailResultDto` (`success: boolean`, `message: string`, `sentTo: string`) — a downstream `EmailDeliveryException` is caught and reported as `success: false` with a specific `message`, never a `5xx`. No request body. |

No other endpoint changes. `GET`/`POST`/`PUT`/`cancel` (`009`, amended by `014`/`016`/`017`) are all untouched. Falls under the existing `/api/v1/platform/**` block already gated `hasRole("platform_admin")` in `SecurityConfig` — confirmed by reading the existing rule; no `SecurityConfig` change needed.

## UI Requirements

Extends the existing Subscription card in `ui/src/pages/admin/SubscriptionList.tsx`, reusing `RecordCard` (`docs/standards/design-system.md`'s mandatory list/CRUD pattern) rather than a bespoke row layout.

- **`ui/src/components/RecordCard/RecordCard.tsx` (extended)** — gains two new, optional, generic props (backward-compatible; `ProductList.tsx`'s existing usage is unaffected since neither is passed there):
  - `secondaryAction?: { label: string; pendingLabel: string; onClick: () => void; pending: boolean }` — rendered in the existing `CardActions` footer row, to the left of the Edit action, as a `Button` (`variant="ghost"`, `size="sm"`, matching the styling already used for the non-router-link Edit case) — one more footer action alongside Edit, not a new menu/kebab interaction shape. Disabled and showing `pendingLabel` while `pending` is true.
  - `feedback?: { message: string; tone: 'success' | 'error' } | null` — an inline `Typography` row (`color: 'success.main' | 'error.main'`, `variant: 'body2'`) rendered inside `CardContent`, below the existing fields/chips slots and above the `CardActions` footer, shown only when non-null. This is the same "coloured `Typography` for the outcome" pattern `018` already establishes for its own test-send button (`EmailSettings.tsx`) rather than introducing a new Alert/Snackbar component — confirmed by grep that no toast/snackbar component exists anywhere in `ui/src` today.
  - Both props are generic (not Subscription-specific) — a future card needing a second footer action with inline pending/outcome feedback reuses them rather than this spec inventing a Subscription-only variant of `RecordCard`.
  - `RecordCard.test.tsx`/`RecordCard.stories.tsx` (existing, per the four-file anatomy) gain coverage for the new props: `secondaryAction` renders and calls `onClick`; `pending` swaps the label and disables the button; `feedback` renders in the correct colour for each tone; both remain absent (no regression) when omitted, covering `ProductList`'s unchanged usage.

- **`ui/src/api/subscriptionApi.ts` (extended)** — one new function and one new type, following the file's existing shape:

  ```ts
  export interface ResendWelcomeEmailResult {
    success: boolean
    message: string
    sentTo: string
  }

  export async function resendWelcomeEmail(id: string): Promise<ResendWelcomeEmailResult> {
    const { data } = await api.post<ResendWelcomeEmailResult>(
      `/platform/subscriptions/${id}/resend-welcome-email`,
    )
    return data
  }
  ```

- **`ui/src/pages/admin/SubscriptionList.tsx` (extended)** — each card gains its own `useMutation` (React Query, per `docs/standards/frontend.md`) calling `resendWelcomeEmail(subscription.id)`, keyed per-card via a local `Record<string, { success: boolean; message: string } | null>` state (or equivalent) so one card's pending/outcome state never leaks onto another's. `secondaryAction` is only passed to `RecordCard` when `subscription.status === 'ACTIVE'` — omitted entirely for a `CANCELLED` Subscription's card, matching Real Architectural Judgment Calls #2's UI-side guard. Label: `"Resend welcome email"`; pending label: `"Sending…"` (matching `EmailSettings.tsx`'s `018` precedent verbatim). On success, `feedback` shows the returned `message` (e.g. `"Welcome email resent to jaco@example.com."`) in `success.main`; on a `success: false` result or a network-level error, `feedback` shows the returned/fallback message in `error.main`. No React Query invalidation of the `['subscriptions', ...]` list query is needed — a resend changes no Subscription field, so the list's own data is already correct.
- **Mobile-first**, per `docs/standards/frontend.md` — the two footer actions (Resend, Edit) wrap onto their own line at `xs` the same way `RecordCard`'s existing `CardActions` row already would with two items; the new feedback `Typography` sits full-width above them at every breakpoint, no new responsive behaviour to design.

## Acceptance Criteria

- A platform admin can trigger a resend of a Subscription's welcome email from its card in `SubscriptionList.tsx`, with no page navigation.
- The resent email's content (club, product, dates, login link) reflects the Subscription's current state at the moment of resend, not a cached copy of its original creation-time content.
- Triggering a resend on a `CANCELLED` Subscription is impossible from the UI (no action rendered) and rejected with a `409` if attempted directly against the API.
- A successful resend shows a specific success message naming the address it was sent to, inline on the card, without a page reload.
- A failed resend (a forced `EmailDeliveryException` in a test) shows a specific, readable error message inline on the card — verifiable by a test asserting on the `200` response's `success: false` body, and by a component test asserting the rendered `error.main`-coloured message.
- `POST /api/v1/platform/subscriptions/{id}/resend-welcome-email` is reachable only by `platform_admin` — verified against the existing, unchanged `/api/v1/platform/**` `SecurityConfig` rule.
- No new database migration, Maven dependency, or Spring config property is introduced by this spec.
- `RecordCard`'s two new props are optional and backward-compatible — `ProductList.tsx`'s existing usage renders unchanged, verified by its existing test suite passing without modification.

## Rollout Notes

- Depends on `017`'s `SubscriptionWelcomeEmailService`/`EmailService`/`EmailDeliveryException` already existing in the codebase (currently implemented, tested, and CI-green on `feature/017-subscription-welcome-email`, not yet merged to `master`) — this spec's own PR should be sequenced after `017` merges, or rebased onto it, since `SubscriptionServiceImpl.resendWelcomeEmail(...)` calls `SubscriptionWelcomeEmailService` directly.
- **Resolves `017`'s own named gap, in part.** `017`'s Non-goals explicitly listed "An admin-facing 'resend welcome email' action, send history, or delivery-status tracking. No screen, no table, no endpoint. If this becomes a real operational need, it's its own follow-up." This spec is that follow-up for the *action* itself — the button, the endpoint, the visible outcome. It deliberately does **not** resolve the "send history" or "delivery-status tracking" half of that same sentence — no persisted record of who resent what, when, or whether it succeeded, beyond whatever application-level logging (`013`) already captures incidentally. If that turns out to be a real, separate operational need, it's still its own follow-up, not solved here.
- `docs/roadmap.md`'s "Next up — notifications / email infrastructure" section should gain a line noting this spec closes `017`'s own named "resend" gap, while leaving the "send history/delivery-status tracking" portion of that same gap still open — the same "resolve part, flag the rest explicitly" pattern `017` itself already used when it resolved only the first of the section's two named use cases.
- No audit trail exists for who triggered a resend or when, beyond incidental application logging (`013`) — same accepted, named gap as `018`'s own "no audit trail for who triggered a test send" Rollout Note. Worth a joint follow-up ("admin-action audit log," covering this, `018`'s test-send, and any future comparable action) only if this turns out to be a real, recurring need — not solved here.
- No rate limiting/cooldown is added (Real Architectural Judgment Calls #4) — flagged for revisit only if actual misuse is ever observed against this or any other `platform_admin`-only action; not expected, not guarded against elsewhere in this codebase's existing admin surface either.
