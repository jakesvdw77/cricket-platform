# 037 — Match Improvements

**Depends on:** `029-league-management.md` (`Match`/`MatchSide`/`MatchSidePlayer`, `MatchController`/`MatchSideController`, `PlayingXiBuilder`, `MatchList`/`MatchFormPage`/`SquadPicker` — every screen and endpoint this spec touches was built there; this spec amends none of `029`'s business rules, only its UI/UX and one payload-construction bug), `033-availability-aware-xi-builder.md` (`PlayingXiBuilder`'s `availabilityByPlayerId` prop and tinted-row convention, unchanged and preserved by this spec's reordering/stepper changes), `028-players.md` (`PlayerForm`/`PLAYER_FORM_ID`/`createPlayer`, reused verbatim for item 8's quick-add flow), `036-view-first-record-detail-screens.md` (`MatchList`'s `viewTo`-by-default card, `MatchDetailPage`/`RecordDetailScreen`, both extended here with a second header action), `027-team-profile.md` (`CreateAndLinkRecordDialog`/`LinkExistingRecordDialog`, reused unmodified for item 8, and reused again — in its other, no-`extraField` mode — for item 9's previous-match picker), `008-product-catalog.md` (`ListToolbar`, the shared filters-bar component this spec's items 3/4 touch), `001-tenancy-identity-model.md` (confirms `Team`, `Season`, and `League` carry no direct association to one another in the entity model — only `Match.season_id`/`Match.league_id` and the separate `LeagueAffiliation` join do — the basis for item 9's previous-match query filtering directly against `Match`'s own columns, not via `LeagueAffiliation`).
**Status:** draft.

## Problem & Goals

`029` shipped Match scheduling and playing-XI selection; `033` layered availability indicators on top. Since then, real click-through use of `/manage/fixtures/matches` and its "Squads" shortcut (`SquadPicker.tsx`) has surfaced nine concrete, independent problems — a mix of missing conveniences, a visual bug, one real state-corruption bug, and one repeat-lineup convenience — none of which need a new entity or a redesign of the entities `029` already built. This spec rolls all nine into one pass because they touch the same three screens (`MatchList.tsx`, `MatchFormPage.tsx`/`PlayingXiBuilder.tsx`, `MatchDetailPage.tsx`) and shipping them piecemeal would mean re-touching the same files repeatedly for unrelated reasons. Item 9 (re-selecting a side's XI from a previous match) surfaced during the same click-through session as items 5–8 and lands on the exact same `PlayingXiBuilder.tsx`/`MatchSideTab` surface those items already touch — folding it in here, while this spec is still unbuilt/draft, avoids opening a second spec/PR that would just re-touch those same two files for another, related reason days later.

**A grounding note on where the actual "team selection" UI lives, since the initial framing of this work referred to it as `SquadPicker.tsx`:** `SquadPicker.tsx` (`029`'s "Squads" dashboard destination) is, as built, a thin wrapper around `MatchList` that changes only the card's primary link target (`?tab=playing-xi` instead of Details) — it renders no form fields of its own. The actual "Add player" row and Captain/Wicketkeeper/Twelfth Man dropdowns described by this spec's source screenshot live in `ui/src/components/PlayingXiBuilder/PlayingXiBuilder.tsx`, rendered inside `MatchFormPage.tsx`'s Home XI/Away XI tabs (via `MatchSideTab`) — reached either through `SquadPicker`'s shortcut or through a match's own Edit action. Items 5, 6, 8, and 9 below are grounded against `PlayingXiBuilder.tsx`/`MatchSideTab`, not a literal edit to `SquadPicker.tsx`'s own (nearly empty) file — flagged explicitly here so this isn't read as a mismatch between the spec and the code once build starts.

**Goals**
- The Matches list defaults to showing only upcoming matches, so a club admin isn't scrolling past a growing pile of past fixtures to find next week's game.
- A club admin can jump straight into a match's team-selection screen from a `RecordCard` or its detail view, without detouring through the separate "Squads" nav entry or manually clicking into Edit and hunting for the right tab.
- The Matches list's filters bar reads as a single, organized control group consistent with the rest of `/manage`, and its Sort-by control never visually clips its own label/value.
- Selecting a Captain, Wicketkeeper, or Twelfth Man no longer silently clears whichever of the other two was already set — a real, reproducible data-loss bug, not a cosmetic one.
- The Captain/Wicketkeeper/Twelfth Man block appears above the Playing XI list on load, since it's a small, fixed-size control group that shouldn't push the (potentially long) batting order down the page.
- Reordering the batting order supports typing/stepping directly to a target position, not only single-step up/down nudges.
- A club admin can add a brand-new player straight into a match's team squad without leaving the match screen, reusing `028`'s existing player-creation form rather than a second, bespoke "quick add" form.
- A club admin building a side's playing XI can pick one of that team's own previous matches — scoped to the identical Season and League as the match they're currently editing — and re-select that side's entire XI (batting order, roles, captain, wicketkeeper, twelfth man) from it in one action, rather than rebuilding a repeat lineup from scratch every time.

## Non-goals

- **Any change to `029`'s `MatchSide`/`MatchSidePlayer` business rules** — squad-membership, age-eligibility, and XI-cap validation are unchanged. Every fix in this spec is UI/UX or a payload-construction correction against the existing, unmodified backend contract. Item 9's copy action is a convenience wrapper around calls to these same, unmodified endpoints — it produces either a fully valid state or a state the admin still needs to finish manually (see item 9's own write-up), never a state that bypasses a rule a manually-built XI would have been held to.
- **A user-facing "Show past matches" toggle.** Item 1 changes the Matches list's *default* filter state, not a hard, un-reversible exclusion — the backend and frontend are both shaped so a future toggle is just flipping one existing boolean (see API Contract/UI Requirements), but building that toggle control itself is explicitly deferred. Flagged as an open item for `docs/roadmap.md` once this ships (see Rollout Notes).
- **Drag-and-drop batting-order reordering.** No drag-and-drop library (`dnd-kit`, `react-beautiful-dnd`, or similar) exists in `ui/package.json` today — confirmed by inspection, not assumed. Adding one would be a new approved-dependency decision on the scale of `@mui/x-tree-view`/`jspdf` (`CLAUDE.md`'s tech stack table), not something this spec's scope justifies. Item 7 ships as a click-to-edit numeric stepper only; drag-and-drop stays a real, named future option.
- **Redesigning `TeamDirectory.tsx`'s identical section-filter layout.** `TeamDirectory.tsx` places its `SectionTreeSelect` filter in the exact same `Box sx={{ maxWidth: 360 }}` below `ListToolbar` that `MatchList.tsx` does — the same shared pattern, not a Match-specific mistake. This spec's items 3/4 touch `MatchList.tsx`'s filters bar only; `TeamDirectory.tsx` is unchanged, so the two don't silently diverge into two different filter-bar shapes without a deliberate decision to do so.
- **Changing `PUT .../sides/{sideId}`'s backend contract.** Its Javadoc-documented "full replace, not a merge" semantics (`UpdateMatchSideRequest`) are intentional and stay exactly as `029` built them — item 5's fix is entirely a frontend payload-construction correction at the one call site that was building an incomplete payload against that contract, not a backend change (see Data Model Changes/API Contract and item 5's own write-up below). Item 9 reuses this same endpoint, and the same always-send-all-three-fields discipline item 5 established, for its own captain/wicketkeeper/twelfth-man copy step — see item 9's write-up.
- **Removing the existing up/down `IconButton` reorder controls.** Item 7 augments `PlayingXiBuilder`'s ordered-list row with a click-to-edit stepper on the batting-order number itself; the existing single-step up/down buttons stay, unchanged, as a quicker path for an adjacent-position nudge.
- **Any change to `033`'s availability-indicator tinting/captions.** Reordering the Captain/Wicketkeeper/Twelfth Man block (item 6) and reworking the batting-order number (item 7) touch layout and interaction only — the `UNAVAILABLE`/`UNSURE` tint/caption logic and its data source (`availabilityByPlayerId`) are unmodified.
- **A bespoke "quick add player" form.** Item 8 reuses `028`'s existing `PlayerForm`/`PLAYER_FORM_ID` and `027`'s existing `CreateAndLinkRecordDialog` verbatim — no new form component, no new dialog component.
- **Cross-season or cross-league copying.** Item 9's previous-match picker is scoped to an *exact* match on Season and League against the match currently being edited — including "no League" matching only another League-less match in the same Season, never a broader "any of this team's past matches" list. A future spec can widen this if a real need for it shows up; not built here.
- **A single action that copies both sides of a match at once.** Item 9 is invoked from, and only ever affects, one side's own Playing XI tab (matching `PlayingXiBuilder`'s own strictly-per-side scope) — re-selecting the Home side's XI from a previous match never touches the Away side, even when both sides exist on the same match.
- **Any "copied from match X" lineage or audit trail.** `MatchSide`/`MatchSidePlayer` gain no new field recording where a copied XI came from — once item 9's copy completes, a copied side is indistinguishable in the data model from one built manually, matching this spec's own Data Model Changes ("None").
- **Undo for item 9's copy.** Confirming the replace (see item 9's write-up) applies immediately, the same as every other XI mutation in this spec (add/remove/reorder) — there's no separate "undo the copy" action; an admin who wants a different result re-runs the picker against a different source match, or rebuilds manually.
- **A real "match completed"/result status.** `029`'s own Non-goals explicitly deferred match results/scores/outcomes to a future Phase 1 spec — nothing here adds one. Item 9's "completed/played matches only" scoping is a deliberate, conservative proxy (`match_date` already in the past relative to the server's current time), not a real status field — see item 9's own write-up and API Contract.
- **A cross-club previous-match picker.** Like every other `/manage` surface in `029`/`037`, item 9's picker only ever surfaces the *acting club's own* scheduled matches (`Match.club_id` = the URL's `clubId`) — even though, per `029`'s own data model, the `teamId` a side references could technically be a cross-club `Team`.

## User Stories

- As a club admin, when I open the Matches list, I see only matches scheduled for today or later by default — a match played earlier today still shows until the day ends, but yesterday's match doesn't clutter today's view.
- As a club admin looking at a match's card or its detail view, I can click a "Select Team" action that takes me directly into that match's Playing XI tab (Home or Away, whichever exists), without first landing on the Details tab and clicking again.
- As a club admin, I see the Matches list's search/sort/section filters laid out as one coherent, properly-organized control group, and the Sort-by dropdown always shows its full label without being visually cut off.
- As a club admin picking a Captain, Wicketkeeper, or Twelfth Man for a side, I can set all three independently — setting one no longer clears whichever of the other two I'd already picked.
- As a club admin opening a match's team-selection screen, I see the Captain/Wicketkeeper/Twelfth Man controls at the top of the page, above the Playing XI list, since I often want to set them before or right after building the batting order, not after scrolling past it.
- As a club admin adjusting the batting order, I can click a player's own batting-order number, type or step to a new position (1–12), and have that player move there with everyone else shifting accordingly — not only nudge them one slot at a time with the up/down arrows.
- As a club admin building a team's squad for a match, I can add a brand-new player — one who isn't in the system yet — directly from the team-selection screen, using the same player-creation form the Players screen already uses, without navigating away and losing my place.
- As a club admin building a side's playing XI, I can pick one of that team's previous matches from the same season and league, and have that side's entire lineup — batting order, roles, captain, wicketkeeper, and twelfth man — copied onto the match I'm currently editing in one action, then tweak it from there using the existing controls; any copied player who's no longer eligible for this match is skipped silently and I'm told how many were skipped, so I know what still needs manual attention.

## Data Model Changes

None. Every item in this spec is UI/UX or a payload-construction fix on top of already-shipped entities — `029`'s `Match`/`MatchSide`/`MatchSidePlayer` and `028`'s `Player`/`PlayerProfile`/`TeamSquadMember`. No new entity, field, or migration. Item 1's date filtering reads the existing `match.match_date` column (`029`'s Data Model Changes) — no schema change needed to support it. Item 7's stepper reorder reuses `MatchSidePlayer.battingOrder` and the existing `PUT .../sides/{sideId}/players/reorder` full-array-reassignment contract (`029`'s `MatchSideServiceImpl.reorderPlayers`) unmodified. Item 9's previous-match picker is a new *read-only query shape* over `Match`'s own already-existing `club_id`/`home_team_id`/`away_team_id`/`season_id`/`league_id`/`match_date`/`active` columns (`029`) — no new column, entity, or migration — and its response reuses the existing `MatchDto` (`029`) unmodified, no new DTO. The copy action itself persists nothing beyond what the existing `POST .../sides/{sideId}/players`, `PUT .../sides/{sideId}`, and `POST .../sides/{sideId}/players/{playerProfileId}/remove` endpoints (`029`) already write — no "copied from" lineage field is added (see Non-goals).

## API Contract

Two backend surfaces change: item 1 extends an existing endpoint with a new optional query param, and item 9 adds one brand-new endpoint for its previous-match picker. Everything else in this spec calls existing, unmodified endpoints.

| Endpoint | Access | Change |
|---|---|---|
| `GET /api/v1/manage/clubs/{clubId}/matches` | `@access.canAccessClub` (unchanged) | **Changed.** Gains one new optional query param, `upcomingOnly` (boolean, `@RequestParam(required = false, defaultValue = "false")`) alongside the existing `sectionId`/`Pageable` params. When `true`, restricts the result to matches whose `match_date` falls on or after the start of today (server/database local date — see UI Requirements' note on timezone scope) — i.e. a match played earlier today is still included, one played yesterday is not. Omitted or `false` preserves today's exact unfiltered behaviour, so this is purely additive; no existing caller breaks. |

**New — item 9's previous-match picker.** A dedicated, team-scoped endpoint rather than more query params bolted onto the paginated `GET /matches` above: the picker's candidate set is naturally small (one team's fixture history within a single Season+League), the same reasoning `029` already gave for nesting the team-squad list under `teams/{teamId}/seasons/{seasonId}/squad` rather than adding `teamId`/`seasonId` filters to a club-wide list — and it needs no pagination, unlike the genuinely unbounded, club-wide match history `GET /matches` exists to page through.

| Endpoint | Access | Purpose |
|---|---|---|
| `GET /api/v1/manage/clubs/{clubId}/teams/{teamId}/seasons/{seasonId}/matches/previous` | `@access.canAccessClub` (same check every endpoint on this resource already uses) | Lists this club's own scheduled matches (`match.club_id = clubId` — never filtered by which club owns `teamId`, since `029` already allows a cross-club `Team` reference on a `Match` this club owns) referencing `teamId` as either `home_team_id` or `away_team_id`, scoped to the given `seasonId` (path — `404` if it belongs to a different club, matching every prior spec's isolation posture) and to an **exact** League match: an optional `leagueId` query param restricts to `league_id = leagueId` when present, and to `league_id IS NULL` when the param is omitted — "same League as the match being edited" means matching its `null`-ness too, not "any League." An optional `excludeMatchId` query param excludes one match id (the one currently being edited) from the results. Restricted to `active = true` matches and to `match_date` strictly before the server's current instant — the practical, conservative "already played" proxy available today, since `029`'s own Non-goals still defer a real match-result/status field to a future Phase 1 spec (see Non-goals above). Further restricted to matches where a `MatchSide` for `teamId` already exists **with at least one `MatchSidePlayer` row** — a match where an XI was never actually built has nothing meaningful to copy, so it's left out of the picker rather than offered as a no-op option. Returns a plain `List<MatchDto>` (the existing, unmodified `029` DTO — no new response shape), ordered `match_date` descending (most recent first). |

Everything else below reuses an existing, unchanged endpoint:

| Endpoint | Purpose here |
|---|---|
| `PUT /api/v1/manage/clubs/{clubId}/matches/{matchId}/sides/{sideId}` | Item 5's fix — the frontend now always sends all three of `captainPlayerId`/`wicketKeeperPlayerId`/`twelfthManPlayerId` (merging in the side's current values for the two fields not being changed), instead of a single-field payload against this endpoint's existing full-replace contract. Item 9 reuses this same endpoint, and the same always-send-all-three-fields discipline, twice — once to clear a non-empty destination side before copying, and once to set the copied captain/wicketkeeper/twelfth-man trio at the end of the copy (see item 9's own write-up). No backend change. |
| `PUT /api/v1/manage/clubs/{clubId}/matches/{matchId}/sides/{sideId}/players/reorder` | Item 7's stepper — computes the full new `playerProfileIds` order (the moved player spliced into the chosen position, everyone else shifted) and calls this existing endpoint exactly as the up/down arrows already do. No backend change. |
| `POST /api/v1/manage/clubs/{clubId}/players` (`028`) then `POST /api/v1/manage/clubs/{clubId}/teams/{teamId}/seasons/{seasonId}/squad/{playerId}/add` (`029`) | Item 8's "Add Squad Member" — creates the `Player` first, then adds the newly-created player to this side's team/season squad, as two sequential calls in one mutation. No backend change; no new "create-and-add-to-squad" combined endpoint. |
| `GET /api/v1/manage/clubs/{clubId}/matches/{matchId}/sides` (`029`) | Item 9 — once a source match is picked, fetches its sides and reads the one entry whose `teamId` matches the destination side's own `teamId` (its ordered `players[]`, `captainPlayerId`, `wicketKeeperPlayerId`, `twelfthManPlayerId`) — the full source XI the copy step below reproduces. No backend change. |
| `POST .../sides/{sideId}/players` (`029`) | Item 9's copy step — called once per source player, in the source's own ascending `battingOrder`, with that player's `{playerProfileId, role}`. Since this endpoint always appends to the end of the destination side's order, replaying the source's players in order naturally reproduces its batting order without a separate reorder call. Any per-call `400` (`PlayerNotInSquadException`/`PlayerAgeIneligibleException`/`PlayingXiCapExceededException`) is caught and that one player is skipped — the loop continues rather than aborting the whole copy. No backend change. |
| `POST .../sides/{sideId}/players/{playerProfileId}/remove` (`029`) | Item 9's clear-before-replace step — called once per player already on the destination side, before the copy begins, only when the destination side is non-empty. No backend change. |

## UI Requirements

**1. Upcoming-only match list — default filter state, not a hard exclusion.** `MatchList.tsx` adds a new piece of local state, `const [upcomingOnly] = useState(true)` (no UI control to change it this pass — see Non-goals), sent as `upcomingOnly: true` in `listMatches`' query params alongside the existing `page`/`sort`/`sectionId`. This is a genuine backend-driven filter (`docs/standards/frontend.md`'s pagination rule — never client-side), landing in the query key so pagination/caching stay correct. `SquadPicker.tsx` inherits this default unchanged (it renders `MatchList` with no override) — a deliberate, complementary call: "which matches do I need to pick a squad for" and "which matches are upcoming" are the same underlying question, so `SquadPicker` narrowing to upcoming matches too is consistent, not an oversight.

**2. "Select Team" shortcut — reuses the exact `?tab=playing-xi` deep link `SquadPicker` already established.** `029`'s `MatchFormPage.tsx` already recognizes `?tab=playing-xi` and jumps to whichever XI tab exists (home, else away) — `SquadPicker.tsx`'s own card already uses this as its primary action. This spec adds the identical shortcut in two more places that don't have it yet:
   - **`MatchList.tsx`'s `MatchCard`** — a new entry in `RecordCard.secondaryActions` (`ui/src/components/RecordCard/RecordCard.tsx`, unmodified — this reuses the existing, generic `secondaryActions` array, no new `RecordCard` prop needed), label "Select Team", icon `GroupsOutlined`, `onClick: () => navigate(\`${editTo(match.id)}?tab=playing-xi\`)`, `pending: false` (a plain navigation, not an async mutation — same non-mutating use of `secondaryActions`' shape `030`'s "Communicate Team Sheet" action already established). **Rendered only when the match has at least one real-`Team` side** (`Boolean(match.homeTeamId) || Boolean(match.awayTeamId)`) — a match between two free-text opponents has no Playing XI tab to jump into (`029`), so the action is omitted entirely rather than shown disabled or landing on an empty tab.
   - **`MatchDetailPage.tsx`** — `RecordDetailScreen` gains one new, additive, optional prop: `secondaryActions?: { label: string; to: string; icon?: ReactNode }[]`, rendered as outlined/text buttons in the header, before the existing single `editTo` button (mirroring `RecordCard`'s own "secondary actions render before the primary action" ordering). `MatchDetailPage` passes one entry, "Select Team", `to: \`/manage/fixtures/matches/${match.id}/edit?tab=playing-xi\`\`, under the same "at least one real-Team side" condition as above. This is a link-shaped action (`to`, not `onClick`) — distinct from `RecordCard.secondaryActions`' callback shape, since this is a plain navigation with no pending/async state, matching `RecordDetailScreen`'s own existing `editTo` being a link rather than a callback.

**3 & 4. Filters bar cleanup and Sort-by clipping — both in `MatchList.tsx`, scoped to that screen's own filter row.** Two distinct, related problems in the same area:
   - The Sort-by `Select` inside `ListToolbar` (`ui/src/components/ListToolbar/ListToolbar.tsx`) has a hard-coded `flex: { xs: 1, md: '0 0 200px' }` — sized comfortably for every other list's short option labels (`"Name"`, `"Label"`, `"Role"`) but not for `MatchList`'s own, notably longer sort-option text (`"Match date (newest first)"` / `"Match date (oldest first)"`, `037`'s own `SORT_OPTIONS` — the longest sort-option strings anywhere in this codebase today), which visually clips inside that fixed 200px box. **Fix:** `ListToolbar` gains one new, additive, optional prop, `sortMinWidth?: number` (default unchanged at `200`), so `MatchList.tsx` alone can pass a wider value (e.g. `260`) without touching every other list's Sort-by width — a deliberately scoped fix rather than a blanket widening of a shared component that risks a visual regression on `TeamDirectory`/`PlayerList`/etc., none of which have this problem today.
   - `MatchList.tsx`'s own filters area currently reads as two visually disconnected rows: `ListToolbar` (search/sort/create) directly above a separate, differently-styled `Box sx={{ maxWidth: 360 }}` holding the `SectionTreeSelect` filter, with no shared border/background/spacing tying them together as one control group. **Fix:** wrap both in a single bordered/tinted container consistent with this codebase's existing filter-grouping convention — reuse the same light `alpha(theme.palette.primary.main, 0.05)`-tinted, bordered `Box` treatment `SponsorDetailPage.tsx` already establishes for a "these controls belong together" visual (`docs/standards/design-system.md`'s Record list pattern table — `RecordCard` itself now uses a solid `background.paper` + shadow, not this tint), rather than two bare, stacked elements. The `SectionTreeSelect` itself is unchanged — only its containing layout.

**5. Fixing the Captain/Wicketkeeper/Twelfth Man clear-each-other bug — root cause and fix, both precise.** `MatchFormPage.tsx`'s `MatchSideTab` wires `onChangeCaptain`/`onChangeWicketKeeper`/`onChangeTwelfthMan` (each passed into `PlayingXiBuilder`) to `updateSideMutation.mutate({ captainPlayerId: id })` (and the equivalent single-field object for the other two) — a JS object containing **only** the one field just changed. `UpdateMatchSidePayload`/`UpdateMatchSideRequest` (frontend TS interface and backend Java record, both a plain 3-field struct with no partial-update semantics) deserialize the two omitted keys as `null`; `MatchSideServiceImpl.updateSide` (`029`, lines ~163–165) then does an **unconditional 3-field overwrite** — `side.setCaptainPlayerId(request.captainPlayerId())` etc. for all three fields, every call — so setting the Captain silently nulls out whatever Wicketkeeper/Twelfth Man were already set, and vice versa for each of the other two. **Fix, entirely frontend:** `MatchSideTab`'s three `onChange*` callbacks must each send the side's **current** values for the two fields not being changed, merged with the one new value — e.g. `onChangeCaptain={(id) => updateSideMutation.mutate({ captainPlayerId: id, wicketKeeperPlayerId: side.wicketKeeperPlayerId, twelfthManPlayerId: side.twelfthManPlayerId })}`, and the equivalent for the other two handlers. `PlayingXiBuilder.tsx` itself needs no change — its `onChangeCaptain`/`onChangeWicketKeeper`/`onChangeTwelfthMan` props already only ever carry the single new id; the merge belongs at the call site that owns `side`'s current state (`MatchSideTab`), consistent with `docs/standards/frontend.md`'s "server state lives in the page" rule.

**6. Reordering the Captain/Wicketkeeper/Twelfth Man block above Playing XI.** In `PlayingXiBuilder.tsx`, the three `Select`s (currently the last block in the component, after the ordered XI list and the "Add player" row) move to render **first**, above the "Playing XI" heading/progress bar/ordered list/"Add player" row block. Purely a JSX reordering inside the existing component — no prop shape change, no change to which options each `Select` offers (Captain/Wicketkeeper still scoped to the current ordered XI, Twelfth Man still scoped to not-yet-added squad members, per `029`/`033`, unchanged).

**7. Click-to-edit batting-order stepper — augments, doesn't replace, the up/down arrows.** In `PlayingXiBuilder.tsx`'s ordered-XI row, the static `<Typography>{entry.battingOrder}</Typography>` becomes a small click-to-edit control: displays as plain text by default; clicking it swaps in a compact numeric stepper input (`Input type="number"`, `inputProps={{ min: 1, max: 12, step: 1 }}` — the `1–12` ceiling matches `League.maxPlayingXiSize`'s realistic maximum, a 12-a-side Vets league per `029`, not this side's own possibly-smaller `cap`) in place of the text, auto-focused; on blur or Enter, commits the new position and reverts to plain text. **Commit behaviour:** the entered value is clamped to `[1, orderedXi.length]` (a position beyond the side's own current player count has no meaningful slot to shift into — the player lands at the end instead of erroring); the component then builds the full reordered `playerProfileIds` array (the moved player spliced out and reinserted at the clamped target index, matching `handleMove`'s existing splice logic) and calls the existing `onReorderPlayers` prop — **the same callback, and the same full-array `PUT .../players/reorder` contract, the up/down arrows already use.** The existing `ArrowUpwardIcon`/`ArrowDownwardIcon` `IconButton`s stay exactly as they are, unchanged, alongside the new stepper — a deliberate augmentation, not a replacement (see Non-goals).

**8. "Add Squad Member" — reuses `028`'s `PlayerForm` and `027`'s `CreateAndLinkRecordDialog` verbatim, the same combination `TeamFormPage.tsx` already uses for Contacts/Sponsors (just not, until now, for Players).** `PlayingXiBuilder.tsx` gains one new, additive, optional prop: `onAddSquadMember?: () => void`, rendered as a `Button` (label "Add Squad Member", `variant="secondary"`) next to the existing "Add player" `Autocomplete`/Role/`Button` row — omitted entirely when the prop isn't passed, so this is purely additive. `MatchSideTab` (`MatchFormPage.tsx`) owns the actual dialog and mutation, matching `docs/standards/frontend.md`'s "server state in the page" rule:
   - Local `squadMemberDialogOpen` state, opened by `onAddSquadMember`.
   - A `CreateAndLinkRecordDialog<PlayerPayload>` (`ui/src/components/CreateAndLinkRecordDialog`, unmodified) wrapping `PlayerForm` (`ui/src/components/PlayerForm`, unmodified) — since `PlayerForm` externalizes its own Basic/Contact/Cricket Info tab bar to its caller (`028`'s own documented design, not a `CreateAndLinkRecordDialog` limitation), the dialog's own small wrapper renders that same three-tab bar locally (mirroring `PlayerFormPage`'s existing tab-owning pattern, not inventing a new one) so the quick-add flow isn't limited to Basic Info only.
   - `onCreateAndLink` runs a two-step mutation: `createPlayer(clubId, payload)` (`028`) then, on success, `addToSquad(clubId, teamId, seasonId, newPlayer.id)` (`029`'s `teamSquadApi.ts`) — both already-existing, unmodified functions, called in sequence, matching `TeamFormPage.tsx`'s own existing `createAndLinkContactMutation`/`createAndLinkSponsorMutation` two-step shape.
   - On success, invalidates the same squad query key `MatchSideTab`'s own `squadQuery` already uses (`['managed-club', clubId, 'teams', teamId, 'seasons', seasonId, 'squad']`) so the newly-created player appears in `PlayingXiBuilder`'s "Add player" `Autocomplete` immediately, without a page reload.

**9. "Re-select from Previous Match" — one-action XI copy from an identically-scoped prior fixture.** `PlayingXiBuilder.tsx` gains one new, additive, optional prop, `onReselectFromPreviousMatch?: () => void`, rendered as a `Button variant="secondary"` labelled "Re-select from Previous Match" next to item 8's "Add Squad Member" button (same row, same omitted-when-not-passed convention — no existing call site/story/test that doesn't pass it changes). `MatchSideTab` (`MatchFormPage.tsx`) owns the picker, the confirmation, and the copy mutation itself, matching `docs/standards/frontend.md`'s "server state in the page" rule every other item in this spec follows:
   - **The picker.** Opening it fetches `listPreviousMatches(clubId, teamId, seasonId, { leagueId: match.leagueId, excludeMatchId: matchId })` (`ui/src/api/matchApi.ts`, new — see API Contract), enabled only while the dialog is open, and renders the results through `LinkExistingRecordDialog<Match>` (`ui/src/components/LinkExistingRecordDialog`, unmodified — the same generic "search an existing record" dialog `029`'s Affiliations and Squad tabs already reuse) in its **no-`extraField`** mode: picking an option fires immediately, with no separate confirm button inside the picker itself (the destructive confirmation, when needed, happens in a second dialog — see below). `getOptionLabel` renders each candidate as `"<match date> — vs <opponent>"`, resolving the *other* side's display name with the exact same `sideDisplayName(teamId, teamName, teamsById)` helper `MatchFormPage.tsx` already defines and uses for its own Home/Away XI tab labels. `MatchSideTab` gains two new props to make this possible — `teamsById: Map<string, Team>` and `leagueId: string | null` — passed down from both existing `<MatchSideTab>` call sites in `MatchFormPage.tsx`, using its own already-computed `teamsById` and `match.leagueId`, so no new team-name-resolution logic is written anywhere.
   - **The confirmation.** If the destination side already has at least one player, or a captain/wicketkeeper/twelfth man already set, picking a source match opens a second, small `Dialog` — inline in `MatchSideTab`, not a new shared `components/**` folder, since it's a one-off two-button confirm with no other consumer yet — reading "Replace the current Playing XI with the one from `<match label>`? This replaces every player, role, and batting-order position currently set for this side." Confirming runs the copy; cancelling leaves the destination side untouched and discards the picker's selection. When the destination side is already empty, this step is skipped entirely — there's nothing to lose, so the copy runs immediately on picking a match.
   - **The copy** — a single `useMutation` (`copyFromPreviousMatchMutation`, mirroring item 8's own `createAndLinkPlayerMutation` "sequential awaited calls inside one `mutationFn`" shape) that:
     1. Fetches the source match's sides via the existing, unmodified `listMatchSides(clubId, sourceMatchId)` (`029`) and finds the entry whose `teamId` matches this side's own `teamId`.
     2. If the destination side is non-empty, clears it first: one `removeMatchSidePlayer` call per player currently on it, then one `updateMatchSide` call setting `captainPlayerId`/`wicketKeeperPlayerId`/`twelfthManPlayerId` all to `null` — the same always-send-all-three-fields shape item 5's fix already established, so this step can never re-trigger item 5's bug.
     3. For each source player, **in ascending `battingOrder`**, calls the existing `addMatchSidePlayer(clubId, matchId, sideId, playerProfileId, role)` — the same call `PlayingXiBuilder`'s own "Add player" control already makes, which always appends at the end of the order, so replaying the source's players in their own order naturally reproduces that exact batting order and role tagging on the destination side, with no separate reorder call needed. Any call that rejects with the server's existing `PlayerNotInSquadException`/`PlayerAgeIneligibleException`/`PlayingXiCapExceededException` (`400`, `029`) is caught, that player is recorded as skipped, and the loop continues to the next source player — one rejected player never aborts the rest of the copy.
     4. Resolves which of the source's `captainPlayerId`/`wicketKeeperPlayerId`/`twelfthManPlayerId` actually made it onto the new side — captain/wicketkeeper must be among the players step 3 just successfully copied; twelfth man must **not** be among them, and must still be present in `squadQuery`'s own already-loaded squad list (the twelfth man is never added as a `match_side_player` row, so it's never separately attempted/validated by step 3, unlike the ordered XI) — and issues one final `updateMatchSide` call with the resolved trio (`null` for any id that wasn't carried over). If that call itself rejects one of the three ids (e.g. the twelfth man is squad-eligible but fails an age check step 3 never exercised), the rejected field is dropped and the call retried once without it, counted as one further skipped selection.
     5. Returns `{ copiedCount, skippedCount, totalSourcePlayers }`; `onSuccess` invalidates the same sides query key every other mutation in this tab already invalidates, closes both dialogs, and stores the result in a new local `copySummary` state.
   - **The summary.** When `copySummary` is set, `MatchSideTab` renders `<Alert severity="info">` beneath `PlayingXiBuilder` (same placement convention as the existing `errorMessage` `Alert`) reading `"Copied <copiedCount> of <totalSourcePlayers> players from the previous XI"`, plus, only when `skippedCount > 0`, a second line: `"<skippedCount> couldn't be copied — no longer eligible for this match. Add them manually."` — matching this item's own settled decision to skip an ineligible player silently during the copy, then surface one small summary afterward, never blocking the whole copy over a single ineligible player.

**Mobile-first**, per `docs/standards/frontend.md` — every new/changed control above (the reordered Select block, the batting-order stepper, the "Add Squad Member" button, the "Re-select from Previous Match" button and its picker/confirm dialogs, the filters-bar regrouping) stacks full-width at 375px, matching every existing control it sits alongside.

## Acceptance Criteria

- The Matches list shows only matches dated today or later by default; a match played earlier today still appears until the calendar day ends.
- A "Select Team" action is available on a match's `RecordCard` (list) and on `MatchDetailPage`, landing directly on that match's Playing XI tab (home, else away) — hidden for a match with no real-`Team` side on either end.
- `MatchList`'s filters bar (search, sort, section) reads as one organized, bordered control group, and the Sort-by control never visually clips its selected label at any supported viewport.
- Setting a Captain, Wicketkeeper, or Twelfth Man never clears an already-set value for either of the other two — verified by setting all three in sequence and confirming each survives the next two changes.
- The Captain/Wicketkeeper/Twelfth Man block renders above the Playing XI list/batting order on `PlayingXiBuilder`'s initial load.
- Clicking a batting-order number and entering a new position (1–12, clamped to the side's current XI size) moves that player to the chosen position and shifts the rest of the order accordingly, using the existing full-array reorder endpoint; the existing up/down arrows still work unchanged.
- A club admin can create a brand-new player and have them added to the current match's team squad in one flow, without leaving `MatchFormPage`'s Playing XI tab, and without a page reload to see them become selectable.
- A club admin can pick one of a side's previous matches — scoped to the identical Season and League as the match being edited, most recent first, played matches only — and have that side's full XI (batting order, roles, captain, wicketkeeper, twelfth man) copied onto the current match in one action; replacing an already-built XI requires an explicit confirmation first, while copying onto an empty side does not.
- A player from the copied XI who's no longer squad-eligible or age-eligible for the current match is skipped silently rather than blocking or erroring the copy, and the admin sees a summary of how many players were copied versus skipped once the copy completes.
- No `029`/`033` business rule (squad membership, age eligibility, XI cap, captain/keeper-must-be-in-XI, twelfth-man-must-not-be-in-XI) is weakened or bypassed by any change in this spec, including item 9's copy action.

## Rollout Notes

- Ships as one PR across `MatchList.tsx`, `MatchFormPage.tsx`/`MatchSideTab`, `PlayingXiBuilder.tsx`, `MatchDetailPage.tsx`, `RecordDetailScreen.tsx`, `ListToolbar.tsx`, `ui/src/api/matchApi.ts` (item 9's new `listPreviousMatches`), and backend `MatchController`/`MatchServiceImpl` (item 1's `upcomingOnly` param and item 9's new `GET .../matches/previous` endpoint) — the nine items share three screens closely enough that splitting them would mean re-touching the same files for unrelated reasons across multiple PRs.
- **Judgment calls made without a live screenshot/mockup for items 3/4 (the filters-bar cleanup), flagged for reviewer sign-off:** the exact visual treatment (a bordered/tinted container matching `RecordCard`'s own tint convention) and the `sortMinWidth` mechanism (an additive `ListToolbar` prop scoped to `MatchList` alone, rather than widening every list's Sort-by column) are this spec's own proposed fix, not a supplied design. A Claude Design pass or a quick live-browser check before merge is worth doing here specifically, unlike the rest of this spec's more mechanically-determined items.
- **Item 7's `1–12` input ceiling is a deliberate literal reading of the original ask**, even though a given side's actual `cap` (`League.maxPlayingXiSize`) may be smaller than 12 — the effective, enforced range clamps to the side's real current XI length, so the wider `1–12` input range never produces an invalid position; flagged so a reviewer doesn't mistake the `12` in the input's `max` attribute for a missed cap check.
- **The "Show past matches" toggle (item 1's stated but undeferred half) is a named, ready-to-build follow-up** — the backend `upcomingOnly` param and the frontend's already-query-keyed boolean mean building the actual toggle control later is additive UI only, no further backend work. A human should add this to `docs/roadmap.md` once this ships.
- **Drag-and-drop batting-order reordering** stays a named, real "later" option (see Non-goals) — revisit only if a `dnd-kit`-class dependency gets approved for an unrelated reason first, the same way `@mui/x-tree-view`/`jspdf` were each added for a specific spec's own stated need.
- **Item 9 needs its own Claude Design pass before build (`docs/workflow.md` Step 2), unlike items 1, 2, 5, 6, 7, and 8 below.** The previous-match picker itself reuses an already-shipped pattern (`LinkExistingRecordDialog`'s no-`extraField` mode, per `027`/`029`'s own precedent), but the destructive-replace confirmation step has no existing analogue anywhere in this codebase today (no generic confirm-dialog component exists to reuse, confirmed by inspection) — a genuinely new small interaction, not a near-miss on something already built. Flag this explicitly for design review rather than letting a builder agent freehand a destructive-action confirmation's copy/layout.
- No Claude Design pass required for items 1, 2, 5, 6, 7, or 8 — each reuses an already-shipped visual/interaction pattern (`SquadPicker`'s own `?tab=playing-xi` deep link, `RecordCard.secondaryActions`, `PlayingXiBuilder`'s existing Select/IconButton/Autocomplete language, `CreateAndLinkRecordDialog`) rather than inventing a new one, matching `033`'s own precedent for when this step can be skipped with a stated reason.
- **Item 9's "played match" scoping is a deliberate, conservative date/time proxy, not a real result/status field** — `match_date` already in the past relative to the server's current instant. `029`'s own Non-goals still defer match results/scores/outcomes to a future Phase 1 spec (see `docs/roadmap.md`); once that ships, a future spec may want to narrow "previous match" further to "has recorded results," but that's out of scope here and shouldn't block this item.
- **Item 9 adds no "copied from" lineage field and no undo action**, both deliberate (see Non-goals) — a copied XI is indistinguishable from a manually-built one once applied, and an admin who wants a different result re-runs the picker or rebuilds manually, matching how every other XI mutation in this spec already behaves.
