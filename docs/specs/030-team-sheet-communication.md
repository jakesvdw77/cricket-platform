# 030 — Team Sheet Communication from the Match Card

**Depends on:** `029-league-management.md` (`Match`, `MatchSide`, `MatchSidePlayer`, `TeamSquadMember` — every entity this spec reads from, none redefined here), `026-teams.md`/`027-team-profile.md` (`Team.logoUrl` — the only per-side branding asset this spec renders), `028-players.md` (`Player.firstName`/`lastName` via `029`'s squad endpoint — the only player fields this spec needs), `008-product-catalog.md` (`RecordCard` — the shared list-card component this spec extends), `019-resend-subscription-welcome-email.md` (`RecordCard.secondaryAction` — the existing single-action shape this spec generalizes).
**Status:** draft.

## Problem & Goals

`029` built match scheduling and playing-XI selection but stopped at persistence — once an admin has picked a side's XI, there is no way to get it in front of the actual team. `029`'s own Non-goals named this explicitly as future scope ("Availability polls, AI-assisted XI suggestion, an 'Announce Team' lock/notify/email workflow, or public/shareable team-sheet graphics... Real future work, not forgotten") and pointed at the legacy Cricket Legend app (`/Users/jaco/Development/cricketlegend`) as the source of that richer, since-trimmed feature set. This spec is the first slice of that future work: a "Communicate Team Sheet" action on each match's `RecordCard` in `ui/src/pages/manage/MatchList.tsx`, opening a dialog built to hold several communication formats over time, with exactly one of them wired this pass.

**Goals**
- A club admin can open a "Communicate Team Sheet" dialog directly from a match's card in `MatchList` (and, since `SquadPicker` reuses `MatchList`'s card shape per `029`, from there too).
- The dialog's first and only wired option, "Print as PDF," generates an A4 team-sheet PDF **entirely client-side** (no new backend endpoint) and opens it in a new tab, ready to print or save — porting the legacy app's `jsPDF` approach (`ui/src/utils/matchPdf.ts`'s `generateTeamsheetPdf`, which itself hand-draws every row rather than using `jspdf-autotable` — that package is used by other legacy PDF generators, not this one, so it's not a dependency here either), not `@react-pdf/renderer`. This is a settled decision, not open for re-litigation in this spec.
- The dialog's option list is intentionally designed to grow (WhatsApp text, Facebook text, image export are the legacy app's own next options) without a structural rework, even though only PDF is wired here.
- `RecordCard` — shared by every `/manage` list screen (Sponsors, Teams, Players, Sections, Leagues, Seasons, Matches, and more) — gains a documented, deliberate way to carry a second card-level action without breaking any of its existing single-action call sites.

## Non-goals

- **WhatsApp text template.** Legacy's `buildWhatsAppText` (`TeamsheetTemplatesDialog.tsx`) is real prior art but not built here — deferred, tracked against this spec (`030`) for `docs/roadmap.md` to index.
- **Facebook text template.** Same as above — legacy's `buildFacebookText`, deferred against `030`.
- **Image export** (a shareable team-sheet graphic, e.g. a PNG card) — not part of legacy's own `matchPdf.ts`/`TeamsheetTemplatesDialog.tsx` either, but a natural future option in the same dialog. Deferred against `030`.
- **Server-side PDF generation.** The PDF is generated in the browser, from data the client already has (or fetches via existing `029`/`026` endpoints) — no new backend endpoint, no server-rendered document. A settled decision (see Problem & Goals), not revisited here.
- **A persisted shirt-number field.** Legacy's teamsheet PDF prints each player's shirt number (`Player.shirtNumber`) beside their name. Neither this codebase's `Player` (`028`) nor `MatchSidePlayer` (`029`) has an equivalent field — a genuine, checked-for data gap, not a silent assumption. This spec's PDF omits shirt numbers entirely rather than adding a new column to either entity; see API Contract's Data Gap note and Rollout Notes for the fast-follow this implies. **Resolved by `031-jersey-numbers.md`** — the PDF now prints each side's per-team-squad jersey number.
- **An "Announce Team" lock/notify/email workflow, availability polls, or AI-assisted XI suggestion.** Still exactly as deferred as `029` left them. This spec's PDF option is reachable regardless of how many players are currently on a side — there is no "lock the XI before it can be printed" gate, and no notification is sent to anyone. "Printable" here means only "has at least one player added" (see UI Requirements) — not a new stateful `announced` flag on `MatchSide`.
- **Editing or copying generated text before sending.** Legacy's dialog shows an editable, copy-to-clipboard `TextField` for its WhatsApp/Facebook templates. Moot until a text-template option exists in this codebase — revisit alongside whichever spec builds the first of those.
- **Any change to `Match`/`MatchSide`/`MatchSidePlayer`/`TeamSquadMember`'s schema.** This is a UI-plus-client-side-utility spec — no migration, no new/changed DTO field, no new backend endpoint (see API Contract).
- **Public or unauthenticated access to a team sheet.** This stays a `/manage`-only action for a club admin, matching `029`'s own identical Non-goal ("Any public-facing schedule, squad, or team-sheet display").
- **A general-purpose overflow/menu component for `RecordCard`.** This spec's `RecordCard` change adds just enough surface for a second ordered action (see UI Requirements) — no `MoreVert` menu, no drag-reordering of actions, no per-card configurable action count beyond what's needed here.
- **Wiring "Communicate Team Sheet" into any screen other than `MatchList`'s card (and, by reuse, `SquadPicker`'s).** No new entry point on `MatchFormPage`'s Details tab, no shortcut from the Playing XI tab itself — the match card is the single, deliberate entry point this pass.

## User Stories

- As a club admin, from a match's card in Matches (or Squads), I can open a "Communicate Team Sheet" dialog for that match.
- As a club admin, within that dialog, I can choose "Print as PDF" and a team scope — Home, Away, or Both Teams — and get an A4 PDF opened in a new browser tab, ready to print or save.
- As a club admin, I can't pick a single side's PDF scope ("Home" or "Away" specifically) when that side is a free-text opponent (no roster exists to print) or currently has zero players added to its XI — that option is disabled, with the "Both Teams" option still available and printing a "Team not yet announced" placeholder for whichever side has nothing to show, matching legacy's own graceful-degradation behaviour.
- As a club admin, if neither side of a match is a real `Team` (e.g. two free-text opponents — an edge case, but a real one this spec's own data model allows per `029`), the dialog tells me there's nothing to print rather than offering a scope choice that can never succeed.
- As a club admin, the PDF lists each printed side's players in batting order, calls out the captain and wicketkeeper inline, and shows a distinct twelfth-man callout — the same information already captured by `029`'s Playing XI builder, just rendered for print.
- As a club admin using a screen reader or a 375px viewport, every control in the dialog (option choice, scope choice, print action) is keyboard-reachable and usable without hover-only or drag interaction.

## Data Model Changes

None. This spec adds no entity, field, or migration — it reads `029`'s already-persisted `Match`/`MatchSide`/`MatchSidePlayer`/`TeamSquadMember` data (via existing endpoints) and `026`'s `Team.logoUrl`/`name`, and renders them into a client-generated PDF. See the Non-goals entry on the missing shirt-number field for the one genuine data gap this spec identified and deliberately declined to close.

## API Contract

**No new or changed endpoint.** Every data need is met by existing, already-implemented endpoints:

| Endpoint | Access | Purpose (in this spec) |
|---|---|---|
| `GET /api/v1/manage/clubs/{clubId}/matches/{matchId}/sides` | `@access.canAdministerClub` (`029`, reused as-is) | Resolves each side's ordered `MatchSidePlayer` rows, `captainPlayerId`, `wicketKeeperPlayerId`, `twelfthManPlayerId` — the PDF's core content |
| `GET /api/v1/manage/clubs/{clubId}/teams/{teamId}/seasons/{seasonId}/squad` | same (`029`, reused as-is) | Resolves player names for the ids on a `MatchSide` — this spec's dialog fetches it per side, keyed on `match.seasonId`, exactly as `MatchFormPage`'s existing `MatchSideTab` already does |
| `GET /api/v1/manage/clubs/{clubId}/teams` | `@access.canAdministerClub` (`026`, reused as-is) | Resolves each real-`Team` side's `name`/`logoUrl` — `MatchList` already fetches this into `teamsById` for its own card titles; this spec's dialog reuses that same map rather than re-fetching |

**Data gap, documented rather than silently worked around:** neither `PlayerDto` (`028`) nor `MatchSidePlayer` (`029`) carries a shirt-number field, unlike legacy's `Player.shirtNumber`. No endpoint change is proposed to close this gap in this spec — the PDF simply omits shirt numbers (see Non-goals). Adding a shirt-number field is real, identifiable future scope (on `PlayerProfile` per `028`, or as a `MatchSidePlayer` column per `029` if it's meant to vary by side rather than being a standing per-player attribute) — a decision for whichever future spec actually needs it, not decided here.

**Resolved by `031-jersey-numbers.md`**: added `PlayerProfile.jerseyNumber` (a standing/default number) and, independently, `TeamSquadMember.jerseyNumber` (per-team-squad, defaulting from the standing number at add-time, editable from then on) — the latter is what this PDF prints, via `listSquad`'s response, unchanged in shape from this spec's own call.

## UI Requirements

**`RecordCard`'s action surface — the decision this spec must fix before build, not leave to be improvised.** `RecordCard` (`ui/src/components/RecordCard/RecordCard.tsx`) today accepts exactly one `secondaryAction: RecordCardSecondaryAction` alongside its Edit action. This spec needs a match card to carry **two** independent secondary actions — the existing Deactivate/Reactivate toggle (`029`) and the new "Communicate Team Sheet" trigger — without touching any of `RecordCard`'s other current call sites (`TeamFormPage` + its test, `SeasonList`, `PlayerList`, `LeagueList`, `LeagueFormPage`, `SponsorContactList`, `TeamDirectory`, `TeamList`, `SponsorList`, `ClubContactList`, `SubscriptionList`, plus `RecordCard.test.tsx`/`RecordCard.stories.tsx`'s own coverage), each of which passes at most one `secondaryAction` today.

**Decision: add a new, optional `secondaryActions?: RecordCardSecondaryAction[]` prop, rendered after the existing singular `secondaryAction` (if both are present) and before the Edit action — `secondaryAction` itself is unchanged, byte-for-byte, and stays fully supported as the single-action convenience shape.** Internally `RecordCard` builds one ordered list — `[...(secondaryAction ? [secondaryAction] : []), ...(secondaryActions ?? [])]` — and renders each entry with the exact same `Button` markup (`variant="ghost"`, `size="sm"`, optional leading icon, pending-label swap while `pending`) `secondaryAction` already uses today, keyed by array index. This was chosen over two alternatives considered and rejected:
- *Generalizing `secondaryAction` itself into an array* would be the more "one shape per concern"-pure outcome long-term, but breaks the type signature at all eleven existing call sites — directly against this spec's own constraint that they keep working unchanged without being touched.
- *A distinct new `actions` slot replacing both* would leave two competing ways to express the same "footer action" concept inside the same component, which is a worse "one shape per concern" outcome than a singular-plus-plural pair that share one render path and one visual treatment.

`MatchCard` (`ui/src/pages/manage/MatchList.tsx`) is the only call site touched by this decision: its existing `secondaryAction` prop (the Deactivate/Reactivate toggle) is left exactly as it is today, and a new `secondaryActions={[{ label: 'Communicate Team Sheet', pendingLabel: 'Opening…', pending: false, onClick: () => setDialogOpen(true), icon: <ShareOutlinedIcon fontSize="small" /> }]}` prop is added alongside it — rendering, left to right in the card footer: Deactivate/Reactivate, then Communicate Team Sheet, then Edit. `RecordCard.test.tsx` gains coverage for `secondaryActions` rendering in order alongside a `secondaryAction`, and for `secondaryActions` alone (no `secondaryAction`) — both without touching any existing test in that file.

**`ui/src/components/TeamSheetCommunicationDialog/`** (new, four-file anatomy) — the dialog itself, opened from `MatchCard`'s new action:
- Props: `open`, `onClose`, `clubId`, `match: Match`, `teamsById: Map<string, Team>` (the same map `MatchList` already builds for its card titles — passed straight through, not re-fetched).
- On open, fetches `listMatchSides(clubId, match.id)` (React Query, `enabled: open`), then, for whichever of `homeTeamId`/`awayTeamId` is a real `Team`, `listSquad(clubId, teamId, match.seasonId)` to resolve player names for that side's `MatchSidePlayer` rows and captain/keeper/twelfth-man ids — the same pattern `MatchFormPage`'s `MatchSideTab` already uses, not a new data-fetching shape.
- **Option list** — a single-column list of communication options, built to hold more than one row even though only the first is wired: a "Print as PDF" row (`PictureAsPdfOutlined` icon, a short description, and the scope/print controls below when selected) is the only enabled entry; a second, visually-present-but-disabled "WhatsApp" row and a third disabled "Facebook" row (each labelled "Coming soon") make the intended growth visible to a real user today rather than only living in this spec's Non-goals section — cheap to include, and it directly answers "is this the only channel we'll ever get" for anyone using it.
- **Team scope**, once "Print as PDF" is selected — a `ToggleButtonGroup` (`both` / `home` / `away`, exclusive), mirroring legacy's own `TeamsheetTemplatesDialog` scope toggle:
  - `home`/`away` are each disabled when that side either isn't a real `Team` (`match.homeTeamId`/`awayTeamId` is null — a free-text opponent) or is a real `Team` whose `MatchSide` doesn't exist yet or has zero `players` — this repo's equivalent of legacy's `teamAnnounced` flag, computed rather than stored, since no `MatchSide`-level "announced" boolean exists here (see Non-goals).
  - `both` stays enabled whenever **at least one** side is printable — selecting it prints whichever side(s) are ready and a "Team not yet announced" placeholder section for whichever isn't, exactly matching legacy's `generateTeamsheetPdf`'s own `xi.length === 0` branch.
  - If **neither** side is printable (including the edge case where both sides are free-text opponents), the scope toggle isn't rendered at all — an inline message ("Add players to at least one side's Playing XI before printing a team sheet.") replaces it, and the Print action is disabled.
  - Default selection: `both` if at least one side is printable, else whichever single side is printable.
- **Print action** — a "Print `<scope>`" button (label mirrors legacy's own `Print Both Teams` / `Print <TeamName>` copy), disabled while generating; on click, calls the new PDF util (below), opens the returned object URL in a new tab (`window.open(url, '_blank')`), and closes the dialog. A caught error (e.g. `jsPDF` itself throwing) surfaces as an inline `Alert`/error `Typography` inside the dialog rather than a silent failure or a closed dialog with no feedback — the dialog stays open so the admin can retry.
- Mobile-first: option rows, scope toggle, and the Print button all stack full-width at 375px — no reliance on a wide dialog, matching `docs/standards/frontend.md`'s baseline.

**`ui/src/utils/teamSheetPdf.ts`** (new util module — plain TypeScript, not a `components/**` entry, so it carries no Storybook story; still gets its own Vitest unit test per the Test Plan) — the dedicated, single home for all `jsPDF` usage in this feature, ported from legacy's `ui/src/utils/matchPdf.ts`'s `generateTeamsheetPdf` and *not* scattered inline into `TeamSheetCommunicationDialog`, per this spec's settled tooling decision:
- `generateTeamSheetPdf(match: Match, sides: { team: Team; side: MatchSide | undefined; squad: Player[] }[], scope: 'both' | 'home' | 'away'): Promise<string>` — builds an A4 portrait `jsPDF` doc: a dark header band with the match title (`home vs away`, falling back to each side's free-text name when it has no real `Team`) and a subtitle line (date, venue, league/season name if set — the same fields `matchFields` in `ui/src/utils/matchRecordFields.ts` already surfaces on the card, reused here rather than re-derived); one section per side in scope — a team header bar with the `Team`'s logo (loaded as base64 via a ported `loadImageBase64` helper, falling back to an initial-letter tile exactly as legacy does when there's no logo or it fails to load) and uppercased name, a "Playing XI (n)" count, numbered player rows in batting order with alternating row shading (name only at this spec's original ship — no shirt number, per the data gap above, resolved by `031`, which now prefixes each name with `#<squadJerseyNumber>` when set; `(C)` appended for the captain, `(WK)` for the wicketkeeper), a distinct twelfth-man callout box, and a "Team not yet announced" placeholder row when that side has no players yet; a `checkPage()` helper adding a new page and redrawing the footer band on overflow, matching legacy's own pagination approach.
- **Footer copy diverges from legacy on purpose.** Legacy's footer hard-codes "Cricket Legend · Generated `<date>`" — appropriate for a single-tenant app, not for this platform's white-labelled, per-club deployment (`CLAUDE.md`'s "sold to multiple clubs... white-labelled per club subdomain"). This spec's footer drops the vendor-name line entirely and prints only "Team sheet generated `<date>`" — no club name or logo is available to this dialog today (only each side's `Team.logoUrl`, not the club's own branding), and inventing a new club-branding data fetch just for this footer is out of scope for a "wire up printing" spec. Revisit if a future spec wires the club's own logo/name into this same dialog.
- Returns `URL.createObjectURL(doc.output('blob'))`, matching legacy's own return shape — the caller (`TeamSheetCommunicationDialog`) owns opening it in a new tab, not this util.

**`ui/src/pages/manage/MatchList.tsx`** (existing, edited) — `MatchCard` gains local `dialogOpen` state, the new `secondaryActions` prop described above, and renders `<TeamSheetCommunicationDialog open={dialogOpen} onClose={() => setDialogOpen(false)} clubId={clubId} match={match} teamsById={teamsById} />`. No route change — the dialog is card-local state, not a navigable screen, so `SquadPicker` (which renders `MatchList` with different `editTo`/`title` props per `029`) picks up the same action automatically without any change of its own.

**`ui/package.json`** — adds `jspdf` as a new runtime dependency, confirmed absent from this repo today (`jspdf-autotable` is deliberately *not* added — the ported logic hand-draws every row, exactly matching legacy's own `generateTeamsheetPdf`, which doesn't use `jspdf-autotable` either). This is the settled tooling decision from Problem & Goals, not a new question: `@react-pdf/renderer` is explicitly not used.

## Acceptance Criteria

- A club admin can open "Communicate Team Sheet" from any match's card in `MatchList` (and, by reuse, `SquadPicker`), without disturbing that card's existing Deactivate/Reactivate action.
- Selecting "Print as PDF" and a team scope opens a new browser tab containing a generated A4 PDF listing that scope's side(s) in batting order, with captain/wicketkeeper called out and a distinct twelfth-man callout.
- A side that is a free-text opponent, or a real `Team` with no players added yet, cannot be individually selected as the sole print scope — "Both Teams" remains available and prints a placeholder for that side instead of failing.
- If neither side of a match has anything printable, the dialog says so and disables printing rather than offering a scope choice that can never succeed.
- No new backend endpoint exists for this feature — the PDF is generated entirely client-side from data already served by `029`'s and `026`'s existing endpoints.
- Every other existing `RecordCard` call site (Sponsors, Teams, Players, Sections, Leagues, Seasons, and the rest) continues to compile and behave exactly as before, unmodified by this spec's `secondaryActions` addition.
- The "Communicate Team Sheet" dialog visibly shows at least one additional, clearly-disabled future option (e.g. WhatsApp) alongside "Print as PDF" — a real user can tell this is the first of several channels, not the only one ever planned.

## Rollout Notes

- **This spec ships as its own small PR on top of `029`** (which must already be merged — every entity and endpoint here is `029`'s, unmodified) and `026`/`027`'s `Team.logoUrl`.
- **`jspdf` is a new runtime dependency** — the first time this codebase ports library-driven PDF generation from the legacy app rather than building fresh; keep all `jsPDF` calls confined to `ui/src/utils/teamSheetPdf.ts`, not spread into `TeamSheetCommunicationDialog` or any other component, so a future second PDF (e.g. a squad-list print, mirroring legacy's `generateSquadPdf`) has one obvious place to extend rather than a second competing util. If that future PDF needs `jspdf-autotable`, add it then — this feature's own hand-drawn tables never needed it.
- **Shirt numbers were a known, deliberate gap, not an oversight** — flagged twice in this spec (Non-goals, API Contract) specifically so `docs/roadmap.md` could pick it up as a concrete, scoped future item. **Resolved**: `031-jersey-numbers.md` added the field and closed this gap in the same PR as the rest of its own work, not deferred.
- **WhatsApp text, Facebook text, and image export are the next three natural additions to this same dialog** — the dialog's option-list shape (this spec's UI Requirements) was deliberately built to make adding a fourth enabled row a small, additive change: a new option entry plus whatever generation logic it needs, not a rework of `TeamSheetCommunicationDialog` itself. Each is real, named future work — track individually against this spec (`030`) in `docs/roadmap.md`, not folded into one vague "more sharing options" bullet.
- **The footer's dropped vendor-branding line is a real product decision, not an oversight** — see UI Requirements' dedicated note. If a future spec wants the *generating club's* own name/logo on the PDF (a genuinely nice touch for a white-labelled product), that's new scope: this dialog isn't handed the club's branding today, only each side's `Team.logoUrl`.
- **A human should confirm `docs/roadmap.md` picks up the three still-deferred communication channels** (WhatsApp, Facebook, image export) once this ships, cross-referenced to this spec's own number per this repo's existing "each spec indexes its own deferred items" convention. The shirt-number gap is no longer one of them — resolved by `031-jersey-numbers.md`.
