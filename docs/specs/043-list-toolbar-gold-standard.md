# 043 — List Toolbar Gold Standard Rollout

**Depends on:** `042-match-list-filters-and-search.md` (`ListToolbar`'s `sortToggle` icon-button pattern and the localStorage filter-persistence convention, both generalized here), `041-list-screen-header-actions.md` (`ListToolbar.filters`/`ManageScreenHeader.action`, the pattern this spec's rollout list all already uses and builds alongside), `034-availability-polls-dashboard.md` (its own "no `ListToolbar`" decision — explicitly reversed for that one screen by this spec, see Non-goals).
**Status:** draft.

## Problem & Goals

`042` fixed Match List's toolbar — real cascading Section/League/Season filters, localStorage persistence, and a compact sort icon toggle replacing a `Select` that clipped at the viewport edge once combined with a filter and a Create button. That last fix never made it anywhere else: every other `/manage` list screen still uses `ListToolbar`'s original `sortValue`/`sortOptions`/`onSortChange` `Select` path, which sizes itself to a fixed, non-shrinking `sortMinWidth` (200px default). Reported live, with a screenshot: on `TeamDirectory`, the "Sort by / Name" control is visibly clipped at the right edge of the viewport once `ListToolbar`'s `filters` slot (a `SectionTreeSelect`) is also present. The same fixed-width `Select` renders on every screen in this spec's rollout list, all equally exposed to the same clipping once a filter or a wide viewport-narrowing combination is present.

Separately, every one of these screens' `Select` currently offers exactly one sort option (ascending only) even though six of the seven already contain a fully-written, dead-code `direction === 'desc' ? sorted.reverse() : sorted` branch with no UI path to reach it — the descending option was never wired up, not deliberately omitted.

**Goals**
- Every `/manage` list screen's Sort control uses the same compact icon-toggle pattern `MatchList` already established, eliminating the clipping by construction rather than tuning widths screen by screen.
- `ClubContactList` — the one screen with two sortable fields (Name, Role), not one — gets a small, genuinely new `ListToolbar` capability: a compact field picker paired with the existing direction toggle, still without reintroducing a wide `Select`.
- Every screen with a real, backend-driven filter (`TeamDirectory`, `PlayerList`, and — newly — `AvailabilityPollsDashboard`) persists that filter's selection to `localStorage` the same way `MatchList`'s Section/League/Season already do, via one small shared hook instead of six copies of the same `try/catch` pair.
- `AvailabilityPollsDashboard` moves its bare, standalone `SectionTreeSelect` into a real `ListToolbar` (gaining Search and Sort for the first time), reversing `034`'s explicit "no `ListToolbar`" call for that screen specifically.
- `docs/standards/frontend.md`'s existing "List screen layout" section (added by `041`) is extended to state this Sort/filter-persistence shape as the required pattern for every current and future `/manage` list screen, not just the header/filter-slot shape it already documents.

## Non-goals

- **Converting Search to a real backend query, or adding pagination, for any of these seven screens.** `MatchList` needed real backend search specifically because match history grows unboundedly and the list is already paginated (`listMatches` returns a `Page<Match>`); every screen in this spec's rollout list calls a plain, unpaginated `list*(clubId): Promise<X[]>` endpoint (confirmed by reading `teamApi.ts`, `playerApi.ts`, `leagueApi.ts`, `seasonApi.ts`, `sponsorApi.ts`, `clubContactApi.ts` directly — none return `Page<T>`) — a club's own contacts/sponsors/teams/players/leagues/seasons/open-polls are bounded, club-scoped lists, not an ever-growing history. Search on every screen here stays exactly what it already is: client-side substring filtering over an already-fully-loaded list. **Flagged for whoever reviews this spec to confirm or override** — if a specific club's data volume on one of these screens turns out to be a real problem in practice, that is its own future spec (client-side substring filtering plus, likely, real pagination together — not backend search bolted onto an unpaginated endpoint).
- **Cascading/narrowing filters against each other**, `MatchList`'s `filter-options`-style endpoint. None of these seven screens has more than one filter dimension today (`TeamDirectory`/`PlayerList`/the newly-migrated `AvailabilityPollsDashboard` each have exactly one: Section) — there is nothing for a second filter to narrow against yet. `041`'s own Non-goals already named "a generic multi-filter `ListToolbar.filters` array" as real, separate future work once a screen actually needs two simultaneous filters; that trigger still hasn't been hit, so nothing changes about `filters` itself here beyond what persistence needs.
- **`ClubContactList`'s Role field gaining its own dedicated filter dropdown.** Only its *sort* gains a field picker (Name/Role) — filtering the list down to one role is a different, unrequested feature.
- **`/admin` (platform-admin) screens** (`ProductList`, `ClubList`, `SubscriptionList`). `041` already scoped these out for the same reason (no `ManageScreenHeader` shell today) — unchanged here.
- **`SponsorContactList`.** Also scoped out by `041` (nested contacts-within-a-sponsor list, no `ManageScreenHeader` of its own) — unaffected by this spec for the same reason.
- **Any change to what each screen's Search box actually matches against** (still name/label substring, per screen, exactly as today) — only the Sort control's shape and, for filtered screens, persistence change.
- **Backfilling `034`'s originally-deferred create action for Availability Polls.** That screen still has no create action of its own (an availability poll is created from a Match's own Availability tab, per `032`) — moving it onto `ListToolbar` doesn't add a `createLabel`/`onCreate` or a `ManageScreenHeader.action` it didn't already have.

## User Stories

- As a club admin on any `/manage` list screen, the Sort control never clips or overlaps another control, at any viewport width, because it's a small icon button rather than a fixed-width dropdown.
- As a club admin on Club Contacts, I can sort by Name or by Role, and toggle either one between ascending and descending, without the control taking up meaningfully more width than a single-field sort would.
- As a club admin on Teams or Players, my chosen Section filter is still applied when I come back to the screen later — it doesn't silently reset to "All sections" every time, the same behavior Matches already has.
- As a club admin, Availability Polls has a real Search box and a working Sort for the first time, and my Section filter choice there persists too, matching every other list screen.
- As a developer building the next `/manage` list screen, `docs/standards/frontend.md` states exactly which Sort control to use and when a filter needs to persist, rather than me needing to reverse-engineer it from `MatchList`'s source.

## Data Model Changes

None — purely a frontend, presentational-layer spec. No entity, field, migration, or endpoint changes; every screen's existing (unpaginated, client-side-filtered) data-fetching shape is unchanged.

## API Contract

None — no endpoint touched. Every filter that already re-fetches from the backend today (`TeamDirectory`'s and `PlayerList`'s `sectionId` param, `AvailabilityPollsDashboard`'s existing `listOpenPolls(..., {sectionId})`) keeps doing exactly that; this spec only adds persistence of the *choice*, not a new query shape.

## UI Requirements

**`ui/src/components/ListToolbar/ListToolbar.tsx`** (existing, edited):
- New optional props, layered onto the existing `sortToggle` (all three passed together or not at all): `sortFieldOptions?: { value: string; label: string }[]`, `sortField?: string`, `onSortFieldChange?: (value: string) => void`. Rendered only when `sortToggle` is present **and** `sortFieldOptions` has more than one entry — a compact field-picker (an `IconButton` opening a small `Menu` of `MenuItem`s, one per field; the currently-active field's short label shown next to the existing direction arrow, e.g. "Name ↑") positioned immediately before `sortToggle`'s own arrow button in the same trailing flex group. When `sortFieldOptions` is omitted, has zero, or has exactly one entry, nothing new renders and `sortToggle`'s existing single-arrow-button behavior (`MatchList`'s current five — soon six, with the `Team*`/`Player`/`Sponsor`/`League`/`Season` screens below — single-field callers) is byte-for-byte unchanged. This keeps the field-picker strictly additive: it composes with `sortToggle`'s existing direction semantics (which stay field-agnostic — "toggle whichever field is currently active") rather than replacing or duplicating them.
- No change to the existing `sortValue`/`sortOptions`/`onSortChange` `Select` rendering path itself — every call site below stops using it, but the path remains for any future screen with a legitimate reason to need a full dropdown (e.g. more than a small handful of sortable fields), not deleted outright.

**New shared hook — `ui/src/hooks/usePersistedListFilters.ts`** (new file; `ui/src/hooks/` does not exist yet in this codebase, this is its first entry). Generalizes the ad hoc, per-screen `try/catch`-wrapped `localStorage.getItem`/`setItem` pair `MatchList.tsx` introduced in `042` (justified there as a one-off, first-and-only use) — this rollout is about to need the identical pattern on three more screens (`TeamDirectory`, `PlayerList`, `AvailabilityPollsDashboard`), which is the real "rule of three-plus" trigger for extracting it now rather than copying it a fourth time. Shape: `usePersistedListFilters<T extends Record<string, unknown>>(storageKey: string, defaults: T): [T, (next: Partial<T>) => void]` — reads and `JSON.parse`s once on mount (falling back silently to `defaults` on a missing key, a parse failure, or a blocked/unavailable `localStorage`), and `JSON.stringify`s the merged state back on every change; every read and write individually wrapped in its own `try/catch`, matching `042`'s own established guard shape exactly. Never touches Search — callers keep `search` as its own separate, non-persisted `useState`, exactly as `MatchList` already does.

**Six list screens migrated onto `sortToggle`** (single field, activating each one's already-written but previously unreachable `direction === 'desc' ? sorted.reverse() : sorted` branch):
- `ui/src/pages/manage/SponsorList.tsx`, `LeagueList.tsx`, `SeasonList.tsx`, `PlayerList.tsx`, `TeamDirectory.tsx`, `TeamList.tsx` — each screen's `sortValue`/`sortOptions`/`onSortChange` triplet is replaced with `sortToggle={{ value: sort.endsWith(',asc') ? 'asc' : 'desc', ascLabel: '<Field>, A to Z', descLabel: '<Field>, Z to A', onToggle: () => setSort(sort.endsWith(',asc') ? '<field>,desc' : '<field>,asc') }}` (field name/labels per screen: Name for Sponsor/Team×2/Player, League name for League, Label for Season). `SORT_OPTIONS` constants are removed once nothing references them for rendering (the `sort` state's own two possible string values stay as-is, only the control changes).

**`ui/src/pages/manage/ClubContactList.tsx`** (existing, edited):
- `sortValue`/`sortOptions`/`onSortChange` replaced with both `sortToggle` (direction of whichever field is active) **and** the new `sortFieldOptions={[{value:'name',label:'Name'},{value:'role',label:'Role'}]}`/`sortField`/`onSortFieldChange` triplet. Selecting a field via the picker keeps the current direction; toggling direction keeps the current field — `sort` state's existing `'name,asc' | 'name,desc' | 'role,asc' | 'role,desc'` shape is unchanged, only how the two parts are edited changes.

**`ui/src/pages/manage/TeamDirectory.tsx` and `PlayerList.tsx`** (existing, edited): their existing Section filter (already a real, backend-driven `sectionId` query param) is wired through the new `usePersistedListFilters` hook (`storageKey`: `teamDirectory:filters:${clubId}` / `playerList:filters:${clubId}`, `defaults: { sectionId: null }`), mirroring `MatchList`'s own persisted-filters convention — on mount, a previously-chosen Section is reapplied; Search is never persisted, exactly as today.

**`ui/src/pages/manage/AvailabilityPollsDashboard.tsx`** (existing, edited — the one screen gaining new capability, not just a control swap):
- Gains `ManageScreenHeader`'s existing header shape is already in place; its bare `Box sx={{maxWidth:360}}`-wrapped `SectionTreeSelect` is replaced with a real `ListToolbar`: `searchValue`/`onSearchChange` (new client-side substring `useState`, matching every other screen's shape, filtering on the resolved home/away team names `PollCard`'s own `sideDisplayName` already computes — no new field), `filters` holding the existing `SectionTreeSelect` (now wired through `usePersistedListFilters`, `storageKey`: `availabilityPolls:filters:${clubId}`, `defaults: { sectionId: null }`), and a new `sortToggle` on match date (`value`/`ascLabel`/`descLabel`/`onToggle` over the poll list's own `matchDate` field, mirroring `MatchList`'s own default-ascending convention from `042` — soonest-upcoming poll first) — client-side sort, since `listOpenPolls` is unpaginated like every other screen here. No `createLabel`/`onCreate` and no `ManageScreenHeader.action` — this screen still has no create action of its own (Non-goals).

**`docs/standards/frontend.md`**: the existing "List screen layout" section (added by `041`) gains explicit language that every `/manage` list screen's Sort uses `ListToolbar`'s `sortToggle` (the `sortFieldOptions` variant when more than one field is sortable), never the `sortValue`/`sortOptions` `Select` path, and that any filter backed by a real server-side query param persists via `usePersistedListFilters` — pointing at this spec and `042` as the worked examples, the same way that section already points at `041` for the header/filter-slot shape.

Mobile-first: the field-picker + direction-arrow pair verified at 375px next to Create/no-Create in every combination this rollout produces; `AvailabilityPollsDashboard`'s new Search/filters/sort verified at 375px against `ListToolbar`'s existing stack-to-full-width-rows behavior — no new breakpoint logic needed, this is `ListToolbar`'s own existing responsive shape doing its job on a screen that never used it before.

## Acceptance Criteria

- Every one of the seven listed screens' Sort control is a compact icon toggle, never a fixed-width `Select` — confirmed at 375px, 768px, and desktop widths with no clipping or overlap with any other toolbar control.
- Club Contacts can sort by Name or Role, each independently toggleable between ascending and descending, via controls that together stay meaningfully narrower than the old single-field `Select` was.
- Teams' and Players' Section filter selection survives a page reload; Availability Polls' Section filter does too, for the first time.
- Availability Polls has a working Search box and Sort control for the first time, composed from the same `ListToolbar` every other list screen uses.
- `docs/standards/frontend.md` states the Sort/filter-persistence rule explicitly enough that a new list screen built from reading only that file (not `MatchList`'s source) gets it right the first time.
- No backend change, no new dependency, no change to any endpoint, entity, or non-persisted Search behavior.

## Rollout Notes

- **This spec ships as its own PR on top of `042`** (already merged) — frontend-only, no backend involvement, no migration, mirroring `041`'s own shape.
- **The Search-stays-client-side call is a recommendation, not a foregone conclusion** — see Non-goals. Confirm or override during spec review before `/plan-feature` runs against this.
- **`usePersistedListFilters` is a new pattern in this codebase** (first file under a new `ui/src/hooks/` directory) — same "flag it, don't silently invent a convention" treatment `042` gave `localStorage`/`Specification`/`freeSolo` the first time each showed up.
- **`041`'s own deferred "generic multi-filter `ListToolbar.filters` array" item is still deferred** — nothing in this spec triggers it (see Non-goals); don't conflate the new *sort* field-picker with a second simultaneous *filter*, they're unrelated capabilities that happen to land in the same PR.
- **A human should update `docs/roadmap.md`** once this ships, resolving any prior entry that referenced Match's toolbar work as Match-specific and noting the pattern is now the documented cross-screen standard.
