# 050 — League Schedule & Fixtures

**Depends on:** `029-league-management.md` (`League`, `Season`, `Match`, `LeagueAffiliation`, `MatchForm` — the entities and components this spec amends/extends, and the club-owned-only architectural decision, see Non-goals below, that this spec deliberately stays inside of), `036-view-first-record-detail-screens.md` (`LeagueDetailPage`'s existing view-screen shape — Details/Affiliations sections — which gains a new Fixtures section here), `049-record-list-edit-action-rollout.md` (most recent touch to `LeagueList`'s and `LeagueDetailPage`'s `RecordCard`s, adding `editTo` alongside `viewTo` — confirms nothing in this spec conflicts with that rollout: the badge/footer-action additions below are new to the same card, not a change to its View/Edit footer).
**Status:** draft.

## Problem & Goals

`029` built club-owned `League`/`Season`/`Match`/`LeagueAffiliation` administration, and its own Non-goals deliberately deferred "vendor-run, cross-club league administration" — a `League` not owned by a single club, with a shared schedule/standings across multiple clubs — as an amendment to `001`'s ADR-02. `docs/roadmap.md`'s "Blocked on the full tenancy model" section still lists this as a real, unscheduled future item. **This spec does not resolve that item.** It was discussed directly with the user and deliberately stays on the club-owned side of that fork: real leagues span many clubs, but not every opposing club is registered on this platform, so a club needs to record its own fixtures against opponents whether or not those opponents exist in the system. That mechanism already exists — `Match.homeTeamId`/`homeTeamName` (exactly one set) and `awayTeamId`/`awayTeamName` (exactly one set), a real `Team` OR a free-text opponent name, no `Team` record required — and `MatchController`'s list endpoint already accepts `leagueId`/`seasonId` filters. What's still missing, entirely within `029`'s existing club-owned model, is: a quick read of how many teams are actually entered in a league this season (today only visible by opening the Affiliations tab and counting), a visual identity for a free-text opponent (today no avatar at all — a blank/generic icon only), a fast way to schedule a match already scoped to a specific league+season (today the standalone match form requires re-picking both from scratch even when starting from that league's own screen), and a friendly, reusable read-only fixture list for a league+season (today only the generic, paginated `MatchList` exists, filtered manually).

A club also needs a place to keep that season's Playing Conditions document (the competition rules for that specific league+season) close to the league itself, and a fast, at-a-glance way to tell — from the League's own card, without opening it — which season a league's numbers belong to, and whether that document has even been uploaded yet. Today `LeagueDto` carries no season context at all outside the Teams tab, and there is no PDF/document upload path anywhere in this codebase — confirmed by inspection: `MediaUpload` (`ui/src/components/MediaUpload/MediaUpload.tsx`) and its backend counterpart `MediaServiceImpl` are both hard-restricted to a fixed image allowlist (`image/png`/`image/jpeg`/`image/webp`), client- and server-side.

**Goals**
- A club admin glancing at a `League`'s `RecordCard` sees, at a glance, how many distinct teams are affiliated for the league's current season, without opening the Affiliations tab.
- The "Affiliations" label used on `LeagueFormPage`'s tab and `LeagueDetailPage`'s section is renamed to "Teams" — a plainer, more accurate label for what a club admin is actually looking at (a list of teams entered in this league).
- A club admin capturing a `Match` against a free-text ("external") opponent can attach a small logo/crest to that side, the same visual polish a real `Team` already gets via `Team.logoUrl`.
- A club admin working from a `League`'s own edit screen can add a new `Match` for that league+season without re-selecting League and Season by hand.
- A new, reusable, presentational "League Fixtures" component exists — date/venue/home-vs-away with avatars — built once so a not-yet-built player-facing view can reuse it later without rework, and used immediately by `LeagueDetailPage` to show a read-only fixture list for the page's own selected season.
- A club admin can upload a Playing Conditions PDF for a league+season from the same screen where they already manage that league's schedule, and replace it later by uploading again — no version history, just the current document.
- A club admin glancing at a League's `RecordCard` sees which season its team-count reflects (a season-label badge alongside the team-count badge), and, when that season has a Playing Conditions document uploaded, a direct action right there on the card to open it in the browser — no need to open the league at all just to check.

## Non-goals

- **No cross-club/shared/vendor-run `League`.** Every `League` stays club-owned, exactly as `029` left it. This spec does not touch `001` ADR-02 or `029`'s own Non-goals any further — `docs/roadmap.md`'s "Vendor-run league administration" item stays exactly as deferred as it is today. Confirmed directly with the user after discussing the cross-club alternative (see Problem & Goals).
- **No results or scores.** Fixture list only this pass — date, venue, teams, avatars. No innings, no score, no outcome field, no points/standings table. `029`'s own Non-goals already named this as a fast-follow "Phase 1" spec; this spec is not that spec. Explicitly confirmed by the user.
- **No external-league-system link field** (e.g. a CricClubs URL, provider selector, or API key). Raised and then explicitly deferred by the user during scoping: a provider/API-key integration model needs its own spec, not a simple URL field bolted onto `League`. Not to be conflated with `League.source = EXTERNAL` (`029`), which already means something different — a full future sync — and stays exactly as unbuilt as `029` left it. Flagged in Rollout Notes as real, distinct future scope.
- **No player-facing screen, route, or player auth.** The new League Fixtures component is built for future reuse only, per `docs/roadmap.md`'s still-open "player profile/results/fixtures views" item — nothing player-visible ships in this spec. The component itself is presentational only (see UI Requirements) specifically so a later spec can drop it into a player-facing context without rework.
- **No change to `MatchList.tsx`'s own card rendering.** Its cards keep their existing generic sport-icon avatar (`SportsCricketOutlinedIcon`) unchanged; the new `homeTeamLogoUrl`/`awayTeamLogoUrl` fields are consumed only by the new League Fixtures component and `MatchForm`'s capture UI, not retrofitted onto every existing `Match` display (`MatchList`, `MatchDetailPage`, `SquadPicker`, team-sheet PDF/WhatsApp exports).
- **No change to `Season`, `LeagueAffiliation` table shape, or the club-owned authorization model.** `assertCanAdministerAnySection`/`canAccessClub`/`canAdministerClub` stay exactly as `035`/`042`/`029` left them — every endpoint this spec touches or adds reuses existing authorization, no new scope check.
- **No bulk fixture import, auto-scheduling, or round-robin generation.** Matches are still entered one at a time, by hand — unchanged from `029`.
- **No retroactive backfill of `homeTeamLogoUrl`/`awayTeamLogoUrl` on existing `Match` rows.** The two new columns are nullable and simply blank on every `Match` created before this spec ships; the League Fixtures component and `MatchForm` both already treat a missing logo as "no avatar image, fall back to initials/icon" (see UI Requirements) — no migration-time data fix needed.
- **Playing Conditions is NOT a versioned document history.** Only the single, latest upload for a given `(league, season)` pair is ever kept — a re-upload replaces `LeaguePlayingConditions.document_url`/`uploaded_at`/`uploaded_by` in place (an upsert against the row's unique `(league_id, season_id)` key), the same "no history, just current state" posture `Sponsor.logoUrl`/`Team.logoUrl` already have. No document list, no prior-version download, no audit trail beyond that single row's own `uploaded_at`/`uploaded_by`.
- **No in-app PDF preview/viewer.** Clicking a "Playing Conditions" action opens the document in the browser's own native PDF viewer via `window.open(url, '_blank')` — the exact existing mechanism `MatchList.tsx`'s "Team Sheet" action already uses for a generated PDF (`handlePrint`/`window.open`, confirmed in code). No embedded PDF.js-style in-app viewer is built.

## User Stories

- As a club admin scanning my club's Leagues list, I can see how many distinct teams are affiliated to each league for its current season, without opening that league's own Teams tab.
- As a club admin on a `League`'s edit or view screen, I see a "Teams" tab/section instead of "Affiliations" — same content, plainer label.
- As a club admin scheduling a match against an opponent with no account on this platform, I can attach a small logo for that opponent, the same way I already can for one of my own `Team`s.
- As a club admin on a `League`'s edit screen, I can jump straight to "Add Match" for that league and season, without re-picking League and Season on the standalone match form.
- As a club admin on a `League`'s view screen, I can see a read-only, friendly list of that league's scheduled matches for a selected season — date, venue, both sides' names and avatars — without navigating to the generic, paginated Matches list and filtering it by hand.
- As a club admin editing a League, I can upload a Playing Conditions PDF for a specific season from that same screen, and replace it later by uploading a new one — the prior document isn't kept.
- As a club admin scanning my club's Leagues list, I can see which season each league's team-count reflects, via a season-label badge on its card.
- As a club admin scanning my club's Leagues list, I can open a league's current season's Playing Conditions document directly from its card, in the browser's own PDF viewer, when one has been uploaded — and I don't see that action at all when one hasn't.

## Data Model Changes

`Season` and `LeagueAffiliation`'s own table shapes are **unchanged** by this spec — every field, index, and constraint `029` gave them stays exactly as-is. `League`'s own table shape is also unchanged (every addition below is either a new sibling table or a read-time computed field on the DTO, never a new column on `league` itself). Three changes:

**`Match` gains two nullable columns** — an opponent's logo, meaningful only alongside the matching free-text name (mirrors the existing `homeTeamId`/`homeTeamName` exclusivity convention: when a side is a real `Team`, its logo already comes from `Team.logoUrl` resolved via the id, so a `*TeamLogoUrl` column is never populated alongside the matching `*TeamId`):

```sql
-- backend/src/main/resources/db/changelog/v1/025-add-match-external-opponent-logo.sql

ALTER TABLE match ADD COLUMN home_team_logo_url VARCHAR(1024);
ALTER TABLE match ADD COLUMN away_team_logo_url VARCHAR(1024);
```

Service-layer validation rule (same posture as `029`'s existing `validateExactlyOneOfIdOrName`, a `ValidationException`, `400`, not a DB constraint — matching this codebase's existing precedent of a clean service-layer message ahead of any DB-level check): `homeTeamLogoUrl` may only be set when `homeTeamName` is set (i.e. `homeTeamId` is null), and likewise for `awayTeamLogoUrl`/`awayTeamName`/`awayTeamId`. Add to `MatchDto`, `CreateMatchRequest`, `UpdateMatchRequest`.

**New entity — `LeaguePlayingConditions`**, one PDF document per `(league, season)` — genuinely new persisted state, not a field on `League`/`Season` themselves, since a league's playing conditions differ by season (this year's rules vs. next year's) while the `League`/`Season` rows themselves are reused across many affiliations and matches:

```
LeaguePlayingConditions {
    uuid       id
    uuid       league_id     -- FK league.id, not null
    uuid       season_id     -- FK season.id, not null
    string     document_url  -- not null — the uploaded PDF's URL, the same "/media/{filename}"-style
                               -- shape MediaServiceImpl already returns for an image, reused here for
                               -- a PDF by the new upload path below
    timestamp  uploaded_at   -- not null
    uuid       uploaded_by   -- nullable
}
```

Unique on `(league_id, season_id)` — one document per league+season. **Re-upload replaces the existing row's `document_url`/`uploaded_at`/`uploaded_by` in place (an upsert, never a second row)** — deliberately no version history (see Non-goals). Same-club consistency, same posture as `Match`'s existing `validateLeagueAndSeason`: `league.club_id` and `season.club_id` must both equal the `clubId` resolved from the URL, or the reference reads as `NotFoundException` (`404`) — the same cross-tenant-isolation posture as every other nested reference in this feature area, not a `400`.

**Migration** (next sequential file after this spec's own Match-logo migration above):

```sql
-- backend/src/main/resources/db/changelog/v1/026-add-league-playing-conditions.sql

CREATE TABLE league_playing_conditions (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    league_id     UUID NOT NULL REFERENCES league(id),
    season_id     UUID NOT NULL REFERENCES season(id),
    document_url  VARCHAR(1024) NOT NULL,
    uploaded_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    uploaded_by   UUID,
    UNIQUE (league_id, season_id)
);

CREATE INDEX ix_league_playing_conditions_league ON league_playing_conditions(league_id);
CREATE INDEX ix_league_playing_conditions_season ON league_playing_conditions(season_id);
```

**`LeagueDto` gains three computed (non-persisted) fields**, all resolved together in the same `LeagueServiceImpl` list/read query change — one round trip, not three:
- `currentSeasonTeamCount: int` — the count of distinct teams affiliated to that league via `LeagueAffiliation` for the club's own *current* season. `0` when the club has zero `Season`s.
- `currentSeasonLabel: String` (nullable) — the resolved current `Season`'s own `label` (e.g. `"2026/2027"`). `null` when the club has zero `Season`s.
- `currentSeasonPlayingConditionsUrl: String` (nullable) — the `documentUrl` of that league's `LeaguePlayingConditions` row for the current season, when one exists. `null` when the club has zero `Season`s, or a current season exists but no document has been uploaded for this `(league, season)` pair yet.

All three share the identical "current season" resolution rule `ui/src/utils/defaultSeason.ts`'s `pickDefaultSeasonId` already uses client-side (the club's `Season` whose `[startDate, endDate]` range contains today, else the club's most-recently-created `Season`) — ported to Java once in `LeagueServiceImpl`'s list/read path rather than reinvented per field; cite `pickDefaultSeasonId` explicitly in the Java implementation's own doc comment so the two never drift into two different definitions of "current season." No new column on `League` itself — this is a read-time computation only, backed by a repository query joining `league_affiliation`/`league_playing_conditions` against the club's resolved current `Season` id (exact query/method shape left to the plan).

## UI Requirements

**1. Two badges on `LeagueList.tsx`'s `RecordCard`** (and anywhere else a League `RecordCard` renders — confirmed by inspection to be `LeagueList.tsx`'s own card only today): the current season's team count and its label, both via `RecordCard`'s existing `badges?: RecordCardBadge[]` array prop (`docs/specs/040-announce-team.md`'s precedent, already used by `MatchList.tsx` for its own multiple badges) — reused as-is, no new `RecordCard` prop. A new exported helper, `leagueSeasonBadges(league)` (alongside the existing `badgeFor`/`leagueRecordFields`/`leagueChips` in `LeagueList.tsx`), returns up to two `RecordCardBadge` entries: a team-count badge (e.g. `${league.currentSeasonTeamCount} teams`) always present, and a season-label badge (`league.currentSeasonLabel`) only when the club has a current season at all (i.e. `currentSeasonLabel` is non-null) — omitted entirely otherwise rather than rendered blank. Rendered via `badges={leagueSeasonBadges(league)}`, coexisting with the card's existing single `badge` (Active/Inactive, `badgeFor`) exactly as `040`'s `badge`+`badges` co-rendering already supports. `leagueRecordFields()`'s existing "Playing XI size"/"Age range" fields are unchanged — the team count moves to a badge instead of a field, per this amendment, rather than appearing in both places.

**2. Rename "Affiliations" → "Teams".** Two call sites, confirmed by direct inspection (both are the exact literal string `'Affiliations'`, nothing else on either line changes):
- `ui/src/pages/manage/LeagueFormPage.tsx` line 234, `<Tab label="Affiliations" />` → `<Tab label="Teams" />`.
- `ui/src/pages/manage/LeagueDetailPage.tsx` line 128, `heading: 'Affiliations'` → `heading: 'Teams'`.

Pure label rename — no route, prop name, query key, or behavior changes on either screen; `affiliationsQuery`/`affiliationsForSeason`/`AffiliatedTeamCard` and every other internal identifier stay as-is (an internal name, not user-facing copy).

**3. External-opponent avatar on `Match`.** In `ui/src/components/MatchForm/MatchForm.tsx`, when a side's `ToggleButtonGroup` is set to "External opponent," render a `MediaUpload` field beneath that side's name `Input` — `<MediaUpload label="Logo" value={homeTeamLogoUrl} onUploaded={(url) => setValues((prev) => ({ ...prev, homeTeamLogoUrl: url }))} variant="logo" namespace="manage" />` (and the mirrored `away` version) — copying `TeamForm.tsx`'s own existing `<MediaUpload label="Logo" value={logoUrl} onUploaded={...} variant="logo" namespace="manage" />` call verbatim as precedent, not rebuilding upload UI from scratch. Optional — a fixture can be captured with no logo, matching `MediaUpload`'s own existing "no value" empty state. Switching a side's toggle from "External opponent" back to "One of our teams" clears that side's `*TeamLogoUrl` from form state (mirrors the existing behavior of clearing `*TeamName` on the same toggle). `MatchPayload` (`ui/src/api/matchApi.ts`) gains `homeTeamLogoUrl?: string | null` / `awayTeamLogoUrl?: string | null`.

**4. New "Schedule" tab on `LeagueFormPage.tsx`.** A third `Tab` (`<Tab label="Details" /> <Tab label="Teams" /> <Tab label="Schedule" />`), scoped to the tab's own selected season — reuses the exact same `selectedSeasonId`/`Select` pattern the "Teams" tab already has (`affiliationsQuery`'s existing `selectedSeasonId` state and default-via-`pickDefaultSeasonId` effect, shared across all season-scoped tabs on this page rather than a second, independent copy). Lists this league's `Match`es for the selected season via the existing `listMatches(clubId, { page: 0, leagueId, seasonId })` call (already supports this filter combination, no new endpoint) rendered via the new League Fixtures component (item 6 below) rather than a third, bespoke rendering. An "Add Match" action pre-fills League and Season so the admin doesn't re-pick either by hand; exact prefill mechanism (router `state`, query params on `/manage/fixtures/matches/new`, or an inline embedded `MatchForm` on this tab itself, matching how some other tabs on this codebase embed a form directly rather than navigating away) is left to the plan — state the requirement, not the mechanism. Whichever is chosen must reuse `ui/src/components/MatchForm/` as-is (its existing four-file anatomy — `MatchForm.tsx`/`.test.tsx`/`.stories.tsx`/`index.ts`), not a second, parallel match-creation form. **This same tab is also the Playing Conditions capture surface** — see item 5 immediately below; both are per-`(league, season)` concerns, so a fourth tab isn't warranted for one PDF field. This placement is the recommendation, not a mandate — final call left to the plan.

**5. New reusable `ui/src/components/DocumentUpload/` component** (four-file anatomy — `.tsx`, `.test.tsx`, `.stories.tsx`, `index.ts`), flagged for the same Claude Design pass as `LeagueFixtures` (item 6) — a genuinely new visual pattern, not a variant of `MediaUpload`. A sibling to `MediaUpload`, not a new `variant` on it: the two have almost nothing in common visually (there's no image to preview for a PDF), so overloading `MediaUpload`'s existing image-specific rendering (its preview box, its `DIMENSIONS` map) would bend that component around a case it wasn't built for. `DocumentUpload` instead shows the current document's filename (or "No document uploaded yet") plus an "Upload"/"Replace" button (same `Button` variant convention `MediaUpload` already uses) and, when a document exists, a "View" action opening it via `window.open(url, '_blank')` — the same mechanism `MatchList.tsx`'s "Team Sheet" action already uses (see Non-goals) — rather than a forced download. Client-side MIME allowlist restricted to `application/pdf` only (mirroring `MediaUpload`'s own client-side allowlist pattern, but for one type instead of three), calling a new `uploadPlayingConditions` function (item 10 below) rather than `uploadMedia`/`uploadManagedMedia`. Rendered on `LeagueFormPage.tsx`'s new Schedule tab (item 4), scoped to that tab's own selected season, fetching the current document via the new `GET .../playing-conditions` endpoint (treating its `404` as "nothing uploaded yet," not an error state) and re-fetching after a successful upload.

**6. New reusable `ui/src/components/LeagueFixtures/` component** (four-file anatomy — `.tsx`, `.test.tsx`, `.stories.tsx`, `index.ts`), flagged for a Claude Design pass before build (`docs/workflow.md` Step 2, same precedent `029`/`036` set for `PlayingXiBuilder`/`RecordDetailScreen`) since this is a genuinely new visual list pattern (an avatar-pair "vs" row), not a near-miss on `RecordCard`. A friendly, read-only presentation of a league+season's matches — date, venue, home vs away, each side's name and avatar (`Team.logoUrl` resolved via `homeTeamId`/`awayTeamId` for a real team, this spec's new `homeTeamLogoUrl`/`awayTeamLogoUrl` for an external opponent, falling back to initials/a generic icon when neither is set — same fallback posture `RecordCard`'s own avatar slot already has). **Deliberately presentational**: accepts an already-fetched `matches: Match[]` (plus whatever team lookup it needs to resolve a real side's name/logo, e.g. a `teamsById: Map<string, Team>` prop) and renders; it does **not** call `listMatches` or any other API itself, so a future player-facing context — which may fetch through a different, not-yet-built API surface entirely — can reuse it unmodified. The data-fetching wrapper lives on the two callers: the new Schedule tab on `LeagueFormPage.tsx` (item 4) and a new Fixtures section on `LeagueDetailPage.tsx` (item 7), each independently calling `listMatches`/`listTeamsForClub` and passing the results down. No results/scores rendered — date, venue, teams, avatars only, matching this spec's own Non-goals.

**7. New Fixtures section on `LeagueDetailPage.tsx`.** A third section (`Details`, `Teams` — renamed per item 2, `Fixtures`) using the same season-selector pattern its existing Teams section already has (`selectedSeasonId`/`Select`, defaulted via `pickDefaultSeasonId`), rendering `LeagueFixtures` against `listMatches(clubId, { page: 0, leagueId: league.id, seasonId: selectedSeasonId })` and `listTeamsForClub(clubId)` (already fetched by this page for the Teams section — reused, not re-fetched a second time).

**8. "Playing Conditions" action on the League `RecordCard`'s footer**, visible only when `league.currentSeasonPlayingConditionsUrl` is non-null. Uses `RecordCard`'s existing `secondaryActions?: RecordCardSecondaryAction[]` slot — a plain, non-async entry (`pending: false`) whose `onClick` calls `window.open(league.currentSeasonPlayingConditionsUrl, '_blank')`, opening the PDF in the browser's own viewer, not a forced download — the exact same mechanism `MatchList.tsx`'s "Team Sheet" `secondaryActions` entry already uses (`handlePrint`, `window.open(url, '_blank')`, confirmed in code), reused verbatim, not reinvented. Rendered conditionally (spread into `secondaryActions` only when the URL is present) alongside the card's existing View/Edit footer actions (`049`) — no change to those.

**9. `ui/src/api/leagueApi.ts`** — `League` interface gains `currentSeasonTeamCount: number`, `currentSeasonLabel: string | null`, `currentSeasonPlayingConditionsUrl: string | null`.

**10. New `ui/src/api/leaguePlayingConditionsApi.ts`** (one file per backend resource, per `docs/standards/frontend.md`) — `getPlayingConditions(clubId, leagueId, seasonId)` (treats a `404` as "no document," returning `null` rather than throwing, so callers don't need a try/catch per call site) and `uploadPlayingConditions(clubId, leagueId, seasonId, file)` (multipart, mirroring `uploadMedia`/`uploadManagedMedia`'s existing `FormData`/`multipart/form-data` shape in `ui/src/api/mediaApi.ts`).

Mobile-first, per `docs/standards/frontend.md`: `LeagueFixtures`' home-vs-away row must stack or wrap (not force horizontal scroll) at 375px; `MatchForm`'s new per-side `MediaUpload` field sits beneath that side's existing toggle/inputs in the same single-column flow already used at that viewport; `DocumentUpload`'s filename/Upload/View row must also stack at 375px rather than overflow; `RecordCard`'s existing footer already wraps (`flexWrap: 'wrap'`, per `049`) so the new conditional Playing Conditions action needs no new layout handling.

## Acceptance Criteria

- A club admin viewing the Leagues list sees each league's card display the count of distinct teams affiliated for that league's current season, and the current season's own label, as two badges.
- `LeagueFormPage`'s tab and `LeagueDetailPage`'s section both read "Teams," not "Affiliations" — no other behavior on either screen changes.
- A club admin capturing a match against a free-text opponent can optionally attach a logo for that opponent via the same `MediaUpload` control `TeamForm` already uses.
- A club admin on a League's edit screen can start "Add Match" with that league and season already selected, without hand-picking either on the resulting form.
- A club admin on a League's view screen can see a read-only, season-scoped list of that league's matches — date, venue, both sides' names and avatars, no results/scores — via the new Fixtures section.
- The new `LeagueFixtures` component renders correctly given only props (a match list, a team lookup) with no data-fetching of its own, confirmed by its component test using mocked props rather than a mocked API call.
- A club admin can upload a Playing Conditions PDF for a league+season from the League's Schedule tab, and re-uploading for the same league+season replaces the prior document rather than creating a second one.
- A club admin sees a "Playing Conditions" action on a league's `RecordCard` only when the current season has a document uploaded, and clicking it opens the PDF in a new browser tab via the browser's own viewer, not a forced download.
- `MatchList.tsx`'s own card rendering is unchanged — still the generic sport-icon avatar, no `homeTeamLogoUrl`/`awayTeamLogoUrl` consumed there.
- No `League` becomes cross-club; every `League`/`Match` created or edited through this spec's changes stays exactly as club-owned as `029` left it.

## Rollout Notes

- **This spec deliberately does not touch `001` ADR-02 or `docs/roadmap.md`'s "Vendor-run league administration" item.** Confirmed directly with the user during scoping — real multi-club leagues are handled today via `Match`'s existing free-text-opponent mechanism, not a shared cross-club `League` entity; that remains real, unscheduled future work, unchanged by this spec.
- **An external-league-provider integration (e.g. CricClubs, with API keys/links) is real, distinct future scope, not built here.** The user raised and then explicitly deferred this during scoping: "this actually requires a spec... let's ignore this for now." A human should add this as a new, explicitly named item under `docs/roadmap.md`'s existing `League.source = EXTERNAL` / CricClubs-sync entry (`029`'s own Rollout Notes' "Phase 2") once this spec ships — framed as a provider/API-key integration model, not a simple URL field, and kept distinct from `League.source = EXTERNAL`'s existing (different) meaning.
- **Results/scores/standings remain `029`'s own still-open "Phase 1" item**, unresolved by this spec. This spec's `LeagueFixtures` component was deliberately built to make that future work easier (a fixture list already exists to extend with a score once that spec is written), not to preempt it.
- **The reusable `LeagueFixtures` component is genuinely unused by any player-facing screen at ship time.** It exists purely so the still-open "player profile/results/fixtures views" roadmap item can drop it in later without a rework pass — a human should note this explicitly against that roadmap item once this ships, the same way `032`'s player-identity-agnostic tables were flagged for the same future consumer.
- **`Match.homeTeamLogoUrl`/`awayTeamLogoUrl` are blank on every pre-existing `Match` row** — no backfill migration, matching this spec's own Non-goals; both the new component and `MatchForm` already treat a missing logo as "show the initials/icon fallback," so this is a non-event in practice, not a rendering bug waiting to happen.
- **This spec introduces the first PDF/document upload path in this codebase.** `MediaServiceImpl`'s existing local-disk storage plumbing (UUID filename generation, `Files.createDirectories`/`Files.copy`, the configured `app.media.storage-path`) has no PDF-aware counterpart today — its `ALLOWED_CONTENT_TYPES` map is hardcoded to three image types. Recommend the plan extract the shared storage plumbing into something both the existing image-upload path and this new Playing Conditions path can call, each supplying its own allowed-content-type map (e.g. a parameterized `MediaService.upload(file, allowedTypes)` overload, or a small shared file-storage helper both a document-specific service and `MediaServiceImpl` delegate to), rather than duplicating that plumbing verbatim in a second class — per `docs/standards/backend.md`'s "shared logic lives in one place" rule. Exact refactor shape is left to the plan, not mandated here. `MediaServiceImpl`'s own known local-disk-storage limitation (doesn't survive/scale across multiple backend instances, flagged in `012`'s Rollout Notes) applies identically to wherever the Playing Conditions PDF ends up stored — not a new limitation this spec introduces, just one it inherits.
- Ships as one PR — two new migrations (Match's opponent-logo columns, the new `league_playing_conditions` table), `LeagueDto`/`MatchDto`/`CreateMatchRequest`/`UpdateMatchRequest` field additions, the new `LeaguePlayingConditions` entity/service/controller, the Affiliations→Teams label rename, `MatchForm`'s new per-side `MediaUpload` fields, `LeagueFormPage`'s new Schedule tab (carrying both the match-scheduling shortcut and the Playing Conditions upload), and the new `LeagueFixtures`/`DocumentUpload` components plus `LeagueDetailPage`'s new Fixtures section and `LeagueList`'s new badges/footer action — all touching the same small cluster of `029`/`036`/`040`/`049` files, not staggered across multiple PRs.
- **Immediate next step before any UI code:** the Claude Design pass for `LeagueFixtures` and `DocumentUpload` together (`docs/workflow.md` Step 2) — the two genuinely new visual patterns in this spec (an avatar-pair "vs" row, and a PDF-only upload control with no image preview); everything else here is either a field/badge addition to an existing shape or a straight label rename.
