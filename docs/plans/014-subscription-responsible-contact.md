# Implementation Plan — 014: Subscription Responsible Contact (Person-based rewrite)

## Context

`docs/specs/014-subscription-responsible-contact.md` was rewritten mid-implementation: an earlier draft embedded a bespoke `Contact` value object directly on `Subscription` (partially built, committed on `feature/014-subscription-responsible-contact`, PR #12 open) — a design discussion concluded the responsible party is specifically, already-confirmed meant to log in later (a future self-serve signup flow), so it should link to a real `Person` (the identity/auth anchor from `001-tenancy-identity-model.md`), not a throwaway `Contact` fact. This plan supersedes `PR #12`'s committed design; the branch/PR stays open and gets built on top of, not closed. `Contact`/`ContactDto` stay completely untouched — reserved for a future "Club Contacts" spec — and are never linked to `Person` by a schema FK, only implicitly by email at runtime.

This plan was produced after reading the rewritten spec in full, `CLAUDE.md`, every file in `docs/standards/`, and the real current state of every file it touches (`Subscription`/`Person`/`Contact`/`ContactDto`, `SubscriptionDto`/`CreateSubscriptionRequest`/`UpdateSubscriptionRequest`, `SubscriptionMapper`+generated impl, `SubscriptionServiceImpl`, `SubscriptionController`, `ClubController`/`ClubServiceImpl`/`ClubRepository` as the `GET /persons` pattern to mirror, all Liquibase migrations through `007`, `db.changelog-master.xml`, `openapi.yaml`'s relevant schema/path blocks, `ClubPicker`'s full four-file source as the `PersonPicker` pattern to mirror, `SubscriptionForm.tsx`/`SubscriptionFormPage.tsx`/`subscriptionApi.ts`/`clubApi.ts`, and every existing test file that references the discarded `Contact`-on-`Subscription` design).

## Resolved decision — legacy NULL-contact Subscriptions

**Confirmed empirically** (queried the local dev Postgres directly): all 4 `Subscription` rows in the current dev database have `responsible_contact_email IS NULL` — they predate `007-add-subscription-responsible-contact.sql` entirely (created via `009-subscriptions.md`'s original flow, before the discarded `Contact` draft's required-on-create validation ever existed). The spec's `009-subscription-responsible-person.sql` backfill (`GROUP BY lower(email)`, insert into `person.email NOT NULL`) would collapse these into one NULL-keyed group and fail the `NOT NULL` constraint immediately — not a hypothetical risk, a certain failure against this exact database as it stands today.

**Decision (confirmed with you):** delete these 4 legacy rows manually before running the migration, rather than adding NULL-handling logic to the SQL. `009-subscription-responsible-person.sql` stays **exactly as the spec's original sketch**, unmodified. This is safe because:
- Nothing is deployed to any real users yet — these are local dev-only rows, `009-subscriptions.md` itself is still "pending review", not shipped.
- Fresh environments (CI's Testcontainers Postgres, a clean clone) apply every migration from `001` onward in sequence against an empty database — `subscription` has zero rows when `009` runs there, so this hazard is specific to *already-running* local dev databases, not a structural gap in the migration itself going forward.

**Action required before `009` runs against this (or any other pre-existing) local dev database:**
```sql
DELETE FROM subscription WHERE responsible_contact_email IS NULL;
```
`backend-builder` runs this against the local dev Postgres (`database_db_1`) as an explicit, called-out step immediately before applying `008`/`009` locally — not folded silently into the migration SQL itself.

## Flags for your review (resolved, not blocking — noted so you can see the calls made)

1. **`SubscriptionMapper.toDto` grows a 4th parameter (`PersonDto responsiblePerson`)**, extending the existing `club`/`product` summary-parameter pattern to `Person` — the spec's code sketch only shows `create()`'s resolution snippet, not this mapper signature change. Every `SubscriptionServiceImpl` method that calls the shared private `toDto` helper (`get`, `list`, `update`, `cancel`, not just `create`) needs a resolved `Person` threaded through — `list()` via the existing `findAllById`-into-`Map` batching pattern (avoiding N+1s, same as `clubsById`/`productsById`), the singular methods via a new `findPersonOrThrow` helper matching `findClubOrThrow`/`findProductOrThrow`'s exact shape.
2. **`PersonService` gains a `search(String search, Pageable pageable)` method** beyond the spec's abbreviated `findOrCreatePerson`-only interface sketch — required because `backend.md` forbids controllers touching repositories directly, and the spec's own API Contract table requires `GET /persons` to exist. Mirrors `ClubServiceImpl.list()`'s exact shape (`withDefaultSort` applied only when the caller's `Pageable` is unsorted, then delegates to `PersonRepository.search`).
3. **`SubscriptionServiceImpl` needs both `PersonService` (for `create()`'s find-or-create) and `PersonRepository` (for `get()`/`list()`/`update()`/`cancel()`'s plain lookups)** — not `PersonService` alone, since `findOrCreatePerson` must never be called from a read path (it would silently create a `Person` instead of 404ing on a bad id). This mirrors the existing convention exactly: `SubscriptionServiceImpl` already injects `ClubRepository`/`ProductRepository` directly, not `ClubService`/`ProductService`.
4. **`update()` gets simpler, not more complex** — it drops the line `subscription.setResponsibleContact(subscriptionMapper.toContact(request.responsibleContact()))` outright (nothing replaces it — `UpdateSubscriptionRequest` has no person-related field at all to read from) and gains one straightforward `findPersonOrThrow` lookup, only needed to populate the response DTO.
5. **`SubscriptionMapper.toContact(ContactDto)` is removed with no replacement** — there's no call site left for one anywhere in this design.
6. **OpenAPI (`backend/openapi/openapi.yaml`) is hand-spliced, not regenerated** — confirmed no `springdoc-openapi-maven-plugin`, generation script, or CI contract-diff step exists anywhere in this repo. Mechanism: run the backend locally, fetch `http://localhost:8082/v3/api-docs.yaml`, hand-splice new/changed schema (`PersonDto`, `ResponsiblePersonRequest`, `PagePersonDto`, edited `SubscriptionDto`/`CreateSubscriptionRequest`/`UpdateSubscriptionRequest`) and the new `/persons` path block into the checked-in file, mirroring `ClubDto`/`PageClubDto`/`/clubs`'s existing block structure exactly. `ContactDto`'s schema stays in the file untouched (still valid, just unused by `Subscription` now).
7. **`PersonPicker` must reuse `ClubPicker`'s exact "never treat a fetch error as zero results" guard** (`showAddAffordance` gated on `!isFetching && !isError && options.length === 0`, not just the length check) — this was a real bug fixed once already during `011`'s standards review; the fix must be copied into `PersonPicker`, not silently dropped.
8. **`SubscriptionFormValues.responsiblePerson` is create-mode-only, non-nullable by validation** (`PersonPickerValue`, excluding `null` the same way `club: SubscriptionClubSelection` already excludes `null` from `ClubPickerValue`'s union) — edit mode has no person-related field in its submitted values at all, since `PUT` never touches it.
9. **`PersonPicker`'s "new" draft makes no separate create call**, unlike `ClubPicker`'s `POST /clubs` step — the typed fields ride directly inside the one `POST /subscriptions` body's `responsiblePerson` field, resolved server-side by `PersonService.findOrCreatePerson`. `SubscriptionFormPage.tsx`'s `onSubmit` keeps the Club draft's existing two-step sequence unchanged (`POST /clubs` → `POST /subscriptions` when a new Club draft is present) and simply adds `responsiblePerson` to the one `POST /subscriptions` call — no third network step, no orphan-record risk, matching the spec's explicit design.
10. **`SubscriptionMapperTest.java` is deleted outright, not repurposed** — every one of its 4 tests exercises `toContact`/`responsibleContact`-specific behavior that no longer exists. A new, small `PersonMapperTest` replaces it (unit, `Mappers.getMapper(...)`, one test covering all 5 `PersonDto` fields including a null-`phone` case). `SubscriptionMapper`'s new 4-parameter `toDto` gets at least one assertion — either its own thin test or folded into `SubscriptionServiceImplTest`'s existing coverage.
11. **A new migration-focused integration test is needed for `009`'s backfill behavior** (dedupe-by-email, exactly-one-`person`-row-per-distinct-email, columns dropped) — this needs to seed raw `responsible_contact_*` data *before* Liquibase applies `008`/`009`, which is a different test setup shape than this repo's existing Testcontainers tests (which all boot with the schema already fully migrated). `test-writer` should confirm whether the existing `AbstractIntegrationTest` base supports point-in-time migration testing or whether this needs its own variant — flagged, not assumed.
12. **`SubscriptionControllerIntegrationTest.java`'s `VALID_CONTACT_JSON` and every request body/assertion using it needs a shape change, not just a rename** — `"responsibleContact": {...}` → `"responsiblePerson": {...}` (`ResponsiblePersonRequest` shape), `jsonPath("$.responsibleContact...")` → `$.responsiblePerson...`, plus a new assertion that `responsiblePerson.id` is a real non-null UUID (a named Acceptance Criterion). A `PUT` request body that illegally includes a `responsiblePerson` field should be confirmed to be silently ignored (Spring's default Jackson behavior — unknown/unmapped properties aren't rejected unless `FAIL_ON_UNKNOWN_PROPERTIES` is explicitly enabled, which it isn't here) rather than assumed.
13. **`CreateSubscriptionRequestValidationTest.java`'s `validContactDto()` helper and its 3 contact-specific tests get reworked** to `validResponsiblePersonRequest()` / `"responsiblePerson"`-prefixed property-path assertions, not deleted.
14. **Confirm `SecurityConfig`'s `/api/v1/platform/**` authorization pattern actually covers the new `/persons` sub-path automatically** (both `ClubController` and `SubscriptionController`'s own Javadoc claim this is a wildcard, not an enumerated list) — a one-line confirmation during backend implementation, not an assumption carried silently into the PR.

## Backend — `backend-builder`

**Domain & migrations** (in order):
1. `backend/src/main/java/com/cricketlegend/domain/Person.java` — replace `fullName` with `firstName`/`lastName` (both `nullable = false`), add `email` (`nullable = false`), add `phone` (nullable). Keep `keycloakUserId` unchanged. Update the class Javadoc — it currently frames `Person` as a bare prerequisite stub; reflect that this spec grows it into a real identity shape.
2. `backend/src/main/resources/db/changelog/v1/008-restructure-person-identity.sql` — exact SQL from spec (drop `full_name`, add `first_name`/`last_name`/`email`/`phone`, `CREATE UNIQUE INDEX ux_person_email_lower`). Safe as-is — zero rows in `person` today.
3. `backend/src/main/resources/db/changelog/v1/009-subscription-responsible-person.sql` — exact SQL from spec, unmodified (per the Resolved Decision above — no NULL-handling added; the 4 legacy rows are deleted manually first, locally, before this runs).
4. `backend/src/main/resources/db/changelog/db.changelog-master.xml` — register `008`/`009` after `007`.
5. `backend/src/main/java/com/cricketlegend/domain/Subscription.java` — remove the `@Embedded Contact responsibleContact` block/imports; add `@Column(name = "responsible_person_id", nullable = false) private UUID responsiblePersonId;` (plain FK column, no `@ManyToOne`, matching `ownerId`/`productId`'s existing shape).
6. `backend/src/main/java/com/cricketlegend/repository/PersonRepository.java` — add `findByEmailIgnoreCase(String email)` and a `search(String search, Pageable pageable)` `@Query`, mirroring `ClubRepository.search`'s exact JPQL shape.

**DTOs & mapper**:
7. `backend/src/main/java/com/cricketlegend/dto/PersonDto.java` (new record) — `(UUID id, String firstName, String lastName, String email, String phone)`.
8. `backend/src/main/java/com/cricketlegend/dto/ResponsiblePersonRequest.java` (new record) — `firstName`/`lastName`/`email` `@NotBlank`(+`@Email`), `phone` optional.
9. `backend/src/main/java/com/cricketlegend/dto/SubscriptionDto.java` — `ContactDto responsibleContact` → `PersonDto responsiblePerson`.
10. `backend/src/main/java/com/cricketlegend/dto/CreateSubscriptionRequest.java` — `@NotNull @Valid ContactDto responsibleContact` → `@NotNull @Valid ResponsiblePersonRequest responsiblePerson`.
11. `backend/src/main/java/com/cricketlegend/dto/UpdateSubscriptionRequest.java` — drop the person/contact field entirely: `(@NotNull UUID productId, LocalDate startDate, LocalDate endDate)`. Rewrite Javadoc per spec's reassignment-is-a-bigger-operation reasoning.
12. `backend/src/main/java/com/cricketlegend/mapper/PersonMapper.java` (new) — `PersonDto toDto(Person person)`, straight 1:1, no `@Mapping` overrides needed.
13. `backend/src/main/java/com/cricketlegend/mapper/SubscriptionMapper.java` — remove `toContact(ContactDto)` and `Contact`/`ContactDto` imports; `toEntity` gains `@Mapping(target = "responsiblePersonId", ignore = true)`; `toDto` gains a 4th param `PersonDto responsiblePerson` (Flag 1).

**Service layer**:
14. `backend/src/main/java/com/cricketlegend/service/PersonService.java` + `service/impl/PersonServiceImpl.java` (new) — `findOrCreatePerson(firstName, lastName, email, phone)` per spec, plus `search(String search, Pageable pageable)` (Flag 2). Constructor-injects `PersonRepository` (+`PersonMapper` for `search`'s DTO mapping).
15. `backend/src/main/java/com/cricketlegend/service/impl/SubscriptionServiceImpl.java` — inject `PersonService` + `PersonRepository` + `PersonMapper` (Flag 3); `create()` resolves via `personService.findOrCreatePerson(...)` before building the entity, sets `responsiblePersonId`; `get()`/`list()`/`cancel()` resolve the `Person` via `findPersonOrThrow`/batched `findAllById` and thread it into the extended `toDto`; `update()` drops its contact-mapping line entirely and gains one `findPersonOrThrow` call for the response only (Flag 4). Add `private Person findPersonOrThrow(UUID id)`.

**Controller**:
16. `backend/src/main/java/com/cricketlegend/controller/PersonController.java` (new) — `GET /api/v1/platform/persons`, `@RequestParam(required=false) String search, Pageable pageable`, mirrors `ClubController.list()`. No `POST`/`PUT`/`DELETE`.
17. Confirm `SecurityConfig`'s existing `/api/v1/platform/**` pattern covers `/persons` automatically (Flag 14) — add an explicit rule only if it doesn't.

**OpenAPI** (after the above compiles): 18. `backend/openapi/openapi.yaml` — hand-splice per Flag 6.

**Javadoc cleanup** (small, do last): 19. `Contact.java`/`ContactDto.java` — update Javadoc to stop citing `014`, describe as reserved for the future Club Contacts spec only, per the spec's own Rollout Notes instruction.

Depends on the backend endpoints above existing first.
