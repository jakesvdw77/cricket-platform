# Implementation Plan — 014: Subscription Responsible Contact

## Context

`009-subscriptions.md` (built, merged) links a `Club` to a `Product` but records no human accountable for the entitlement. `014-subscription-responsible-contact.md` adds a required-on-create `responsibleContact` — first name, last name, email, phone — as a new generic, reusable `Contact`/`ContactDto` embeddable, deliberately unscoped (mirrors `012-club-profile.md`'s `Address`/`AddressDto` precedent) so the future Club Contacts spec can embed the same type rather than redefining it. This is a real behavior change to `009`'s already-shipped `POST`/`PUT /api/v1/platform/subscriptions` endpoints, not a purely additive change — existing callers/tests need updating, not just new coverage added.

This plan was produced after reading the spec in full and the real current state of every file it touches: `Subscription.java`/`SubscriptionDto`/`CreateSubscriptionRequest`/`UpdateSubscriptionRequest`/`SubscriptionMapper`/`SubscriptionServiceImpl` (confirmed `update()` uses manual setters on the retrieved entity, not a MapStruct `toEntity` pass — the new `responsibleContact` handling needs to follow that same manual-setter convention, not introduce a different pattern), `Address.java` (the exact `@Embeddable` Lombok/JPA shape to mirror for `Contact`), and `SubscriptionForm.tsx`/`subscriptionApi.ts` (confirmed the exact existing field/validation/submit conventions the new contact fields must match).

## Flags for your review

1. **Existing tests will break, not just need extending — the spec doesn't enumerate this, but it's real.** `SubscriptionServiceImplTest.java` has 5 call sites constructing `CreateSubscriptionRequest` (lines 127/140/153/167/186) with no `responsibleContact` argument — all 5 stop compiling the moment the record gains a new required component, before validation even enters the picture. `SubscriptionControllerIntegrationTest.java` builds request bodies as raw JSON strings (a `body` variable reused across several `mockMvc.perform(...)` calls, plus two inline literal JSON strings around lines 206/216) — every one of those needs a `responsibleContact` object added or those tests will now get `400`s instead of their expected outcomes. `backend-builder` must update every one of these existing call sites as part of this change, not treat it as `test-writer`'s job to add coverage on top of a broken baseline.
2. **`SubscriptionMapper` needs one explicit new method, not just automatic nested mapping.** `create()` and the read paths (`toEntity(CreateSubscriptionRequest)`, `toDto(...)`) can rely on MapStruct's own automatic nested-object mapping for `ContactDto ⇄ Contact` (matching field names, no ambiguity) — no extra method needed there. But `update()` doesn't go through a MapStruct `toEntity` call at all; it mutates the retrieved entity's fields directly with manual setters. That path needs an explicit `Contact toContact(ContactDto dto)` method declared on `SubscriptionMapper` so `SubscriptionServiceImpl.update()` can call `subscriptionMapper.toContact(request.responsibleContact())` directly — including when the request's `responsibleContact` is `null` (MapStruct-generated mapping methods return `null` for a `null` source by default, which is exactly the "omitting it clears any previously-set contact" behavior the spec requires — confirm this in the generated `SubscriptionMapperImpl` rather than assuming).
3. **Migration number confirmed**: `007-add-subscription-responsible-contact.sql` is correct — `006-add-club-profile.sql` is the latest existing file in `backend/src/main/resources/db/changelog/v1/`.

## Backend — `backend-builder`

1. **`backend/src/main/java/com/cricketlegend/domain/Contact.java`** (new) — `@Embeddable`, same Lombok shape as `Address.java` (`@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder`), four fields (`firstName`, `lastName`, `email`, `phone`) with their own bare `@Column(name = "first_name")` etc. — **no baked-in prefix**, unlike `Address` (spec's explicit, deliberate design point: `Contact` is meant to be embedded at more than one site with different prefixes, supplied per-site via `@AttributeOverride`).
2. **`backend/src/main/java/com/cricketlegend/domain/Subscription.java`** (edit) — add `@Embedded` `responsibleContact` field with `@AttributeOverrides` mapping `firstName`/`lastName`/`email`/`phone` to `responsible_contact_first_name`/`responsible_contact_last_name`/`responsible_contact_email`/`responsible_contact_phone`, per the spec's exact sketch.
3. **`backend/src/main/java/com/cricketlegend/dto/ContactDto.java`** (new) — record with `@NotBlank`/`@Email` per the spec's exact sketch (deliberately different from `AddressDto`, which has no validation annotations — see spec's Data Model Changes for the reasoning, don't second-guess it).
4. **`backend/src/main/java/com/cricketlegend/dto/SubscriptionDto.java`** (edit) — add `ContactDto responsibleContact` field.
5. **`backend/src/main/java/com/cricketlegend/dto/CreateSubscriptionRequest.java`** (edit) — add `@NotNull @Valid ContactDto responsibleContact`.
6. **`backend/src/main/java/com/cricketlegend/dto/UpdateSubscriptionRequest.java`** (edit) — add `@Valid ContactDto responsibleContact` (no `@NotNull` — optional).
7. **`backend/src/main/java/com/cricketlegend/mapper/SubscriptionMapper.java`** (edit) — add the explicit `Contact toContact(ContactDto dto)` method (Flag #2). Verify `toEntity`/`toDto`'s existing `@Mapping` annotations don't need a new exclusion for `responsibleContact` (they shouldn't — matching field names on both sides map automatically) by generating and reading the actual `SubscriptionMapperImpl` after adding it.
8. **`backend/src/main/java/com/cricketlegend/service/impl/SubscriptionServiceImpl.java`** (edit) — `update()` gains one line, unconditional (Flag #2): `subscription.setResponsibleContact(subscriptionMapper.toContact(request.responsibleContact()));`, placed alongside the existing `setProductId`/`setStartDate`/`setEndDate` calls. `create()` needs no change — `subscriptionMapper.toEntity(request)` already carries `responsibleContact` through automatically once step 7 is done and the record gains the field.
9. **`backend/src/main/resources/db/changelog/v1/007-add-subscription-responsible-contact.sql`** (new) — exact SQL from the spec (four nullable `ADD COLUMN`s, no default, no backfill).
10. **`backend/src/main/resources/db/changelog/db.changelog-master.xml`** (edit) — register the new migration.
11. **`backend/openapi/openapi.yaml`** (edit) — add `ContactDto` schema, update `SubscriptionDto`/`CreateSubscriptionRequest`/`UpdateSubscriptionRequest` schemas to include `responsibleContact`, matching the hand-splice approach `012`'s plan already established (append-only, preserve existing `operationId` style — don't raw-regenerate the whole file).
12. **Fix the 5 existing `CreateSubscriptionRequest` call sites in `SubscriptionServiceImplTest.java`** and **every `body`/inline-JSON request in `SubscriptionControllerIntegrationTest.java`** to include a valid `responsibleContact` (Flag #1) — needed just to keep the existing suite compiling/green, independent of `test-writer`'s new-coverage pass below.

## Frontend — `frontend-builder`

Depends on the backend endpoints above existing first.

1. **`ui/src/components/EmailInput/`** (new, four-file anatomy per `docs/standards/frontend.md`) — thin `Input` wrapper, `type="email"`, trims + lowercases on blur (per spec's exact reasoning for why this isn't a bare `PhoneInput` copy — real distinguishing behavior, not decorative).
2. **`ui/src/api/subscriptionApi.ts`** (edit) — add the canonical `Contact` interface (firstName/lastName/email/phone, all `string | null` per the spec's exact shape), add `responsibleContact: Contact` (required) to `SubscriptionPayload`, add `responsibleContact?: Contact | null` to `UpdateSubscriptionPayload`, add `responsibleContact: Contact | null` to the `Subscription` read type.
3. **`ui/src/components/SubscriptionForm/SubscriptionForm.tsx`** (edit) — add four new fields (First name, Last name via `Input`; Email via the new `EmailInput`; Phone via the existing `PhoneInput` from `012`) grouped visually beneath the existing Club/Product/date fields, no tabs (spec confirms this form's field count doesn't cross `012`'s tab-introduction threshold). Validation per the spec's exact rule: **create mode** — all four required; **edit mode** — the four fields are optional as a *set* (an admin can leave the whole thing blank to clear a contact, or leave it exactly as loaded) but touching *any one* of the four requires all four filled before submit. Implement this as: track a `contactTouched` boolean (set `true` the moment any of the four fields changes from its initial value), and only apply the "all four required" check when `contactTouched` is true in edit mode (always applies in create mode, matching the existing `endDateTouched`/`slugTouched` pattern already used elsewhere in this component and `ClubForm`).
4. **`ui/src/pages/admin/SubscriptionFormPage.tsx`** (edit) — thread `responsibleContact` through `initialValues` (edit mode fetch) and into the `onSubmit` payload for both create (`SubscriptionPayload`) and update (`UpdateSubscriptionPayload`) calls. Read this file in full first to match its existing `createSubscription`/`updateSubscription` call-site conventions exactly before editing.

Flagged in the spec's own Rollout Notes but explicitly **not required by this spec's file boundary**: swapping `ClubForm.tsx`'s existing inline `Input type="email"` to use the new `EmailInput`. Leave it untouched unless you want to pick it up as a genuinely separate drive-by — don't silently fold it in without saying so.

## Tests — `test-writer`

Backend and frontend both apply this time (unlike `013`, which had no frontend surface).

**Backend:**
- `SubscriptionServiceImplTest` — `create` rejects a missing/`null` `responsibleContact` (400/validation), rejects one with any blank sub-field, accepts a complete one; `update` with a provided `responsibleContact` fully replaces the previous one; `update` with `responsibleContact` omitted (`null`) nulls out a previously-set one; a legacy `Subscription` (no contact) maps to a `SubscriptionDto` with `responsibleContact: null` without throwing.
- `SubscriptionRepositoryTest` (Testcontainers) — `007-add-subscription-responsible-contact.sql` applies cleanly against the existing `subscription` table (alongside `006-add-club-profile.sql`); a pre-migration-style seeded row (all four new columns left `NULL`) reads back correctly; the embedded `Contact` fields round-trip through the `responsible_contact_*` columns.
- `CreateSubscriptionRequestValidationTest`/equivalent — bean validation on the new required nested `ContactDto` (missing object, blank sub-fields, malformed email).

**Frontend:**
- `EmailInput.test.tsx`/`.stories.tsx` (new) — blur normalizes case/whitespace, error state driven by parent validation, one Storybook story.
- `SubscriptionForm.test.tsx` (extended) — create mode rejects submit with any contact field blank; edit mode allows submit with all four blank (clears) or all four filled, rejects a partial mix; submitted payload shape includes `responsibleContact` correctly in both modes.
- `SubscriptionFormPage.test.tsx` (extended) — `responsibleContact` threaded correctly into both create and update calls.
- E2E: extend the existing `009` Subscriptions golden path (Playwright, not wired into CI, same precedent as `009`–`013`) — creating a Subscription now also fills in the four contact fields before submit; the created Subscription's edit view shows the contact back correctly.

## Verification

- `cd backend && ./mvnw verify` — full build + unit + integration tests. This is the sharpest signal that Flag #1's existing-test-fixture fixes were actually done — if any of the 5 `SubscriptionServiceImplTest` call sites or the `SubscriptionControllerIntegrationTest` bodies were missed, this fails at compile time or with 400s, not silently.
- `cd ui && npm run lint && npm run test && npm run build`.
- Manual smoke test: log in as `platform-admin`, go to `Configuration → Subscriptions`, create a new Subscription — confirm the four contact fields are required and a malformed email is rejected inline. Open an existing (pre-`014`) Subscription in edit mode — confirm the contact fields render blank, not an error. Fill in all four and save — confirm they persist on reload. Clear all four and save — confirm they're cleared, not left stale.
