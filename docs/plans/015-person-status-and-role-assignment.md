# Implementation Plan — 015: Person Status & Role Assignment

## Context

`014-subscription-responsible-contact.md` (implemented, verified, staged) gave `Person` a real identity shape but no lifecycle state and no way to be granted anything. `RoleAssignment` has been a named-but-unbuilt concept since `001-tenancy-identity-model.md`. `015-person-status-and-role-assignment.md` builds both: a `PersonStatus` enum (`PENDING | ACTIVE | SUSPENDED`, `PENDING` reserved-only) and a real `RoleAssignment` entity/table, wired into `AccessService.canAdministerClub`'s one real production call site. This is entirely backend/data-model — no controller, no endpoint, no DTO, no frontend (confirmed by the spec's own API Contract/UI Requirements sections, both "None"). A separate, later spec (not this one) does Keycloak account provisioning; this spec explicitly stops short of that.

This plan was produced after reading `015` in full, `CLAUDE.md`, `docs/standards/backend.md`, and the actual current state of every file it touches — `Person.java`, `PersonServiceImpl.java`, `PersonRepository.java`, `AccessService.java`, `AccessServiceTest.java` — confirmed to match exactly what the spec's code sketches assumed (no drift). Confirmed `009-subscription-responsible-person.sql` is the actual current highest migration file, so `010`/`011` numbering is correct. Confirmed `JwtAuthenticationToken.getName()` returning the JWT `sub` claim is a real, already-used precedent (`RequestCorrelationFilter.java` line 59), not a new assumption.

## Backend — `backend-builder`

In order:

1. **`backend/src/main/java/com/cricketlegend/domain/PersonStatus.java`** (new) — bare 3-value enum (`PENDING, ACTIVE, SUSPENDED`), exact Javadoc from spec.
2. **`backend/src/main/java/com/cricketlegend/domain/Person.java`** (edit) — add `@Enumerated(EnumType.STRING) @Column(nullable = false) private PersonStatus status;` and a `@PrePersist` method defaulting `status` to `ACTIVE` when null (mirrors `Subscription.prePersist()`'s exact pattern — `Person` currently has no `@PrePersist` at all, this is the first one).
3. **`backend/src/main/resources/db/changelog/v1/010-add-person-status.sql`** (new) — exact SQL from spec: `ALTER TABLE person ADD COLUMN status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE'`. Single metadata-only op, backfills existing rows automatically — no separate UPDATE needed.
4. **`backend/src/main/java/com/cricketlegend/domain/RoleAssignmentRole.java`** (new) — enum `CLUB_ADMIN, MANAGER, PLAYER`.
5. **`backend/src/main/java/com/cricketlegend/domain/ScopeType.java`** (new) — enum `PLATFORM, CLUB, SECTION, TEAM`.
6. **`backend/src/main/java/com/cricketlegend/domain/RoleAssignment.java`** (new) — entity exactly per spec's sketch: `id`, `personId` (plain UUID FK, no `@ManyToOne`, matches codebase convention), `role`, `scopeType`, `scopeId` (nullable, no DB FK — polymorphic), `createdAt` (`@PrePersist`-defaulted).
7. **`backend/src/main/resources/db/changelog/v1/011-add-role-assignment.sql`** (new) — exact SQL from spec: table + `chk_role_assignment_scope_id` CHECK constraint + two indexes + the `COALESCE`-sentinel unique index preventing exact-duplicate grants while explicitly allowing multiple different grants per person.
8. **`backend/src/main/resources/db/changelog/db.changelog-master.xml`** (edit) — register `010`/`011` after `009`.
9. **`backend/src/main/java/com/cricketlegend/repository/RoleAssignmentRepository.java`** (new) — `existsByPersonIdAndRoleAndScopeTypeAndScopeId(...)` (what `AccessService` needs) + `findByPersonId(UUID)` (for the future `/me/access` endpoint, per spec).
10. **`backend/src/main/java/com/cricketlegend/repository/PersonRepository.java`** (edit) — add `Optional<Person> findByKeycloakUserId(String keycloakUserId)`.
11. **`backend/src/main/java/com/cricketlegend/service/impl/PersonServiceImpl.java`** (edit) — `findOrCreatePerson`'s create branch (`.orElseGet(...)`) adds `.status(PersonStatus.ACTIVE)` to the `Person.builder()` call. The found-by-email branch needs no change at all — `status` simply isn't touched, "link, don't overwrite" extends automatically.
12. **`backend/src/main/java/com/cricketlegend/config/AccessService.java`** (edit substantially) — per spec's exact sketch: constructor gains `PersonRepository`/`RoleAssignmentRepository` (currently has no constructor — Spring implicit default; becomes explicit constructor injection matching this codebase's convention). `canAdministerClub` keeps the `platform_admin` check first (unchanged, superset/override, returns `true` immediately), then falls through to `personRepository.findByKeycloakUserId(authentication.getName()).map(...).orElse(false)` checking for a `CLUB_ADMIN` `RoleAssignment` at `ScopeType.CLUB`/this `clubId`. Javadoc updated per spec's exact text, including the "known, honest limitation" paragraph (this branch is correct but dormant until the next spec sets `keycloakUserId`).

**Keep the existing test suite compiling and passing** (same posture `014`'s backend-builder pass took):
- **`AccessServiceTest.java`** — currently does `new AccessService()` (no-arg). Must become `new AccessService(personRepository, roleAssignmentRepository)` with both mocked (Mockito, matching this codebase's existing service-test convention). The three existing tests (`returnsFalseForNullAuthentication`, `returnsFalseWhenAuthorityIsNotPlatformAdmin`, `returnsTrueWhenAuthorityIsPlatformAdmin`) must still pass unchanged in behavior — for the `platform_admin`-true case, the mocked repositories should never even be consulted (short-circuit), worth a `verifyNoInteractions` if that's this codebase's existing style, otherwise just leave as-is if not.
- **`PersonServiceImplTest.java`**, **`PersonRepositoryTest.java`** — verify these still compile and pass as-is. `Person.status` is `@PrePersist`-defaulted, so any existing test building a `Person` via `.builder()`/`repository.save(...)` (confirmed: no raw JDBC `INSERT INTO person` exists anywhere in the current test suite — the `014` migration-backfill test only raw-inserts `club`/`product`/`subscription` rows, never `person`) should need no changes at all. Confirm this empirically rather than assuming — if anything breaks, fix it minimally.
- No other existing test file references `AccessService`, `Person.status`, or constructs a `Person` via raw SQL — confirmed by search during planning.

Do not touch `openapi.yaml` — the spec is explicit ("API Contract: None... no controller, no new or changed endpoint, and no DTO"), and `AccessService.canAdministerClub`'s method signature (already used by `012`'s `@PreAuthorize`) is unchanged.

## Tests — `test-writer` (after backend-builder)

Per spec's Test Plan table (Unit + Integration only — Contract/Component/E2E all explicitly "Not applicable"):

- **`PersonServiceImplTest`** (extended) — `findOrCreatePerson` sets `status = ACTIVE` on a newly-created `Person`; a `Person` found by existing email keeps its own stored `status` untouched, including a `SUSPENDED` one (proves "link, don't overwrite" now covers `status` too).
- **`AccessServiceTest`** (extended beyond backend-builder's compile-fix) — `platform_admin` returns `true` regardless of `RoleAssignment` state; a `Person` holding a matching `CLUB_ADMIN` grant for the exact `clubId` returns `true`; the same grant against a *different* `clubId` returns `false`; a `Person` holding only `MANAGER`/`PLAYER` (no `CLUB_ADMIN`) returns `false`; no `Person` found for the caller's `keycloakUserId` returns `false`, not a throw.
- **`PersonRepositoryTest`** (extended, Testcontainers) — `010-add-person-status.sql` applies cleanly against a pre-existing seeded `person` row (inserted before the migration, mirroring `014`'s own migration-test pattern) and backfills it to `'ACTIVE'` with no manual step; a `NULL` `status` insert fails at the DB level.
- **`RoleAssignmentRepositoryTest`** (new, Testcontainers) — `011-add-role-assignment.sql` applies cleanly after `010`; `person_id` FK enforced; unique index rejects an exact-duplicate grant but allows two different grants (different `role` and/or `scope_type`/`scope_id`) for the same `person_id` to coexist — the concrete proof of the multi-role concern being solved, not just documented; `CHECK` constraint rejects a non-`PLATFORM` row with `NULL` `scope_id`.
