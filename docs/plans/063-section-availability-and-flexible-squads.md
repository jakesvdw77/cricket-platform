# Plan: 063 — Section Availability Windows & Flexible Match Squads

## Context

`docs/specs/063-section-availability-and-flexible-squads.md` (draft) adds a second, opt-in squad-selection mode (`Team.squadMode`, `STATIC`/`FLEXIBLE`) alongside `029`'s existing season-squad model, in four parts: **A** — `SectionAvailabilityWindow`/`SectionAvailabilityResponse`, a section-scoped, public, no-login availability ask (mirrors `032`'s poll pattern exactly); **B** — the `Team.squadMode` toggle and `MatchSquadMember`, a per-match squad pool for `FLEXIBLE` teams, built via a new two-pane picker; **C** — the cross-match hard block, a real DB unique constraint on `(section_availability_window_id, player_profile_id)`, shipped as part of B's own migration/service since the constraint must exist before any row is written; **D** — a small, mostly-frontend integration pass so `033`'s XI-tinting and `029`'s existing squad-membership checks keep working for `FLEXIBLE` teams by reading from this spec's new tables instead of `032`'s/`029`'s.

Every entity shape, migration SQL, endpoint list, exception type, and UI component list below is taken exactly as the spec fixes it — this plan orders the work and names the concrete files, it does not redefine any of it. Two things the spec's own Non-goals/Rollout Notes explicitly accept as known limitations and does **not** ask this build to fix — carried forward here only so neither reads as an oversight later:
- **A rescheduled match doesn't re-resolve its `MatchSquadMember.section_availability_window_id`.** Resolved once, at add-time, from `(team.sectionId, match.matchDate)`; a later reschedule leaves existing picks pointing at the original bracket. No reschedule-time hook is built.
- **Cross-section double-booking isn't prevented.** The Part C unique constraint is scoped to one `SectionAvailabilityWindow` (one section's own bracket) only; a player tagged to two sections isn't protected across them.

**Sequencing:** the spec offers up to four smaller PRs or one large one. Every prior spec in this repo's actual history (`003`–`062`) shipped as a single PR per spec number (confirmed via `git log`: one `feat(...): ... (NNN) (#N)` per spec). Recommending **one PR** for the whole spec, matching that observed convention, with the file list below still grouped by Part (A / B+C / D) so commits can be split by concern per `docs/workflow.md` step 9, and so it can still be split into separate PRs along exactly these boundaries if preferred.

**Dispatch order:** `backend-builder` (all backend, Parts A→B/C→D in order — D's backend footprint is zero) → `frontend-builder` (all frontend, same order, since Part D's frontend work directly extends Part B/C's) → `test-writer`. **Before `frontend-builder` starts on `SectionAvailabilityWindows.tsx`, `PublicSectionAvailabilityWindow.tsx`, and `MatchSquadPicker`**, run `docs/workflow.md` Step 2 (Claude Design) + Step 3 (`design-token-sync`/`new-ui-component`) — these are the spec's own two "genuinely new visual patterns flagged for a Claude Design pass" (its UI Requirements section names them explicitly). `SectionAvailabilityShareDialog` (mirrors `PollShareDialog`) and every `TeamForm.tsx`/`TeamFormPage.tsx`/`MatchFormPage.tsx` edit below reuse existing patterns (dialog, tabs, info panel) and need no separate design pass.

## Flags for your review

1. **Resolved — spec `063` has been amended to use `035`'s section-scoped access, matching every other current admin endpoint.** The original draft of `063` assumed `034`/`035` were unbuilt and gated every new endpoint at `canAdministerClub` (whole-club) only; both are in fact already built (`AccessService.canAdministerSection`/`assertCanAdministerSection`/`assertCanAdministerAnySection` are live, and every current admin endpoint — `TeamController`/`TeamSquadServiceImpl`/`MatchAvailabilityPollController` — already uses them). `063`'s Depends-on, Non-goals, API Contract, and Rollout Notes have all been corrected accordingly. This plan below is written against the corrected spec: every new controller uses `@access.canAccessClub` (the broad club-reachability gate, matching `MatchAvailabilityPollController`'s own precedent for resources without a `sectionId` path variable), and every new service asserts `accessService.assertCanAdministerSection(...)` (single-team/single-window resources here, since none of this spec's new resources are genuinely multi-section the way a match's two sides are) immediately after loading the resource and before other business validation, exactly mirroring `TeamSquadServiceImpl`'s own call shape. `docs/roadmap.md`'s "Deferred by `063`" section has also been corrected; its separate, pre-existing "Blocked on the full tenancy model" entry describing `035` as unbuilt is flagged there as stale too, but left for a human to fix separately since it predates and is unrelated to `063`.
2. **`Team.squadMode`'s backend plumbing must land with Part A's migration, not deferred to "Part B" as the spec's own section headers might suggest.** `ddl-auto=validate` means the JPA entity must match the schema the moment `squad_mode` exists as a column — so `Team.java`'s new field, `CreateTeamRequest`/`UpdateTeamRequest`/`TeamDto`/`TeamMapper`/`TeamServiceImpl` all need the field from the first commit, even though the spec files `TeamForm.tsx`'s *visible toggle* under its own "Part B/C" UI Requirements. 6. **Exception messages stay plain strings.** This codebase's `GlobalExceptionHandler` only ever returns `ProblemDetail.forStatusAndDetail(...)` — a single `detail` string, no structured error body anywhere in the app. The spec's "carrying which matchId/teamId/team name"/"carrying the unresolved sectionId/windowDate/dayPart triple" language for `PlayerAlreadyPickedForWindowException`/`SectionAvailabilityWindowRequiredException` is satisfied by embedding those values in the message text (exactly like every existing exception here, e.g. `DuplicateSquadJerseyNumberException`) — the actual structured data the UI renders from (the `pickedElsewhere` badge, the pre-filled "create window" shortcut) comes from the successful `GET .../squad` response's own DTO fields, already resolved before the picker ever calls a mutating endpoint. Flagging so nobody invents a new structured-exception-body pattern just for this feature.
