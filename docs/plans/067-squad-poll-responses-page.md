# Plan 067 — Squad Poll Responses Page

Implements `docs/specs/067-squad-poll-responses-page.md` (approved). The page design is `065`'s, unchanged (https://claude.ai/artifact/5CUvicghrTHBhdmKLWV1vP). Frontend only; no backend or API change. Branch: `feature/067-squad-poll-responses-page` (off master, which has 064–066).

## Context

The group poll card's **Responses** opens a dedicated page (065); the squad poll card's **Responses** jumps to the match edit screen's Availability tab. Same button, different destination and layout. 067 makes a squad poll open the same page and views, as a poll with one time slot, with an **Open match** link back to the match screen (whose tab stays as is).

## Findings that shape the plan

1. **The three views and the helpers already work on a bracket model** (`SlotGroup`, `ResponseRow` with `statuses[{windowId, status}]`, `groupBySlot`, `statusFor`, `OverrideProps`). A squad poll can be fed in as ONE synthetic bracket (`windowId = pollId`) plus rows each with one status and ONE synthetic match, so **no view and no helper changes**.
2. **Everything the page needs for a squad poll exists in the API:** `getPollResponses` (rows with `squadJerseyNumber`, counts, `open`, `publicPath`; no match data, no autoClose), `listPolls` (`MatchAvailabilityPoll`: `id`, `autoClose`, `scheduledCloseAt`, `open`), `getMatch` (date, venue, home/away ids and names), `setPlayerStatus` (returns the full responses payload, so it goes straight into `setQueryData`), `listTeamsForClub` for team names, `updatePollCloseTime`/`openPoll` via `EditCloseTimeDialog`.
3. **Lowest-risk shape: extract a shared page shell, keep two thin route pages.** `GroupPollResponsesPage` (222 lines) mixes group-specific data/dialogs with generic UI (view/search state, toggle+search, closed note, error alert, empty text, the three views, memoised grouping). Move the generic part into `ResponsesPageShell`; the group page keeps its three queries/mutation/dialogs and renders the shell; a new `SquadPollResponsesPage` does the same with the squad data through a **pure adapter**. This avoids a ~100-line copy-paste and avoids rewriting the group data layer. The group page's **21 existing tests must pass untouched** (they pin headings, region names, query keys/cache writes and loading/error ordering).
4. **The group header's DOM must not change**; the shell therefore takes header slots (`title`, `meta`, `actions`) instead of imposing one layout. The squad page passes its own badge row, subtitle and Closes line.
5. Squad title/side/team-name logic already exists in `pollHelpers.ts` (`squadPollTitle`, `squadPollSideLabel`) and `PollCard` (`squadTeamName` for `PollShareDialog`); the last is extracted so the page and card share it. `squadPollHref` (match Availability tab link) is reused for **Open match**.
6. Query keys for the squad page must sit under the prefixes `EditCloseTimeDialog` already invalidates (`['managed-club', clubId, 'matches', …]` and `'availability-polls'`), so Edit close time/Reopen refresh the page and the dashboard without new invalidation code.
7. Tests that encode the old squad destination must change: `PollCard.test.tsx` (~L139 expects the match tab URL) and `AvailabilityPollsDashboard.test.tsx` (~L279-298, probe route for the match page; needs a probe route for `availability/squad/:matchId/:pollId`).

## Flags for your review

1. **Shared shell extraction touches `GroupPollResponsesPage`** (mechanical move; its 21 tests must stay green unchanged). The alternative (a pure sibling page) duplicates ~100 lines.
2. **A synthetic bracket/match** (`windowId = pollId`) feeds the existing views, so squad rows' override key is `${playerProfileId}:${pollId}`; the squad `onOverride` ignores the window id.
3. **The slot's match line repeats the date** that is also in the page subtitle (the views' `SlotMatches` always renders "Team v Opponent · date time"); cosmetic and left as is.
4. **Morning/Afternoon uses the browser's local time**, same documented caveat as the card.
5. **Squad page needs four queries** (responses, polls, match, teams); no backend change.
6. Playwright is not extended (no live services here), as before.
