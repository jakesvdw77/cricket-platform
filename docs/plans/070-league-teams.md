# Plan 070 — League Teams

Implements `docs/specs/070-league-teams.md` (approved; design approved). Design: https://claude.ai/artifact/7thJAiYfdMf9yKywejxeE5. Branch: `feature/070-league-teams` (off master; spec already committed as `f5a1a31`).

## Context

A club plays opponents in a league each season but can only type their names by hand on every match. This adds a lightweight **league team** (name, abbreviation, logo; per league and season; club admin only), a Copy action from any other league and season of the club, and a third side option on `MatchForm` (My team / League team / Other). A match stores the league-team reference **and** copies name and logo into the existing columns, so every existing consumer is unchanged.

## Findings that shape the plan

1. **Template to mirror:** `LeaguePlayingConditions*` (separate controller with full paths on each method, `@PreAuthorize("@access.canAdministerClub(authentication, #clubId)")`, `LeagueSeasonAccessValidation.assertLeagueBelongsToClub/assertSeasonBelongsToClub`, MapStruct `toDto`, `@Transactional(readOnly = true)` reads). Action routes mirror `LeagueController` (`deactivate`/`reactivate` via `InvalidStatusTransitionException`, `POST` 201 on create). Duplicate check style mirrors `ProductRepository.existsByCodeIgnoreCase(+AndIdNot)`. Batched count style mirrors the `LeagueAffiliationRepository` projection query.
2. **`MatchServiceImpl.update` re-runs every validator against the request and never compares to the stored match**, so the spec's rule "an already-referenced inactive league team may be kept" needs the stored match loaded first. Plan: in `update`, load the match (`findOrThrowForClub`) before side validation and pass the stored `homeLeagueTeamId`/`awayLeagueTeamId` into the league-team check (inactive only blocks a *new* selection). Order of the existing validations otherwise unchanged.
3. **No `@Modifying` query exists yet and `@PreUpdate` does not fire on bulk JPQL.** The propagation query is `@Modifying(clearAutomatically = true, flushAutomatically = true)` and sets `m.updatedAt = :now` itself. It sets a new convention; its Testcontainers test re-reads after the clear.
4. **Record-component fan-out is small:** `MatchDto` positional constructor in `MatchServiceImpl.enrichList` (~L363) plus `MatchServiceImplTest` (MatchDto L109/543/545/585, CreateMatchRequest ~12 sites, UpdateMatchRequest ~5 sites). `MatchMapper` maps the two new Match→MatchDto ids automatically.
5. **UI toasts/snackbar do not exist** (spec mentions "toast"/"snackbar"). Plan uses the app's existing feedback conventions: inline MUI `Alert` in dialogs and above the section, and `errorDetail()` for server messages. **Flag 1** (wording only, no scope change).
6. **No way today for the UI to tell a club admin from a section manager** (`MeAccess` = `{platformAdmin, clubAdminClubIds}` only). The League team toggle must be admin-only. Plan: `MatchFormPage` computes `canUseLeagueTeams` from `MeAccess` (`platformAdmin || clubAdminClubIds.includes(clubId)`), the builder verifies `clubAdminClubIds` really holds only CLUB-scope assignments (backend `activate` path); if it does not, the fallback is to treat a 403 from the league-teams list as "hide the option". **Flag 2** — a small decision, no API-shape change unless the builder finds `clubAdminClubIds` includes section scopes (then stop and tell me).
7. **Fixture fan-out:** ~25 UI files build `Match` objects. Declare the new fields **optional** on the `Match` type (`homeLeagueTeamId?: string | null`) so none of them change; `makeMatch` in `matchTestUtils.ts` is the only one updated.
8. `MatchForm` is only rendered by `MatchFormPage`. Home/away blocks are copy-pasted (L233-327); the new three-way side selector is extracted into one page-local `MatchSideFields` used for both sides (spec design shows identical blocks) rather than tripling the duplication.

**B2. League team resource.** `LeagueTeamRepository` (case-insensitive exists check + AndIdNot variant, list by league+season sorted by name, batched `referencedByMatchCount` projection query counting matches by home or away reference, `existsReference` helper), `LeagueTeamMapper`, DTOs (`LeagueTeamDto` with `referencedByMatchCount`, `CreateLeagueTeamRequest`/`UpdateLeagueTeamRequest` with `@NotBlank name`, `CopyLeagueTeamsRequest`, `CopyLeagueTeamsResponse` + skipped record, `RemoveLeagueTeamResponse {outcome DELETED|DEACTIVATED, leagueTeam}` with a top-level `LeagueTeamRemoveOutcome` enum), `DuplicateLeagueTeamNameException extends ConflictException`, `LeagueTeamService` + `LeagueTeamServiceImpl`, `LeagueTeamController` (the seven endpoints and paths from the spec; `activeOnly`). No nested/synthetic classes in `service.impl` (ArchUnit): use separate enums/records.
**B3. Propagation.** `MatchRepository` `@Modifying` bulk UPDATEs (home and away) setting name, logo, `updatedAt`; called from `LeagueTeamServiceImpl.update` in the same transaction only when name or logo actually changed.
**B4. No change to `AccessService`, `MatchSideServiceImpl`, polls, availability, specs (the "Must not change" list).
**B5. `openapi.yaml`:** additions only, by hand (the seven paths following the playing-conditions/affiliations shapes, new schemas, the request/DTO fields).
