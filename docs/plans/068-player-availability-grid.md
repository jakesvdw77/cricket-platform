# Plan 068 — Player Availability Grid

Implements `docs/specs/068-player-availability-grid.md` (approved, design approved). Design: https://claude.ai/artifact/XmHwCXhsmRY3qECVf6hKmP (games as columns grouped under date then Morning/Afternoon; players as rows; read-only; picked dot; scrolling season grid). Branch: `feature/068-player-availability-grid` (off master; spec already committed).

## Context

Managers can only see one poll at a time. 068 adds a **Player Availability** screen: a season-at-a-glance grid built from the data we already have (squad polls, group polls, picked squads), narrowed by Season/League/Section/Team filters, with no per-team settings. One new read endpoint plus one new page; no data-model change.

## Findings that shape the plan

1. **Everything is already stored, but there are no batch queries.** The existing resolvers (`SectionAvailabilityAudienceResolver`, `AvailabilityPollSquadResolver`, `MatchPollCoverageService.resolve`) work one window/poll/match at a time and are N+1 internally, so the grid **must not call them per game**. It needs these new IN-list repository methods (each with a Testcontainers test): `SectionAvailabilityWindowMatchRepository.findByMatchIdIn`, `MatchAvailabilityPollRepository.findByMatchIdIn`, `PlayerAvailabilityRepository.findByPollIdIn`, `SectionAvailabilityResponseRepository.findByWindowIdIn`, `MatchSquadMemberRepository.findByMatchIdIn`, `MatchSidePlayerRepository.findByMatchSideIdIn`, `TeamSquadMemberRepository.findByTeamIdInAndSeasonIdIn`, `PlayerSectionRepository.findBySectionIdIn` (exact sections; callers pass the descendant set from `AccessService.sectionAndDescendantIds`). Already available: `MatchSideRepository.findByMatchIdIn`, `findAllById` (windows, rounds, profiles, persons), `MatchRepository.findAll(Specification, Sort)`.
2. **Games come from `MatchSpecifications`** (`clubId`, `sectionIn`, `leagueIdEquals`, `seasonIdEquals`, `matchDateOnOrAfter`); a **`teamIdEquals`** spec (home or away) is new. `startOfToday()` is private in `MatchServiceImpl`; extract it to a shared util instead of copying.
3. **Authorization pattern to copy:** `MatchAvailabilityPollServiceImpl.listScopedPolls` (accessible sections via `accessibleSectionIds`, `assertCanAdministerSection` for a `sectionId` param → 403/404, narrow to `sectionAndDescendantIds`). Match section ids via `resolveMatchSectionIds`.
4. **Day part has one rule** (local time before noon = MORNING, server zone) in `SectionAvailabilityMatchResolverImpl.dayPartOf`, which is private. Group-covered games use their window's stored `dayPart`; for the rest, expose `dayPartOf(Instant)` on the resolver interface rather than duplicating the rule.
5. **Audience rules used for `NOT_IN_POLL`** (same sources the poll screens use, but batched): group = `PlayerSection` of the window's section, active profiles only; squad poll = `TeamSquadMember(teamId, match.seasonId)`. Rows use `PlayerProfile.jerseyNumber` (one number per row, as the group audience does).
6. **Season default is a frontend concern:** there is no server "current season"; `utils/defaultSeason.ts#pickDefaultSeasonId` already mirrors the server's private rule. `usePersistedListFilters` loads after the first render, so the page must treat a stored `seasonId` of null/undefined as "not yet chosen" and not overwrite a stored choice.
7. **Frontend has no sticky first column/header table and no collapse-filters-on-phone pattern** (new work, page-local). `ResponsesByPlayer.tsx` is the closest model (bordered `overflowX: auto` box, tabular-nums, hide-non-answerers switch, `statusTintSx`); `StatusOverrideMenu` is NOT reused (read-only grid).
8. **`NewPollPage` only passes `sectionId`/`matchId` to the group branch**, so a game with no poll links to `/manage/availability/new?type=group&sectionId=…&matchId=…`; the game column therefore needs the game's `sectionId` (not in the spec's game shape; added, additive).
9. `backend.md` says "MapStruct, never by hand", but aggregate DTOs in this area (`buildResponsesDto`, `toOpenPollDto`) are assembled by hand in the service; the grid follows that precedent.

## Final API shape (additive to the spec's: `sectionId` on a game and a top-level `truncated`)

`GET /api/v1/manage/clubs/{clubId}/player-availability?seasonId=&leagueId=&sectionId=&teamId=&includePast=` → `PlayerAvailabilityDto { games: GameColumnDto[], players: PlayerRowDto[], truncated: boolean }`
- `GameColumnDto { matchId, matchDate (Instant), dayPart (MORNING|AFTERNOON), label ("Villagers 1 v CBC"), venue, leagueId, leagueName, teamId (this club's team in the game), sectionId, pollType (SQUAD|GROUP|null), pollId, roundId }` (`pollId` = squad poll id or group round id; `roundId` set for group; all null for no poll).
- `PlayerRowDto { playerProfileId, firstName, lastName, jerseyNumber, answeredCount, pickedCount, cells: CellDto[] }` with `CellDto { matchId, status (AVAILABLE|UNSURE|UNAVAILABLE|NO_RESPONSE|NOT_IN_POLL), picked }`; `cells` are in the same order as `games`.
- Section scope exactly as `availability-polls/open`; a `teamId` outside the club is 404, outside the caller's scope 403.

## Part 1 — Backend (`backend-builder`; build/test ONLY in an rsync'd scratch copy, never in `backend/`)

**B1.** The eight batch repository methods above (+ Testcontainers repository tests), `MatchSpecifications.teamIdEquals` (+ test), the extracted `startOfToday` util, and `dayPartOf` exposed on `SectionAvailabilityMatchResolver`.
**B2.** `dto/PlayerAvailabilityDto` (+ the three nested records as top-level files per the flat `dto/` convention), `service/PlayerAvailabilityService` + `service/impl/PlayerAvailabilityServiceImpl` (`@Transactional(readOnly = true)`, constructor injection; **no nested record/class inside the impl** — ArchUnit's `Impl` rule), `controller/PlayerAvailabilityController` (`@PreAuthorize("@access.canAccessClub(authentication, #clubId)")`, Javadoc spec reference).
**B3. Aggregation algorithm (all batched, no per-game/per-player queries):** resolve scope (as `listScopedPolls`) → games via specification, sorted by date, cut to `MAX_GAMES` (public constant, documented) → one batch each for window links, group windows, squad polls, squad answers, group answers, picked sets (`MatchSquadMember` + `MatchSide`→`MatchSidePlayer`, "picked" = in either, regardless of `announced` — flagged) → audiences (`PlayerSection` over the section+descendants for window sections; `TeamSquadMember` over team×season pairs) → rows = Team filter ? that team's squad : section audience, ordered by name, cut to `MAX_PLAYERS`; `truncated` true if either cap hit → cells per rules (group: audience member → answer or NO_RESPONSE else NOT_IN_POLL; squad poll: squad member → answer or NO_RESPONSE else NOT_IN_POLL; no poll → NOT_IN_POLL) → counts. Names and jersey numbers via `findAllById` batches.
**B4.** Regenerate `backend/openapi/openapi.yaml` via the scratch-copy temporary `@SpringBootTest` (additions only; revert springdoc reordering noise).
**Tests (builder; `test-writer` fills gaps):** service unit tests (group-covered, squad-covered, no-poll, a player in two teams' squads with different answers on two games in one slot → two cells, NOT_IN_POLL outside audience, picked from both sources, filters, `includePast`, caps + `truncated`, answered/picked counts, ordering); an integration test class in the style of `UnifiedAvailabilityPollsIntegrationTest` (fixtures `newMatch`, `savePoll`, `saveRound`, `saveWindow`, `addPlayer`, `grantSectionAdmin`) incl. section scope `403`/`404`, team filter, and that the grid agrees with the poll endpoints for the same game; batch-query count sanity (no N+1); repository tests for every new method.

## Flags for your review

1. **`sectionId` on each game and a top-level `truncated` flag** are added to the spec's response shape (additive): `sectionId` is needed for the no-poll "Open a poll" link; `truncated` makes the hard cap visible instead of silent.
2. **"Picked" = in the game's `MatchSquadMember` set or its `MatchSidePlayer` selection, regardless of whether the team sheet is announced** (the spec doesn't say; counting unannounced selections helps rotation planning but can show draft picks). Say if you'd rather count announced only.
3. **League options list all club leagues**, not only those with games in view (the spec says "only leagues that have games in view"); narrowing them would need a second backend query. Tell me if you want it exact.
4. **Eight new IN-list repository queries** (and a `teamIdEquals` specification) are required to keep the endpoint free of N+1; each gets a Testcontainers test.
5. **Phone filters** need a new page-local "Filters" collapse (no existing pattern).
6. **Aggregate DTO assembled by hand** in the service, following `buildResponsesDto`/`toOpenPollDto` precedent despite `backend.md`'s MapStruct rule.
7. **Season default is chosen in the browser** (`pickDefaultSeasonId`), not by the server; the endpoint treats a missing `seasonId` as "all seasons".
8. Playwright is not extended (no live services here), as before.
