Implements `docs/specs/148-player-hub-club-info.md` (draft 2026-11-13, owner decisions of 2026-11-12: logos on About with no pill, club contacts only (never players or their managers), all active club contacts with no per-contact opt-in, existing clubs start visible, team managers and coaches appear, a listed contact with no value shows "Not shared"). Branch: a new `feat/148-player-hub-club-info` cut from master after #164 merges. Commits local only; push and PR only on the owner's go-ahead.

## Context
The Hub's Club info item is a locked "Soon" panel. Parents and players cannot reach the club's address, phone, email, website, socials, logos or its contacts, though the club entered them for the manager screens. The spec makes it a real, read-only page with a club-level privacy model (switches on `club_profile`, directory/phone/email off by default). Nothing here redefines an entity, an API shape or a scope rule the spec fixed.

## Points to flag back to the human (the plan follows the latest decisions; nothing is silently reinterpreted)
1. **Stale lines in the spec after the "all club contacts" decision.** These still describe the dropped per-contact opt-in and must be cleaned in one small docs commit (Slice 0) before the build: API table row `PUT .../contacts/{contactId}` "carries the three hub flags" (line 136); Non-goal "no automatic inclusion ... opted that contact in" (line 27) and "beyond the three new flags" (line 32); Owner decision 3 "a contact opts in individually" (line 40, history: keep but mark superseded); the user story "I can see which contacts are in the Player Hub" (line 97, meaning unclear: default: the Player Hub card says "All active contacts, adults only", no list); test plan "`ClubContactForm` Player Hub section and `ClubContactList` chip" (line 236) and "ClubContactForm" in New client files (line 202); "count of listed contacts" (line 161); acceptance/`no consent timestamp` wording (line 220); Rollout "the contact flags" (line 278). The plan follows Decisions 9, 10 and the owner line 45: **no change to `club_contact`, `ClubContactDto`, `ClubContactForm` or `ClubContactList`**.
2. **Switches versus toggle chips.** The spec says "labelled switches" on the manager Player Hub card; `page-anatomy.md` (and the existing `ShareFormatsSettings`) say an on/off choice is a **toggle chip, not a loose switch**. The plan builds the card the `ShareFormatsSettings` way (toggle chips, `InfoCard flat`). Confirm.
3. **Guard test name and the clipboard.** The spec names `hubStatsNoExport.test.ts`; the real guard is the `hubStatsNoExport` describe inside `pages/view/myPlayers/stats/statsGuards.test.ts`, and it bans `navigator.clipboard`. Copy needs the clipboard through the existing `hooks/useCopyToClipboard`. The plan adds `pages/view/myPlayers/clubInfo/clubInfoGuards.test.ts` (same helpers) that bans share/print/download/CSV/vCard/`createObjectURL`/`Blob`/`navigator.share`/`window.print` and **allows only** the `useCopyToClipboard` hook import in the directory row; the one `download` attribute lives in `HubClubImages`.
4. **`useCopyToClipboard` returns no message.** The polite "Number copied" status line is built in the row component from `copiedKey`/`failed` (an `aria-live` region), not from the hook.
5. **Tab bar reuse.** The spec wants the league tab bar's tablist behaviour; `HubLeagueTabBar` is bound to `LeagueTab`. The plan generalises it to a generic `HubTabBar<T extends string>` (the league wrapper stays, no visual change) instead of copying it.
6. **No debounce hook found in the Hub.** `HubFields` filters on the client. The 300 ms debounce into `query` needs a small `useDebouncedValue` (reuse one from `hooks/` if present, else add one with a test).
7. **No `Cache-Control` precedent in the backend.** `private, no-store` is set on the two reads with a `ResponseEntity` and `CacheControl.noStore().cachePrivate()`; pinned by a test.
8. **Directory query is new on `ClubContactRepository`** (only `findByClubId` and `findByClubIdAndActiveTrueAndIsPrimaryTrue` exist today); it is called only by the directory service (ArchUnit-checked by test, no new rule needed because `ClubContactRepository` is not in the `ownersRegex()` allow-list).
