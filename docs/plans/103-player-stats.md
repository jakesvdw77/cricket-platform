# Plan: 103 Player statistics and leaderboards

Spec: `docs/specs/103-player-stats.md` (branch `feature/103-player-stats`, master merged in). Mockups approved (canvas, 11 boards). Compute on read, manager-only, Awards output (PDF/text) deferred.

## Context

Managers capture and publish scorecards (spec 101) but nothing reads them back. This builds: a live Stats card on the Player page, a per-player breakdown (Batting/Bowling/Fielding), a Leaderboards page with an Awards view, a Players-list Stats shortcut, and a menu item. One pure `PlayerStatsCalculator` defines every figure so card, boards and awards cannot disagree.

## Spec changes needed BEFORE building (flagged back to the owner, not reinterpreted)

The plan follows the spec except where later decisions contradict its body. These need spec edits first (first commit of the build, text only):

1. **"No migration / no new table" is no longer true.** Decision 11 + provisional Q14 (selectable award categories, stored per club, server-side) needs migration `052` and a settings endpoint. Non-goal line "A per-category settings screen" must be reversed. Plan: mirror spec 114's share-settings exactly.
2. **"A match was played" rule (What counts, row 2) and decision 7 are superseded by the owner's answer today:** a match counts as played, and its figures count, when the outcome is WON/TIE/DRAW, **or** the outcome is NO_RESULT/ABANDONED **and at least one ball was bowled**. An abandoned/no-result match with no ball bowled counts for nothing (not a game, no stats). A FORFEIT never counts. "Ball bowled" = some REGULAR innings of the result has `balls > 0` or some `bowling_entry.balls > 0`. This also changes `Matches`, "Record while playing" (no-result/abandoned adds to none of won/lost/tied/drawn; no new counter) and the integration-test list. `101`'s appearance rule is overridden for statistics only.
3. **Decision 12 / Q5 (provisional yes): the Player page gets Section and Team filters.** The spec's `GET /players/{playerId}/stats` has no `sectionId`; add it (same closure rule, same section-scoped-manager narrowing as boards). The Stats card itself stays unfiltered career.
4. **Players list Stats shortcut (owner chose: fourth footer button).** The mockup's outlined text button and "⋮ View stats" menu item are not built: `PlayerCard` footer becomes 4 icon-over-caption buttons (Status, Edit, View, **Stats**), `PlayerTable` gets a Stats icon button beside Change status. There is no row menu, so spec's "where one exists" clause is a no-op.
5. Note for the PR (no spec change): the "OpenAPI contract diff fails CI" claim in standards is not implemented in CI (`mvn -B verify` only); the folder-shape CI script and dependency-cruiser are also not present. `openapi.yaml` is regenerated by hand.

## Backend (backend-builder). Package `com.cricketlegend`

Migration: `052-club-leaderboard-award-categories.sql`: nullable column on `club_profile` (`leaderboard_award_categories jsonb`, null = the nine defaults), registered in `db.changelog-master.xml`. Entity field not mapped by `ClubProfileMapper` (copy `share_initials_only` handling: `ClubProfile`, `ClubShareSettings*`).

Layout (follow `backend.md` skeleton; services = interface + `service.impl.*Impl`, `@Transactional(readOnly = true)`):

- `service.support` (pure, no Spring/repo/entity/access info): `PlayerStatsCounters` (record of additive counters), `PlayerStatsCalculator` (every derived figure, rounding HALF_UP once, nulls never 0/inf, `notCaptured` catalogue), `StatsScope` (club, seasonId, leagueId, teamIds, competition, optional team restriction), `LeaderboardBoard` (enum catalogue: code, group, label, direction, minimumKind, help/tie-break text), `LeaderboardRanker` (ordering, competition ranking, unranked group last, optional minimum, paging), `LeaderboardQualification` (clamp defaults). Reuse `OversFormat` (display only) and `DismissalType`.
- `repository`: `PlayerStatsAggregateRepository` (Spring Data, native `@Query` with interface projection; codebase has no JdbcTemplate, JPQL/projection pattern is `ResultPlayerRepository.findGuestNames`; use `cast(:x as uuid) is null` optional params and a never-empty sentinel list for team ids) grouped by `player_profile_id`, fixed predicates (club, `status = 'PUBLISHED'` via a shared constant next to `ResultVisibility`, not opposition, profile not null, not substitute, `import_match is null`, innings `kind = 'REGULAR'`, played rule from item 2). Plus `PlayerStatsFactsRepository` (small per-player queries: last 5 innings/spells, positions, bowler dismissal modes, best-innings detail for HIGHEST_SCORE/BEST_BOWLING rows). No new index expected; run `EXPLAIN` on a seeded set and record it in the PR.
- `service`: `PlayerStatsService`/`Impl`, `LeaderboardService`/`Impl` (catalogue, board, awards from ONE aggregate query), `ClubLeaderboardSettingsService`/`Impl` (with `ClubLeaderboardSettingsController`).
- Section filter: resolve `sectionId` through `AccessService.sectionAndDescendantIds`/`sectionClosures` (the walk `ResultPlayerEligibility` uses) to team ids; narrowing for section-scoped managers via `ClubMatchScope.resolve(authentication, clubId, sectionId, teamId)` (intersects accessible sections with the filter; 404 other-club team, 403 out of scope). Note `MatchServiceImpl.resolveAuthorizedSectionIds` does NOT intersect, do not copy it. Team filter is per row side: `(home_team_id = :t AND rp.side='HOME') OR (away_team_id = :t AND rp.side='AWAY')`; Section uses the row's side team's `section_id`.
- `controller`: `PlayerStatsController` (`GET /players/{playerId}/stats`), `LeaderboardController` (`GET /leaderboards`, `/leaderboards/{board}`, `/leaderboards/awards`), `ClubLeaderboardSettingsController` (`GET/PUT /leaderboard-settings`, body: selected award category codes), all `@PreAuthorize("@access.canAccessClub(authentication, #clubId)")`, base `/api/v1/manage/clubs/{clubId}`. DTO records in `dto/` per the spec's response tables. Unknown board/player/season/league/team/section: 404; bad `competition`/`minimum`: 400 (`ValidationException`); no new exception types.
- Season "current" default is client-side; API with no `seasonId` = all time. Awards defaults: `LeaderboardQualification` from M = busiest player's matches in scope.
- Awards categories: the nine defaults plus selectable extras (most sixes, most 50+, most maidens) from existing boards; `AwardsViewDto` returns the club's selected categories.
- **ArchUnit (`LayeringRulesTest`) must change or the build fails:** add `PlayerStatsServiceImpl`, `LeaderboardServiceImpl` and the two stats repositories to `ownersRegex()` (rule `noMatchResultAccessOutsideTheResultServices`), and extend the `containsExactlyInAnyOrder(...)` set in `theResultDataOwnersAreExactlyWhoWeExpect` only if a stats class uses `MatchResultRepository`. Add new rules: the stats repositories are touched only by the stats services; `PlayerStatsCalculator`/`LeaderboardRanker`/`LeaderboardQualification` depend on no Spring/repository/entity; stats code uses the published predicate and never `MatchSpecifications.hasResult` etc. (rule 7 forbids it). Amend the sentence in `backend.md`. Prove the new rule non-vacuous once by a deliberate break.
- `backend/openapi/openapi.yaml` regenerated by hand, additions only.
