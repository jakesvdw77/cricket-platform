# Plan: spec 096, Duplicate league

## Context

A club often runs leagues that are identical in setup and differ only in teams and schedule (Division 1 and Division 2). Today the manager has to retype everything. Spec `docs/specs/096-duplicate-league.md` (user decisions 2026-10-10: the new league does NOT copy the club's own team affiliations, opponent teams or the schedule; it DOES copy the league profile (format, XI size, age rules and cutoff, logo, phone, email, website, social links), the playing conditions for the chosen seasons, and the active contacts; "same affiliation" meant website, email, branding and social media, which are profile fields; new name required; a league has no start or end dates, season dates are the club-wide Season's) adds a **Duplicate league** action: one backend endpoint that copies in one transaction, and a dialog reached from the league page header and the League edit page. After success the manager lands on the new league's Teams tab to add its teams. Branch `feat/096-duplicate-league`, rebased on top of `feat/095-league-edit-gold-standard` (095 is built but not merged, so the edit page it describes is the one in this tree; when 095 merges, this branch rebases onto master). Two slices, one commit group per step, one PR only on the user's say-so, and 095's PR must merge first. Nothing below redefines the spec; where the spec disagrees with the code it is under Flags.

## Findings that shape the plan

- `League` carries every profile field the spec lists (`LeagueSource source`, `format`, `maxPlayingXiSize`, `minAge`, `maxAge`, `ageCutoffDate`, `logoUrl`, `phone`, `website`, `email`, lazy `socialLinks` ElementCollection into `league_social_link`, `active`, audit fields); `LeagueServiceImpl.create` builds with `League.builder()` and never trims or checks the name; entities have no `@Version`; ids are client-generated UUIDs (no per-row selects on `saveAll`).
- `LeaguePlayingConditions` (unique `(league_id, season_id)`), `LeagueContact` (embedded `Contact`, `ux_league_contact_primary` partial unique index on active primary, at most one on the source) copy as straight field duplicates; a new `Contact` and a new `SocialLink` list must be built (a Hibernate collection cannot be shared between two entities). No Liquibase migration, no unique constraint on `league.name`.
- `LeagueController`: no class-level mapping, full-path mappings, `@PreAuthorize canAdministerClub`; `create` is the 201 precedent. Result-object precedent: `CopyLeagueTeamsRequest`/`Response` (that one returns 200). Named 409 precedent: `DuplicateLeagueTeamNameException extends ConflictException`.
- ArchUnit only enforces layering and that `service.impl` classes are `*Impl` `@Service` (which in effect forbids nested types there); records and `LeagueCopyRules` go top-level in `service/support`.
- UI: 095 is built (tabs and `?seasonId=` handled by `LeagueEditTabs`/`resolveLeagueEditTab` and a `useEffect` in `LeagueFormPage`); the edit page footer exists only on Details; the League page header top row holds Season pill, outlined Share schedule and filled Edit; `LeagueCard` has four footer buttons and no overflow menu; there is NO toast mechanism in the app (the Copy dialog uses an inline `Alert` in a component that unmounts); `CopyLeagueTeamsDialog` is a controlled dialog (parent owns the mutation), mounted only while open, full-screen below `sm`, `Checkbox` rows, Select all/none ghost buttons.

## Flags for your review (spec versus code; plan's resolution in bold)

1. **`updatedBy` is never set on create** (no code sets it anywhere) while the spec says the copy gets "the acting user as for create": **leave it null as create does** (no `Authentication` threading); same for the copied contacts' `updatedBy`. `LeaguePlayingConditions.uploadedBy` is copied from the source with the PDF reference. Spec corrected.
2. **Season validation:** the helper the spec cites (`LeagueSeasonAccessValidation.assertSeasonBelongsToClub`) does one `findById` per id and would break the fixed query count: **one `seasonRepository.findByClubId(clubId)` plus `SeasonResolution.resolve(seasons, id)` per non-null id** (404 "Season not found: id" for a foreign or unknown id; `resolve` returns the current season for a null id, so null ids are rejected as 400 first).
3. **`League.source`:** `LeagueSource.EXTERNAL` is a reserved placeholder; copying it verbatim would be wrong: **the copy is always `INTERNAL`**, as `create` defaults. Spec corrected.
4. **Name check:** needs a new `LeagueRepository` query (case-insensitive, trimmed, all leagues of the club, active or inactive) with a Testcontainers repository test; loading `findByClubId` would also fetch social links. Plan adds `existsByClubIdAndNameIgnoreCase`-style JPQL (`lower(trim(l.name)) = lower(:name)`).
5. **Query-count guard:** `getPrepareStatementCount()` counts INSERTs too, which grow with copied rows. **The guard compares (prepared statements minus the known number of inserts) for a small source (1 season, 2 contacts) and a large one (3 seasons, 20 contacts)**, so SELECTs must be equal; builder may use a statement inspector instead if cleaner.
6. **Rollback test:** with seasons validated up front, "an invalid season after valid ones" is trivially atomic. **Add a real mid-copy failure** (spy/mock a repository `saveAll` to throw after the league row is saved) and assert nothing remains.
7. **Test fixtures:** `ManagerOverviewFixtures.cleanUp` deletes `league` without first deleting `league_social_link`, `league_playing_conditions`, `league_contact` and `league_team` (FKs without cascade): extend it, and add helpers (`league` with profile and social links, `playingConditions`, `contact`, `leagueTeam`). `LeagueServiceImpl` gains `LeagueContactRepository` in its constructor, so `LeagueServiceImplTest.setUp` (positional constructor) is updated.
8. **The Duplicate button is not available on every edit tab:** the edit page footer exists only on Details (spec 095). **Place it in the Details footer beside the status toggle (edit mode only)**; it is available on every tab of the league page via the header. The spec's "every tab of the edit page" claim is corrected.
9. **The `?tab=`/`?seasonId=` deep link already exists (095)**: the spec's deep-link work is dropped. **New risk the spec missed: navigating from `/leagues/A/edit` to `/leagues/B/edit?...` reuses the same `LeagueFormPage` instance** (same route), so the seeded `selectedSeasonId` and other local state leak and the new `?seasonId=` is ignored: **render the page with `key={leagueId}` (a thin route wrapper in `App.tsx` or inside the page)**, with a test.
10. **No toast mechanism exists:** the spec's "shared toast the Copy dialog uses" does not exist. **Success notice travels in router state** (`navigate(url, { state: { notice } })`); `LeagueFormPage` reads it and shows a dismissible `Alert` above the tabs, then clears the state. Spec corrected; a shared toast component stays out of scope.
11. **Navigate only after the league list is fresh:** the edit page finds the league in the cached list; navigating first would show "Couldn't load this league". **Await `invalidateQueries(['managed-club', clubId, 'leagues'])` before navigating.**
12. **Checkbox, not switch:** the dialog keeps `Checkbox` rows like `CopyLeagueTeamsDialog` and the spec (a "tick what to copy" dialog; switches stay for settings).
13. **The dialog owns its mutation hook** (`useDuplicateLeague`), a deliberate divergence from the controlled Copy dialog, as the spec says; focus-and-select of the prefilled name is new (`inputRef` plus `onFocus` select).
14. **Phone header:** the header row wraps; the spec's "icon only below `sm`" is optional polish: **plan keeps the labelled button and lets the row wrap** (check in the browser).

## Order of work (each step ends with tests and one commit)

### Slice A: backend (`backend-builder`; scratch copy, never `mvn` in `backend/`)

**A1. Support, repositories, exception, DTOs**
- `service/support/LeagueCopyRules.java` (final, private constructor, static pure functions): `copyOfLeague(source, name, clubId)` (always `INTERNAL`, `active = true`, new `SocialLink` instances, no audit fields), `copyOfPlayingConditions(source, newLeagueId)` (every structured field and the PDF reference `documentUrl`/`uploadedAt`/`uploadedBy`, bonus thresholds forced null when bonus is off), `copyOfContact(source, newLeagueId)` (new `Contact`, role, primary flag, `active = true`), `normaliseName`.
- `dto/DuplicateLeagueRequest` (`@NotBlank @Size(max=255) name`, `List<UUID> seasonIds`, `Boolean copyPlayingConditions`, `Boolean copyContacts`) and `DuplicateLeagueResponse { leagueId, name, seasonsCopied, playingConditionsCopied, contactsCopied }` (one-line records with a spec 096 Javadoc line); `exception/DuplicateLeagueNameException extends ConflictException`.
- `LeagueRepository`: name-clash query; `LeagueContactRepository.findByLeagueIdAndActiveTrue`; `LeaguePlayingConditionsRepository.findByLeagueIdAndSeasonIdIn` (derived); repository tests for each new query.

**A2. Service, controller, OpenAPI**
- `LeagueService.duplicate(clubId, leagueId, request)` and `LeagueServiceImpl.duplicate` (`@Transactional`; constructor gains `LeagueContactRepository`): `findOrThrowForClub` (404 other club), trim and validate name (400 blank or over 255), flags null means true, de-duplicate seasonIds, empty `seasonIds` with `copyPlayingConditions` true is 400 (ignored when false), one `findByClubId` seasons read and `SeasonResolution.resolve` per id (404), name-clash check (409 `DuplicateLeagueNameException`, message "A league named X already exists"), save the new league, then `saveAll` playing conditions for chosen seasons that have a source row and `saveAll` active contacts; return counts. A fixed number of SELECTs: source league, its social links (lazy), name check, seasons, source conditions (one query), source contacts (one query).
- `LeagueController.duplicate`: `@PostMapping(".../leagues/{leagueId}/duplicate")`, `@PreAuthorize canAdministerClub`, `@ApiResponse(201)`, `ResponseEntity.status(CREATED)`.
- `backend/openapi/openapi.yaml`: hand-add the path (grep for an unused `operationId` first) and the two schemas, additions only.

**A3. Tests**
- `LeagueCopyRulesTest` and `LeagueServiceImplTest` (every rule in the spec's unit row: profile fields incl. social links and the four XI and age fields, `active` true from an inactive source, `INTERNAL` source, name trimmed and source name not reused, each flag off copies nothing of its group, flags default true, no affiliation or league team or match is ever created, season without a source row copies nothing, PDF reference copied, bonus thresholds null when off, only active contacts and primary kept, 400 and 404 and 409 cases (409 case-insensitive, against an inactive league, with surrounding spaces), duplicate season ids de-duplicated); extend `LeagueServiceImplTest.setUp` for the new constructor argument.
- `LeagueDuplicateIntegrationTest` (Testcontainers, not `@Transactional`, `ManagerOverviewFixtures` extended: `cleanUp` FK order plus the new helpers): full-copy case with a rich source (two seasons of conditions and affiliations, three contacts of which one inactive and one primary, social links, league teams, matches); the new league has exactly the expected rows and zero matches, league teams and affiliations; the source is unchanged; a real mid-copy failure rolls everything back; controller tests through real HTTP (real CLUB_ADMIN 201, another club's admin 403 or 404, platform_admin, 404 / 400 / 409). `LeagueDuplicateQueryCountIntegrationTest` (Flag 5).
- Run in a scratch copy: `rsync` to the scratchpad `be-run`, `./mvnw -q -o test -Dtest='*Duplicate*,LeagueServiceImplTest,League*,*Repository*'` plus `LayeringRulesTest`, then the full suite once alone (Docker needed). The user restarts the IntelliJ backend afterwards.
