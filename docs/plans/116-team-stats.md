# Plan: 116 Team statistics (Part 2 of statistics)

Spec: `docs/specs/116-team-stats.md` (branch `feature/116-team-stats`; owner decisions 13-19 recorded, mockups approved: canvas https://claude.ai/artifact/3cw6pVcWQE74i9ubCUnrLo). Builds on 103 and 115. Compute on read: **no migration, no table, no index**, manager-only, club's own teams only.

## Context

Nothing answers "how is each team doing?". This adds a Teams table (fifth tab on `/manage/leaderboards`, `?tab=teams`), a team page (`/manage/teams/:teamId/stats`) and a Statistics card on Team detail. Every figure is defined once in a pure `TeamStatsCalculator` over additive SQL counters of "counted team results"; the table and page share it (parity). Team stats read `match_result` + `match_innings` only, so summary-level results are included.

## Spec points the plan follows, and things the code research settled (no owner decision needed)

- **Forfeit side (decision 15, "plan confirms"):** `winning_side` on a FORFEIT is the side that received the win (`ResultValidator.validateForfeit` requires it; no innings are required and imports drop them), so the conceding team is the other side. Gate forfeits on `outcome_type = 'FORFEIT'`, never on missing innings: `PlayerStatsSeed.result()` inserts default innings even for forfeits, so the SQL must never read a forfeit's innings.
- **Shared counting constants:** extract `PUBLISHED` and the played predicate (needs alias `r`) from `PlayerStatsSql` into a package-private `StatsCountingSql` (`PUBLISHED`, `PLAYED_RESULT`); `PlayerStatsSql.APPEARANCES` splices them at the same positions (text identical apart from whitespace). Team stats use `PLAYED_RESULT or outcome_type = 'FORFEIT'` in `TEAM_RESULTS`, so the shared constant itself is unchanged and 103/115 behaviour is untouched. Existing `PlayerStatsSqlLiteralsTest` hand-lists constants: add the new constants and the two team repositories to its `allSql()`, and new regex checks for the team literals (`decided_by`, `margin_type`, `outcome_type = 'FORFEIT'`, `batting_side`).
- **Paging:** size above 100 is a **400** (spec 116), unlike the leaderboard which silently clamps; default 25; the 1,000-team cap is a 400 + `log.warn`. New constants, not the package-private leaderboard ones.
- **Columns DTO:** a new `TeamStatsColumnInfo` (code, label, longLabel, sortable, direction, minimumKind `NONE|MATCHES`, **help**); `LeaderboardColumnInfo` has no `help` and its kinds are INNINGS/OVERS. Team `notCaptured` is `{code, label, reason}` (no `tab` field, unlike the player one).
- **Team ranking:** a standalone `TeamTableRanker` plus an optional tiny generic `RankingSupport<T>` (competition-rank loop, `page(list, page, size)`, null-safe comparators) only if rewiring `LeaderboardTableRanker`/`LeaderboardRanker` stays minimal and their existing 672-line tests pass untouched; otherwise standalone with duplicated few lines. CPD is documented but **not wired in the build** (review rule only).
- **Section scope:** `StatsScopeResolver.resolve(...)` is called, not copied. For a single-team page `ClubMatchScope` returns that team's whole section as `sectionTeamIds` (never null, even for an unrestricted admin): the SQL must filter per `tr.team_id`, so the restriction is harmless; unit-test this. A Section filter chooses which teams are listed and never changes a team's own figures (a team's page takes no `sectionId`).
- **Opponent name** as 115: `case side when HOME then coalesce(awt.name, m.away_team_name) else coalesce(ht.name, m.home_team_name) end`; derby opponent = the other club team's name. "Ours" = side's team id set AND `team.club_id = :clubId` (a team of another club can sit in a team-id slot).
- **Frontend:** `StandingsTable` is tied to the player model (PlayerName, cellText, unrankedReason, statsLink, innings/overs minimum text). Plan: extract its layout pieces (grid/pinned rank+first column, `HeaderRow` with a `firstColumnLabel`, `Notice`, `UnrankedDivider`, footer/Show more shape) into a shared module under `pages/manage/leaderboards/`, keep row content in two sibling components (`StandingsTable`, `TeamStandingsTable`); the existing leaderboard tests must pass unchanged.
- **Filters:** Teams tab reuses `useLeaderboardFilters`' saved key (`leaderboards:filters:<clubId>`: Season, League, Section; ignores `teamId`), `useStatsFilterLookups` (pass `teamIds: []`, omit `teams` from `FilterBar`) and `FilterBar.extraSelects` for Competition (copy `PlayerStatsPage` ~252). Filter options come from `GET /team-stats/filter-options`.
- **Routes:** Team detail is `sections/:sectionId/teams/:teamId` (`?from=section`, `?seasonId=`); the new `teams/:teamId/stats` does not clash with `teams`/`teams/new`. The Statistics card goes on `TeamDetailPage` (InfoCard `actions` with an outlined 44 px "View statistics" `RouterLink` button; link carries router state `{ backTo, backLabel }` pointing back to the team detail URL).
- **Cache keys:** unpublish/delete refresh does not invalidate stats keys today; stats stay fresh because `new QueryClient()` has staleTime 0 (`App.tsx:90`). Team keys `['managed-club', clubId, 'team-stats', ...]` follow the same pattern; no behaviour change to the result pages.
- Spec 116 needs no change before building. (If an owner answer changes later, the spec is updated first.)

## Backend (backend-builder). `backend/src/main/java/com/cricketlegend/`

1. `repository/StatsCountingSql` (new, package-private) with `PUBLISHED`, `PLAYED_RESULT`; `PlayerStatsSql` uses it (refactor, no behaviour change; run 103+115 tests unchanged).
2. `repository/TeamStatsSql`: `TEAM_RESULTS` CTE (`tr`): two rows per match (HOME where `home_team_id` is set + team of this club, AWAY likewise; `mrid, match_id, match_date, side, team_id, section_id, outcome, winning_side, decided_by, margin_type, margin_value, bpo, scheduled_balls, league_id, season_id, derby`), gated by `PUBLISHED`, club id, `PLAYED_RESULT or FORFEIT`; filters seasonId/leagueId/competition/teamId and the section list via `StatsScopeResolver.sectionTeamParameter` (same named-parameter idiom, no `playerId`). Additive counters in separate CTEs joined to innings so rows never multiply: `rec` (played, won, lost, tied, drawn, noResult, forfeits received/conceded, internal), `own` and `opp` innings sums (usable-innings = runs, wickets, balls all non-null; runs, wickets, balls, balls/bpo, extras + the five components each with its recorded-count), `nrr` over NRR-usable results (WON/TIE, REGULAR innings, both usable, an all-out innings at `scheduled_balls` known; excluded: DLS, draw, no result, forfeit, friendlies) with distinct league/season counts, and encoded maxima/minima for highest total, lowest total over complete innings, highest chase, largest victory by runs / by wickets. Every classification beyond a column compare (complete innings, chase qualification, NRR usability) is a named constant in `TeamStatsSql`. Basis counters (no-ball-bowled no-results, forfeits, internal) from sibling CTEs.
3. `repository/TeamStatsAggregateRepository` + `TeamStatsFactsRepository` (native, `extends Repository<MatchResult, UUID>`, interface projections with quoted camelCase aliases, epoch-millis dates): table aggregate (all teams in scope), one-team aggregate, filter-options (`seasonIds, leagueIds, sectionIds, competitions` with counted team results, narrowed), and the page facts (last five results with opponent names, and the match references for highs/lows/chase/victories).
4. `service/support/` (pure): `TeamStatsCounters`, `TeamStatsCalculator` (every definition in "Precise definitions", HALF_UP once, nulls never 0/inf, coverage, NRR status SHOWN/NOT_ONE_COMPETITION/NO_USABLE_RESULTS with the full-quota rule and "N of M", the `NOT_CAPTURED` catalogue = partnerships), `TeamStatsColumn` (enum: the table's 15 columns with natural direction, rate flag, unranked rule, tie-break criteria), `TeamTableRanker`; an adapter class mapping projections to the pure inputs (like `PlayerStatsCountersReader`).
5. `service/`: `TeamStatsService` + `service/impl/TeamStatsServiceImpl` (`@Transactional(readOnly = true)`; `StatsScopeResolver`; table: validate sort/direction/minimum/page/size; one section-names read for rows; page: unknown/other-club team 404, `ClubMatchScope` 403; empty reach = empty table 200; no person named; no name in logs).
6. `controller/TeamStatsController`: `GET /team-stats`, `GET /team-stats/filter-options` (literal route before any variable one), `GET /teams/{teamId}/stats`; `@PreAuthorize canAccessClub`; params as spec (page/size `Integer`, rest `String`/UUID).
7. `dto/`: `TeamStatsTableDto` (+ nested `TeamStats*` records; reuse `LeaderboardPageInfo`), `TeamStatsDto`, `TeamStatsFilterOptionsDto`.
8. `LayeringRulesTest`: add `TeamStatsAggregateRepository|TeamStatsFactsRepository` to `ownersRegex` and `STATS_REPOSITORIES`; `TeamStatsServiceImpl` + adapter to `STATS_SERVICES` and the exact-users list; `TeamStatsSql` + `StatsCountingSql` to the "touched only by" exclusion; `TeamStatsCalculator|TeamStatsCounters|TeamStatsColumn|TeamTableRanker` to `PURE_STATS_CLASSES` and recount `thePureStatsClassesExist` (39 today; every record/enum/nested type counts). `PlayerStatsSqlLiteralsTest` extended as above.
9. `backend/openapi/openapi.yaml`: three paths (after `leaderboards/filter-options`), tag `team-stats-controller`, unique operationIds (`getTeamStatsTable`, `getTeamStats`, `getTeamStatsFilterOptions`), schemas, 400/403/404.
