# Plan: 100 — Match Results: Core Capture and Publish Gate

Spec: `docs/specs/100-match-results-core.md` (approved in review; mockups: https://claude.ai/artifact/S7sqyz6DnZ6xad351EpSwh). Branch: `feature/100-match-results` (already created). On approval this file is copied verbatim to `docs/plans/100-match-results-core.md`.

## Context

Matches have no end state: no result, no completed status, no data for stats. Spec 100 builds the foundation: `match_result` + `match_innings` tables, a draft/publish gate, the Results page (Matches gold standard), a capture picker and a four-step wizard (Result, Toss and field, Scores, Review), and a result page. Scorecards (101/102), stats (103) and imports (104) are out of scope but the model and the data-driven stepper are shaped for them.

## Items to flag back to the human (spec says X, code says Y)

The file is `backend/openapi/openapi.yaml` and **no contract-diff test exists** (`docs/standards/backend.md:85` describes one that was never built). Default: regenerate the file by hand (per the "don't build under the live backend" rule), do not build the diff test in this slice; the Contract tier of the Test Plan is met by a hand review of the diff. Say if you want the diff test built here.
2. **Delete-blocker.** The spec's Rollout Notes say slice 100 "satisfies" the schedule-import delete blocker. Spec 098 (`MatchDeletionBlockerProvider`, structural test over `information_schema`) is **not built**, so there is nothing to register with. Default: nothing built here; the roadmap line stays open and `098`'s structural test will pick up `match_result` when it exists.
3. **Routes.** The spec puts the wizard at `/manage/matches/{matchId}/result`. Matches routes in `App.tsx` live under `fixtures/matches/...`, and the menu already has a `results` item at `/manage/results` (with a "Coming soon" placeholder route, `App.tsx:244`). Default: list `/manage/results`, result page `/manage/results/:matchId`, wizard `/manage/results/:matchId/capture`. (Capture from a match card/page links there too.)
4. **Draft validity.** The spec says "a draft is saved without full validity" and the outcome rules are "enforced in the service". Default: every **save** enforces structural validity only (non-negative numbers, wickets 0 to 10 or 0 to 2 in a super over, ball digit below `balls_per_over`, sequence/kind consistency); the full outcome-rule matrix runs in `validate` and `publish`. `match_result.outcome_type` is therefore nullable while `DRAFT`.
5. **Section-scoped managers.** The spec says any club manager can capture and publish (`canAccessClub`). `MatchServiceImpl` already has a per-match section-aware gate (`assertCanAdministerMatch`) and `list` narrows to accessible sections. Default: Results lists/summary reuse the same section narrowing, and writes reuse `assertCanAdministerMatch`, so a section-restricted manager can only touch results of matches in their sections. Club admins are unaffected. Confirm.
6. **`source_payload jsonb`.** No jsonb exists in the backend today (grep). Default: add the column in 043 mapped with `@JdbcTypeCode(SqlTypes.JSON)` (Hibernate 6), unused until 104; the unique index on `(club_id, source, external_id)` is partial (`external_id IS NOT NULL`).
7. **"Won / Lost per team" counters** are computed over **published** results only; the summary "Played" counts matches. An internal fixture is both a win and a loss by construction (see backend step 5).

## Backend (backend-builder) — in this order

1. **Migration** `backend/src/main/resources/db/changelog/v1/043-match-results.sql` + include in `db.changelog-master.xml`. Tables `match_result` and `match_innings` exactly as the spec's Data Model (CHECK constraints for enums, `ux_match_result_match` unique on `match_id`, partial unique `ux_match_result_source_external`, FK `match_innings.match_result_id ... ON DELETE CASCADE`, unique `(match_result_id, sequence)`, index on `(club_id, status)`). Use the new-migration skill.
2. **Domain:** enums `ResultStatus`, `ResultDetailLevel`, `ResultOutcomeType`, `ResultDecidedBy`, `ResultSide` (`HOME/AWAY`), `ResultMarginType`, `TossDecision`, `InningsKind`; entities `MatchResult`, `MatchInnings` (plain UUID columns, matching `Match`'s style; `source_payload` as above).
3. **Repositories + specifications:** `MatchResultRepository` (`findByMatchId`, `findAllByMatchIdIn`), `MatchInningsRepository`. **`ResultVisibility`** specification (adds `status = PUBLISHED` for any non-capturing caller; structural test requires its use). Extend `MatchSpecifications` with subquery specs: `hasResult(status?)`, `noResult()`, `resultOutcomeIn(...)`, and own-side won/lost predicates (below). Add `from`/`to` date-range specs for the results list.
4. **Shared logic (one place):** `ResultValidator` (outcome-rule matrix, margin-vs-scores and toss-vs-order and wicket/overs consistency warnings; returns errors + warnings), `ResultDraftMapper`-style MapStruct `MatchResultMapper`. Overs ⇄ balls live only on the frontend edge; backend handles balls.
5. **DTOs:** `ResultDraft` (the canonical shape and the PUT body; partial allowed), `MatchResultDto`, `InningsDto`, `ResultListItemDto` (match summary + result summary for cards: names, logos, scores, result line inputs, status), `ResultsSummaryDto` (played, won, lost, tiedOrNone, drafts, awaiting), `ResultValidationDto`. Add `resultStatus` to `MatchDto` (positional record: update `enrichList` and `withPlayingArea`).
6. **Service** `ResultService`/`ResultServiceImpl` (each read `@Transactional(readOnly = true)`, writes `@Transactional`): `list` = **a Match page filtered by `hasResult`**, then batch-load results and compose `ResultListItemDto` (reuses the whole Matches filter/section/sort pipeline; no second query stack); `awaiting` = `noResult()` + `active` with `includeUpcoming`; `summary` with the counters (won = WON/FORFEIT results where an own side is the winning side; lost = where an own side is the other side; an internal fixture satisfies both; drafts are counted in Drafts only); `filterOptions` delegates to the matches one; `get`, `upsertDraft` (creates with `playing_area_id` defaulted from the match and `scheduled_balls` defaulted from `LeaguePlayingConditions` when the match has a league), `validate`, `publish` (re-validate, require `acknowledgedWarnings`), `unpublish`, `deleteDraft`. Inactive matches refused; any club-owned active match without a result is capturable, past or future (spec decision 1).
7. **Controller** `MatchResultController` with the nine routes in the spec's API Contract, plus `resultStatus` request parameter on the existing matches list/summary. Exceptions in `com.cricketlegend.exception`: `ResultAlreadyExistsException`, `ResultPublishedException` (both extend `ConflictException`), `InvalidResultException` (extends `ValidationException`, carries `errors`/`warnings`; handler in `GlobalExceptionHandler` sets them as ProblemDetail properties).
8. **OpenAPI:** regenerate `backend/openapi/openapi.yaml` by hand, additions only.
