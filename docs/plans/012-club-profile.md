# Implementation Plan — 012: Club Profile

## Context

`010-minimal-club-creation.md` shipped a bare `Club` (name + slug + status) with platform-admin-only CRUD at `/admin/onboarding`. Nothing beyond that exists — no org type, no logo/banner, no address, no way to reach a club by email/phone/website, and the only way to add any of it today is a direct database write. `012-club-profile.md` is the next slice: a new `ClubProfile` entity (1:1 with `Club`, mirroring `001-tenancy-identity-model.md`'s `ClubBranding` precedent) plus a first, generically-reusable image-upload mechanism, both reachable from the existing `010` edit screen rather than a new page.

This plan was produced after two parallel research passes read every backend file this feature touches (`Club`/`ClubStatus`, `ClubDto`/`CreateClubRequest`/`UpdateClubRequest`, `ClubMapper`, `ClubRepository`, `ClubService`/`Impl`, `ClubController`, every exception class, `SecurityConfig`, `application*.properties`, the Liquibase changelog, and the OpenAPI spec) and every frontend file it touches (`ClubForm`, `ClubNameSlugFields`, `Input`, `RecordFormScreen`, `ClubFormPage`, `ClubList`, `clubApi.ts`, `productApi.ts`'s `Page<T>` convention, `App.tsx`'s routes, and confirmed via grep that no `@Embeddable`, no `@PreAuthorize`, no multipart upload, and no MUI `Tabs`-for-forms pattern exist anywhere yet). Where the spec's UI Requirements suggested an approach that doesn't fit the actual code (see Flag #1), this plan proposes a concrete alternative and flags it rather than quietly building something different from what a reviewer would expect.

## Flags for your review

1. **`ClubForm`'s tab UI lives inside `ClubForm` itself, not as a new `RecordFormScreen` prop.** The spec's UI Requirements suggested `RecordFormScreen` "gains an optional `tabs` composition mode." Having now read `RecordFormScreen.tsx` and `ClubForm.tsx` in full: `ClubForm` renders `<Box component="form" sx={{ display: 'contents' }}>`, which deliberately flattens its fields into direct items of `RecordFormScreen`'s own 2-column CSS grid — that's how `ProductForm`/`SubscriptionForm` work too, and changing `RecordFormScreen`'s contract would ripple into both of those unrelated forms. Instead: `ClubForm`'s root becomes a single grid-spanning cell (`gridColumn: '1 / -1'`, the same "full-width field" mechanism `ProductForm` already uses for its Description field), containing its own local `<Tabs>` (controlled by a plain `useState<number>`, no route change) and, inside, one `<form>` covering all four tab panels' fields (only the active panel is rendered — since all form state already lives in one `ClubForm`-level `useState`, unmounting inactive panels is safe and simpler than hide-via-CSS). `RecordFormScreen` itself is untouched — zero risk to `ProductFormPage`/`SubscriptionFormPage`. If you'd rather actually extend `RecordFormScreen`'s contract (e.g. because other future forms will want the same tab chrome), say so now — it's a bigger, shared-component change instead of a `ClubForm`-local one.
2. **First `@PreAuthorize` in the codebase — needs `@EnableMethodSecurity` and a minimal `AccessService` bean.** Nothing today uses method security; `SecurityConfig` gates everything by URL-matcher only. The spec requires `PUT /profile` specifically to carry a scope-shaped check. Plan: add `@EnableMethodSecurity` to `SecurityConfig`, and a new `@Component("access") AccessService` with `canAdministerClub(Authentication auth, UUID clubId)` — for now it just re-checks the flat `platform_admin` authority (everyone who reaches the method already passed the `/api/v1/platform/**` URL gate), but the call-site shape (`@PreAuthorize("@access.canAdministerClub(authentication, #id)")`) matches `docs/standards/backend.md`'s documented *future* `@access.canAdminister(...)` convention, so swapping in real `RoleAssignment` resolution later touches only `AccessService`'s body. `GET /profile` and `POST /media` stay on the existing flat URL-matcher gate (spec only calls out `PUT /profile`).
3. **`/media/**` static serving is `permitAll`, not `platform_admin`-gated.** The spec doesn't state this explicitly. Logos/banners are club-facing assets meant to be visible pre-login (same posture `001`'s `ClubBranding.logo_url` already has) — an admin-only upload *endpoint* (`POST /media`, gated) writes the file, but *serving* it back needs to be public or every club page needing a logo would need an authenticated fetch. New `WebMvcConfigurer` bean (`WebConfig`) registers `/media/**` → the configured storage directory; `SecurityConfig` gets one new `.requestMatchers("/media/**").permitAll()` line.
4. **`PUT /profile` is a full replace, not a partial patch.** The spec shows every field as optional/nullable in the request body, which could mean "omit = leave unchanged" or "omit = clear it." Given `ClubForm` always submits its entire current form state (not a diff), and standard REST `PUT` semantics are full-resource-replace, this plan treats a missing/null field as "set to null" — matching how `ClubServiceImpl.update()` already works for `Club` itself.
5. **Uploaded-but-never-saved files aren't cleaned up.** `MediaUpload` uploads on file selection, independent of the profile `PUT`. If an admin uploads a logo then navigates away without saving, that file sits on disk unreferenced forever. Matches the spec's own "deliberately small, honest first version" framing for media — not solved here, just naming the gap explicitly so it isn't mistaken for an oversight later.
6. **`PhoneInput`/`WebsiteInput` risk tripping the jscpd duplicate-code scan** (`docs/standards/frontend.md`'s ~70%-shared-logic rule) since both are thin `Input` wrappers. Kept genuinely distinct per the spec's explicit instruction to build both: `WebsiteInput` normalizes a missing protocol (prepends `https://` on blur if absent) — real, useful behavior `PhoneInput` has no equivalent for, which should keep them under the similarity threshold. If CI flags them anyway, that's a legitimate signal to collapse them, not a bug in this plan.
7. **New `app.media.storage-path` config property, first custom `app.*` namespace in the codebase.** Proposed: `app.media.storage-path=${MEDIA_STORAGE_PATH:./data/media}` in `application.properties`, following the exact `${ENV_VAR:default}` pattern `KEYCLOAK_ISSUER_URI` already uses. Also adding `spring.servlet.multipart.max-file-size=5MB` / `max-request-size=5MB` (no multipart config exists today; 5MB is a reasonable default for a logo/banner, not spec'd explicitly — flagging the number as my own call).
8. **`backend/openapi/openapi.yaml` looks generated (springdoc), not hand-authored** — `operationId`s match Java method names exactly, and the schema boilerplate (`PageXxxDto`, `SortObject`) is auto-derived. `backend-builder` should regenerate it via whatever process produced the existing file (booting the app and capturing `/v3/api-docs.yaml`, or the project's existing script if one exists) rather than hand-editing entries, so it doesn't drift from the real generated shape.

## Backend — `backend-builder`

**Migration & config**
1. `backend/src/main/resources/db/changelog/v1/006-add-club-profile.sql` — exact SQL already given in the spec's Data Model Changes section (`club_profile` table, `club_id UUID PRIMARY KEY REFERENCES club(id)`, `type`/`logo_url`/`banner_url`/`address_*`/`email`/`phone`/`website`/audit columns).
2. `backend/src/main/resources/db/changelog/db.changelog-master.xml` — append `<include file="db/changelog/v1/006-add-club-profile.sql" relativeToChangelogFile="false"/>`.
3. `backend/src/main/resources/application.properties` — add `app.media.storage-path=${MEDIA_STORAGE_PATH:./data/media}`, `spring.servlet.multipart.max-file-size=5MB`, `spring.servlet.multipart.max-request-size=5MB` (see Flag #7).

**Domain**
4. `backend/src/main/java/com/cricketlegend/domain/ClubProfileType.java` — enum `CLUB, ACADEMY, SCHOOL, OTHER`.
5. `backend/src/main/java/com/cricketlegend/domain/Address.java` — `@Embeddable`, fields `number`/`street`/`city`/`provinceState`/`country`/`postalCode`, each `@Column(name = "address_...")` matching the migration's flat column names exactly (first `@Embeddable` in the codebase — no existing pattern to mirror, standard JPA). **Deliberately named `Address`, not `ClubAddress`** — JPA embeddables don't support meaningful inheritance, so the way to make this reusable by the future Club Contacts/Sponsors specs isn't subclassing, it's embedding this exact same class into their own entities too (`@Embedded private Address address;`, with `@AttributeOverride` only if a future entity's table can't use the `address_*` column-name convention). One class, reused as-is — not duplicated per entity.
6. `backend/src/main/java/com/cricketlegend/domain/ClubProfile.java` — `@Entity @Table(name = "club_profile")`, `@Id @Column(name = "club_id") UUID clubId` (no `@GeneratedValue` — set explicitly by the service, matching the FK-shared-PK shape), `type` (`@Enumerated(STRING)`), `logoUrl`, `bannerUrl`, `@Embedded Address address`, `email`, `phone`, `website`, `createdAt`/`updatedAt`/`updatedBy` with the identical `@PrePersist`/`@PreUpdate` pattern `Club.java` already uses. No JPA relationship annotation to `Club` (`@OneToOne`/`@MapsId`) — matches this codebase's existing convention of plain UUID FK columns with no entity graph navigation (see `Club.updatedBy`, a bare `UUID`, not a `Person` reference).

**DTOs**
7. `backend/src/main/java/com/cricketlegend/dto/AddressDto.java` — record, same six fields, all nullable. Generic like the entity above — `ClubProfileDto.address` uses it now; a future `ClubContactDto`/`SponsorDto` reuses it directly rather than getting its own copy.
8. `backend/src/main/java/com/cricketlegend/dto/ClubProfileDto.java` — record: `clubId, type, logoUrl, bannerUrl, address, email, phone, website, createdAt, updatedAt, updatedBy`.
9. `backend/src/main/java/com/cricketlegend/dto/UpdateClubProfileRequest.java` — record, all fields optional/nullable: `type` (no annotation, Jackson enum-validates), `logoUrl`, `bannerUrl`, `address` (nested, reuse `AddressDto` as the request shape too — no separate request-address type needed, none of its fields are ever required), `email` (`@Email`, permits null), `phone`, `website` (`@Pattern` matching a basic URL regex, permits null).
10. `backend/src/main/java/com/cricketlegend/dto/MediaUploadResponse.java` — record: `String url`.

**Mapper**
11. `backend/src/main/java/com/cricketlegend/mapper/ClubProfileMapper.java` — `@Mapper(componentModel = "spring")`, `ClubProfileDto toDto(ClubProfile entity)` (MapStruct maps the nested `Address → AddressDto` automatically via a second interface method it infers, `AddressDto toDto(Address address)`, declared right here since `ClubProfile` is the only consumer today — trivial to hoist into a shared `AddressMapper` and pull in via `@Mapper(uses = AddressMapper.class)` the moment a second entity needs the same mapping, no rework of this method itself). No `toEntity` — per Flag #4, the service applies an `UpdateClubProfileRequest` onto a `ClubProfile` via explicit setters (same manual-setter style `ClubServiceImpl.update()` already uses for `Club`, not a MapStruct `@MappingTarget` update-in-place — no precedent for that pattern in this codebase).

**Repository**
12. `backend/src/main/java/com/cricketlegend/repository/ClubProfileRepository.java` — `extends JpaRepository<ClubProfile, UUID>`, no custom queries needed (lookup is always by the shared `club_id` PK).

**Exception**
13. `backend/src/main/java/com/cricketlegend/exception/UnsupportedMediaTypeException.java` — `extends ValidationException` (400), same one-line shape as `ReservedSlugException`, thrown when an uploaded file's content type isn't in the image allowlist.

**Services**
14. `backend/src/main/java/com/cricketlegend/service/ClubProfileService.java` + `service/impl/ClubProfileServiceImpl.java` — constructor-injects `ClubRepository` (to verify the club exists — reuse the existing `findOrThrow`-style `NotFoundException` pattern from `ClubServiceImpl`) and `ClubProfileRepository`/`ClubProfileMapper`.
    - `get(UUID clubId)`: verify `Club` exists (404 if not) → `clubProfileRepository.findById(clubId)` → if present, map to DTO; if absent, build and return a default-shaped `ClubProfileDto` with `clubId` set and every other field `null` (per spec — no 404 for a club with no profile row yet).
    - `upsert(UUID clubId, UpdateClubProfileRequest request)`: verify `Club` exists → `clubProfileRepository.findById(clubId).orElseGet(() -> { var p = new ClubProfile(); p.setClubId(clubId); return p; })` → apply every field from the request via setters (full replace, Flag #4) → save → map to DTO.
15. `backend/src/main/java/com/cricketlegend/service/MediaService.java` + `service/impl/MediaServiceImpl.java` — `@Value("${app.media.storage-path}") String storagePath`. `upload(MultipartFile file)`: validate `file.getContentType()` against `Set.of("image/png", "image/jpeg", "image/webp")` → `UnsupportedMediaTypeException` if not allowed; generate `UUID.randomUUID() + extensionFromContentType`; `Files.createDirectories(...)` + `Files.copy(file.getInputStream(), targetPath)`; return `new MediaUploadResponse("/media/" + filename)`.

**Controllers**
16. `backend/src/main/java/com/cricketlegend/controller/ClubProfileController.java` — `GET /api/v1/platform/clubs/{id}/profile` (no `@PreAuthorize`, relies on the existing URL-matcher gate), `PUT /api/v1/platform/clubs/{id}/profile` with `@PreAuthorize("@access.canAdministerClub(authentication, #id)")` (Flag #2).
17. `backend/src/main/java/com/cricketlegend/controller/MediaController.java` — `POST /api/v1/platform/media`, `consumes = MULTIPART_FORM_DATA_VALUE`, `@RequestParam("file") MultipartFile file` → `MediaService.upload`.

**Config**
18. `backend/src/main/java/com/cricketlegend/config/AccessService.java` — new, `@Component("access")` (Flag #2).
19. `backend/src/main/java/com/cricketlegend/config/WebConfig.java` — new, `implements WebMvcConfigurer`, `addResourceHandlers` registers `/media/**` → `file:${app.media.storage-path}/` (Flag #3).
20. `backend/src/main/java/com/cricketlegend/config/SecurityConfig.java` — add `@EnableMethodSecurity` to the class; add `.requestMatchers("/media/**").permitAll()` to the filter chain (Flag #3).

**Contract**
21. `backend/openapi/openapi.yaml` — regenerate (Flag #8) to pick up the three new paths and `ClubProfileDto`/`AddressDto`/`UpdateClubProfileRequest`/`MediaUploadResponse` schemas.

## Frontend — `frontend-builder`

Depends on the backend endpoints above existing first.

1. `ui/src/api/clubApi.ts` — add `ClubProfileType`, `Address`, `ClubProfile`, `ClubProfilePayload` types and `getClubProfile(id)`/`updateClubProfile(id, payload)` functions, same shape/conventions as the existing `Club`/`ClubPayload`/`getClub`/`updateClub`. `Address` is deliberately generic, not `ClubAddress` — mirrors the `Page<T>` precedent (`clubApi.ts` re-exports `productApi.ts`'s canonical `Page<T>` rather than redefining it): `clubApi.ts` becomes the canonical home for `Address` since it's the first consumer, and a future `clubContactApi.ts`/`sponsorApi.ts` does `import type { Address } from './clubApi'` + `export type { Address }` rather than redefining the same six fields.
2. `ui/src/api/mediaApi.ts` (new) — `MediaUploadResponse` type, `uploadMedia(file: File)`: builds a `FormData`, `POST`s to `/platform/media` with `Content-Type: multipart/form-data` via the shared `api` axios instance, returns `{ url }`.
3. `ui/src/components/AddressFields/` (new, four-file anatomy) — single `value: Address`/`onChange: (address: Address) => void` pair (not six separate callbacks — a deliberate, noted deviation from `ClubNameSlugFields`' one-callback-per-field precedent given the field count, still "props in, callbacks out, no internal fetching"), rendering six `Input`s in a `React.Fragment` matching `ClubNameSlugFields`' composition style. Takes the generic `Address` type from `clubApi.ts` (see above) — nothing about this component is Club-specific, so it's already positioned for the Club Contacts/Sponsors specs to import and reuse unchanged.
4. `ui/src/components/PhoneInput/` (new, four-file anatomy) — thin wrapper around `Input`, `type="tel"`, no format enforcement (Flag #6).
5. `ui/src/components/WebsiteInput/` (new, four-file anatomy) — thin wrapper around `Input`, `type="url"`, normalizes a missing protocol by prepending `https://` on blur (Flag #6). Actual format-invalid error state is still driven by the parent's validation (`error`/`helperText` props), matching `ClubNameSlugFields`' pattern of centralizing validation logic in the consuming form.
6. `ui/src/components/MediaUpload/` (new, four-file anatomy) — props `label: string`, `value: string | null`, `onUploaded: (url: string) => void`. Hidden native `<input type="file" accept="image/png,image/jpeg,image/webp">` behind a styled `Button`, image preview when `value` is set, calls `uploadMedia` from `mediaApi.ts` on selection (client-side MIME pre-check before the request, mirroring — not replacing — the backend's own allowlist), inline error text on rejection/failure, loading state during upload.
7. `ui/src/components/ClubForm/ClubForm.tsx` (major edit — see Flag #1):
    - New props: `profileInitialValues?: Partial<ClubProfilePayload>` (only passed in edit mode once the profile fetch resolves — `undefined` in create mode) and `onSubmit` changes shape to `(values: { club: ClubPayload; profile?: ClubProfilePayload }) => void`.
    - Root becomes a full-width grid-spanning `Box` (`gridColumn: '1 / -1'`) containing a local `<Tabs value={activeTab} onChange={...}>` (`useState<number>`, no route change) with four tabs: **Basic Info** (existing `ClubNameSlugFields`, plus the org-`type` `Input select` — `type` itself disabled/omitted while `profileInitialValues` is `undefined`, i.e. create mode), **Contact** (email `Input`, `PhoneInput`, `WebsiteInput`), **Address** (`AddressFields`), **Branding** (`MediaUpload` × 2, logo + banner). Basic Info is the default tab and is the only one enabled in create mode; the other three render as disabled `<Tab>`s with a tooltip ("Save the club first") when `profileInitialValues === undefined`.
    - One `<Box component="form" onSubmit={...}>` still wraps everything (single Save submits both club and profile fields); only the active tab's panel is rendered underneath it, since all field state lives in one component-level `useState`, not per-panel — switching tabs never loses data.
    - `validate()` extends to also check profile-tab fields (email format, website format) when `profileInitialValues !== undefined`, surfacing errors on whichever tab holds the invalid field (switch to that tab on submit if it's not already active, matching how a real form should surface a hidden error rather than silently failing).
8. `ui/src/pages/admin/ClubFormPage.tsx` (edit):
    - New `useQuery({ queryKey: ['club', id, 'profile'], queryFn: () => getClubProfile(id as string), enabled: isEdit })` alongside the existing club fetch.
    - New `profileSaveMutation = useMutation({ mutationFn: ({ id, payload }) => updateClubProfile(id, payload) })`.
    - `handleSubmit` becomes `async ({ club, profile }) => { const saved = await saveMutation.mutateAsync(club); if (profile) { await profileSaveMutation.mutateAsync({ id: saved.id, payload: profile }); } navigate(...) }` — sequenced mutations, matching `011-inline-club-creation-in-subscription-form.md`'s existing precedent for chaining two independent mutations from one submit.
    - **Create-mode navigation changes**: on successful create, navigate to `/admin/onboarding/${saved.id}/edit` instead of back to the list (per spec: profile completion continues in edit mode) — a deliberate, spec-called-out change from `010`'s original create→list redirect.
    - `ClubForm` call site passes `profileInitialValues={profileQuery.data}` (only meaningful once `isEdit && profileQuery.isSuccess`).

No `App.tsx` changes — confirmed `010`'s existing three routes (`onboarding`, `onboarding/new`, `onboarding/:id/edit`) already cover this feature; no new route.
