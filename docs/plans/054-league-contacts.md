# Plan: 054 — League Contacts

## Context

`docs/specs/054-league-contacts.md` (approved) gives `League` its own list of named contacts (league administrator, umpire coordinator, etc.), structurally a field-for-field clone of the already-built `SponsorContact` feature (`024`), retargeted at `league_id`. The one deliberate divergence from `024`: no standalone list page — Contacts surfaces as a tab on `LeagueFormPage` and a section on `LeagueDetailPage`, positioned last, matching those two pages' own existing multi-tab/section convention. This is the second of three sibling specs (053 merged, 054 this plan, 055 next); 053's PR is already merged to `master` and this branch (`feature/054-league-contacts`) was cut from that updated `master`.

**Verified directly against current source this session**: the full `SponsorContact` backend stack (`SponsorContactServiceImpl` — two-level `findOrThrowSponsorForClub`/`findOrThrowContactForSponsor` isolation, `saveAndFlush`-based `unsetOtherActivePrimaries`; `SponsorContactController`; `SponsorContactMapper` — confirmed the real `isPrimary`/`primary` MapStruct quirk; `SponsorContactDto`/`CreateSponsorContactRequest`), the full frontend stack (`SponsorContactForm.tsx` four-file component, `SponsorContactFormPage.tsx`, `SponsorContactDetailPage.tsx`, `SponsorContactList.tsx`'s exported `fullName`/`badgeFor`, `sponsorContactApi.ts`), `App.tsx`'s Sponsor Contact routes, `db.changelog-master.xml` (confirmed `029` is now the highest migration after 053's merge, so `030` is genuinely next — matches the spec's own reconciled numbering), and the **current, post-053** state of `LeagueFormPage.tsx` (outer tabs: Details=0, Teams=1, Schedule=2, Playing Conditions=3 — Contacts becomes tab **4**) and `LeagueDetailPage.tsx` (sections in order: Details, Playing Conditions, Teams, Fixtures — Contacts becomes the **5th**, last section).

## Files to touch, in order

### Backend (`backend-builder`)

Direct structural clone of the `SponsorContact` stack — same shape, `league_id` instead of `sponsor_id`, no `/platform` mirror:

1. **`backend/src/main/resources/db/changelog/v1/030-add-league-contact.sql`** (new) — exact SQL from the spec's Data Model Changes: `league_contact` table, `ix_league_contact_league` index, `ux_league_contact_primary` partial unique index. Register in `db.changelog-master.xml` after `029`.
2. **`backend/src/main/java/com/cricketlegend/domain/LeagueContact.java`** (new) — mirrors `SponsorContact.java` exactly: `id`, `leagueId` (`UUID`, not null), `@Embedded Contact contact`, `role`, `isPrimary`, `active`, audit columns.
3. **`backend/src/main/java/com/cricketlegend/dto/LeagueContactDto.java`**, **`CreateLeagueContactRequest.java`**, **`UpdateLeagueContactRequest.java`** (new) — mirror `SponsorContactDto`/`CreateSponsorContactRequest`/`UpdateSponsorContactRequest` field-for-field, `sponsorId` → `leagueId`, reusing `ContactDto` unchanged.
4. **`backend/src/main/java/com/cricketlegend/mapper/LeagueContactMapper.java`** (new) — mirrors `SponsorContactMapper` exactly, including the `@Mapping(target = "isPrimary", source = "primary")` on `toDto` and the `isPrimary` (not `primary`) ignore-target on `toEntity` — this is a real, easy-to-get-backwards quirk, copy it precisely rather than re-deriving.
5. **`backend/src/main/java/com/cricketlegend/repository/LeagueContactRepository.java`** (new) — mirrors `SponsorContactRepository`: `findByLeagueId(UUID)`, `findByLeagueIdAndActiveTrueAndIsPrimaryTrue(UUID)`.
6. **`backend/src/main/java/com/cricketlegend/service/LeagueContactService.java`** + **`impl/LeagueContactServiceImpl.java`** (new) — mirrors `SponsorContactServiceImpl` exactly: `list`/`create`/`update`/`deactivate`/`reactivate`, two-level `findOrThrowLeagueForClub`/`findOrThrowContactForLeague` isolation (mirroring `LeagueServiceImpl.findOrThrowForClub`'s existing club-isolation shape for the first level), `unsetOtherActivePrimaries` using `saveAndFlush` from day one (not rediscovered as a bug).
7. **`backend/src/main/java/com/cricketlegend/controller/LeagueContactController.java`** (new) — mirrors `SponsorContactController` exactly: `GET`/`POST`/`PUT .../{contactId}`/`POST .../{contactId}/deactivate`/`POST .../{contactId}/reactivate`, all under `/api/v1/manage/clubs/{clubId}/leagues/{leagueId}/contacts`, same `@PreAuthorize("@access.canAdministerClub(authentication, #clubId)")` on every method.
8. **`backend/openapi/openapi.yaml`** — hand-edit to document the four new endpoints and `LeagueContactDto`/`CreateLeagueContactRequest`/`UpdateLeagueContactRequest` schemas (reuse the existing `ContactDto` schema, don't redeclare).
9. **Required-by-standards unit tests, same PR**: new `LeagueContactServiceImplTest.java` mirroring `SponsorContactServiceImplTest.java`'s exact case list (create/update, primary auto-unset, deactivate/reactivate `409`s, two-level cross-tenant `NotFoundException` isolation for both a wrong-club league and a wrong-league contact).

### Frontend (`frontend-builder`, after backend types are settled)

1. **`ui/src/api/leagueContactApi.ts`** (new) — mirrors `sponsorContactApi.ts` exactly: `LeagueContact`/`LeagueContactPayload` types, `listLeagueContacts`/`createLeagueContact`/`updateLeagueContact`/`deactivateLeagueContact`/`reactivateLeagueContact`, base path `/manage/clubs/${clubId}/leagues/${leagueId}/contacts`.
2. **`ui/src/components/LeagueContactForm/`** (new, four-file anatomy) — near-copy of `SponsorContactForm.tsx` (First Name/Last Name/Email/Phone/Role Inputs + "Is primary contact" checkbox, same `EMAIL_PATTERN`/required-field `validate()`), retargeted at `LeagueContactPayload`. No photo field.
3. **`ui/src/utils/leagueContact.ts`** (new) — exports `fullName(contact: LeagueContact)` and `badgeFor(contact: LeagueContact)`, identical logic to `SponsorContactList.tsx`'s same-named exports (Primary/Inactive badge rules), as a standalone module since there's no League Contacts list page to own them.
4. **`ui/src/pages/manage/LeagueContactFormPage.tsx`** (new) — near-identical to `SponsorContactFormPage.tsx`: `leagueId` from route, `clubId` from Outlet context, `contactId` optional route param for edit, no single-contact GET (fetches the full list, finds by id client-side), deactivate/reactivate on this screen's own actions bar. Back link → `/manage/fixtures/leagues/{leagueId}/edit`.
5. **`ui/src/pages/manage/LeagueContactDetailPage.tsx`** (new) — near-identical to `SponsorContactDetailPage.tsx`: same list-plus-find-by-id fetch, imports `badgeFor`/`fullName` from `ui/src/utils/leagueContact.ts`, one un-headed `DetailFieldGrid` (Role/Email/Phone/Primary contact). Back link → `/manage/fixtures/leagues/{leagueId}`.
6. **`ui/src/pages/manage/LeagueFormPage.tsx`** — add `<Tab label="Contacts" />` as the 5th tab (after Playing Conditions, line ~348), and a new `{isEdit && activeTab === 4 && (...)}` block (after the existing `activeTab === 3` Playing Conditions block, line ~497 area) rendering `listLeagueContacts(clubId, leagueId)` as a `RecordCard` grid — same inline-grid-plus-navigate-out shape the Teams tab's `AffiliatedTeamCard` already uses (avatar `circular`/`initialsFromName(fullName(contact))`, `badgeFor` badge, `fields` = Role/Email/Phone, `viewTo`/`editTo` into the two new pages), plus an "Add Contact" `Button` navigating to `/manage/fixtures/leagues/{leagueId}/contacts/new`.
7. **`ui/src/pages/manage/LeagueDetailPage.tsx`** — add a 5th section object to `sections` (after 'Fixtures', line ~441 area), heading "Contacts": same `listLeagueContacts` query and `RecordCard` grid shape as the `LeagueFormPage` tab above, `viewTo`/`editTo` per card, no inline "Add" action (read-only page, mirrors every other section's defer-to-edit-screen convention).
8. **`ui/src/App.tsx`** — add three routes: `fixtures/leagues/:leagueId/contacts/new` → `LeagueContactFormPage`, `fixtures/leagues/:leagueId/contacts/:contactId` → `LeagueContactDetailPage`, `fixtures/leagues/:leagueId/contacts/:contactId/edit` → `LeagueContactFormPage`. No `fixtures/leagues/:leagueId/contacts` list route (the list is embedded in the two host pages, not standalone — see spec's Non-goals).
