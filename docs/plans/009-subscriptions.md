# Implementation Plan — 009: Subscriptions

*Permanent record of the plan approved via `/plan-feature docs/specs/009-subscriptions.md`. The working copy Claude Code keeps under `~/.claude/plans/` is a scratch file; this is the git-tracked copy, kept alongside the spec it implements.*

## Context

`001`'s `Subscription` entity has never been implemented — `plan` is a bare string. `008` built a real `Product` catalog so a club's plan could point at something real; `009` links the two: a `Subscription` FKs a `Club` to an `ACTIVE` `Product`, admin-managed at `Configuration → Subscriptions` (the card `007` already reserved). Scoped to `CLUB` owners only — `Section` doesn't exist in code, so `SECTION`-owned subscriptions and ADR-03's walk-up-the-tree resolution are out of scope per the spec's own Non-goals.

## Flags for your review

Five things resolved during planning, surfaced here before build starts, per `docs/workflow.md` step 5:

1. **`ClubSummaryDto`'s public shape needs to grow an `id` field.** The spec's UI Requirements assumed the Subscription form's Club picker could reuse `004`'s existing `GET /api/v1/public/clubs` search endpoint as-is — but that endpoint's `ClubSummaryDto` only returns `name`/`slug`, never `id` (confirmed by reading the actual DTO/mapper/frontend type). A `Subscription` needs the Club's real database `id`, not just its name. **Resolution:** add `id` to `ClubSummaryDto` (backend), `ClubMapper.toSummaryDto`, and the frontend `ClubSummary` type — a small, additive, backward-compatible change to an already-shipped public endpoint. The value is an opaque UUID, not sensitive; this doesn't change that endpoint's "no branding/membership detail" privacy posture.
2. **`Product`'s list endpoint needs a `status` filter it doesn't have yet.** The Subscription form's Product picker needs "`ACTIVE` products only" — `008`'s spec already flagged this as a needed additive change, not built yet. Adds an optional `status` param to `GET /api/v1/platform/products`, `ProductRepository.search()`, and `ProductService.list()`. **Consequential edit:** existing test call sites in `ProductServiceImplTest`/`ProductRepositoryTest` that already call `.search(...)`/`.list(...)` need their signatures updated too — not just new tests added.
3. **No JPA `@ManyToOne` relationships for `Subscription`→`Club`/`Product`.** Kept as plain `UUID` fields (`ownerId`, `productId`) with DB-level FK constraints only, matching this codebase's existing flat-field convention (`Product`, `Lead`, `Club` — none use `@ManyToOne`). Cross-entity data (the embedded Club/Product summaries in `SubscriptionDto`, and name-search across the Club↔Subscription join) is assembled via explicit JPQL `JOIN ... ON` queries and service-layer composition, not object-graph traversal. Don't introduce ORM relationships as a "cleaner" alternative — it'd be a new pattern this codebase hasn't used, needing its own standards discussion first.
4. **Naming collision risk, same shape as `008`'s Retire/"Don't retire" fix.** `SubscriptionFormPage` has a nav-away "Cancel" button (leaves the form) *and* a business "Cancel Subscription" action (ends the entitlement) whose own inline-confirm needs a dismiss button — three controls that can't share the word "Cancel". Building it right the first time: nav button stays "Cancel", the business action is labeled "Cancel Subscription" (not bare "Cancel"), its confirm-dismiss button reads "Keep subscription".
5. **Default sort for the Subscription list** (`startDate` descending when unsorted) isn't mandated by the spec — my call, matching how `008` defaulted to `displayOrder`. Flagging since it's a real behavior choice, not neutral.

## Backend — `backend-builder`

Mirrors `Product`'s exact shape throughout (`ProductController`/`ProductServiceImpl`/`ProductRepository`/`ProductMapper` — read each fully first, they're the ground truth). **Reuse `InvalidStatusTransitionException`, `NotFoundException`, `ValidationException`** — only two new exception classes needed.

1. `backend/src/main/resources/db/changelog/v1/004-add-subscription.sql` — per the spec's sketch exactly: `subscription` table (`id`, `owner_type` default `'CLUB'`, `owner_id` `REFERENCES club(id)`, `product_id` `REFERENCES product(id)`, `status` default `'ACTIVE'`, `start_date` default `CURRENT_DATE`, `end_date` nullable, audit columns), plus `CREATE UNIQUE INDEX ux_subscription_active_owner ON subscription (owner_type, owner_id) WHERE status = 'ACTIVE'` (partial unique index, same pattern as `001` ADR-01).
2. `backend/src/main/resources/db/changelog/db.changelog-master.xml` — register the new migration.
3. `backend/src/main/java/com/cricketlegend/domain/SubscriptionOwnerType.java` — enum `CLUB`, `SECTION` (only `CLUB` validates — see spec Non-goals).
4. `backend/src/main/java/com/cricketlegend/domain/SubscriptionStatus.java` — enum `ACTIVE`, `CANCELLED`.
5. `backend/src/main/java/com/cricketlegend/domain/Subscription.java` — `@Entity`, mirrors `Product.java`'s Lombok/`@PrePersist` shape: `id`, `ownerType` (default `CLUB`), `ownerId`, `productId`, `status` (default `ACTIVE`), `startDate` (default today), `endDate`, audit fields. Plain `UUID` columns for `ownerId`/`productId` (see Flag #3).
6. `backend/src/main/java/com/cricketlegend/dto/ProductSummaryDto.java` — new small record `(UUID id, String name, String code)` for embedding in `SubscriptionDto` — genuinely a different shape/purpose than the full `ProductDto`, not a near-miss duplicate.
7. `backend/src/main/java/com/cricketlegend/mapper/ProductMapper.java` — add one method, `ProductSummaryDto toSummaryDto(Product product)` (reuse the existing mapper file, don't create a new one).
8. `backend/src/main/java/com/cricketlegend/dto/SubscriptionDto.java` — record embedding `ClubSummaryDto club` and `ProductSummaryDto product` alongside `id`/`ownerType`/`ownerId`/`status`/`startDate`/`endDate`/audit fields.
9. `backend/src/main/java/com/cricketlegend/dto/CreateSubscriptionRequest.java` — `ownerType`, `ownerId`, `productId` (all `@NotNull`), `startDate`/`endDate` optional.
10. `backend/src/main/java/com/cricketlegend/dto/UpdateSubscriptionRequest.java` — `productId` (`@NotNull`), `startDate`/`endDate` — no `ownerId`/`ownerType` (Club is immutable after creation per spec's UI Requirements: "you change the Product, not the owner").
11. `backend/src/main/java/com/cricketlegend/mapper/SubscriptionMapper.java` — `toEntity(CreateSubscriptionRequest)`; `SubscriptionDto toDto(Subscription subscription, ClubSummaryDto club, ProductSummaryDto product)` (MapStruct's multi-source-param support — verify the generated impl like `ProductMapper`'s Javadoc precedent did for `isFree`, don't assume).
12. `backend/src/main/java/com/cricketlegend/repository/SubscriptionRepository.java` — `extends JpaRepository<Subscription, UUID>`: `boolean existsByOwnerTypeAndOwnerIdAndStatus(...)` (duplicate-active pre-check); a `@Query` joining `Subscription`/`Club` via `JOIN Club c ON s.ownerId = c.id` for name search (mirrors `ProductRepository.search`'s null/blank-returns-everything shape).
13. `backend/src/main/java/com/cricketlegend/exception/ProductNotActiveException.java` and `DuplicateActiveSubscriptionException.java` — both `extends ConflictException`, same single-`String`-message shape as `DuplicateProductCodeException`.
14. `backend/src/main/java/com/cricketlegend/service/SubscriptionService.java` / `service/impl/SubscriptionServiceImpl.java` — business rules: `ownerType != CLUB` → `ValidationException`; missing `Club` → `NotFoundException`; `productId` not `ACTIVE` (on create AND update) → `ProductNotActiveException`; existing active subscription for the same owner (on create) → `DuplicateActiveSubscriptionException`; `update` changes `productId`/dates in place, never creates a row; `cancel` on already-`CANCELLED` → `InvalidStatusTransitionException`; `list` defaults sort to `startDate` descending when unsorted (Flag #5). Fetches the `Club`/`Product` needed for `SubscriptionDto`'s embedded summaries via their existing repositories (`ClubRepository`, `ProductRepository` — read `ClubRepository` first to confirm its exact query methods).
15. `backend/src/main/java/com/cricketlegend/controller/SubscriptionController.java` — `@RestController`, no class-level `@RequestMapping`, mirrors `ProductController` exactly: `GET /api/v1/platform/subscriptions` (`search` + `Pageable`), `GET .../{id}`, `POST ...` (201), `PUT .../{id}`, `POST .../{id}/cancel`.
16. **`Product`'s `status` filter** (Flag #2): `ProductRepository.search(...)` gains an optional `status` param (`AND (:status IS NULL OR p.status = :status)`); `ProductService.list()`/`ProductServiceImpl.list()`/`ProductController.list()` thread it through; `@RequestParam(required = false) ProductStatus status`.
17. **`ClubSummaryDto`'s `id` field** (Flag #1): add `UUID id` to the record, update `ClubMapper.toSummaryDto` to map it (read `ClubMapper.java` first for its exact current shape).
18. `backend/openapi/openapi.yaml` — add the five Subscription paths + `SubscriptionDto`/`CreateSubscriptionRequest`/`UpdateSubscriptionRequest`/`ProductSummaryDto` schemas; add `status` to `ClubSummaryDto`'s schema; add the `status` query param to the existing `GET /platform/products` path.

## Frontend — `frontend-builder`

Depends on the backend endpoints above existing first. Mirrors `ProductList.tsx`/`ProductFormPage.tsx`/`ProductForm.tsx` exactly — read all three fully first, they're the ground truth for this pattern's second real usage.

1. `ui/src/api/leadApi.ts` — add `id: string` to the existing `ClubSummary` interface (Flag #1) — no other change, `searchClubs()` already returns the full object.
2. `ui/src/api/productApi.ts` — add `status?: ProductStatus` to `ListProductsParams`, pass through in `listProducts()` when present (Flag #2).
3. `ui/src/api/subscriptionApi.ts` (new) — mirrors `productApi.ts`'s exact shape: `Subscription`, `SubscriptionPayload`, `UpdateSubscriptionPayload` types (embedding `club`/`product` summary shapes matching the backend DTOs), `Page<Subscription>`, `listSubscriptions`/`getSubscription`/`createSubscription`/`updateSubscription`/`cancelSubscription`.
4. `ui/src/components/SubscriptionForm/` (new shared component, four-file anatomy) — a Club picker (MUI `Autocomplete`, async search via the existing `searchClubs()`, **disabled when editing** — matches spec's "you change the Product, not the owner"), a Product picker (populated from `listProducts({ status: 'ACTIVE', size: 100 })` — a plain select is enough given an admin-curated catalog, not another Autocomplete), `startDate`/`endDate` fields, submit via `onSubmit` prop (component owns no mutation, same convention as `ProductForm`).
5. `ui/src/pages/admin/SubscriptionList.tsx` (new, at `/admin/configuration/subscriptions`) — `ListToolbar` (search by Club name, sort options Club name / Start date, "Add Subscription") + `RecordCard` grid (title = Club name, badge = `Active`/`Cancelled` using `positive`/`muted` tones, description = Product name, fields = Product code + Start date, footer = Edit) + pagination + `isError`/empty states — copy `ProductList.tsx`'s structure line for line where it applies, including the `isError` → `EmptyState` handling from the start (Flag: don't repeat `008`'s blank-screen review finding here).
6. `ui/src/pages/admin/SubscriptionFormPage.tsx` (new, at `/admin/configuration/subscriptions/new` and `/:id/edit`) — `RecordFormScreen` wrapping `SubscriptionForm`; actions bar has Save + nav "Cancel" (leaves the form) + (edit mode, non-`CANCELLED` only) a "Cancel Subscription" business action with inline confirm ("Keep subscription" dismiss button) — see Flag #4 for the exact labels. `isError` handling on the edit-mode fetch from the start, same as above.
7. `ui/src/App.tsx` — replace the `subscriptions` `EmptyState` route (currently nested under `configuration` in `ConfigurationHome`'s route tree) with `SubscriptionList`/`SubscriptionFormPage` at `/admin/configuration/subscriptions`, `/new`, `/:id/edit`. No change to `ConfigurationHome.tsx` itself — its `Subscriptions` card already points at the right path.
