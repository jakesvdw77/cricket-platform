# Plan 149: Account sign-up and club entry flow (beta)

Implements `docs/specs/149-signup-and-club-entry-flow.md` (draft 2026-11-13, requested by the owner for a beta on a real server). Branch `feat/149-signup-club-entry` (stacked on `feat/sign-up-link`, PR #166, which already carries the Create Account button, `/register`, `?idp=google`, the compact registration form and the Keycloak back links; rebase onto master once #166 merges). Commits local; push and PR per slice on the owner's go-ahead. Spec Decision 14 stands: **no data model change, no Liquibase migration**.

## Context
New parents and players can already register (Keycloak form or Google) and find players on `/welcome`, but the club they came from is dropped, and three paths dead-end for beta testers: a registered-but-unlinked account's second login lands on `/admin` "Not authorized" (F2), opening `/post-login` with no session 401s to `/admin` (F3), and `/welcome` shows "verify your email" for a suspended person (F4). The spec fixes these, carries the club by the **host** (the redirect URI; no cookie, signed value or stored hint, preselection only), and adds the beta deployment checklist. Nothing here redefines an entity, API shape or scope rule of the spec.

## Points to flag back to the human (the plan follows the spec; nothing is silently reinterpreted)
1. **Decision 6 puts `/register` in `AUTH_AWARE_PATH_PREFIXES` (`ui/src/auth/keycloak.ts`).** That turns on `check-sso` for `/register`, which means a **redirect round trip to Keycloak and back** for every signed-out visitor before `keycloak.register()` runs. The module comment forbids this for `/login` and `/post-login` (it once broke the OAuth callback). `/register` has no pending callback, so it is allowed, but it adds one hop and should be hand-checked in the beta smoke test. The alternative (await init without check-sso) cannot see an SSO session, so the spec's choice stands.
2. **Decision 8 versus the section-scoped manager fallback.** `PostLoginRedirect` keeps `/admin` for "a caller WITH a Person but no club-admin grant (e.g. a section-scoped manager)". The spec sends a verified-unlinked account to `/welcome` and keeps `/admin` only for an older response without `profiles`. The builder must confirm in `MeServiceImpl`/`MeAccess` that a section-scoped manager **does** get a `profiles` entry (then Decision 8 is safe) and, if not, keep them on `/admin` and stop for the human. The plan makes this the first check of slice B.
3. **`PublicAttemptTracker` writes a database row per lookup** (`REQUIRES_NEW` increment in a table). The by-slug lookup runs on every club-host `/login` and `/register` load, so each page view is a write, 60 per address per 15 minutes. Acceptable at beta scale and exactly what the spec names; an in-memory limiter is the alternative if it ever hurts.
4. **The backend has no `server.forward-headers-strategy` setting.** Per-address limits (077 and by-slug) read `getRemoteAddr()`, so behind the proxy everyone looks like one address unless `SERVER_FORWARD_HEADERS_STRATEGY=framework` is set in the environment. No code change (Spring relaxed binding), it is a **checklist item**, and the plan adds a startup test only if cheap.
5. **`LinkRequestForm` has no "preselect this club" input that does not need a person prefill.** It preselects `prefill.clubId`, then a name match, then the only club. The plan adds one optional prop `initialClubId` (and keeps the existing order) instead of faking a prefill.
6. **Three copies of the root-domain logic** exist (`utils/activeProfile.ts` `currentClubSlug`, `App.tsx` `isRootDomain` whose fallback is `'localhost'` while the others use `'localhost:5173'`, and `FindYourClubLogin.tsx`). The new `utils/clubFromHost.ts` replaces all three; the differing fallback is normalised (hostname without port) and covered by a test.
7. **Spec Open question 8 (harden the public search: min 2, cap 20) changes an existing public endpoint's behaviour**; built as written (default yes). The LIKE search does not escape `%` and `_` today; out of scope, noted for the roadmap.
8. **No token invitation link exists** (003's `Invitation` was never built). The "invitation links" are the club-aware agent-invitation and outcome emails; the plan only adds tests that their URLs are `https://{slug}.{root}/account`.

## Design (reuse first)

### Slice A: backend and theme (spec Rollout PR 1) — backend-builder
- `repository/ClubRepository`: `Optional<Club> findBySlugIgnoreCaseAndStatus(String slug, ClubStatus status)`; the search query gets `ORDER BY c.name` and is called with a 20-row limit (`Pageable`/`findTop20`-style, keep `searchActiveByNameOrSlug` for admin untouched if used elsewhere: check).
- `service/ClubSearchService` + `impl/ClubSearchServiceImpl`: `search` trims, returns empty under 2 characters, caps at 20; new `Optional<ClubSummaryDto> findActiveBySlug(String slug)` (`@Transactional(readOnly = true)`, lowercases, validates against `^[a-z0-9]+(-[a-z0-9]+)*$` and length ≤ 63 before touching the repository, maps with the existing `ClubMapper.toSummaryDto`).
- `controller/PublicClubController`: `GET /api/v1/public/clubs/by-slug/{slug}` takes `HttpServletRequest` for `getRemoteAddr()`, applies the 077 limiter, returns the summary or 404 with one `NotFoundException("Club not found")` for unknown, inactive and malformed alike. Limiter: reuse `PublicAttemptTracker.increment("club-slug:" + address, MAX + 1)` with a named constant `MAX_LOOKUPS_PER_ADDRESS = 60`; over the limit `PublicRateLimitedException(secondsUntil(...))` (existing 429 handler). Put the limiter call in a small `service/support` class (pure + tracker) rather than in the controller.
- `exception/EmailOnPlayerRecordException extends ConflictException` (`CODE = "EMAIL_ON_PLAYER_RECORD"`, the spec's message), its own `GlobalExceptionHandler` method (409 `ProblemDetail` with property `code`, same pattern as `handleEmailNotVerified`); `MeServiceImpl.register` throws it instead of the generic `ConflictException`. A suspended person stays `AccessDeniedException` 403 without the code.
- `backend/openapi/openapi.yaml` by hand: the new path, the search note (min 2, cap 20), the 409 `code` on `/me/register`, the 429 on by-slug.
- Theme: `keycloak/themes/cricketlegend/login/login-verify-email.ftl` + `messages/messages_en.properties` gain the one line "Open the link on this device to carry on where you left off." (manual check at 320 and 1280 px).
- (No scratch-copy rule is broken: backend is built and tested only in an rsync'd copy, never `mvn` in `backend/`.)

### Slice B: the dead ends (spec Rollout PR 2) — frontend-builder
- First check (flag 2): confirm `profiles` for a section-scoped manager; stop and report if the assumption fails.
- `pages/view/PostLoginRedirect.tsx`: await `keycloakInitPromise`; if `!keycloak.authenticated` (no session, no pending callback) call `keycloak.login({ redirectUri: origin + '/post-login' })` and do not call `activate` (gate the query with `enabled: ready`); a verified account with **no profiles, no platform admin, no club-admin grant and no players goes to `/welcome`** whether or not a `Person` exists (Decision 8); the `/admin` fallback stays only for a response with no `profiles` field; 403 without `EMAIL_NOT_VERIFIED` is still the suspended `StatusScreen`.
- `pages/view/FindYourPlayersPage.tsx`: failure classification by code, not status: `EMAIL_NOT_VERIFIED` keeps the verify-email warning; a 403 without the code shows `StatusScreen kind="suspended"`; a 409 `EMAIL_ON_PLAYER_RECORD` shows an `Alert severity="warning"` with the API message and two compact actions ("Use A Different Account": `keycloak.logout({ redirectUri: origin + '/login' })`; "Ask The Club To Correct It": opens the ask-the-club form); "No player found" shows the signed-in address and a quiet "Use A Different Account".

### Slice C: club awareness (spec Rollout PR 3) — frontend-builder
- `utils/clubFromHost.ts` (pure): `rootDomain` (with port, for building links), `rootHostname`, `isRootDomain()`, `clubSlugFromHost()`, `clubAddress(slug, path)`; `utils/activeProfile.ts` re-exports `currentClubSlug` from it; `App.tsx` and `FindYourClubLogin.tsx` use it.
- `api/leadApi.ts`: `getClubBySlug(slug)` returning `ClubSummary | null` (404 to null; other errors throw) and a `useClubFromHost()` hook (react-query key `['public-club', slug]`, enabled only on a club host, `retry: false`, long `staleTime`) in `hooks/`.
- `pages/view/Login.tsx` and `Register.tsx`: on a club host look the club up first: loader while pending; **404 shows `StatusScreen kind="not-found"`** with one gold compact "Go To The General Page" (root origin) and never calls Keycloak; a lookup error **fails open** to Keycloak; the root domain does no lookup. `Register` also awaits `keycloakInitPromise` and sends an authenticated person to `/post-login` (needs `/register` in `AUTH_AWARE_PATH_PREFIXES`, comment updated: flag 1).
- `pages/view/LandingPage/FindYourClubLogin.tsx`: the "new here" row is club-aware: with a remembered club (`login:lastClub`) it reads "New to <Club>?" and Create Account / Continue With Google go to `clubAddress(slug, '/register')` and `/login?idp=google`, with a "Not <Club>? Search Above" cue on the same row that clears the memory; with none, today's club-free behaviour; picking a result and Platform admin unchanged.
- `FindYourPlayersPage.tsx` + `LinkRequestForm.tsx`: on a club host a "Welcome to <Club>" line above the heading (display face, one line, truncates on a phone); matches ordered visited club first (client-side, none hidden or added, the server response untouched); the form's club select starts on the visited club (new optional `initialClubId` prop), on the root domain on the remembered club (preselection only).
- Copy rules: second person allowed on landing, dialog, `/welcome` and Keycloak; no "you/your" in the Hub pages. Shared compact `Button`, Title Case, no hex, `minmax(0, 1fr)` tracks, 390 px, no lone control in its own row.

## Risks
- The `/register` check-sso hop (flag 1) and the section-scoped manager route (flag 2) are the two behaviours most likely to surprise; both have a named check.
- The other-browser verification case lands on the root domain by design (Decision 12); the beta smoke test confirms it is merely inconvenient.
- Registration on a public beta invites spam: Verify Email, brute-force detection and the instant "User registration Off" switch are the controls (Open question 11).
