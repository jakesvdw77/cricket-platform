# Plan: 121 Player Hub menu and Field Directory

Spec: `docs/specs/121-player-hub-menu-and-fields.md` (approved 2026-10-24, amended the same day with Decisions 22 and 23). Nothing here redefines an entity, an API shape or a scope rule. Standing rules: build first, the owner hand-checks between checkpoints, tests and the standards review come after the owner approves, no `mvn` inside the live `backend/` (use an rsync'd scratch copy and hand-edit `openapi.yaml`), `nvm use 22.12.0` before any `ui/` command.

## Flags for the owner (spec gaps, not guessed)

1. **Cap marker.** Decision 21 wants a "showing the first 200" note, but the API Contract returns a bare `List<FieldDto>`, which cannot carry a truncated flag. Plan: the 200 cap is server side and the UI shows the note when `length === 200`. A real `truncated` flag is a contract change and needs a spec edit first.
2. **Active matches.** The spec does not say whether away fields come from active matches only. Plan: `m.active = true`, as `countActiveByPlayingAreaIds` does. Confirm.
3. **Owner nullability.** `owner_name` is non-null in the entity but `FieldDto.owner` is nullable: map a blank value to null.
4. **DTO name.** A `FieldDto` clash check is the first step in B. Fall back to `MyFieldDto`, as the spec allows.
5. **Profile edit Back target.** Decision 15 and 22 say the footer reads "Back to Profile" in the edit views. Plan: the label is fixed, the target is the Profile page the view was opened from (for example Contact), not the Profile sub menu. Confirm.
6. **Per-page edit and the PUT.** The scoped edit forms send the existing whole-whitelist `PUT /api/v1/me/players/{key}` with the page's values merged over the current values. The first step in A is to confirm `MyPlayerServiceImpl.update` treats an unchanged value as a no-op (and logs field names only); if it nulls omitted fields the merge covers it, and if it audits unchanged values the plan adds a diff before sending. No API change either way.

## Checkpoint B: Field Directory endpoint and screen, and the agents list for every linked agent

Agents: backend-builder and frontend-builder in parallel against the spec contract; the test-writer follows after approval. B's backend has no dependency on A and can start while A is under review.

**Backend** (`backend/src/main/java/com/cricketlegend/`)
- `dto/FieldDto.java` as a record with the 11 spec keys exactly (`MyFieldDto` if there is a clash); `mapper/MyFieldMapper.java` (MapStruct from `PlayingArea`, `home` as an extra source parameter, address lines flattened, reusing `PlayingAreaMapper.toDto(Address)` through `uses`).
- `service/MyFieldService.java` and `service/impl/MyFieldServiceImpl.java`, `@Transactional(readOnly = true)`: the club comes from `MyPlayerAccess.resolve(auth, key).profile().getClubId()`; home fields from `ClubPlayingAreaRepository` (new `findByClubIdAndHomeTrue`); the current season from `SeasonResolution.currentSeasonId(seasonRepository.findByClubId(clubId))`; away fields from a new `MatchRepository` query for the distinct non-null `playingAreaId` of that club's active matches in the current season. Merged-away ids resolve to `mergedIntoId`; REJECTED, merged and non-`CRICKET_FIELD` rows are excluded; the rest is loaded with `PlayingAreaRepository.findAllById`. Home is de-duplicated against away, ordered home first then by case-insensitive name, and capped at 200. Reuse `PlayingAreaMatchResolver` for the merge-target logic if it exposes it; do not copy it.
- `controller/MePlayersController.java`: add `GET /{playerKey}/fields` and the `MyFieldService` parameter, with no `@PreAuthorize`, as for the other methods there.
- **Agents list (Decision 23):** in `MyPlayerServiceImpl` (and the `MyPlayerDto` agent entry record and its mapper), fill `agents` for every linked agent of the held player and for the adult player on their own record, ordered primary (`main`) first, then by case-insensitive name, then link id; set `maskedEmail` and `linkId` only when the caller is the main agent (null otherwise, omitted from the JSON by the existing null-handling), never any other contact field; `agentCount`, `canManageAgents` and `myLinkId` unchanged. Reuse the existing masking helper and the existing `INVITED`/`ACTIVE` status mapping; no new exception type and no authorisation change.
- `backend/openapi/openapi.yaml` by hand: one path and one schema for fields, and the changed description of `MyPlayerDto.agents` (nullable `maskedEmail` and `linkId`). No migration.

**Frontend**
- `ui/src/api/myPlayersApi.ts`: the `FieldDto` type and `useMyPlayerFields(playerKey)` with key `['my-players', playerKey, 'fields']`; the agent entry type makes `maskedEmail` and `linkId` optional.
- `HubFields.tsx` (replacing the placeholder) and a hub-local `HubFieldCard.tsx`; `fieldFormat.ts` for the pure helpers `isHttpsUrl`, `joinAddress`, `countryName` (grep for an existing utility first) and `matchesSearch`.
- The search uses `darkFieldSx`, buttons use the compact `Button` with `hubOutlineButton`, and Directions is an `<a target="_blank" rel="noopener noreferrer">`. States: the existing `Skeleton`, an `Alert` with retry, the two empty copies, a note that is always shown, and the 200 note when the list length is 200.
- In `hubNav.ts`, `club.fields` loses its `soon` flag. Client side search over the unpaged list is allowed because the spec fixes the contract as unpaged and capped.
- `AgentsPage.tsx`: for a non-main caller the list now arrives, so render names and tags without the masked email or Cancel invitation (the count line stays only as the fallback when no list is sent).

**Tests (after approval):** JUnit `MyFieldServiceImplTest` (merge of home and away, de-duplication, exclusions, ordering, the cap, a null season) and `MyPlayerServiceImplTest` agents mapping (primary first, masked email and link id for the main agent only); integration `MePlayersFieldsIT` (home and away rows, a free-text venue adds nothing, a field in a non-current season is excluded, a merged field resolves, REJECTED is excluded, UNVERIFIED is returned with `verified=false`, two-club isolation, 404 for a foreign, malformed, dropped-out or manager-but-unlinked key, 401 without a token, 403 when SUSPENDED, the exact key set with no manager-only fields) and an agents integration test (main agent gets names, masked emails and link ids with the primary first; a second linked agent gets the same list and order with no `maskedEmail` and no `linkId` and no email text anywhere in the body; INVITED rows included for both; adult player on their own record as today; a key the caller does not hold is 404); `LayeringRulesTest` unchanged; Vitest `fieldFormat.test.ts` and `HubFields.test.tsx` (cards, tags, owner hidden, Directions, search, the states, the refetch on player change, no Edit or Add); stories; a hand review of the `openapi.yaml` diff.

**Risks:** the match query (indexed by club and season) needs a performance check; a null `ownerName`; `mapUrl` scheme re-validated in the UI; the "Field Directory" label wrapping in the 220 px column; the agents change is the first time a non-main agent receives other agents' names, so the integration test must prove no email, phone or person id leaks to them and that the `linkId` is absent (it is used by the main agent only).

**Owner checks:** real club data with home and away fields, a verified and an unverified field, Directions opening a new tab, a two-club parent switching players, and the Agents page as a second parent (names visible, no emails, no Cancel invitation, primary first).

**Order:** repository queries, then service and mapper, then controller and `openapi.yaml` (backend, fields and agents in separate commits); in parallel `fieldFormat`, then the API hook, then `HubFields`, then the Agents page switch (frontend); then integrate and run both.
