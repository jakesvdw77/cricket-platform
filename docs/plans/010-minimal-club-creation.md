# Implementation Plan — 010: Minimal Club Creation

## Context

`Club`/`ClubStatus`/`club` table already exist as a minimal stub (`backend/src/main/resources/db/changelog/v1/001-prerequisite-club-person.sql`, `domain/Club.java`, `domain/ClubStatus.java`), built for `004-landing-page.md`'s public club-search typeahead. Nothing can create one — the only way a `Club` gets into the database today is a direct SQL insert, which is exactly what blocked manually testing `009-subscriptions.md` (a `Subscription` FKs to a real `Club.id`). This plan implements `010-minimal-club-creation.md`: the smallest useful admin CRUD around the existing entity — create/list/edit/suspend/reactivate — landing status `ACTIVE` immediately, no branding/section/invitation flow (that's `003-club-onboarding.md`'s full scope, unbuilt).

Mirrors `Product`'s exact shape throughout (`ProductController`/`ProductServiceImpl`/`ProductRepository`/`ProductMapper`/`ProductDto`/`CreateProductRequest` on the backend; `ProductList.tsx`/`ProductFormPage.tsx`/`ProductForm`/`productApi.ts` on the frontend — all read in full during planning, confirmed as the ground truth). `/api/v1/platform/**` is already gated by `platform_admin` at the URL-matcher level in `SecurityConfig.java` — no security config changes needed, `/platform/clubs/**` is automatically covered.

## Flags for your review

1. **Slug format validation isn't specified by the spec beyond the reserved-word list.** Adding `@Pattern(regexp = "^[a-z0-9]+(-[a-z0-9]+)*$")` plus `@Size(min = 3, max = 63)` on `CreateClubRequest.slug`/`UpdateClubRequest.slug` (lowercase alphanumeric + single hyphens, DNS-label-length bounds) — rejected via the existing `MethodArgumentNotValidException` handler, same as `CreateProductRequest`'s `@NotBlank`/`@Size` fields. The reserved-word check (list membership, case-insensitive) can't be a bean-validation annotation cleanly, so it's a service-layer check throwing a new `ReservedSlugException extends ValidationException` (400) — not named in the spec, but follows `docs/standards/backend.md`'s "prefer a specific, named exception" rule the same way `DuplicateSlugException` (which the spec *does* name) does.
2. **The ADR-04 reserved-word list** (`www, auth, api, app, admin, static, mail, cdn, status, docs`) lives as a `private static final Set<String>` in `ClubServiceImpl` for now — `002-realm-subdomain-auth.md`'s `TenantResolutionFilter` doesn't exist yet to share it with. Flagging so it isn't forgotten as a future extraction point once `002` is actually implemented.
3. **New `ClubDto`, distinct from the existing `ClubSummaryDto`.** `ClubSummaryDto` (`id`, `name`, `slug`) is the public-facing shape `004`'s search and `009`'s Subscription form already consume — left untouched. This admin screen needs `status` + audit fields too, so it gets its own `ClubDto` record (mirrors `ProductDto`'s shape) and its own `ClubMapper.toDto(Club)` method added alongside the existing `toSummaryDto`, not a change to the summary shape.
4. **Default sort for the Club list**: `name` ascending when unsorted — no natural equivalent to `Product.displayOrder` or `Subscription.startDate` exists on `Club`, so alphabetical is the most usable default for "find the club I'm looking for." My call, flagging since it's a real behavior choice like `008`/`009`'s equivalent flags were.
5. **Slug stays editable on update** (per the spec's own User Stories: "I can edit a Club's name **or slug**"), re-validated against format + reserved-word + uniqueness-excluding-self on every update — same shape as `Product.code`'s `existsByCodeIgnoreCaseAndIdNot` pattern, just for slug.

## Backend — `backend-builder`

1. `backend/src/main/resources/db/changelog/v1/005-add-club-audit-columns.sql` — `ALTER TABLE club ADD COLUMN created_at TIMESTAMPTZ NOT NULL DEFAULT now(), ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now(), ADD COLUMN updated_by UUID;` (exact column types match `003-add-product.sql`'s precedent).
2. `backend/src/main/resources/db/changelog/db.changelog-master.xml` — register the new migration.
3. `backend/src/main/java/com/cricketlegend/domain/Club.java` — add `createdAt`/`updatedAt`/`updatedBy` fields + `@PreUpdate` hook, mirroring `Product.java`'s exact shape (its `@PrePersist` already sets `status` default — extend it to also default `createdAt`/`updatedAt` the same way `Product`'s does).
4. `backend/src/main/java/com/cricketlegend/dto/ClubDto.java` — new record: `id, name, slug, status, createdAt, updatedAt, updatedBy` (mirrors `ProductDto`'s field ordering convention: identity → business fields → status → audit).
5. `backend/src/main/java/com/cricketlegend/dto/CreateClubRequest.java` — `name` (`@NotBlank`), `slug` (`@NotBlank`, `@Pattern`, `@Size(min=3,max=63)`) — see Flag #1.
6. `backend/src/main/java/com/cricketlegend/dto/UpdateClubRequest.java` — same shape as `CreateClubRequest` (`name`, `slug`) — no `status` field, status only moves via the dedicated suspend/reactivate endpoints (matches the spec's API Contract table exactly).
7. `backend/src/main/java/com/cricketlegend/mapper/ClubMapper.java` — add `ClubDto toDto(Club club)` alongside the existing `toSummaryDto` (read the current 13-line file first — trivial addition, MapStruct maps by convention, no explicit `@Mapping` needed since field names match).
8. `backend/src/main/java/com/cricketlegend/repository/ClubRepository.java` — add to the existing interface (don't touch `searchActiveByNameOrSlug`, `004`'s method stays untouched): `boolean existsBySlugIgnoreCase(String slug)`, `boolean existsBySlugIgnoreCaseAndIdNot(String slug, UUID id)`, and a `@Query` for the admin list — case-insensitive substring match against name OR slug, **no status filter** (unlike `004`'s search, this admin list must show every status, not ACTIVE-only) — mirrors `ProductRepository.search`'s shape minus the status param.
9. `backend/src/main/java/com/cricketlegend/exception/DuplicateSlugException.java` — `extends ConflictException`, same one-line shape as `DuplicateProductCodeException`.
10. `backend/src/main/java/com/cricketlegend/exception/ReservedSlugException.java` — `extends ValidationException` (see Flag #1).
11. `backend/src/main/java/com/cricketlegend/service/ClubService.java` / `service/impl/ClubServiceImpl.java` — new service, separate from `ClubSearchService` (same separation `009` kept between `SubscriptionService` and `ProductService`). Methods: `create`, `get`, `list`, `update`, `suspend`, `reactivate`. Business rules: format validated by bean validation; reserved-word list checked in `validateSlug(slug)` helper (case-insensitive, checked on create and update) → `ReservedSlugException`; slug uniqueness (excluding self on update) → `DuplicateSlugException`; `create` sets `status = ACTIVE` directly (bypassing `Club`'s `@PrePersist` default of `ONBOARDING` — set explicitly on the entity before save, not by changing the default, since the default stays `ONBOARDING` for any future direct-insert or `003`-era code path); `suspend` on an already-`SUSPENDED` club → `InvalidStatusTransitionException` (reused, not new); `reactivate` on a non-`SUSPENDED` club → same; `list` defaults sort to `name` ascending when unsorted (Flag #4).
12. `backend/src/main/java/com/cricketlegend/controller/ClubController.java` — `@RestController`, no class-level `@RequestMapping`, mirrors `ProductController` exactly: `GET /api/v1/platform/clubs` (`search` + `Pageable`), `GET .../{id}`, `POST ...` (201), `PUT .../{id}`, `POST .../{id}/suspend`, `POST .../{id}/reactivate`.
13. `backend/openapi/openapi.yaml` — add the six Club paths + `ClubDto`/`CreateClubRequest`/`UpdateClubRequest` schemas, matching `008`'s Product schema additions' shape.

## Frontend — `frontend-builder`

Depends on the backend endpoints above existing first. Mirrors `ProductList.tsx`/`ProductFormPage.tsx`/`ProductForm`/`productApi.ts` exactly — this pattern's third real usage (after `008`, `009`).

1. `ui/src/api/clubApi.ts` (new) — mirrors `productApi.ts`'s shape: `Club` (`id, name, slug, status, createdAt, updatedAt, updatedBy`), `ClubPayload` (`name, slug`), `Page<Club>` (reuse/re-export the existing `Page<T>` type from `productApi.ts` the way `009`'s `subscriptionApi.ts` already does, per that spec's precedent — don't redefine a third copy), `listClubs`/`getClub`/`createClub`/`updateClub`/`suspendClub`/`reactivateClub`.
2. `ui/src/components/ClubForm/` (new shared component, four-file anatomy) — `name` + `slug` text fields only, inline format validation mirroring the backend's `@Pattern`/`@Size` rules for immediate feedback, submit via `onSubmit` prop (component owns no mutation, same convention as `ProductForm`/`SubscriptionForm`).
3. `ui/src/pages/admin/ClubList.tsx` (new, at `/admin/onboarding`) — `ListToolbar` (search by name/slug, sort options Name / Created date, "Add Club") + `RecordCard` grid (title = name, badge = `Active`/`Suspended`/`Onboarding` using `positive`/`muted`/`neutral` tones per `RecordCard`'s existing `RecordCardBadgeTone` type, description = slug, footer = Edit) + pagination + `isError`/empty states from the start — copy `ProductList.tsx`'s structure line for line where it applies.
4. `ui/src/pages/admin/ClubFormPage.tsx` (new, at `/admin/onboarding/new` and `/:id/edit`) — `RecordFormScreen` wrapping `ClubForm`; actions bar has Save + nav "Cancel" + (edit mode) a single status-transition button: "Suspend" when `status === 'ACTIVE'`, "Reactivate" when `status === 'SUSPENDED'`, with the same inline-confirm pattern as `008`'s Retire / `009`'s Cancel Subscription. `isError` handling on the edit-mode fetch from the start.
5. `ui/src/App.tsx` — replace the single `<Route path="onboarding" element={<EmptyState .../>} />` with three flat sibling routes (matching how `products`/`subscriptions` sit as flat siblings under `configuration`, not nested behind an index): `onboarding` → `ClubList`, `onboarding/new` → `ClubFormPage`, `onboarding/:id/edit` → `ClubFormPage`. Sidebar label in `AdminHome.tsx` stays "Club Onboarding" — no change there.
