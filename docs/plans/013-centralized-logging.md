# Implementation Plan — 013: Centralized Logging

## Context

The backend has no real logging setup today: SLF4J+Logback arrives transitively via `spring-boot-starter-web` and is entirely unconfigured beyond one `logging.level.com.cricketlegend=DEBUG` line in `application-dev.properties` — no `logback-spring.xml`, no request correlation, nothing shipped anywhere beyond a developer's own console. `013-centralized-logging.md` closes that gap: a real `logback-spring.xml` (console + a Loki sink), an MDC filter stamping `requestId`/`username`/a path-derived `clubId` onto every log line, a first `docker-compose.logging.yml` (Loki + Grafana, pre-wired), an ArchUnit rule banning `System.out`/`System.err`, and the matching `docs/standards/backend.md` edit. No frontend surface at all — this plan is backend + local infra only.

This plan was produced after reading the spec in full, `docs/standards/backend.md` in full (for the Non-negotiables list this spec amends and the existing class-skeleton/enforcement conventions), and the real current state of every file this touches: `backend/pom.xml` (no logging dependency declared today), `backend/src/main/java/com/cricketlegend/config/SecurityConfig.java` (confirmed exactly how JWT auth is wired — `.oauth2ResourceServer(oauth2 -> oauth2.jwt(...))`, no custom filter added to the chain anywhere yet), `backend/src/test/java/com/cricketlegend/architecture/LayeringRulesTest.java` (the existing ArchUnit suite's exact shape), and `backend/src/main/resources/application.properties` (the exact `${ENV_VAR:default}` comment-and-property style `012-club-profile.md` already established, to match).

## Flags for your review

1. **`RequestCorrelationFilter` must NOT be a `@Component` — the spec's own code sketch has this wrong, and it's a real bug, not a style nitpick.** `OncePerRequestFilter` implements `jakarta.servlet.Filter`. If it's also `@Component`-annotated, Spring Boot's own filter auto-registration (`FilterRegistrationBean` auto-configuration) will register it a *second* time as a generic servlet-container filter, independently of — and in addition to — the `http.addFilterAfter(...)` wiring inside `SecurityConfig`'s `filterChain()` bean. Net effect: it runs twice per request, generating two different `requestId` values and potentially double-writing the response header. The filter has zero constructor dependencies (no beans to inject — just `MDC`/`SecurityContextHolder`/`UUID` calls), so the fix is simple: drop `@Component`, construct it with `new RequestCorrelationFilter()` directly inside `SecurityConfig.filterChain()`, and add it via `http.addFilterAfter(new RequestCorrelationFilter(), BearerTokenAuthenticationFilter.class)`. Still fully unit-testable via direct instantiation, no Spring context needed for that tier.
2. **`loki-logback-appender` version `1.5.2` is unverified — the spec flagged this itself.** `backend-builder` must run `./mvnw dependency:tree` after adding it to confirm compatibility with whatever `logback-classic` version `spring-boot-starter-parent:3.4.3` actually resolves, and bump the pinned version if Maven reports a conflict. Same goes for the `grafana/loki:3.2.1`/`grafana/grafana:11.3.1` image tags in the compose file — spec-author picked reasonable, current-at-writing versions without being able to verify live; confirm they still resolve (`docker compose pull`) and bump if not, keeping tags pinned either way (never `:latest`).
3. **`docs/standards/backend.md` needs a real edit, not just a test-suite change** — the spec calls this out explicitly (Rollout Notes) and I'm carrying it into this plan as its own numbered step, not an afterthought, matching how `012`'s plan would have flagged an equivalent standards-doc change.

## Backend & Infra — `backend-builder`

No frontend slice — this spec is entirely backend + local infra tooling (confirmed by the spec's own Non-goals).

1. **`backend/pom.xml`** — add the `loki-logback-appender` dependency (see Flag #2 for version verification):
   ```xml
   <dependency>
       <groupId>com.github.loki4j</groupId>
       <artifactId>loki-logback-appender</artifactId>
       <version>1.5.2</version> <!-- verify against resolved logback-classic version, Flag #2 -->
   </dependency>
   ```
2. **`backend/src/main/resources/logback-spring.xml`** (new) — exact shape from the spec's Configuration & Infrastructure Changes §2: `springProperty` reads for `app.logging.loki-url` and `spring.profiles.active`, one shared `LOG_PATTERN` (`requestId`/`username`/`clubId` from MDC), a `CONSOLE` appender and a `LOKI` appender (`Loki4jAppender`, low-cardinality labels only — `app`/`environment`/`level`/`logger` — with `requestId`/`username`/`clubId` in the message body per the spec's explicit Loki-cardinality reasoning, never as labels), both wired under `<root level="INFO">`.
3. **`backend/src/main/java/com/cricketlegend/config/RequestCorrelationFilter.java`** (new) — the spec's sketch, with the Flag #1 correction (no `@Component`): `OncePerRequestFilter` reading/generating `X-Request-Id`, echoing it on the response, stamping `requestId` into MDC unconditionally; stamping `username` from `SecurityContextHolder`'s `Authentication` when present/authenticated/JWT-backed; stamping `clubId` via the spec's precise regex (`/clubs/([0-9a-fA-F]{8}-[0-9a-fA-F-]{27})(?:/|$)` against `request.getRequestURI()` — matches only the literal `clubs/` path segment, never a bare `{id}`, so `/subscriptions/{id}` is never misattributed); `MDC.clear()` in a `finally` block around `chain.doFilter(...)`.
4. **`backend/src/main/java/com/cricketlegend/config/SecurityConfig.java`** (edit) — inside the existing `filterChain(HttpSecurity http)` bean method, after the `.oauth2ResourceServer(...)` call: `http.addFilterAfter(new RequestCorrelationFilter(), BearerTokenAuthenticationFilter.class)` (see Flag #1 — plain `new`, not an injected bean), plus the new import (`org.springframework.security.oauth2.server.resource.web.authentication.BearerTokenAuthenticationFilter`). Update the class-level Javadoc to mention this addition, matching how it already documents the `012` `@EnableMethodSecurity` addition.
5. **`backend/src/main/resources/application.properties`** (edit) — new property, matching the exact comment-and-property style `012`'s `app.media.storage-path` already established immediately above it:
   ```properties
   # Grafana Loki push endpoint — 013-centralized-logging.md. Local dev default assumes
   # docker-compose.logging.yml's loki service is running on its default port.
   app.logging.loki-url=${LOKI_URL:http://localhost:3100}
   ```
6. **`backend/src/test/java/com/cricketlegend/architecture/LayeringRulesTest.java`** (edit) — add the import (`static com.tngtech.archunit.library.GeneralCodingRules.NO_CLASSES_SHOULD_ACCESS_STANDARD_STREAMS`) and one new `@Test void noClassesAccessStandardStreams() { NO_CLASSES_SHOULD_ACCESS_STANDARD_STREAMS.check(CLASSES); }`, same shape as the three existing rules in this file.
7. **`docs/standards/backend.md`** (edit, Flag #3) — add one line to the existing "Non-negotiables" bullet list: no `System.out`/`System.err`, use the injected SLF4J `Logger`, enforced by ArchUnit's `NO_CLASSES_SHOULD_ACCESS_STANDARD_STREAMS` (added to `LayeringRulesTest` per step 6).
8. **`docker-compose.logging.yml`** (new, repo root) — exact shape from the spec's §5: `loki` (pinned tag, port `${LOKI_PORT:-3100}`, named volume) and `grafana` (pinned tag, port `${GRAFANA_PORT:-3000}`, admin user/password env-var-overridable with `admin`/`admin` local defaults, anonymous auth off, provisioning directory bind-mounted read-only, `depends_on: loki`), two named volumes.
9. **`ops/grafana/provisioning/datasources/loki.yml`** (new) — the spec's provisioning file verbatim, so Grafana has the Loki datasource pre-wired on first boot.

## Tests — `test-writer`

Backend-only, matching the spec's Test Plan exactly — no component/E2E tiers apply (no frontend surface).

- **`RequestCorrelationFilterTest.java`** (new, unit, no Spring context — direct instantiation per Flag #1's correction makes this straightforward): inbound `X-Request-Id` reused verbatim when present; a fresh UUID generated when absent; the response echoes the same header back; `username` stamped only when `Authentication` is present/authenticated; `clubId` extracted correctly from `/api/v1/platform/clubs/{uuid}` and `/api/v1/platform/clubs/{uuid}/profile`; `clubId` NOT stamped for `/api/v1/platform/subscriptions/{uuid}` (the specific false-positive case the regex exists to avoid) or any path without a `clubs` segment; `MDC.getCopyOfContextMap()` is empty after the filter returns, including when the downstream chain throws.
- **A `@SpringBootTest` integration slice** (extend an existing suitable integration test class or add a new one under `backend/src/test/java/com/cricketlegend/`) — attach a Logback `ListAppender` to the root logger for the duration of the test; assert an authenticated mock-JWT request (`spring-security-test`) against a `/clubs/{id}` route produces a captured log line containing `requestId`, `username`, and `clubId` together; assert an unauthenticated request against `/api/v1/public/**` produces a log line with `requestId` only.
- **Architecture**: `LayeringRulesTest.noClassesAccessStandardStreams()` (added in step 6 above) passes against the current, already-clean codebase.

## Verification

- `cd backend && ./mvnw verify` — full build + unit + integration + ArchUnit, confirms the new filter, its tests, and the new architecture rule all pass, and that `logback-spring.xml`/the new dependency don't break existing Testcontainers-based integration tests (they shouldn't — Loki being unreachable in a test environment should not fail a test; confirm the `Loki4jAppender`'s own internal error handling degrades silently rather than throwing, and note in the PR if it needs an explicit `neverBlock`/error-handling setting to guarantee that).
- `docker compose -f docker-compose.logging.yml up`, then `cd backend && ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev` — confirm console output is unchanged from before this spec (human-readable, same as today), then open `http://localhost:3000` (Grafana, `admin`/`admin` unless overridden), confirm the Loki datasource is already present with no manual setup, and in Explore confirm log lines are arriving filtered by `app="cricketlegend"`.
- Manual request-correlation check: make one authenticated request against a `/api/v1/platform/clubs/{id}` route (e.g. via the already-running frontend, or `curl` with a real bearer token), read the `X-Request-Id` response header, and confirm every log line for that request in both the console and Grafana shares that same `requestId` plus the expected `username`/`clubId`.
- Manual ArchUnit check: temporarily add a throwaway `System.out.println(...)` anywhere under `backend/src/main/java`, confirm `./mvnw verify` fails at `LayeringRulesTest.noClassesAccessStandardStreams`, then remove it.
