# Plan 098: League schedule import

Implements `docs/specs/098-league-schedule-import.md` (approved 2026-10-10, defaults accepted). Plan only; the spec is not redefined. It is the first consumer of the framework built under plan 097 (backend and UI are on this branch, `feat/097-098-import-framework-and-schedule-import`, compiled but never run against a database). Completing this slice is what declares the framework done.

## Context
A league publishes a season's schedule as a spreadsheet; a club admin retypes 90 to 130 fixtures. This adds "Import schedule" for a league and season: our template (Excel or CSV), team names resolved by link or create with ranked proposals, a fully validated preview, an explicit confirm, a report, and a guarded delete. Re-import never duplicates a match. Result: `LEAGUE_SCHEDULE` handler plus its template, parsers, matcher, rules, entry points and the wizard page.

## Findings that differ from the spec's literals (to confirm)
1. **A match delete already exists** (spec 109): `MatchService.delete(auth, clubId, matchId)`, refusing with `MatchNotEmptyException` via `MatchEmptiness` (attachments: `DRAFT_RESULT`, `PUBLISHED_RESULT`, `POLL`, `SQUAD`, `TEAM_SELECTION`, `AVAILABILITY_WINDOW`), and removing empty `match_side` rows. Spec 098 says none exists and proposes `MatchService.deleteForImport`. **Plan: do not add `deleteForImport`; delete through `MatchService.delete`.** Blockers are computed first, in one batch, from `MatchEmptiness.attachmentsFor(ids)` (mapped to the spec's reason codes: POLL, GROUP_POLL, SQUAD_POOL, SELECTION, RESULT), so a 130-match check is a handful of queries and the delete is still all or nothing. Check at build that `TEAM_SELECTION` covers the spec's `ANNOUNCED_TEAM` (announced flag); if not, add an `ANNOUNCED_TEAM` check beside it.
2. **Results exist now** (specs 100 to 104), so the `RESULT` blocker is real, not a seam. The handler must not touch `MatchResultRepository` (ArchUnit owner list in `LayeringRulesTest`); it goes through `MatchEmptiness` and `ResultStatusResolver`. The spec's `MatchDeletionBlockerProvider` bean list is replaced by that existing component plus a thin mapper class `ScheduleDeletionBlockers`. The structural test (every FK into `match(id)` is covered, or on a "deleted with the match" list) is kept, written against `match_side`, `match_availability_poll`, `match_squad_member`, `section_availability_window_match`, `match_result`.
3. **New rule `DATE_OUTSIDE_LEAGUE_DATES` (Error).** `MatchService.create` calls `LeagueSeasonDates.assertWithin` and `MatchOutsideLeagueDatesException` (spec 111, whose standard says an import must check it per fixture). The spec's validation table lacks it, so a row could pass preview and fail commit. Add it, not downgradable.
4. **Framework additions (additive, small):**
   - `ReferenceProposalDto.Candidate` gains optional `source`, `seasonLabel`, `leagueName` (the spec's API lists them; band is derived from `confidence`). Mirror in `ui/src/api/importApi.ts`.
   - `ImportDecisionsDto.Resolution` gains optional `abbreviation` (for create) and the UI `ImportResolution` the same. Mapping of the spec's kinds onto the framework: `LINK_OWN_TEAM` and `LINK_LEAGUE_TEAM` are `kind LINK` with `targetKind` `OWN_TEAM` or `LEAGUE_TEAM`; `COPY_LEAGUE_TEAM` is `LINK` with `targetKind COPY_LEAGUE_TEAM` (`targetId` the source league team); `CREATE_LEAGUE_TEAM` is `CREATE` (`targetName` the tidied name); `SKIP_ROWS` unchanged. `identifiedAsOurs` stays a list of sheet names, with each name's own team recorded as an `OWN_TEAM` link resolution under the same key.
   - UI: `ImportWizard` gains `uploadExtras` (a slot whose values merge into `scope.params`, for `windowDays` under "Advanced"), label overrides for the Check and Done steps, and an identify-step description prop. `ImportResumePage` currently renders the wizard with no consumer props, so it needs a consumer registry (`importConsumers.ts`, type to wizard configuration) used by both the new page and the resume page; otherwise a resumed schedule loses its columns and wording.
5. **Resource for synonyms.** There is no YAML resource or loader today. Use a plain Java table (`TeamNameSynonyms`, a constant map plus tests) rather than `team-name-synonyms.yml`; the spec's wording is a maintained table, not a file format. Confirm SnakeYAML is not wanted before adding a loader.
6. **Existing helpers to reuse for `TeamNameMatcher`:** `TeamNameForms` (words, numbers, `compatible`, never equates "Villagers 1" and "Villagers 2"), `PlayerNameMatcher.canonical` and `editDistance`/`withinTolerance`, `NameAliases.normalise`, and the `import_alias` repository for remembered aliases (written by the framework from `CommitOutcome.aliases`; the handler never touches the table). The suffix hard rule, acronyms, synonyms and the confidence bands are new.
7. **`MatchService.createBatch`** does not exist (create is one row per call). Add it in `MatchServiceImpl`: shared lookups (league, season, league teams, own-team sections, league-season dates) fetched once, then the same per-row validation as `create`, including `assertCanAdministerAnySection`. One transaction; one bad row rolls everything back.
8. **`LeagueTeamService.create` and `copy` take no `Authentication`** (the section check lives in the controller). The handler runs under a club admin only, so call them directly; add a bulk `createAll` for new teams (one name-collision check) and reuse `copy` for COPY. Missing queries to add to `LeagueTeamRepository`: league teams of this league in earlier seasons, and league teams of the club's other leagues (by `leagueId in`, all seasons). Own teams affiliated to the league and season come from `LeagueAffiliationRepository.findByLeagueIdInAndSeasonId` then `TeamRepository.findAllById`.
9. **Time zone:** the handler converts local date and time to an `Instant` with `ImportOptions.zone()`; existing code reads it back in the server zone (a known gap, spec 097 R11). DST gap and ambiguity are Errors as the spec says.
10. **Match create does not auto-attach to availability windows** (read from `MatchServiceImpl.create`: no listener or hook). Open Question 11 therefore resolves to "no"; keep the integration test the spec asks for to prove it.
11. **UI facts:** `LeagueScheduleView` has no `pinned` action slot today (its `ContentControlsLine` has scope and switches only; `LeagueEditScheduleTab` already uses `pinned`); `LeagueEditScheduleTab` has no `clubId` prop; there is no inactive-league tooltip wording anywhere (only the missing-season text). Add "League is inactive" as the tooltip. `schedule` is a child of the `LeagueViewLayout` route, so the wizard route is registered as an absolute sibling, `fixtures/leagues/:leagueId/schedule/import`, beside the `edit` route (about `App.tsx:258`). `CopyLeagueTeamsDialog` is at `ui/src/pages/manage/leagueTeams/`, the precedent for the copy source choice.
12. **Fixtures:** the user's real sheet is not in the repo (`docs/samples/` is git-ignored). Build `example-1-converted.xlsx` and `.csv` from the spec's table (15 rows, 10 teams, 6 venues) and `example-1-source-merged.xlsx` for the merged-cells rejection; the owner's real file can replace it later.

## Slices

### A1. Backend pure logic (backend-builder, no I/O, no Spring where avoidable)
`service/support/schedule/` (package for the consumer's helpers; framework stays out of `service.adaptor`):
1. `ScheduleDateParser` (every accepted date form incl. `13-Sept-26`, two-digit year note, day-first only and the once-per-file warning, Excel serial, weekday prefix) and `ScheduleTimeParser` (`8.00`, `14h30`, `2:30 pm`, fraction, 24:00 error, DST gap and ambiguity).
2. `TeamNameSynonyms`, `TeamNameMatcher` (normalise and base/suffix split, synonyms, acronyms, numeric-suffix hard rule, token similarity, bands Exact 100, High 90 to 99, Medium 70 to 89, Low below 70, only Exact and alias preselected, reasons text; sources in the spec's order) as a `@Component` over batched candidate lists loaded once per preview.
3. `ScheduleConstants` (`OWN_TEAM_MIN_GAP_MINUTES` 120, `VENUE_MIN_GAP_MINUTES` 180, weekday 60%, `windowDays` default 14 range 1 to 60, "half the teams").
4. `LeagueScheduleValidator` (every code in the spec's table plus `DATE_OUTSIDE_LEAGUE_DATES`, each tagged `ALL`/`B`; `OURS_ONLY` skips the round rules) and `LeagueScheduleIdentity` (unordered resolved pair plus local date key, NEW, DUPLICATE, DIFFERS, POSSIBLE DUPLICATE (a) to (c), within-file DUPLICATE_ROW_IN_FILE and CONFLICTING_ROW_IN_FILE, free-text existing side compared by normalised name).

### A2. Backend handler and I/O (backend-builder, after A1)
1. `ScheduleFileReader` (over `XlsxTableReader`/`CsvTableReader`: sheet "Schedule", aliases `Home`, `Team 1`, `Away`, `Team 2`, `Ground`, `Start`, `_meta` scope-mismatch warning, version check) and `ScheduleTemplateWriter` (over `XlsxTemplateWriter`: Schedule, Instructions with example row, Lookups by template scope, hidden `_meta`, warn-only drop-downs; CSV header via `CsvTemplateWriter`).
2. `LeagueScheduleImportHandler` (`@Component`, implements `ImportTypeHandler`: type `LEAGUE_SCHEDULE`, version 1, supports ours scope, `scopeKey league:<id>|season:<id>`; parse, validate, propose (identify-ours and resolve steps), identity, planned changes, commit, `checkDeletion`, `delete`). Commit order per spec: league teams (new then copies, recording `copiedFrom` and the name/abbreviation/logo snapshot in `detail`), matches via `createBatch`, opt-in updates via `MatchService.update` (time and venue only, blocked or warned per the spec), then aliases returned in `CommitOutcome` for the framework to write. 3. Deletion: `ScheduleDeletionBlockers` over `MatchEmptiness` (batched), whole batch refused if any match is blocked, matches removed with `MatchService.delete`, created league teams removed only when unused, unedited (snapshot compare) and active, otherwise kept and reported, updates reverted from `previous`, non-blocking notes (edited since import, past, deactivated). Race handling: lock matches `FOR UPDATE`, re-check, map FK violation to `ImportDeletionBlockedException`.
4. `MatchService.createBatch`, `LeagueTeamService` bulk create, new repository queries (Finding 8), additive framework DTO fields (Finding 4), resource `backend/src/main/resources/imports/prompts/LEAGUE_SCHEDULE/v1.md` from the spec's Appendix A with the `{{...}}` placeholders filled by `aiPrompt(scope)`.
5. Hand-edit `backend/openapi/openapi.yaml` (additions only: the candidate and resolution fields). No migration (spec: none; framework tables already exist as 058).
Never run `mvn` in `backend/`: rsync to the scratch copy, JDK 17, compile only until the tests phase.

## Risks
Match delete reuse changes the spec's text (Finding 1): confirm. `ANNOUNCED_TEAM` coverage in `MatchEmptiness` unverified. `TeamNameMatcher` quality on real names (thresholds are constants, fixtures pin them). POI memory per request (2 MB cap). Time zone gap persists. Framework never run end to end yet, so first real file may expose framework defects (budget for fixes). Past matches get imported (spec R15 default). League-wide matches will appear in the club Matches list (spec R3 follow-up, not built here).
