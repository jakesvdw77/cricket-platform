# Plan: 042 — Match List Filters, Real Search, and Sort

## Context

`docs/specs/042-match-list-filters-and-search.md` (approved) closes a real, previously-flagged gap (`search` sent by the frontend but silently ignored by the backend, per `ui/src/api/matchApi.ts`'s own comment) and adds League/Season filters, cascading option-narrowing between Section/League/Season, client-side team-name search suggestions, `localStorage`-persisted filter selections, and an icon-based sort toggle defaulting to soonest-upcoming-first — all on `MatchList` specifically, not rolled out to any other list screen.

Two research passes (this session) confirmed the exact current shape of every file this touches and, importantly, corrected two assumptions the spec made:
- **`Specification`/`JpaSpecificationExecutor` has zero precedent anywhere in this backend** — this is a first-of-its-kind pattern here, not one matching an existing style. `spring-boot-starter-data-jpa` already provides it, no new dependency needed.
- **`localStorage` has zero precedent anywhere in this frontend** — the spec's own text ("see docs/standards/frontend.md/any existing localStorage call site") assumes a convention that doesn't exist. This plan defines the pattern from scratch, simply.
- `freeSolo` MUI `Autocomplete` also has no precedent (existing `Autocomplete` usages — `ClubPicker`, `PersonPicker`, `PlayingXiBuilder`, `LinkExistingRecordDialog` — are all non-`freeSolo`, controlled pickers). `ClubPicker`'s controlled `inputValue`/`open` handling is the closest reference, simplified since these suggestions are fully client-side (no server debounce needed for the *suggestion list* itself — only the actual backend search call stays debounced, exactly as today).
- **A real, previously-untested integration tier already exists and is the right place for Specification-correctness tests**: `backend/src/test/java/com/cricketlegend/repository/MatchRepositoryTest.java` (`@SpringBootTest @Import(AbstractIntegrationTest.class) @Transactional`, real saved entities, real Postgres via Testcontainers). `MatchServiceImplTest`'s existing pure-Mockito style (`verify(matchRepository, never()).findByX(...)`) cannot meaningfully test filter *correctness* once every branch collapses to one `matchRepository.findAll(Specification, Pageable)` call — see Flags for your review.

## Files to touch, in order

### Backend

**1. `backend/src/main/java/com/cricketlegend/repository/MatchRepository.java`** — add `extends JpaSpecificationExecutor<Match>` alongside the existing `JpaRepository<Match, UUID>`. Add a new small companion class/nested static class `MatchSpecifications` (or a separate `backend/src/main/java/com/cricketlegend/repository/MatchSpecifications.java` — prefer the separate file, matching this codebase's one-concept-per-file convention) with one static factory method per filter, each returning `Specification<Match>`:
- `clubId(UUID clubId)`
- `sectionIn(Collection<UUID> sectionIds)` — **ports the existing JPQL verbatim**: `(root, query, cb) -> cb.or(cb.in(root.get("homeTeamId")).value(teamIdsSubquery(...)), cb.in(root.get("awayTeamId")).value(...))`, built via `query.subquery(UUID.class)` selecting `Team.id` where `Team.sectionId IN :sectionIds` — same shape as `findByClubIdAndSectionIdIn`'s own JPQL, not redesigned.
- `matchDateOnOrAfter(Instant startOfToday)`
- `leagueIdEquals(UUID leagueId)`
- `seasonIdEquals(UUID seasonId)`
- `searchMatches(String term)` — `cb.or(` case-insensitive `LIKE` on `homeTeamName`/`awayTeamName`, plus an `EXISTS` subquery against `Team` for `homeTeamId`/`awayTeamId` matching `Team.name` case-insensitively `)`. Use `cb.like(cb.lower(...), "%" + term.toLowerCase() + "%")` — same case-insensitive-contains semantics the spec's own Non-goals settle ("nothing smarter").
Compose with `Specification.where(...).and(...)` — `null`/absent filters simply aren't `.and()`-ed in (Spring Data JPA's `Specification.and()` already null-safely no-ops on a `null` argument, confirm this in the actual `spring-data-commons` version this repo uses before relying on it — if not null-safe in this version, guard with `Specification<Match> spec = Specification.where(clubIdSpec); if (x != null) spec = spec.and(...)`).

**2. `backend/src/main/java/com/cricketlegend/service/MatchService.java`** (interface) — `list(...)` gains three new parameters: `String search`, `UUID leagueId`, `UUID seasonId` (inserted after `upcomingOnly`, before `Pageable`). New method: `MatchFilterOptionsDto filterOptions(Authentication authentication, UUID clubId, UUID sectionId, UUID leagueId, UUID seasonId, String search, boolean upcomingOnly)`.

**3. `backend/src/main/java/com/cricketlegend/dto/MatchFilterOptionsDto.java`** (new) — `public record MatchFilterOptionsDto(List<UUID> sectionIds, List<UUID> leagueIds, List<UUID> seasonIds) {}`.

**4. `backend/src/main/java/com/cricketlegend/service/impl/MatchServiceImpl.java`**:
- Refactor `list(...)`: keep the existing `accessibleSectionIds`/`assertCanAdministerSection`/`sectionAndDescendantIds` authorization/section-scoping logic **exactly as it is today** (this is authorization, not filtering — do not fold it into the generic `Specification` composition; compute the *authorized* section id set first, then build one `Specification<Match>` combining `clubId` + that authorized-section-set (via `MatchSpecifications.sectionIn`, only added when the caller is actually section-restricted or passed an explicit `sectionId` — an unrestricted caller with no explicit `sectionId` adds no section predicate at all, preserving today's `findByClubId` behavior exactly) + `upcomingOnly` + the three new filters, then call `matchRepository.findAll(spec, sorted).map(matchMapper::toDto)`, then `enrichAnnounced(...)` exactly as today.
- New `filterOptions(...)` method: same authorization resolution as `list()` (reuse a shared private helper — extract the "resolve which section ids this caller may see, given an optional explicit `sectionId`" logic out of `list()` into a private method both call, since it's now needed twice). Then, for each of the three returned arrays, build a `Specification<Match>` combining `clubId` + authorized-sections + `upcomingOnly` + **every filter except the one being computed** (e.g. `sectionIds` array's own query omits any section predicate but includes `leagueId`/`seasonId`/`search` if set), run it via `matchRepository.findAll(spec)` (unpaginated — this result set is bounded by however many distinct matches exist, and only distinct ids are extracted, not full rows returned to the client), then:
  - `leagueIds`/`seasonIds`: `matches.stream().map(Match::getLeagueId).filter(Objects::nonNull).distinct().toList()` (same for `seasonId`, which is never null).
  - `sectionIds`: **not just the direct `Team.sectionId` of each match's home/away team** — a parent `Section` in the tree must also read as "reachable" if any descendant is, or `SectionTreeSelect`'s own tree UI would show a parent as unreachable while a child underneath it isn't. Resolve each match's home/away `Team.sectionId` (one extra lookup — reuse a `Map<UUID, Team>` built from `teamRepository.findAllById(...)` over the distinct team ids in the result set, avoiding N+1), then **walk each resolved section's ancestor chain** (fetch the club's full `Section` list once — already small/bounded elsewhere in this codebase's own convention — build a `parentSectionId` lookup map, and add every ancestor of every directly-reachable section to the result set). Document this ancestor-closure step clearly in a Javadoc comment — it's a genuine, deliberate design decision, not an oversight, and the mirror-image of `AccessService.sectionAndDescendantIds`'s existing *downward* closure (this is *upward*).
- Add `MatchFilterOptionsDto` import, `TeamRepository`/`SectionRepository` as new constructor dependencies if not already present (check — `leagueRepository`/`seasonRepository`/`teamRepository` are likely already injected per the earlier research; `sectionRepository` may not be, since `list()` never previously needed to read `Section` rows directly, only ids via `AccessService`).

**5. `backend/src/main/java/com/cricketlegend/controller/MatchController.java`**:
- `list(...)`: add `@RequestParam(required = false) String search`, `@RequestParam(required = false) UUID leagueId`, `@RequestParam(required = false) UUID seasonId`, pass through to `matchService.list(...)`.
- New endpoint: `@PreAuthorize("@access.canAccessClub(authentication, #clubId)") @GetMapping("/api/v1/manage/clubs/{clubId}/matches/filter-options") public ResponseEntity<MatchFilterOptionsDto> filterOptions(Authentication authentication, @PathVariable UUID clubId, @RequestParam(required=false) UUID sectionId, @RequestParam(required=false) UUID leagueId, @RequestParam(required=false) UUID seasonId, @RequestParam(required=false) String search, @RequestParam(required=false, defaultValue="false") boolean upcomingOnly)`.

**6. `backend/openapi/openapi.yaml`** — regenerate (same manual-regen approach used for `040`: temporary local backend instance on a non-default port, `curl .../v3/api-docs.yaml`, verify the `servers.url` line still reads the real dev port before committing — a mistake made and caught once already this session).

- New: `export interface MatchFilterOptions { sectionIds: string[]; leagueIds: string[]; seasonIds: string[] }` and `export async function listMatchFilterOptions(clubId: string, params: Omit<ListMatchesParams, 'page' | 'size' | 'sort'>): Promise<MatchFilterOptions>` hitting `${matchesPath(clubId)}/filter-options`.

**8. `ui/src/components/ListToolbar/ListToolbar.tsx`** — new optional prop `sortToggle?: { value: 'asc' | 'desc'; ascLabel: string; descLabel: string; onToggle: () => void }`. When omitted, every existing call site's Sort `Select` renders byte-for-byte as today.

**9. `ui/src/pages/manage/MatchList.tsx`** — the largest single file change:
- New `leagueId`/`seasonId` state (`useState<string | null>(null)`), added to the existing page-reset effect's dependency array alongside `sectionId`.
- New `filterOptionsQuery` (`useQuery`, key `['managed-club', clubId, 'matches', 'filter-options', sectionId, leagueId, seasonId, debouncedSearch, upcomingOnly]`, calling `listMatchFilterOptions`) — `enabled: Boolean(clubId)`, same shape as the other always-on reference queries.
- Section/League/Season option lists each filtered client-side against `filterOptionsQuery.data`'s matching array before being passed to their respective picker — `SectionTreeSelect` (unchanged component, filtered `sections` prop plus ancestor-closure already resolved server-side so the tree still renders coherently), and two new `Input select`s for League/Season (plain `MenuItem`s, matching `SectionTreeSelect`'s trigger height/visual weight per the spec).
- New `localStorage` persistence — a small local helper (not a new shared hook/util unless a second call site ever needs it — YAGNI, this is the first and only use):
  ```ts
  const FILTERS_STORAGE_KEY = `matchList:filters:${clubId}`
  // on mount: try { const raw = localStorage.getItem(FILTERS_STORAGE_KEY); if (raw) { const parsed = JSON.parse(raw); setSectionId(parsed.sectionId ?? null); ... } } catch { /* ignore — storage unavailable/corrupt, start from defaults */ }
  // on change (useEffect deps: [sectionId, leagueId, seasonId]):
  try { localStorage.setItem(FILTERS_STORAGE_KEY, JSON.stringify({ sectionId, leagueId, seasonId })) } catch { /* ignore — storage full/unavailable, filters just won't persist this session */ }
  ```

## Flags for your review

- **The spec's Non-goals/Rollout Notes reference "docs/standards/frontend.md/any existing localStorage call site for the exact guard shape" and an implicit backend-style precedent for `Specification` usage — neither exists.** Both patterns are being introduced fresh by this plan, in the simplest form that satisfies the spec's own requirements (no new shared hook/util for `localStorage` unless a second call site ever needs one; a plain `Specification` composition with no new abstraction layer beyond `MatchSpecifications`'s static factory methods). Flagging this as a spec/reality gap caught here, per `docs/workflow.md`'s own stated purpose for this step — not silently patched around.
- **`MatchServiceImplTest`'s existing testing style changes shape**, not just gains new tests — the old "assert exactly one of four distinct repository methods was called" pattern stops being meaningful once there's one `findAll(Specification, Pageable)` entry point. Filter *correctness* moves to `MatchRepositoryTest`'s real-database tier, which is more correct anyway (a `Specification`'s actual predicate logic literally cannot be verified through a Mockito mock — only that it was passed to `findAll` at all). This is a real, deliberate shift in testing responsibility between two existing test files, not a coverage gap.
- **The `sectionIds` ancestor-closure requirement in `filterOptions()`** is a real design decision this plan is making that the spec's own text doesn't spell out explicitly (the spec only says "narrows to what's actually filterable," which is ambiguous about whether a parent section in the tree UI should read as reachable via a reachable descendant). Recommend proceeding with ancestor-closure (the alternative — leaving parent nodes looking "dead" in the tree when a child underneath them is actually selectable — reads as a real UI bug, not a minor style choice) but flagging it explicitly since it's not literally spelled out in `042`'s own text.
