# Implementation Plan — 008: Product Catalog Configuration

*Permanent record of the plan approved via `/plan-feature docs/specs/008-product-catalog.md`. The working copy Claude Code keeps under `~/.claude/plans/` is a scratch file; this is the git-tracked copy, kept alongside the spec it implements.*

## Context

`docs/specs/001-tenancy-identity-model.md`'s `Subscription` entity has a bare `plan` string with no structure behind it. `docs/specs/008-product-catalog.md` fixes that by giving a platform admin a real screen to define **Products** (subscription tiers — Free, Club Standard, Club Pro, etc.) with pricing and usage limits, so a later Subscriptions spec can point `Subscription.plan` at something real. `docs/specs/007-configuration-hub-overview.md` is the umbrella spec this depends on: it turns the `Configuration` sidebar item (already scaffolded in `006-post-login-home-shells.md` as a static `EmptyState` placeholder) into a real card-grid landing page, with `Products` as its one working card.

Neither spec has been planned or built yet — only the spec files exist. Per the "007 dependency" question asked before this plan was written, **007's minimal scope is folded into this plan** rather than run as a separate `/plan-feature` cycle first, since 007 is UI-only scaffolding (one new page, a router change, four `EmptyState` leaf routes) with no backend or data model of its own. This is recorded as `docs/plans/008-product-catalog.md` — 007 gets no separate plan file since it has nothing independently plannable beyond what's listed here.

## Flags for your review

Per `docs/workflow.md` step 5's "don't quietly patch around it" rule — six things resolved during planning, visible here before build starts:

1. **007 folded into 008, confirmed via `AskUserQuestion`.** This plan builds 007's `ConfigurationHome` landing page (card grid, router change, roadmap placeholders) alongside 008's full Product Catalog. No separate `docs/plans/007-*.md` file.
2. **Naming clash in spec 008's UI Requirements**: it names both the shared form component and its routed page `ProductForm`. Resolved as two distinct files: `ui/src/components/ProductForm/ProductForm.tsx` (the shared, four-file-anatomy component used by both create and edit) and `ui/src/pages/admin/ProductFormPage.tsx` (the thin routed wrapper that fetches/mutates and renders it). Same behavior the spec describes, just disambiguated file names.
3. **`billingInterval`'s "required unless `isFree`, default `MONTHLY`" reading.** Interpreted as: the column/domain default is `MONTHLY`, and the service applies that default server-side whenever `isFree=false` and the request omits it — only `price`/`currency` are hard-required (no sensible default exists for either). `billingInterval` is never rejected as "missing."
4. **`isFree` toggle has no existing shared component to reuse** — no `Switch`/`Toggle` exists anywhere in the codebase yet (confirmed by exploration). Built as a bare MUI `Switch`/`FormControlLabel` directly inside the new `ProductForm` shared component, not spun off into its own shared library component with a Claude Design pass — `docs/standards/frontend.md`'s extraction threshold is two-or-more real uses sharing markup, and nothing else needs a generic toggle yet.
5. **Frontend pagination is first-of-its-kind in this codebase.** No existing `Page<T>`-consuming pattern to copy (confirmed by exploration — zero matches for `useInfiniteQuery`/`Pageable`/`totalPages` anywhere in `ui/src`). `ProductList` implements the simplest compliant version: `useQuery` keyed on the current page index, calling the backend's `page`/`size` params directly, with Prev/Next controls — never a client-side slice of a full fetch, per `docs/standards/frontend.md`.
6. **New E2E test not wired into CI**, matching `005`'s plan's own precedent — `.github/workflows/ci.yml` has no Keycloak service today, and standing one up is a separate infra decision this feature doesn't need to make. The new `admin-configuration-products.spec.ts` documents its prerequisite (a seeded `platform_admin` test user) in a header comment and runs locally via `npm run test:e2e`, same as `005`'s `admin-login.spec.ts`.

## Backend — `backend-builder`

Mirrors `LeadController`/`LeadServiceImpl`/`LeadRepository`'s exact shape (flat `controller`/`service`/`service.impl`/`repository`/`domain`/`dto`/`mapper` packages, no class-level `@RequestMapping`, constructor injection, MapStruct mapping, `Page<T>` list endpoint with a default-sort helper). **No `SecurityConfig` change** — `/api/v1/platform/products/**` is already covered by the existing `.requestMatchers("/api/v1/platform/**").hasRole("platform_admin")` match. **Reuse the existing `InvalidStatusTransitionException`** (already used by `Lead`, per spec 008's own decision) — do not create a new one.

1. `backend/src/main/resources/db/changelog/v1/003-add-product.sql` — new migration, next sequential after `002-add-lead.sql`. Uses spec 008's own sketch verbatim: `product` table (`id`, `code`, `name`, `description`, `is_free`, `price`, `currency`, `billing_interval`, `max_period_months`, `max_sections`, `max_teams`, `max_players`, `status`, `display_order`, `created_at`, `updated_at`, `updated_by`), enums stored as `VARCHAR` (matching `Lead`'s convention — no native Postgres enum type), plus `CREATE UNIQUE INDEX ux_product_code ON product (LOWER(code))`.
2. `backend/src/main/resources/db/changelog/db.changelog-master.xml` — add the third `<include file="db/changelog/v1/003-add-product.sql" relativeToChangelogFile="false"/>` line.
3. `backend/src/main/java/com/cricketlegend/domain/ProductStatus.java` — enum `DRAFT`, `ACTIVE`, `RETIRED`.
4. `backend/src/main/java/com/cricketlegend/domain/BillingInterval.java` — enum `MONTHLY`, `ANNUAL`.
5. `backend/src/main/java/com/cricketlegend/domain/Product.java` — `@Entity`, Lombok `@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder` (mirrors `Lead.java`), `@Enumerated(EnumType.STRING)` on `status`/`billingInterval`, `@PrePersist` defaulting `status=DRAFT`, `displayOrder=0`, `createdAt`/`updatedAt=now()` when unset; `@PreUpdate` bumping `updatedAt`.
6. `backend/src/main/java/com/cricketlegend/dto/ProductDto.java` — `record`, full read shape (all entity fields).
7. `backend/src/main/java/com/cricketlegend/dto/CreateProductRequest.java` — `record` with `jakarta.validation`: `@NotBlank code`, `@NotBlank name`, `@NotNull isFree`, `@Positive` (nullable-safe) on `maxPeriodMonths`/`maxSections`/`maxTeams`/`maxPlayers`, `price`/`currency`/`billingInterval` left un-annotated at the bean-validation level since their requiredness is conditional on `isFree` — enforced in the service (see below), not via `@NotNull`.
8. `backend/src/main/java/com/cricketlegend/dto/UpdateProductRequest.java` — `record`, same editable fields as create, plus `status` (only `DRAFT`/`ACTIVE` are valid values here — the service rejects `RETIRED` sent through this path, since retirement is the dedicated endpoint below).
9. `backend/src/main/java/com/cricketlegend/mapper/ProductMapper.java` — `@Mapper(componentModel = "spring")`, `toEntity(CreateProductRequest)` (`@Mapping(target = "...", ignore = true)` for every server-managed field), `toDto(Product)`.
10. `backend/src/main/java/com/cricketlegend/repository/ProductRepository.java` — `extends JpaRepository<Product, UUID>`: `boolean existsByCodeIgnoreCase(String code)`, `boolean existsByCodeIgnoreCaseAndIdNot(String code, UUID id)`.
11. `backend/src/main/java/com/cricketlegend/exception/DuplicateProductCodeException.java` — `extends ConflictException`, same single-`String`-message constructor shape as `InvalidLeadFieldException`.
12. `backend/src/main/java/com/cricketlegend/service/ProductService.java` — interface: `create`, `get(id)`, `list(Pageable)`, `update(id, req)`, `retire(id)`.
13. `backend/src/main/java/com/cricketlegend/service/impl/ProductServiceImpl.java` — `@Service`, business rules: code uniqueness (case-insensitive, excluding self on update) → `DuplicateProductCodeException`; when `isFree=true`, clear `price`/`currency`/`billingInterval` server-side regardless of request payload; when `isFree=false`, require `price`+`currency` (missing → `ValidationException`) and default `billingInterval` to `MONTHLY` if omitted; `update`'s status transition only allows `DRAFT→ACTIVE` or same-status no-op, anything else (including `RETIRED` via this path) → `InvalidStatusTransitionException`; `retire` on an already-`RETIRED` product → `InvalidStatusTransitionException`; `list` applies a default sort by `displayOrder` ascending when the caller's `Pageable` carries no sort (mirrors `LeadServiceImpl`'s `withDefaultSort` helper).
14. `backend/src/main/java/com/cricketlegend/controller/ProductController.java` — `@RestController`, no class-level `@RequestMapping`: `GET /api/v1/platform/products` (`Pageable` param → `Page<ProductDto>`), `GET /api/v1/platform/products/{id}`, `POST /api/v1/platform/products` (`@Valid @RequestBody`, 201), `PUT /api/v1/platform/products/{id}`, `POST /api/v1/platform/products/{id}/retire`.
15. `backend/openapi/openapi.yaml` — hand-add the five paths (tag `product-controller`, matching the minimal-annotation style `LeadController` uses — only an `@ApiResponse` for the 201 create response) and three schemas (`ProductDto`, `CreateProductRequest`, `UpdateProductRequest`).

## Frontend — `frontend-builder`

Depends on the backend endpoints above existing first (build order: backend, then frontend). Reuses `Card`, `EmptyState`, `Input`, `Button` as-is; mirrors `ManagerDashboard.tsx`'s data-driven card-grid pattern and `LeadCaptureForm.tsx`'s local-state form conventions; mirrors `adminApi.ts`/`leadApi.ts`'s one-file-per-resource API client shape.

1. `ui/src/api/productApi.ts` — new, one file per `docs/standards/frontend.md`'s convention: `export interface Product { ... }` (full read shape), `export interface ProductPayload { ... }` (create/update shape), a local `Page<T>` interface matching Spring's JSON envelope (`content`, `totalElements`, `totalPages`, `number`, `size` — first paginated resource in the frontend, see Flag #5), and `listProducts(page, size)`, `getProduct(id)`, `createProduct(payload)`, `updateProduct(id, payload)`, `retireProduct(id)` async functions built on the shared `api` instance from `axiosConfig.ts`.
2. `ui/src/components/ProductForm/ProductForm.tsx` (+ `index.ts`, `ProductForm.stories.tsx`) — new shared component, four-file anatomy. Props: `initialValues?: Partial<ProductPayload>`, `onSubmit: (values: ProductPayload) => void`, `submitLabel: string`, `isSubmitting?: boolean`. Local `FormState`/`validate`/`handleChange` pattern per `LeadCaptureForm.tsx`. `isFree` as a MUI `Switch`/`FormControlLabel` (see Flag #4) that hides/disables `price`/`currency`/`billingInterval` fields when on. Component itself owns no mutation — the routed page below wires `useMutation` and passes `onSubmit`, keeping the component reusable/story-testable in isolation.
3. `ui/src/pages/admin/ConfigurationHome.tsx` — new page (not a shared component — `pages/**` don't need the four-file anatomy per `frontend.md`). One flat, data-driven array of 5 cards (mirrors `ManagerDashboard.tsx`'s `GROUPS`/`Card` grid, minus the two-group split — one group here): `Products` → `/admin/configuration/products` (real); `Subscriptions` → `/admin/configuration/subscriptions`, `Discounts & Promotions` → `/admin/configuration/discounts`, `Invoicing` → `/admin/configuration/invoicing`, `System Settings` → `/admin/configuration/settings` (all four `EmptyState` "Coming soon", per spec 007's table).
4. `ui/src/pages/admin/ProductList.tsx` — new page. `useQuery(['products', page], () => listProducts(page))`; `Card` grid (same responsive `sx` as `ManagerDashboard.tsx`) — one card per product showing name, price (or "Free"), the three limit fields as chips, and a status chip; an "Add Product" card/button to `/admin/configuration/products/new`; Prev/Next controls driven by the response's `totalPages` (see Flag #5); `EmptyState` when `content` is empty.
5. `ui/src/pages/admin/ProductFormPage.tsx` — new page, routed at both `/admin/configuration/products/new` and `/admin/configuration/products/:id/edit`. Reads `:id` via `useParams` (absent = create mode); when editing, `useQuery` fetches the existing product and feeds `ProductForm`'s `initialValues`; wires `useMutation` for `createProduct`/`updateProduct`, navigating back to the list on success; edit mode adds a "Retire" button with an inline confirm state (no `Modal` — doesn't exist yet, per spec 008's own UI Requirements) calling `retireProduct`.
6. `ui/src/App.tsx` — replace the single `<Route path="configuration" element={<EmptyState .../>} />` line with a nested subtree, still inside the existing `/admin` → `AdminHome` → `<Outlet>` chain:
   ```tsx
   <Route path="configuration">
     <Route index element={<ConfigurationHome />} />
     <Route path="products" element={<ProductList />} />
     <Route path="products/new" element={<ProductFormPage />} />
     <Route path="products/:id/edit" element={<ProductFormPage />} />
     <Route path="subscriptions" element={<EmptyState title="Subscriptions" description="Coming soon." />} />
     <Route path="discounts" element={<EmptyState title="Discounts & Promotions" description="Coming soon." />} />
     <Route path="invoicing" element={<EmptyState title="Invoicing" description="Coming soon." />} />
     <Route path="settings" element={<EmptyState title="System Settings" description="Coming soon." />} />
   </Route>
   ```
   No change to `AdminHome.tsx`'s `NAV_ITEMS` — the sidebar's `Configuration → /admin/configuration` entry already points at this subtree's `index` route.

## Post-build additions (from manual review of the shipped pages, after this plan was executed)

Both slices were built, independently verified (`mvn compile`/`npm run lint|test|build`), manually smoke-tested end-to-end in a real browser, and `test-writer` had just finished the test tiers (39/39 backend tests green) when a manual page-by-page review surfaced real spec gaps — three missing `Product` fields. `docs/specs/008-product-catalog.md` was updated first (Field Reference table, migration sketch, a new User Story, Test Plan/Acceptance Criteria rows, UI Requirements note), per usual "spec before code." Full detail lives there — summary for whoever picks this back up:

1. **`showAds`** (boolean, default `false`) — whether the subscribing club's public pages show ads under this product.
2. **`allowSubdomain`** (boolean, default `false`) — whether the club may use its own subdomain under this product.
3. **`allowWhitelisting`** (boolean, default `false`) — whether the club can configure the platform's Whitelisting feature under this product.

All three default off — a free/lower tier isn't granted any of them just by being free; an admin opts a specific product in explicitly. Backend and frontend ship as two separate follow-up passes this time (backend first, per direct instruction), not together as the original `007`+`008` build was.
