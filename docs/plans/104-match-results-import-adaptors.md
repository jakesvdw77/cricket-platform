# Plan: 104 — Match Results: Import Adaptors and the Result Processor

Spec: `docs/specs/104-match-results-import-adaptors.md` (merged to master via PR #120; first revision, **no AI**). Branch: `feature/104-import-adaptors` (created from master). On approval this file is copied verbatim to `docs/plans/104-match-results-import-adaptors.md`.

## Context

Results can only enter the platform by retyping them in the capture wizard (`100`, `101`). 104 adds an **adaptor framework** (one small stateless class per source format, discovered automatically) that turns any input into ONE common import JSON, and ONE **Result Processor** that resolves team and player names deterministically (exact + remembered aliases, normalised, initials/prefixes, ranked fuzzy suggestions that never auto-link), derives a **draft** result + scorecard and hands it to the existing wizard, where every non-exact player is flagged as a **guess** that blocks publish until confirmed. First adaptor: our own JSON. STUMPS PDF follows as its own spec. 104 is built before 103 so real scorecards prove the wizard's rules.

## Items to flag back to the human (spec says X, code says Y)

Each has a default the plan follows unless told otherwise.

1. **Name normaliser.** The spec says reuse `PlayerNameMatcher.canonical/canonicalSurname`. They exist (`service/support/PlayerNameMatcher.java`) but `canonical` collapses all spaces (word order lost), and there is **no tokeniser, initials, particle-abbreviation ("vdW"), surname-prefix or scoring** logic. Tiers 3 and 4 are new code. Default: new package-private helpers in `service.support` (`NameTokens`, `NameTiers`, `NameSimilarity`) that tokenise then apply `canonical` per token; `PlayerNameMatcher.editDistance` (package-private, same package) is reused for tier 4. `alias_normalised` = the tokens' `canonical` forms joined by a single space **in written order** (word-order variants are tier 2, not alias hits). `ScorecardContext.normalise` (weak, used by `GUEST_NAME_MATCHES_PLAYER`) is left alone.
2. **`OversFormat` has no parser** (only `display`). Default: add `OversFormat.parse(String, ballsPerOver)` (backend), mirroring the existing UI `parseOvers`.
3. **`saveImportedDraft`.** `upsertDraft` never writes `external_id` and sets `source = MANUAL` only on create; `MatchResultMapper.applyDraft` ignores both; its `catch DataIntegrityViolationException` maps everything to `ResultAlreadyExistsException`. Default: split `ResultServiceImpl.upsertDraft` into a private `doUpsert(..., ImportOrigin)`; `upsertDraft` passes null; `saveImportedDraft` sets `source`/`external_id` (also on a re-import over a MANUAL draft), pre-checks `(club, source, external_id)` through a new `MatchResultRepository` finder, and inspects the violated constraint name so `ux_match_result_source_external` raises `ImportExternalIdAlreadyUsedException` and `ux_match_result_match` keeps `ResultAlreadyExistsException`.
4. **ArchUnit ownership.** `LayeringRulesTest` allows only `ResultServiceImpl`, `ScorecardServiceImpl`, `ResultStatusResolver`, `ScorecardRows` and the mappers to use result entities/repositories (exact-set assertion). Default: `ResultImportServiceImpl`/the processor touch **no** result entity or repository: draft saving goes through `ResultService.saveImportedDraft`; the "existing result for this match / external id" flags come from new `ResultService` read methods; alias writes inside the scorecard save live in `ScorecardServiceImpl`; `NameAlias` is not a result entity so `NameAliasRepository` is free to use. New rule: `service.adaptor` depends on no repository, result service, entity or the processor.
5. **`import_match` mapping trap.** MapStruct would auto-map the new `importMatch` in `ScorecardMapper.toPlayerEntity/applyPlayer`, letting a client set it. Default: `@Mapping(target="importMatch", ignore=true)` on both; `ScorecardServiceImpl.replace/link` set or clear it explicitly (clear-only for clients). Existing positional `ResultPlayerDto` constructors (tests, `ScorecardDtos`) are updated.
6. **`IMPORTED_NAME_UNCONFIRMED` location.** Raised in `ScorecardRules.validate` (publish-time, next to `lineupChecks`), **not** in `structure` (which would refuse a save). Needs `importMatch` on the DTO and round-tripping through `ScorecardMapper.toPlayerDto` and the stored-draft path.
7. **Strict JSON.** Spring's default mapper ignores unknown properties; the spec wants them to be an error. Default: a dedicated strict `ObjectMapper` (`FAIL_ON_UNKNOWN_PROPERTIES`, jsr310) inside `JsonAdaptor`/`ImportedResultValidator`; the global setting is not changed (it would alter every endpoint).
8. **Multipart with a JSON part** is new in this codebase (`@RequestPart("request")` + optional `file`); the UI sends the request as a `Blob` of type `application/json`.
9. **`DocumentUpload` cannot do what the spec needs** (hard-coded to PDF, uploads immediately, no `accept`/`maxBytes`, file-type check by MIME which is unreliable for `.json`/`.csv`). The spec said to extend it with two props; more is needed. Default: extend it with `accept`, `maxBytes`, `helperText` and a `mode="select"` (holds the file, no upload, no stored URL), default behaviour and its consumer (`LeagueFormPage`) unchanged, tests and stories extended.
10. **Smaller UI gaps:** `errorList()` stringifies objects, so the import page gets its own typed reader (`importErrors.ts`); `ResultStepper` has no "Step N of M" caption and every step is clickable (the import page adds the caption and guards later steps); `ResultCapturePage` caches the result with `staleTime: Infinity`, so the import must remove/invalidate `resultsKey(clubId)` before navigating (and reads `?imported=1`); `ManageScreenHeader.action` is one node (wrap the two buttons); route `/manage/results/import` must rank above `results/:matchId` (route test); `ResultPlayer` type gains `importMatch`.
11. **Match candidates.** `MatchService.listMatching` is paged, does not filter `active`, and `hasResult/noResult` specs are ArchUnit-restricted. Default: the processor builds candidates with `listMatching` + extra spec (`MatchSpecifications.active()` + `matchDateBetween(startOfDay(d-1), startOfDay(d+2))`) and gets `existingResult` through `ResultService`.
12. **Candidate set for names.** `ScorecardServiceImpl.prefill` is the selection only (no squad) and `oursSides` is private. Default: the processor has its own loader in `service.support` (`MatchSideRepository`, `MatchSidePlayerRepository`, `TeamSquadMemberRepository.findByTeamIdAndSeasonId`, `SelectionEligibility.loadPlayers`), never the whole club.
13. **The measurement needs a real team sheet.** The spec's first task is to run the matcher over the real sample reports. The STUMPS sample (`docs/samples/Stumps_Match_Report.pdf`) has the report's names but our registered spellings for "Irene Villagers U15" are not in the dev DB. **Needed from the user:** the registered player names (as they are in the system) for that team, or a squad export. Without it the measurement can only self-match (meaningless). The harness is throw-away, under the scratch directory, and the counts go to the spec's Rollout Notes.
14. **Design pass.** The spec requires approved mockups (Source, Match, Teams steps, error list, candidate rows, `GuessChip` + Teams banner) before the import wizard UI is built (`docs/workflow.md` Step 2); they do not exist yet. The mockup slice is its own step before slice 5.
15. **No new libraries** in slices 1-5 (Jackson ships with Boot; PDFBox arrives with the STUMPS spec). Migration number `048` re-confirmed free (latest `047`).
16. **Tests held** until the user's browser approval (project rule); the ArchUnit rule and fixtures are written in the test phase.
