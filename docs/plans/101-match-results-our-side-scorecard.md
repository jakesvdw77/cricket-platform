## Context

Spec 100 (merged, PR #116) captures what happened in a match (outcome, toss, innings totals) but not who did it. 101 adds our side's scorecard for regular innings: `result_player` list, batting/bowling/fielding entries, extras breakdown, standouts (relative rules plus a star override), player of the match awards, guest and swap handling, derby support, a Full name / First name display toggle, and 12 reconciliation warnings in the shared `ResultValidator`. Four optional wizard steps are registered after the toss (Our team, Our batting, Our bowling and fielding, Awards). Super-over scorecards (105), the opposition scorecard (102), stats (103) and imports (104) are out of scope.

## Items to flag back to the human (spec says X, code says Y)

Each has a default the plan follows unless told otherwise.

1. **Validation issues are plain strings today.** `ResultValidationDto(canPublish, List<String> errors, List<String> warnings)` and `InvalidResultException(message, errors, warnings)`; `WarningCode` exists but is attached to nothing. The spec's `code`/`step`/`side`/`severity` therefore change the response shape. Default: **add** a new `issues` list of `ResultIssueDto{code, step, side, severity, message}` beside the existing `errors`/`warnings` string lists (kept, additive, so the current frontend and any caller keep working), in both `ResultValidationDto` and the `InvalidResultException` ProblemDetail. Frontend moves to `issues`; `dedupeWarnings` removal is the follow-up the spec already names, not a blocker.
2. **`ResultDraft` is a positional record** (14 components, `withDefaults` rebuilds it). Adding the optional `scorecard` component touches every `new ResultDraft(...)` including tests. Default: add `scorecard` as the last component (null = untouched) and update call sites in one pass.
3. **Innings are deleted and recreated on save** (`ResultServiceImpl.upsertDraft` runs `deleteByMatchResultId`, a JPQL bulk delete that does not use the FK cascade). Default: the spec's in-place reconcile, matched on `(kind, battingSide)`; `ux_match_innings_sequence` must become `DEFERRABLE INITIALLY DEFERRED`. If 043 created it as a plain unique index (not a constraint), 044 drops and recreates it as a constraint; the migration test proves it.
4. **`MatchResultMapper.applyDraft` ignores `detailLevel`**, so the server sets `OUR_SIDE`/`SUMMARY` itself in the service (spec: server-set), not through the mapper.
5. **`PlayerProfile` has no name fields** (names are on `Person`) and there is no club-wide player name search (`listPlayers` is unpaged, local filtering). Default: `GUEST_NAME_MATCHES_PLAYER` uses one new club-scoped JPQL join on `Person` (normalised, trimmed, case-insensitive); the "Anyone in the club" picker filters the already-loaded `listPlayers` locally (no new server search); the guest-name suggestions are the new paged `results/guest-names` endpoint.
6. **Stepper has no `isApplicable` or Optional concept**, and existing tests/e2e pin step numbers (`Step 4: Review` in `ResultCapturePage.test.tsx:86` and both e2e tests). Once scores exist the three new steps appear and Review becomes step 7, so those assertions are updated (select by name, not number) in the test phase.
7. **No grid/keyboard engine exists** (`ScorecardGrid` is new). It borrows only the look (`stickyFirstColSx`, `zebraTint`, scroll-box region) from `PlayersGrid`/`ResponsesByPlayer`. `CardProgressBar` has no amber state: add an optional `tone` prop. `badgeSx` has no `info` tone: use `neutral`.
8. **Reorder extraction from `TeamSelectionList`** (spec plan note): extract a `useReorderableRows` hook (drag state, `move`, `commitPosition`, `dropAt`) and a `PlayerRowMenu` (Move up/down, position field, extra-item slots), parameterised on `{ids, maxPosition, onReorder}`. `TeamSelectionList` keeps its behaviour; its 405-line test pins test ids (`selection-row-*`, `drag-handle`, `batting-end-drop`, `holding-area`) and the per-row button set, so the extraction must add no row buttons and the existing tests must stay green.
9. **Section scope and the publish gate:** all new routes reuse `matchService.requireAdministrableMatch` and the existing `canAccessClub` gate; the link route is the one write allowed on a published result (exempt it from `ResultPublishedException`, nothing else). No new non-manager read path, so `ResultVisibility` is unchanged; ArchUnit allow-lists in `LayeringRulesTest` are extended for the new entities/repositories/service.
10. **Contract tier:** still no OpenAPI diff test (as in 100); `backend/openapi/openapi.yaml` is regenerated by hand, additions only. Default: no diff test built here.
11. **Decision 15 defaults are still unconfirmed** (name popup, now on Our team, offers Swap player, Mark as 12th man / substitute and Remove; group optional steps in the stepper if crowded; keep the "planned N" caption). The plan builds them as assumed; one-line changes if reversed.
12. **Migration `044`** is free on every branch (verified); re-check at build time.
13. **Decision 21 (2026-10-14, user): the Our team step.** Team confirmation comes first; see the amended Frontend step 3 and the test work below. Server side nothing new is needed: swap is one `result_player` update, removal cascades its entries, and `LINEUP_TOO_LARGE` already counts only players who took part. The mockup board **Our team step** is added to https://claude.ai/artifact/2QZZKDccNRVoJ7TeyHsjyT before the step is built.
