# Plan: spec 094, Club structure on the Club Profile and Seasons as their own page

## Context

Spec 094 (`docs/specs/094-club-structure-and-seasons.md`, decisions recorded 2026-10-10: panel card under the chart "Option A", Seasons first in the Schedule menu group, Club profile key figures Teams / Leagues / Players, "+" opens an Add section dialog, new counts endpoints, `/manage/fixtures/seasons` URL kept, drag to re-parent deferred) brings the one remaining non-gold-standard manager page, the Club Profile, up to standard and gives Seasons its own menu item and gold-standard page. Branch `feat/094-club-structure-and-seasons` (rebased on master after PR #109; spec and the `nav/season-cricket` icon already committed there). ## Findings that shape the plan (from code exploration)

- **The org chart already exists** (spec 025): `ui/src/components/SectionTreeEditor/SectionTreeEditor.tsx` (`TreeScroller`, `TreeList`, `TreeItem`, `NodeCard` with the 22 px "+", the private `ageRangeLabel`), fed by `utils/sectionTree.ts` `buildSectionTree`. Extract it into a shared `SectionOrgChart`; fix the 025 depth-0 `flex-start` workaround with an inner `width: max-content` row with auto side margins.
- **Edit screen** `pages/manage/ClubStructure.tsx` keeps `selectedId` in local state and has no `useSearchParams`; `handleAddChild` creates a "New section" placeholder (stays there, unchanged).
- **Club Profile** `pages/manage/ClubOverviewPage.tsx` (455 lines): `PageHeaderBand` with "Back to Dashboard", hand-built cards, local `SectionTreeList`, hand-rolled Seasons card. Its test file asserts the Structure and Seasons cards (to be replaced).
- **Seasons** pages (`SeasonList`, `SeasonDetailPage`, `SeasonFormPage`, `components/SeasonForm`) are on the old toolbar-and-card look; `badgeFor` is shared between list and detail; no single-season GET (pages find it in the list); `pickDefaultSeasonId` (`utils/defaultSeason.ts`) is UTC-date based and ignores `active`, used by six consumers: leave its semantics alone.
- **Gold standard to mirror for Seasons:** `LeagueList.tsx` (state, summary query that hides counters on error, `PageCounters density="compact"`, `FilterBar` + `ContentControlsLine` + `SortMenu`, `useListViewPreference`, three EmptyStates), `leagues/LeagueCard.tsx` (`RecordCard`, `CardTimeStrip`, `CardProgressBar`, `badgeSx`), `leagues/LeagueTable.tsx` (grid table, `zebraTint`, `data-desktop-only`), `league/LeagueViewLayout.tsx` + `LeagueKeyFigures.tsx` (record detail header and `KeyFigureTile` strip), `LeagueForm` (`FormSectionHeading`), `utils/teamCounters.ts` (client counter and quick-filter model with its unit test).
- **Backend:** no migration, no tree endpoint. `SectionController` / `SeasonController` use `@PreAuthorize("@access.canAdministerClub(...)")`; nearest summary template is `LeagueController.summary` + `LeagueServiceImpl.summary` + `LeaguesSummaryDto`. The current-season rule (`resolveCurrentSeasonId`) and the "season belongs to the club, else 404" rule (`resolveSeasonId`) are **private in `LeagueServiceImpl`**: extract once into `service/support` and have both services use it (backend.md: shared logic in one place; it must stay in lockstep with the UI's `pickDefaultSeasonId`). Active player = `profile.isActive() && verificationStatus != REJECTED` (as `PlayerServiceImpl.visibleRoster`); `totals.players` = all such club profiles, tagged or not (matches the Players page counter for an unrestricted caller). Player to section is the `player_section` tag; team to section is `team.section_id`; leagues for a section come from `league_affiliation` joined to `team` for a season; seasons figures come from three grouped queries (leagues per season, distinct own teams per season, active matches per season; affiliation has no `club_id`, so join `team`).
- **Standards constraints:** four-file anatomy for new `components/**` (component, test, stories, index); `components/**` must not import `pages/**`; no near-duplicates (jscpd): `SeasonCard` shares `CardTimeStrip`, `badgeSx`, `RecordCard` with `LeagueCard`; mobile-first at 375 px; `useMediaQuery(..., { noSsr: true })`; `try/catch` around every `localStorage` access; UK spelling, no em dashes; backend ArchUnit: classes in `service.impl` are `*Impl` + `@Service`, no nested types or enum switches there, records in `service/support`, DTOs top-level in `dto`.

## Flags for your review (spec versus spec or code; I will not reinterpret these silently)

1. **Key-figure count:** Acceptance Criteria says "four-tile key-figure strip"; the recorded decision and UI section say three (Teams, Leagues, Players). Plan builds **three**; the spec's acceptance line is corrected.
2. **Seasons counters:** UI Requirements lists four (Current, Upcoming, Past, Inactive); the decisions paragraph says "Current, Upcoming, Past". Plan builds **four** (Inactive amber when above zero) as the UI section specifies; all client-side.
3. **Test Plan** says the Seasons item is "in the Club group"; the UI section and decision say Schedule, first. Plan follows **Schedule, first**; the test-plan line is corrected.
4. **Toolbar wording:** spec and exploration agree the gold standard is `FilterBar` + `ContentControlsLine` (not `ListToolbar`); plan uses those.
5. **"Add season" casing:** spec says "Add season"; sibling pages and today's Seasons page use "Add League" / "Add Season". Plan follows the siblings (**"Add Season"**); say if you want the spec's casing.
6. **Age chip dash:** `ageRangeLabel` renders "6–9" (en dash) today; the spec and mockup show "6-9". Plan keeps `ageRangeLabel` output unchanged (025 tests depend on it, an en dash is not an em dash) and uses a separate written form in the panel ("6 to 9 years", "40 and over", "Under 12", "Not set").
7. **"Current season" and time zones:** `pickDefaultSeasonId` uses the UTC date; the new season status derivation uses the browser's local date. The backend resolver uses the server date. Plan does not change `pickDefaultSeasonId`; the three may differ for a few hours around midnight. Flagged, not fixed here.
8. **OpenAPI:** `backend/openapi/openapi.yaml` is springdoc-generated though the spec calls it handwritten; plan hand-adds the two paths and four schemas next to the Leagues summary entries so existing responses are untouched (additions only).
9. **dependency-cruiser:** frontend.md mentions it but no config file exists in the repo; the plan still obeys the rule (no `components/` to `pages/` imports) and does not add the tool.
10. **Small shared-component extensions** the spec implies but does not name: `InfoCard` gets an optional `headerAction` slot (additive, for "Add top-level section"); the Club Profile header composes `PageHeaderBand` like `LeagueViewLayout` (logo tile, name, chip, Edit) instead of extending `ManageScreenHeader`; `SectionTree` (phone list) gets opt-in age chip and "+" props.
