# Plan 125: Editable import rows and starting without a file

Implements `docs/specs/125-editable-import-rows.md` (approved 2026-10-30). Plan only; the spec is not redefined. Builds on the import framework (097) and schedule import (098) already on branch `feat/097-098-import-framework-and-schedule-import` (uncommitted, compiled, never run end to end).

## Context
During hand-testing the owner found the file-only start too rigid. The file becomes a guide: the wizard loads it, the manager edits, adds and removes rows, and can start with no file at all. The server already validates, matches teams, detects duplicates, confirms, commits all or nothing and deletes; this adds edits as decisions on the batch, applied by the framework in one place, plus a blank `MANUAL` batch and the editable-row UI.

## Findings from the code (they shape the design; none redefine the spec)
1. **One choke point exists.** `ImportServiceImpl.evaluate` (about line 536) runs `handler.validate`, applies exclusions, builds the `EffectiveImport`, plans changes and recomputes `propose` on every call. It is fed by `preview` (parsed rows) and by `saveDecisions` and `commit` through `parsedOf(stored)` (about line 574). Edits and added rows therefore need to be applied in exactly one new place that `parsedOf` calls: `parsedOf(stored, decisions)`. Proposals are already recomputed on every evaluate, so team cards follow edits with no extra work.
2. **The payload currently stores evaluated rows, whose values are the file's.** After an edit the original file values must still be known (for "was ...", Reset, and re-applying edits on each evaluate). So `ImportPayload` gains `fileRows` (the parsed rows, never changed) beside `rows` (the effective, evaluated rows). Back-compat: a payload without `fileRows` (an old preview, 24 h lifetime at most) treats `rows` as the file rows.
3. **Digest covers edits for free** if `effective.rows()` holds the edited values (it hashes the effective rows, resolutions, updates, planned changes). The whole-file hash `rowsSha` stays over the parsed file rows. Verify the digest hashes row `values` and not provenance fields that could differ without a data change; `origin` and `fileValues` are display fields and must not make the digest unstable.
4. **Rows are strings.** `ScheduleFileReader` produces string values under the keys `date, home, away, venue, time, notes`; the handler's `validate` parses them with `ScheduleDateParser.parseText` and `ScheduleTimeParser.parseText`. An edited string therefore goes through the same parsers and rules with no handler change. Row numbers 1001 and up need no special handling in the validator, aliases, planned changes or `Committed.rowNumber`; a null `sourceRef` is safe.
5. **Excluded wins.** Exclusion is handled by `ImportReview.applyExclusions` and inside the handler; an added row can be excluded too (spec: removing an added row deletes it, excluding is for file rows, but the framework's exclusion works by row number so both stay consistent).
6. **Counts come from rows.** `ImportReview.counts` can derive `edited` and `added` from each row's new `origin`, so it needs no decisions input.
7. **Decision serialisation is tolerant.** `ImportDecisionsDto` is a record with null-to-empty normalisation and Jackson `convertValue`; a missing field in an old stored decision becomes empty, so adding `rowEdits` and `addedRows` is backward compatible. Its 7-argument constructor and `empty()` need updating (a small number of call sites).
8. **A blank batch reuses `preview`.** Extract a `newBatch(...)` helper from `preview` (limits, scope, expiry, audit fields). Blank values: file name "Typed in the wizard", `sha256(empty)`, size 0, `source = MANUAL` (`ImportSource` gains the value; `@Enumerated(STRING)`, `VARCHAR(24)`; the `058` check constraint `ck_import_batch_source` does NOT allow it, so migration `059-import-batch-source-manual.sql` is required: found in hand-testing, the blank start failed with a 409 "A conflicting record already exists"), `parse` and the file sniffer skipped, the earlier-import check skipped, an empty `ParsedImport` whose `meta` still carries `timeZone` (the schedule handler reads it), then a normal `evaluate` so payload and counts are consistent.
9. **API gaps found:** `ImportBatchDto` has no `source`, so the UI cannot tell a typed-in batch apart (add `source`, additive); `ImportTypeDto` and `types()` need `editable` and `editableColumns`; `ImportRowDto` is a record that needs `origin` and `fileValues` and a `withResult` that preserves them.
10. **Pagination is unchanged:** `rows()` pages the effective rows from the payload (bounded by 1,000), so edited and added rows appear there once stored.
11. **No backend tests exist** for `ImportServiceImpl`, `ImportReview`, `ImportDigest`, `LeagueScheduleImportHandler` or `ImportDecisionsDto`, so every backend test for this spec is new (written in the tests phase with the 097 and 098 tests, per the standing rule).
12. **UI building blocks:** `ImportIssueTable` (table and phone cards, `actions()` helper for Exclude and Update, rows keyed by `rowNumber`), the wizard's `persist(next)` save path and `useSaveImportDecisions` (replaces the cached batch, rows refetch on revision), `ImportUploadStep` sections, `importFakes.ts` (axios adapter with a route table and `evaluate()`), `ImportResultReport` key figure tiles, `ImportHistoryPanel` file-name line. `utils/importDecisions.ts` `hasDecisions` must count `rowEdits` and `addedRows` or a reload would not restore them. Inputs: `components/Input` (a `TextField` wrapper) is enough; `DateTimeField` couples date and time, so use plain text inputs for date and time (they accept what the parsers accept), with the column's `kind` giving only a hint and `inputMode`.
13. **Resolutions for vanished names.** The spec says the server drops a resolution for a name that no longer appears. Implement as a prune step after evaluate in `saveDecisions` (remove resolutions and `identifiedAsOurs` entries whose key is in no current proposal, in either step), tested carefully so an ours name (an `IDENTIFY_OURS` key) or an opponent (a `RESOLVE` key) is never dropped while it still appears.

## Slices

### 1. Backend (backend-builder). Never run `mvn` in `backend/`: rsync to the scratch copy, JDK 17, compile only.
1. DTOs (additive): `ImportDecisionsDto` gains `rowEdits: List<RowValues>` and `addedRows: List<RowValues>` with nested `RowValues(int rowNumber, Map<String,String> values)`; `ImportRowDto` gains `origin` (`FILE`, `EDITED`, `ADDED`) and `fileValues`; `ImportBatchDto` gains `source`; `ImportTypeDto` gains `editable` and `editableColumns` (`key`, `label`, `kind TEXT|DATE|TIME`); `ImportMapper` and `openapi.yaml` (additions only); `ImportSource.MANUAL`.
2. `ImportTypeHandler.editableColumns()` (default empty list); `LeagueScheduleImportHandler` declares date (DATE), home (TEXT), away (TEXT), venue (TEXT), time (TIME), notes (TEXT). `types()` fills `editable` and the columns.
3. New `service/support/ImportRowEditor` (pure): `apply(fileRows, decisions, editableColumns)` returns the effective rows (edits overlaid, no-op edits dropped, `origin` and `fileValues` set, added rows appended with `origin ADDED`, `sourceRef` null) and `validate(...)` that throws a plain `ValidationException` for: unknown column key, edit of a row that does not exist, duplicate or below-1001 added row numbers, effective rows over `ImportLimits.MAX_ROWS`, a value over the 1,000-character cell limit.
4. `ImportPayload` gains `fileRows` (back-compat fallback in `parsedOf`); `ImportServiceImpl`: `parsedOf(stored, decisions)` calls `ImportRowEditor`; `saveDecisions` and `commit` pass the decisions; `evaluate` stores effective rows in `rows` and keeps `fileRows`; `ImportReview.counts` adds `edited` and `added` from row origin; the prune step of Finding 13; `importRowsSha` untouched.
5. Blank batch: `ImportService.startBlank(auth, clubId, type, scopeDto, timeZone)`, `POST /imports/{type}/blank` in `ImportController` (`canAdministerClub`, `400` for a non-editable type, same limits and `409` open-preview caps), `newBatch` helper extracted from `preview`, whole-file check skipped for `MANUAL`.
6. Report and history data: the committed `import_batch_entity.detail` records `rowOrigin`; the batch counts carry `edited` and `added`.
7. `docs/standards/backend.md`: a short note under the Import framework block (edits are decisions applied by `ImportRowEditor`; blank batch is `MANUAL`).

### 2. UI (frontend-builder; parallel with slice 1 once the DTO names above are settled, hand-typed as before)
1. `api/importApi.ts`: `ImportRowOrigin`, `fileValues` and `origin` on `ImportRow`, `source` on `ImportBatch`, `editable` and `editableColumns` on `ImportType`, `rowEdits` and `addedRows` on `ImportDecisions` (`emptyImportDecisions`, `hasDecisions` in `utils/importDecisions.ts`), `startBlankImport` and `useStartBlankImport` (mirrors `usePreviewImport`: sets the batch cache, invalidates history).
2. `utils/importDecisions.ts`: `withRowEdit`, `withoutRowEdit` (Reset), `withAddedRow`, `removeAddedRow`, next added row number (1001 upward, never reused), unit-tested.
3. `ImportIssueTable`: an **Edit** action beside Exclude opening the row in edit mode (text inputs per editable column from `ImportType.editableColumns`, labels with row number, Save, Cancel, Reset to file values), Enter saves and Escape cancels, focus returns to the Edit button; **Add row** above and below the table (new row opens in edit mode with date and venue copied from the previous row); Remove for added rows; `Edited` and `Added` chips and "was: ..." under a changed value; phone card edit mode with stacked 44 px inputs and full-width Save and Cancel; empty state "No rows yet. Add the first match." One save per Save press (one decisions PUT, only changed keys), never per keystroke.
4. Wizard wiring: `onEditRow`, `onAddRow`, `onRemoveRow`, `onResetRow` through `persist`; `ImportUploadStep` gets `Start with an empty schedule` (a secondary button, only when `type.editable`) calling `useStartBlankImport` and moving to Check rows; `importConsumers` and the schedule wizard props need nothing else.
5. Wording: report tiles and history rows show "N typed in, M edited" and "Typed in the wizard" for `source MANUAL`; `ImportResultReport` and `ImportHistoryPanel`.
6. `importFakes.ts` (blank route, `evaluate()` applies edits and added rows and updates counts), `importFixtures.ts`, stories (edit row, empty state, typed-in report), minimal tests; `docs/standards/frontend.md` Imports paragraph. Compact buttons (44 px touch below md), UK spelling, no em dashes, MUI and theme tokens only. `nvm use 22.12.0` first.

### 3. Tests (test-writer, after the owner's hand-check; folded into the existing 097 and 098 tests phase)
Per the spec's Test Plan: `ImportRowEditor` and effective-rows rules, digest changes with an edit and an added row and is stable otherwise, token refused after an edit, proposals recomputed and the prune rule, blank batch (placeholders, `MANUAL`, earlier-import check skipped, rejected for a non-editable type), handler flow with edited date, time and team name, integration (blank to commit to delete; edit then commit writes the edited value; foreign club and section manager refused; caps; cleanup), UI component tests (edit, save sends only changed keys, cancel sends none, reset, chips, add row copy, start empty only when editable, keyboard, phone), extended Playwright golden path (skipped in CI).

### 4. Docs and review
`docs/roadmap.md`: the spec's "Later" items (paste many rows, add a round, copy a previous season, a "Create schedule" entry point); amend `097` "The standard flow" step 1 (the Upload step also offers Start with an empty schedule) as the spec states; then the standards review, full suites, and the PR only when the owner asks.

## Order
Slice 1 and slice 2 in parallel (DTO names fixed by the spec and this plan), then the owner hand-checks (restart backend; no migration), then tests, review, docs.

## Risks
Payload shape change (`fileRows`) with the back-compat fallback; prune step could drop a valid resolution if mis-keyed (test both steps and both modes); digest stability (do not hash provenance fields); an edit that removes a team name changes proposals and may leave a stale resolution until pruned; the 1,000-row cap now counts added rows; the framework has never run end to end, so more defects may surface; `ImportRowDto` and `ImportDecisionsDto` constructor changes touch every call site (small, but compile-check in the scratch copy).

## Verification
Backend: scratch-copy compile; at the tests phase the full suite there. UI: `npx tsc -b`, `oxlint`, import-related vitest, Storybook at 375, 768 and wide. Manual in the browser on a dev league: upload a file, edit a row's date, add a row, see the table revalidate, resolve teams, confirm, check the matches carry the edited values, then start a second import with an empty schedule, type two fixtures, confirm and delete it. Owner restarts the backend (no migration) and hard refreshes.
